## 需要修正的发现

### P1：GL 叶子允许必需用例全部跳过后成功退出

位置：[GL 任务](../../gradle/demo-tasks.gradle)、[日志审计](../../gradle/release-verification.gradle)、[限时包装](../../verify.ps1)。具体为 `glLeafVerification` 的配置及 `verify.ps1` 第 105 行的退出码判定。

任务设置了筛选器和系统属性，但没有对必需类／case 的实际执行、skip 和空结果做验收核对。`doLast` 的 GL 审计只检查 XML 中的错误日志；全部跳过时没有错误日志，因此也通过。`verify.ps1 -Mode Gl` 再把退出码 0 直接记为 PASS；它不像 UI 模式那样核对结构化证据。

已用一次隔离负例复现：通过 `build/v0275-independent-review-20261110/probes.gradle` 将该任务的 `haikalat.glSmoke` 改为 `false`，输出定向到独立目录。**61 suites、314 tests、314 skipped、0 failures，Gradle 仍为 BUILD SUCCESSFUL／exit 0。** 正常 GL 报告未被负例覆盖。此负例直接检验叶子任务；未声称用未修改的 `verify.ps1` 执行了负例，包装器接受 exit 0 的行为由源码确认。

修正要求：在 GL 叶子／聚合层核对必需集合和本次执行结果；全部或部分必需用例跳过、空选择、未执行应失败。增量复用必须明确标记并验证证据，不能仅凭退出码签收。正常通过与跳过负例均应得到自动化验证，不必为每个生产类增加测试。

### P2：新报告字段不足以绑定脏工作树候选和 GL 执行证据

位置：[verify.ps1](../../verify.ps1) 第 63–74、138–147 行。

`buildVersion`、`gitHead` 和 `workingTreeEntries` 只能描述版本、提交和修改条目数量。同一文件再次修改时，这三个字段可以完全不变；脚本也没有运行前后内容摘要比较。新 GL 模式的 `scopedEvidence=null`，没有绑定本次 case 清单与 XML 归档。共享 `build/test-results/glLeafVerification` 可被后续运行覆盖。因此，当前文档中“失败／超时报告已绑定候选身份”的说法超过实现能力，特别是 GL 模式。

修正要求：沿用现有 focused/UI 的内容摘要及运行前后校验机制，将 GL 结果绑定到具体 run、必需 case 和归档证据；启动失败或超时也应保留可核对的候选。明确区分新执行、UP-TO-DATE 和经校验的历史复用。不要以全局禁用增量构建代替证据协议。
