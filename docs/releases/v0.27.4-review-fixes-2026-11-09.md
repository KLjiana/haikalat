# 0.27.4 复审修复（2026-11-09）

0.27.4 签收后复审发现两处状态一致性问题。本文记录缺陷、根因、修复与回归证据；
功能范围、API 和合同不变。

## 1. R02：退役失败导致 active graph 与 effective 配置分裂

### 现象

`applyPendingFeatureRequest` 在候选图已经激活后，如果旧代退役抛异常（`retireGeneration`
的 fence／close 或注入故障），异常处理仍执行 `applyFeatureFields(previous)` 并
`features.failed(...)`。此时 `activeGeneration` 已是新候选，而配置字段和 effective
observation 被回滚到旧值，下一帧继续用新图渲染旧配置。

### 根因

- `activateGeneration` 在 `retireGeneration` 之前已经设置 `activeGeneration = candidate`。
- 统一入口的 catch 未区分“发布前失败”和“发布后退役失败”，对两者都回滚。
- 现有局部 `apply*` 路径已有 `activeGeneration == before` 守卫，统一路径漏掉了同等判断。

### 修复

`RenderPipeline.applyPendingFeatureRequest` 在 `createGeneration`／`activateGeneration`
的 catch 中检查当前活动代：

- 若 `activeGeneration != current`：候选已发布，保留 requested 字段并
  `features.publish(requested, revision, activities)`；不再回滚配置或标记请求失败；
  若从暂停恢复，仍执行历史失效。
- 仅当活动代未变化时，才回滚字段、标记 `FAILED` 并设置 `feature-request` 失败阶段。

退役故障仍由 `lastFailureStage = "retirement-after-publication"` 与诊断暴露，但不再
把已成功的配置发布报告为失败。

### 回归

`RenderFeatureControlGlTest.retirementFailureAfterPublicationKeepsGraphAndEffectiveConfigurationAligned`：
用 `haikalat.test.failVolumeRetirement` 在体积雾候选发布后注入退役失败，断言
`status=APPLIED`、effective 体积雾开启、活动图包含 `VolumetricMedium`，下一帧仍一致。

## 2. R12：失败请求被后续帧隐式重试

### 现象

`RenderFeaturesControl.pending()` 除 `PENDING/PREPARING` 外还检查
`requestedRevision > effectiveRevision`。请求失败后 revision 不会推进，后续帧会再次
执行同一失败快照；同时 `executeFrame` 在 pending 为 false 时会调用
`publishCompatibilityFeatureState()`，可能把 `FAILED` 覆盖为 `APPLIED` 并清空失败原因。

### 修复

- `pending()` 只返回 `PENDING` 或 `PREPARING`；`FAILED` 是已结算状态，只有新的
  `submit`（`recordRequest` → `PENDING`）才允许再次尝试。
- `executeFrame` 仅在状态不是 `FAILED` 时刷新兼容观察值，避免下一帧把失败静默清掉；
  局部 `apply*` 成功仍会通过兼容发布清除旧失败。

### 回归

`GtaoModularityGlTest.failedFeatureRequestIsNotRetriedUntilANewSubmission`：
`failGtaoGraph` 让统一 GTAO 请求失败；清除故障后再次执行一帧，断言状态仍为
`FAILED`、requestedRevision 不变、effective GTAO 仍关闭；只有显式重新提交后才
`APPLIED` 并出现 GTAO Pass。
