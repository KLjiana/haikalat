## 需要收口的发现

### F01 / P2：跨包迁移公开了场景帧的可写存储

位置：`src/main/java/com/kaleblangley/haikalat/subsystems/render3d/scene/SceneFrame.java:8–21`，以及 `scene/WorldBounds.java:5–11`。

原根包内的 `SceneFrame` 与字段均为包内可见；迁移后类型变为 public，`models`、`worldBounds`、`mirrored`、`changedIndices` 等数组，以及 `forwardCount`、`shadowCount`、帧号和统计等均成为 public 可写字段。`WorldBounds` 的坐标也全部 public 可写。`ShadowCasterPlanner` 直接读取这些数组，surface／geometry 直接读取队列计数，说明这不是无人使用的残留。

跨模块调用者现在可以替换数组、改变计数或修改 bounds，而无需经过 scene owner 的构建／revision 逻辑；这会使共享帧的数据和缓存判断失去封装约束。将类型登记为 internal 只限制使用域，不能限制同域兄弟模块的写入。计划 C10 明确要求“不公开字段”，合同将 scene↔geometry 描述为不可变快照引用，也不符合这些公开可写存储的事实。

建议保留 scene 内部更新入口，对消费者提供只读查询／遍历能力；矩阵和 bounds 不能仅换成返回同一可变数组的 getter。可以使用只读接口或 caller-owned 输出参数，避免为了封装引入逐对象复制。补充对跨包帧合同的负例门禁，现有检查只验证 `PipelineGeneration` 没有 public 字段，未覆盖此处。

此发现没有声称当前消费者已经恶意修改或本轮发生画面损坏；阻断的是明确的跨包封装交付要求。

### F02 / P2：阴影程序的具体所有权仍留在编排代次

位置：`src/main/java/com/kaleblangley/haikalat/subsystems/render3d/pipeline/PipelineGeneration.java:193–217`，关闭路径 `:549–603`。

`assembleDrawing` 仍逐个选择并编译普通、MASK 和实例阴影 Shader，保存三个 `ShaderProgram` 字段，决定逐程序借用并在代次关闭时逐个释放。`shadow.ShadowCasterRecorder` 接收这些程序，只负责录制，没有接管构造、兼容性和销毁。也就是说绘制职责已归 shadow，但程序 owner 的内部细节仍在 pipeline。

这与计划“构造、参数分类及私有实现移至所属模块”“阴影模块归集程序与采样规则”的目标尚有差距，也与模块合同把阴影程序列为 shadow 所有资源的描述不一致。这里没有发现双重释放；问题是模块目录和实际所有权尚未完全对应。

建议由 shadow 中的具体资源 owner 管理这组程序及兼容／关闭规则，Generation 只管理该 owner 的候选与转交。复用现有事务，不新增通用管理器。补验三类 shader 创建失败清理、实例阴影开关、无关效果切换复用与最终关闭对账，再更新所有权表。

## 已确认的迁移成果

- 后处理已分为独立效果 owner 和 `PostProcessPipeline` 颜色链装配；逐效果 borrowed／owned 转交不再是整体后处理资源的单一 ownership 开关。
- postprocess 不再依赖 Render3D；共享表面通过适配合同保留真实 producer 和帧租约。
- `SceneRenderer` 承担实际 forward／透明／实例绘制循环，`ShadowCasterRecorder` 承担阴影录制，`FrameLightBinder` 承担光照绑定，并非仅新增空壳。
- Generation 字段已私有化，Bloom 变化可以保留无关 owner 和 TAA 历史；环境替换、混合切换及资源估算修正有新鲜回归证据。
- UI rebind 在旧图执行中被拒绝、在帧边界换图的修复回归通过。

`scene`↔`geometry` 的双向依赖已经在开发合同中登记；本次不单凭存在双向引用追加失败，但其“只读快照”解释必须随 F01 实现一起修正。
