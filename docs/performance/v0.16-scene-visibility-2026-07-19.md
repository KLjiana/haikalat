# v0.16 Scene visibility 性能报告

日期：2026-07-19
版本：`0.16.0`
环境：Windows 11、Oracle JDK 21.0.3 toolchain、LWJGL 3.3.3、Intel i7-12650H、
NVIDIA GeForce RTX 3050 Laptop GPU、driver 576.88、OpenGL 4.6、VSync off、hidden window、debug callback on。

## 方法

命令：

```powershell
.\gradlew.bat runSceneScalabilityBenchmarks --rerun-tasks
```

每项使用同一程序化 scene、clear、present 和 shader，预热 100 帧，正式统计 1000 帧，共五轮。
每轮相邻运行 disabled/enabled，并交替两种模式的先后顺序，降低温度、P-state 与运行顺序造成的偏差。
disabled 仍执行 updater、world bounds 和 primitive queue，只关闭 frustum 删除，因此可以直接比较。
表中数值是“五个逐轮 median”的中位数；allocation 是当前线程整帧分配，包含命令录制，并非只计算
SceneFrame。

## Paired 结论

- 100 all-visible 的成对 culling overhead：1080p `0.003 ms`（约 `3.3%`），4K `0.001 ms`
  （约 `1.2%`），均低于 5% 目标。表内独立中位数与成对差值因统计口径不同可能方向不同。
- 10,000 large：draw 减少 `90%`，超过至少 85% 的目标。成对统计中，1080p CPU/GPU 分别
  节省 `3.907/0.874 ms`；4K 分别节省 `3.881/1.155 ms`。
- 10,000 all-visible：queue 多出 frustum classification；成对 CPU 开销在 1080p/4K 分别为
  `0.108/0.113 ms`，约占 disabled 中位帧时间的 `2.2%`，没有随帧增长的 arena 分配。
- 10,000 all-hidden：除显式 unbounded probe 外没有普通 draw；整帧分配 `2.2 KiB/frame`，
  证明 SceneFrame/queue 热路径低于 64 KiB/frame 目标。large/all-visible 的较高分配随可见 draw
  数线性变化，来自 command/uniform 录制，不应错误归因给 culling arena。
- updater 计数由 integration 每帧断言为 renderer count；没有 query wait、readback 或 `glFinish`。
- state-cache skip 在 1,000～10,000 draw 场景为 `98.7%～99.1%`。

基准套件自动输出每种模式的五轮中位数和逐轮 pairedSaved 中位数。正式跨机器比较仍应锁定
电源模式并同时保存 Nsight/驱动频率数据。

v0.15 没有在实现开始前保存同构 100/1k/10k 普通 renderer 基准，因此本报告不伪造旧版本基线；
disabled 是 v0.16 内部同路径 A/B，不宣称等于 v0.15 checkout。
