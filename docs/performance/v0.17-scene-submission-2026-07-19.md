# v0.17 真实场景 CPU 提交性能报告

日期：2026-07-19
版本：`0.17.0`
环境：Windows 11、Oracle JDK 21.0.3 toolchain、LWJGL 3.3.3、Intel i7-12650H、
NVIDIA GeForce RTX 3050 Laptop GPU、driver 576.88、OpenGL 4.6、VSync off、hidden window、debug callback on。

## 方法

正式矩阵使用以下命令：

```powershell
.\gradlew.bat runSceneSubmissionBenchmarks
```

每项预热 100 帧、统计 1,000 帧，共五轮。compat 关闭 static model/bounds cache、queue cache 和
primitive mat4 arena；optimized 同时打开三者。程序化场景与真实 glTF 场景都走正式
`Scene -> RenderPipeline -> RenderGraph -> CommandBuffer` 路径。表中数值是五个逐轮 median 的中位数；
allocation 是渲染线程整帧分配。窗口为 1280×720，clear、present、VSync 和 debug 设置保持一致。

真实场景资源是项目自有 `/scenes/gltf/scalability.gltf`：2 个 node、8 个 primitive、8 个实际材质、
4 种纹理角色、共享 mesh 引用、non-uniform 与 mirrored transform。扩容只创建 scene membership 和
固定 root transform；单份 GPU asset 始终为 8 mesh、8 material、2 texture variant、2 sampler，
估算 storage 约 0.001 MiB，不随 renderer 数增长。

## 硬门槛复测

- 程序化 10,000 all-visible 的五轮 allocation 中位数为 `2.6 KiB/frame`，相对 v0.16 的
  `2,502 KiB/frame` 下降约 `99.9%`，低于 `512 KiB/frame` 门槛。
- 程序化 10,000 / 10% visible 为 `15.6 KiB/frame`，相对 `252 KiB/frame` 下降约 `93.8%`，
  低于 `128 KiB/frame` 门槛。真实 glTF 同口径为 `7.3 KiB/frame`。
- 10,000 static/all-hidden 五轮稳定后 SceneFrame + queue 为 `0.062～0.080 ms`，低于
  `0.15 ms` 门槛；首轮包含额外 JIT 热身，仍为 `0.108 ms`。
- 100 all-visible compat CPU median 为 `0.069 ms`，低于 v0.16 的 `0.090 ms`，没有超过 5% 回退线。
- 1,000 glTF camera-motion 五轮 median：compat `0.397 ms`，optimized `0.382 ms`；强制
  forward rebuild 时没有回退，allocation 从约 `46.3` 降至 `6.6 KiB/frame`。
- 10,000 all-visible 的 matrix arena 保存 10,000 个 primitive 快照，object payload 相比 legacy
  少 10,000 个矩阵对象；最终像素 parity、reset 和扩容测试均通过。
- 正式版材质隔离加固后再次执行 allocation integration：真实 glTF 10,000 all-visible 与 10% visible
  均为 `12.6 KiB/frame`，仍显著低于 `512/128 KiB/frame` 硬门槛；同模板无 override 实例继续
  折叠 binding，有 override 的实例保持逐对象提交。

## 结论与 v0.18 决策

真实 glTF 10,000 / 10% visible 在优化后只提交 1,000 draw，CPU median `0.626 ms`、GPU median
`0.259 ms`。它低于路线图进入 GPU-driven 所要求的约 2 ms CPU 压力和 3,000 个持续可见 draw；
当前材质/纹理碎片也不能证明扩大 bindless/MDI 协议会优先获益。因此 v0.18 暂不进入 GPU culling、
Hi-Z 或 MDI。下一阶段优先考虑 RenderGraph texture preview、透明排序合同和已有 UI allocation 收敛；
只有新真实场景重新同时触发 CPU、draw 数、批兼容性和 GPU 非瓶颈条件时再开启 GPU-driven 设计。
