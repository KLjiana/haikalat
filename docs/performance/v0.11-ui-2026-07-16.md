# v0.11 Retained-mode UI 五轮基准（2026-07-16）

## 环境与方法

- GPU：NVIDIA GeForce RTX 3050 Laptop GPU 4 GiB，驱动 576.88；
- JVM：Oracle JDK 21.0.3；OpenGL 4.6 core debug context；
- 命令：`.\gradlew.bat runUiBenchmarks --rerun-tasks`；
- 每个场景和分辨率独立创建 `UiSystem`，执行 1 个 cold frame、30 帧预热、120 帧正式统计，
  共 5 轮并取轮间 median；VSync 关闭，窗口隐藏；
- GPU 数据来自 RenderGraph query，分配量来自当前 update/render 线程的
  `ThreadMXBean.getThreadAllocatedBytes`；FPS 包含 UI update、graph execute 和 hidden-window present；
- `layout/shape=0` 表示 warm steady-state 没有重复执行 Yoga layout 或 HarfBuzz shaping，不是计时器缺失。

## 结论与后续优化点

- 静态场景预热后 layout、shape 和 atlas upload 都归零，atlas hit 为 100%；10,000 quad
  场景保持 1 draw，persistent ring 的等待低于 0.002 ms/frame。
- 10,000 logical item 列表在 1080p/4K 只保留 53/67 个可绘制节点，证明内存与可见窗口相关，
  不与 logical item count 线性增长。
- 当前主要问题在 CPU 分配：10,000 quad 为约 1.57 MiB/frame，2,000 glyph 为约
  506 KiB/frame。`UiPainter` 的临时 glyph/quad 对象和 snapshot/display-list 复制应成为 v0.11
  后的首要优化，不能把这组数据解释为“steady-state 零分配”。
- virtual list 的每个文本 cell 仍形成独立 glyph batch，1080p/4K 分别为 51/65 draws。
  后续应让相邻同 atlas page、同 clip 的 glyph run 跨 Label 合并，同时保持 paint order。
- FPS 的短窗口会受 JIT 与驱动调度影响；容量决策优先比较 update/render/GPU 帧时间，而不是只看 FPS。
