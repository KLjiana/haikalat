# v0.17.2 发布与静态提交加固性能报告

日期：2026-07-21

版本：`0.17.2`

环境：Windows 11、Java 21、LWJGL 3.3.3、OpenGL 4.6.0 NVIDIA 576.88、
NVIDIA GeForce RTX 3050 Laptop GPU，VSync off、debug callback on。

## 方法

静态场景均使用 1280×720、10,000 个 fixed renderer、100 帧 warmup、1,000 帧统计并运行五轮；
表中是五个逐轮结果的中位数。preview 使用 1920×1080、MSAA、相同 warmup/sample/rounds。
结构化原始结果由 `writePerformanceResult` 写入 `build/reports/performance/current.json`，审查后的同机
baseline 位于 `docs/performance/baselines/v0.17.2-windows-rtx3050.json`。

## 五轮结果

| 场景 | CPU median ms | GPU median ms | queue ms | command record ms | allocation KiB/frame |
| --- | ---: | ---: | ---: | ---: | ---: |
| static all-hidden | 0.056 | 0.034 | 0.001 | 0.010 | 2.4 |
| static mostly-hidden（1,000 visible） | 0.318 | 0.059 | 0.000 | 0.033 | 2.0 |
| static all-visible（10,000 draws） | 2.835 | 1.043 | 0.000 | 0.460 | 2.0 |

| preview 场景 | present FPS | CPU median ms | GPU median ms |
| --- | ---: | ---: | ---: |
| closed | 1569.6 | 0.271 | 0.430 |
| direct HDR | 1101.1 | 0.375 | 0.482 |

资源生命周期场景执行 6 个真实 GL 用例，覆盖 ID reuse、128 次 VAO rebuild、100 次 framebuffer
resize 式 rebuild、多 context 切换与无 context 查询；最近一次总耗时约 `0.803 s`，审计到的 HIGH/MEDIUM
消息数为 `0`。该耗时与消息数同时写入 schema-v1 结果，不用单一 success 布尔值代替测量证据。

all-hidden 的 queue `0.001 ms` 远低于不变的 `0.15 ms` 硬门槛，五轮全部通过；allocation 从
v0.17.1 收尾记录的约 `4.0 KiB/frame` 降到 `2.4 KiB/frame`，达到 `<= 2.5 KiB/frame` 目标。
修复前本分支的 mostly-hidden/all-visible allocation 分别约为 `65.4/627.9 KiB/frame`；复用
shader program 的 direct matrix scratch 与后续命令收敛后分别为 `15.0/120.4 KiB/frame`。进一步跳过空的
pending-state flush，并以常量时间判定无 override 的材质实例后，正式五轮两者都稳定为 `2.0 KiB/frame`，
相对修复前约下降 `96.9%/99.7%`。
all-visible CPU median 从修复前约 `3.216 ms` 降至 `3.039 ms`；正式验收时发现重复的 `uModel`
location 查询仍在逐 draw 执行字符串哈希。加入 program-local 两路 identity 热缓存、跨连续 draw 的
pipeline state 去重和 matrix arena 常用容量快路径后，JFR 同轮复测为 `2.935 ms`，command record
为 `0.533 ms`。继续折叠相同 program、避免无关材质重绑 frame state、复用 override 快照并合并
draw opcode 写入后，再以 `MaterialInstance.hasOverrides()` 避免 all-visible 路径反复构造/遍历覆盖快照，
并用 JOML bulk copy 写入 matrix arena。最终 readiness 整链五轮确认值为 `2.835 ms`、command record
`0.460 ms`，保持在固定基线的
5% 门槛内。全可见命令数由约 `32,559` 降至 `21,943`；该变化只移除相同状态/绑定包，未跨 draw、
pass、透明物体顺序或 `custom()` 改变状态语义。

## JFR allocation 证据

执行 `runSceneSubmissionStaticJfr`，每个布局 1,000 warmup + 10,000 measured frames。修复前录制中
`MemoryStack.mallocFloat -> MemoryUtil.wrap -> ShaderProgram.setMat4` 出现约 1,830 个 allocation sample，
证明每次矩阵 uniform 都创建 FloatBuffer wrapper。改用 program-owned direct scratch 后，该调用链已退出
前十；identity 热缓存也使 `HashMap.getNode` 从 CPU 样本的主要热点中消失。修复后 JFR 的前十个
Haikalat 栈如下；weight 是 JFR 对整次进程（含初始化）的统计采样权重，
不能除以帧数冒充精确逐帧分配：

| allocation site | samples | JFR weight KiB |
| --- | ---: | ---: |
| `GlDebug.handleDebugMessage` | 18 | 9601.8 |
| `RenderGraph.execute` line 201 | 8 | 6668.7 |
| `VisibilityStatistics.from` | 7 | 5811.5 |
| `RenderGraph.execute` line 243 | 9 | 5802.1 |
| `SceneFrameBuilder.ensureCapacity` line 387 | 15 | 5299.7 |
| `UniformBlock.setMat4` | 4 | 4322.9 |
| `GlDebug.latestHighSeverityMessageOrNull` | 6 | 3853.0 |
| `SceneFrameBuilder.ensureCapacity` line 390 | 9 | 3632.7 |
| `CommandExecutor.execute` | 7 | 3521.5 |
| `SceneFrameBuilder.reuseImmutableFrame` | 8 | 3473.3 |

JFR 同轮报告的 ThreadMXBean allocation 为 all-hidden `2.3`、mostly-hidden `2.0`、all-visible
`2.0 KiB/frame`；JFR 会改变运行时采样行为，因此发布数值仍采用上方无 JFR 的五轮中位结果。

## 结论

本轮没有引入跨帧完整 command cache。静态 queue 继续 O(1) 复用，命令仍逐帧录制，matrix/object
payload 数与 draw 保持一致。剩余 all-visible 成本主要来自 10,000 次真实 draw/命令编码和不可变诊断快照，
不值得在补丁版本中暴露 secondary command buffer 或缓存 native handle。
