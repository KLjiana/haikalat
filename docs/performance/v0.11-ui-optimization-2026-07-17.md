# v0.11 UI 分配与 batch 优化复测（2026-07-17）

## 方法

- 与 [`v0.11-ui-2026-07-16.md`](v0.11-ui-2026-07-16.md) 使用同一机器、分辨率、隐藏窗口、
  VSync、debug context 和五轮方法；
- 每个场景独立创建 `UiSystem`，执行 1 个 cold frame、30 帧预热和 120 帧正式统计，取五轮 median；
- 分配量覆盖 UI update、RenderGraph record/execute 和 present 的当前线程，不只统计 painter；
- 本次增加 batch-break 原因，顺序为 order/shader/texture/sampler/blend/clip；每个新 batch 只归入一个首要原因。

## 瓶颈变化

- `UiSnapshotExchange` 的每个槽现在拥有可复用只读 primitive arena；producer 只覆写 FREE 或尚未
  acquire 的槽。renderer 持有最后一个 lease 直到被新快照替换或关闭，因此异步重放不会看到被改写的数组。
- glyph 热路径直接把标量写入 arena，复用 resolved glyph 数组，并从缓存的 `PositionedGlyph.glyphKey`
  查询 atlas；恢复文本硬裁剪后，steady 2,000 glyph 仍低于 128 KiB/frame 目标。
- 所有 Label 和 TextField 文本按自身边界硬裁剪，防止 bearing、长文本或缺字占位越出控件。
  virtual list 的 50/64 个 order break 来自这些不可跨越的节点 clip，未通过透明全局排序改变语义；
  后续若优化 draw，必须设计能证明等价的 clip group，而不是删除裁剪。
- 10,000 quad 的 frozen snapshot 数组分配已消失，但完整帧仍约 600 KiB。下一步应先用 allocation
  profile 分离 retained-tree 遍历、矩形/列表视图和 command/render record 开销，再决定是否增加
  painter primitive writer；不能通过共享可变 snapshot、缩短 lease 或跳过 ring fence 达成数字。
