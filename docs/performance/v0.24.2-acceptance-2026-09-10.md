## F1 / P1：PBR 查 cluster 的视空间 Z 取错矩阵方向

位置：`src/main/resources/shaders/render3d/pbr/pbr-forward.frag:346`。

当前：

```glsl
float viewZ = dot(uStableView[2].xyz, vWorldPosition) + uStableView[3].z;
```

GLSL 的 `matrix[2]` 取第三列，而 `view * vec4(worldPosition,1)` 的 z 分量需要第三行。相机旋转时两者不相同。XY 来自正确的 stableViewProjection，Z 却来自错误公式，片元会查到不属于自己的深度 cluster，造成局部灯缺失或跳变。

修复应使用：

```glsl
float viewZ = (uStableView * vec4(vWorldPosition, 1.0)).z;
```

或明确构造第三行。同步检查测试参考 shader 中复制的 resolveCluster/debug 代码，避免修一处留一处。

复现测试：`src/test/java/com/kaleblangley/haikalat/subsystems/render3d/ClusterRotatedViewAuditGlTest.java`。复用原生产 lab factory 和全灯参考，设相机位置 `(12,4.5,12)`、yaw `-135°`，18 局部灯含 6 Spot，K=128。结果最大差 32，而原容差为 2。

原 ClusterLightingGlTest 在有 Spot 的两种对照中都设置 K=8，容易触发全灯 fallback；fallback 绕开正常索引列表，不能充分证明正常 clustered lookup 正确。新增测试故意使 K 大于灯数，排除这个掩盖条件。

执行：

```powershell
.\gradlew.bat glSmoke --tests '*ClusterRotatedViewAuditGlTest.clusteredLightingMatchesFullScanReferenceForManyLights'
```

修复后补充不同 yaw/pitch、跨 Z 边界、正常列表与 overflow 分开的对照，不要降低图像容差。

## F2 / P1：CPU p50/p95 实际取的是未排序帧数组位置

位置：`Render3dClusteredBenchmarkSuite.java:169–170,207–210`。

wall/record 按帧序写数组后直接传给 percentile；只有 GPU List 经 toArray 时排序。percentile 参数虽叫 sorted，却没有保证 wall/record 已排序。所谓 CPU p50/p95 是第 50%/95% 位置那一帧，不是统计分位数。

这直接解释性能文档中 p50>p95。对于同一组样本的有序分位数，硬件抖动也不可能导致 p50>p95。`docs/performance/v0.24.2-clustered-forward.md` 中相应解释和 CPU 数字应标记失效，不能继续引用。

修复：统一对样本副本排序后求分位数；保留原帧顺序样本用于归因。加乱序序列、单样本、空样本测试；空样本显示 unavailable/失败，不能返回 0 冒充性能良好。

## F3 / P1：GPU 样本仍可重复、越过测量窗口，没有完整结果收集

位置：`Render3dClusteredBenchmarkSuite.java:189–195`。

collectGpu 每次看到 AVAILABLE 就追加 gpuNanos，未检查 sampleFrameSequence，也没有按提交帧去重。它可能重复使用上一帧结果、把 warmup 查询计入 measured，并漏掉测量尾部尚未完成的查询。`90/90` 只说明追加了 90 次，不证明有 90 个唯一测量帧。

修复：复用 v0.24.1 已有的显式完整 GPU sample collection；按 submission sequence 过滤窗口、去重、drain、统计覆盖率。未 dispatch 的 BoundsPass 不能填入旧耗时。保存原始帧号/每 pass 纳秒数与实际 viewport，缺样按门槛失败。

## F4 / P1：名为验收的 benchmark / quality 实际不能执行规划门禁

位置：`Render3dClusteredBenchmarkSuite.main/run`；`Render3dClusteredDemo.java:202–208`；`gradle/demo-tasks.gradle` 的 benchmark/quality 任务。

- benchmark 只有一轮配置遍历和打印，没有检查 assign 预算、同灯数全灯比率、缺样、实际 4K extent；默认 30/90 也不是规划的 3 轮 120/300。
- 没有源码指纹、原始样本文件和 512/1024 矩阵；即使性能超标，进程也可成功退出。
- quality 捕获帧的断言仅为相邻图片变化超过 500 bytes。错灯、闪烁、随机噪声同样能满足该条件，不能视作图像正确或时域稳定的证明。
- 专项实际只有 4 个类共 15 项，未纳入 ComputePassContractTest；透明层、阴影重编号/槽迁移、resize 分配失败、多视图、形变与 jitter lookup 等规划证据仍需补齐。

当前性能文档已承认缺项和预算未达标，这一点应保留。但成功退出的任务不得包装成“性能/画质验收通过”。应拆 smoke capture 与 quality gate，并按规划实现数值/图像对照及失败退出。

## F5 / P2：构造时存储分配失败会泄漏两个 compute program

位置：`ClusteredLightingResources.java:49–69`。

两个 shader 在 try/catch 内创建成功后，`storage = createStorage(width,height)` 在清理保护范围之外。合法的小 memoryBudget、高分辨率或实际分配失败都可能在这里抛异常；对象构造未完成，调用方无法 close，此前创建的 boundsProgram/assignProgram 遗失。

修复：把 storage 创建纳入同一 candidate 清理事务，任何阶段失败都关闭所有已创建资源；内存预算尽量在 shader 创建之前检查。增加真实 GL 资源计数测试：重复触发预算拒绝后，PROGRAM 数量不增长。

## F6 / P2：读取诊断会同步读当前 GPU counter

位置：`RenderPipeline.java:812` → `ClusteredLightingResources.java:327–331` → `GlBuffer.read`。

lastRender3dDiagnostics 调用 readCounters，后者直接 glGetNamedBufferSubData 当前帧由 Assign 写入的 buffer。它可能等待 GPU；GL_CLIENT_STORAGE_BIT 只是存储提示，不会把读回变成异步，也不能替代生产者到 buffer readback 的正确可见性协议。

这不是“Assign 本身一定慢”的证明，但会让每帧更新诊断 UI 的调用者额外串行化 CPU/GPU。修复为延迟读回 ring+fence，返回带 sampleFrameSequence 的最近完成快照，未完成显示 unavailable。测试/debug 的同步最终读回可以保留为显式独立路径。
