## 尚未关闭的事项

### R1：正式入口仍默认隔离运行，不能替代正常性能证据

位置：`gradle/demo-tasks.gradle:392`，`Render3dClusteredBenchmarkSuite.java:240` 附近。

正式 Gradle 入口传入 `--cpu-isolation`，测量帧开始前调用 glFinish，并把等待排除在 execute wall 之外。这符合隔离归因用途，但不符合规划 §14.3 的正常正式运行契约。

关闭方式：正常正式入口移除该参数，另保留独立隔离入口；对最终候选生成非隔离的 3×120+300 报告。报告应分别解释 CPU 提交与 GPU 完成耗时。不能只把 JSON 的 formal=true 当作完整发布门禁。

### R2：最新报告不对应当前源码指纹

- 报告：`e692975d14415228f81effe8e9105c4c536359e2cea6dbe531df16fdedc15914`。
- 本次按相同文件范围、排序、路径分隔符和零字节分隔规则重算：`a5cf19f8538959c35b964ac04d0d63522a8246ba824060b95f465f3c3a646328`。

在测试完成后重复计算结果一致。报告生成后修改过的文件包括 `ClusteredDemoSceneFactory.java`、`Render3dClusteredDemo.java`、`RenderPipeline.java`、`PbrFallbackTextures.java` 和 `gradle/demo-tasks.gradle`。时间戳仅辅助定位，指纹不一致本身才是证据。

旧报告仍能证明其候选的测量结果；不能直接给当前代码背书。关闭方式：冻结最终候选后重新归档与其指纹一致的报告，并在文档中引用确切路径。

### R3：GPU 样本跨轮过滤和末尾回收仍有缺陷

位置：`Render3dClusteredBenchmarkSuite.java:258–271`。

回收样本按当前 CPU 循环所属轮的 windowStart/windowEnd 过滤。上一轮晚到的有效样本进入下一轮后被丢弃；最后一轮结束后也没有专门收尾回收。此次各配置 Geometry 均只有 897/900 个样本，与该问题一致。按 sampleFrameSequence 去重已修复，不应重新指称为重复计数。

关闭方式：按样本自身 sequence 判断它属于哪个 measured 窗口，接收所有轮次有效样本；最后提交结束后在计时窗口外有界等待并回收剩余 query。保留真实缺样状态，并分别报告各 pass、各轮覆盖率。补跨轮延迟和末尾延迟回归。

当前覆盖率达到已有 95% 门槛，因此此项是采样准确性残留，不推翻已有 Assign 预算通过事实。

### R4：原规划的整体收益门禁仍缺证据

仍需相同场景、相同灯数/阴影预算的 full-scan 对照，验证 256 灯的 Assign+Forward 相对参考比例、8 灯总 GPU 增量，以及相对零局部灯的 snapshot+pack+record CPU p95 增量。现有 record p50 不能代替 CPU 增量 p95。

质量任务也仍不能代替规划要求的 linear HDR oracle 和完整集成矩阵。专项 GL 比较通过是有效证据，但不等同于所有透明、变形、阴影重编号及 temporal 联动均已验收。

这些是既定规划的剩余项；若决定缩小发布范围，应明确记录延期项与接受的限制，而不是把现有 passed 扩写成全部达标。

## 文档校正与建议顺序

`v0.24.2-clustered-forward.md` 仍称 512/1024 只跑了 informal 单轮；最新 JSON 实际包含它们的三轮结果，应更新该说明。覆盖率应保留足够精度，不统一显示为 1.00。新增 Stats 使用 workgroup barrier，不宜称为“无跨 warp 同步”。

建议先修采样回收和正式入口、补齐对照门禁，再冻结候选运行一次正式矩阵，避免现在反复跑仍不能封版的数据。当前可以确认核心功能专项与 Assign 优化有效；完整发布签收应等待上述证据闭环。
