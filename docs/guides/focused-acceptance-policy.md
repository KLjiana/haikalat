# Haikalat 有侧重验收规范 v2

制定日期：2026-10-04。适用范围：当前 0.24.3 工作树之后的开发、修复、功能验收与发布准备。

**目标：用最少的新增执行，证明本次改动及其直接影响链路正确；复用仍然有效的证据，把完整矩阵留给确有必要的场合。** 减少无关场景、重复执行和无效复测，不以降低正确性要求或把 smoke 当正式性能结果节省时间。

本文是新的验收决策规范。当前 Gradle 的 `releaseReadiness`、`localGlVerification`、`localReleaseVerification` 等仍采用原有大范围依赖，**本文不会自动改变它们的执行行为**。第 12 节规定任务改造；完成之前按第 11 节手工选择已有叶子任务，报告明确标记“按 v2 人工选测”。不得把该结果写成旧 `releaseReadiness` 已通过。

本文统一后续验收的范围、证据复用与结果解释；历史计划中的“每次全量重跑”、长期固定旧性能基线和无期限例外不再直接成为新候选的选测依据。历史报告保留原事实。特定功能承诺的数学精度、混合公式、失败恢复等合同仍有效，不能用缩小执行范围取消它们。

## 1. 一页执行规则

1. 冻结本次要验证的差异，包含 staged、unstaged 和会进入交付的 untracked 文件；不要只看 `git diff HEAD` 的已跟踪结果。
2. 选定一个主要验收域，列出直接影响域；跨域改动允许多个主域。
3. 从变更矩阵选用例，复用输入未变且证据完整的结果；未知影响先做定向调查，不默认无影响。
4. 先跑便宜、最容易定位问题的检查，再跑实际 GL、画质和必要性能。
5. 硬错误出现后停止依赖它的昂贵测试；独立结果仍归档，失败也生成摘要。
6. 修复后只重跑失败用例及被修复影响的依赖；其他有效结果继续使用。
7. 封版校验必需证据是否齐全，不把所有历史验证入口再次串起来执行。

**常规功能修复的默认组合：定向 JVM + 定向 GL + 一个主场景；是否增加 benchmark、第二分辨率、长序列，由触发条件决定。**

## 2. 验收层级与时间目标

时间为暖缓存、正常开发机上的执行器建设目标，包含构建和进程启动，不是当前实测保证。超出目标要报告主要耗时，不得到时自动记通过。冷构建/依赖下载单列。

| 层级 | 使用时机 | 默认执行内容 | 时间目标 |
| --- | --- | --- | --- |
| L0 文档/记录 | 普通 Markdown、报告文字、非行为注释 | 链接/格式/差异检查；版本元数据变更另跑对应 guard | 约 30 秒内 |
| L1 开发检查 | 每轮实现/局部修复 | 编译受影响源码、定向 JVM；shader 改动加实际编译/最小像素验证 | 约 1～3 分钟 |
| L2 功能验收 | 一个功能完成、一次 bug 修复签收 | L1 有效证据 + 本域 GL/数值/主场景 + 直接邻接风险；必要时代表性能 | 约 3～10 分钟 |
| L3 发布收口 | 发布候选冻结或共享底层改变 | 全 JVM/guard 一次 + 受影响域 L2 + 跨域短烟雾 + 必需的新增正式性能 | 常规局部版本约 10～20 分钟 |
| X 扩展验证 | 有明确触发条件 | 多硬件、完整质量档/灯数矩阵、长 soak、大容量压力 | 单独安排，不计入每轮修复 |

层级不是四套从头叠加执行的任务。L2/L3 消费已有有效结果；一次 Gradle 调用也不会因同一任务有多条依赖就重复执行。需要消除的是不同任务中相同用例的重复，以及跨次调用中的无效重跑。

L3 是“本次发布所需证据完整”，不要求无关动画、文本、IME、VFX 容量 benchmark 每个渲染版本都重跑。依赖锁、JDK/LWJGL、共享 backend、命令或线程模型变化时，按第 4 节升级受影响范围。

## 3. 变更分类与影响闭包

### 3.1 判定步骤

输入为相对上一个接受候选的完整差异，而非仅最后一次修复。构建 `变更文件 → 所属域 → 被改变合同 → 直接消费者 → 必需用例` 映射。临近封版新增文件也必须进入差异和指纹。

路径用于初筛，语义用于确认：同一 `RenderPipeline.java` 的注释修改与资源所有权修改不应触发相同矩阵。降低路径默认风险时，在计划中写一句具体理由；修改 shader include、绑定、数据布局或生成器时检查所有实际消费者，不能仅看 Java import。

未知文件或无法判定的调用关系先执行相关构建/合同检查并补充映射；仍无法确定时扩大到最近的共享边界。只有实际影响全局时才升级整个兼容矩阵，不直接启动所有性能压力任务。

### 3.2 选测矩阵

| 变更域/触发点 | 必测重点 | 必加的直接影响验证 | 通常不新增执行 |
| --- | --- | --- | --- |
| 普通文档/报告文字 | 本地链接、示例名称、事实一致性 | 构建版本/发布元数据改变时跑 metadata guard | 编译、GL、benchmark |
| 预设颜色/曝光/Bloom 标量 | codec/原子应用、该场景固定镜头与对照 | 自动曝光开关、Bloom 边界按改动选择 | 全灯数压力、动画、IME |
| 模型/贴图/材质素材 | 资产清单、加载、目标场景图像 | MASK/透明/切线、包围盒按变更选择；面数/覆盖变化时加主场景性能 | 全部效果 benchmark |
| GTAO estimate/math | 独立数学参考、法线/深度边界、GTAO 像素 | PBR 间接光接入、一个 TAA 联合场景 | 全 Outdoor、字体/动画容量 |
| GTAO/TAA/Outdoor 历史 | 重投影、显露、移动、resize、失败恢复 | 共享深度/velocity/reactive 的实际消费者 | 无关阴影容量矩阵 |
| Clustered/灯表/索引 | CPU oracle、旋转视图、GPU 布局、overflow | PBR 着色与 shadow slot；体积消费者存在时纳入 | 每轮 512/1024 全容量 |
| 阴影 scheduler/cache | old/new membership、槽位、脏区、失败提交 | MASK、实例/变形 caster；主场景的接收阴影 | 无关 UI/文本性能 |
| Forward 队列/颜色链 | OPAQUE/MASK/ALPHA/ADDITIVE、深度、透明顺序 | HDR VFX、TAA、MSAA、曝光/Bloom 的连接处 | 所有模型/灯数笛卡尔积 |
| 资源/命令/StateCache/Generation | typed commands、真实 GL 写读、关闭、resize、失败、状态恢复 | 渲染/后期/UI/VFX 的短消费者；embedded；涉及 instancing 时补跨 pass 生命周期 | 默认不跑各域完整性能矩阵 |
| Scene/资产/热重载 | schema、依赖、过期结果、候选替换、缓存 lease | 一个静态场景和一个角色场景；替换失败与关闭 | 纯灯光质量矩阵 |
| 动画/skin/morph | pose/Graph/约束及变形正确性 | Forward、MASK/shadow、velocity 按实际受影响路径 | 雾算法参考、IME |
| UI/文字/输入 | 布局、字形、组合输入和状态边界中的改动项 | 一个 UI+3D 共存场景；native hook 改动才增加对应 soak | Clustered/GTAO 大矩阵 |
| benchmark/门禁代码 | 延迟/缺样/重复/跨轮等合成样本、正式性拒绝、失败报告 | 一个真实 GL 采样校准，变化口径对应的代表性能 | 未受影响的视觉金图生成 |
| JDK/LWJGL/驱动/平台 | 构建/启动、能力合同、资源/宿主恢复、依赖影响域 | 受影响 native 路径及代表性能；旧环境性能不可直接继承 | 不以环境变化为由改写旧基线 |

“通常不新增执行”表示可复用既有证据，不表示删除该功能的测试。若素材是 shader/reference 生成器的输入，或配置控制算法、容量、采样数、质量档，则按对应功能代码变更处理，不能归为普通内容修改。

## 4. 何时升级验证

### 4.1 必须扩大兼容覆盖

- 深度/法线/velocity/reactive 语义、坐标空间、shader ABI 或 sampler/SSBO 绑定改变。
- 资源代次、关闭顺序、resize 事务、成功帧提交、线程或 command replay 规则改变。
- shared shader include、material variant、alpha/depth/AA 路径改变。
- 核心依赖、JDK/GL 驱动或宿主适配改变。
- 定向测试失败指向共享模块，或出现跨域不一致、GL 错误、泄漏、死锁、NaN。

这些条件要求 L3 的相关跨域短验证。扩大正确性覆盖与扩大所有性能配置是两件事；没有性能影响证据，不启动全域容量 benchmark。

### 4.2 扩展验证 X 的触发条件

| 扩展项 | 触发条件 |
| --- | --- |
| 3,600 帧或更长 soak | 修改生命周期/并发/长期缓存；修复泄漏；新长期持有资源首次验收 |
| 全灯数/全 quality 压力 | 修改容量、overflow/fallback、内存增长策略，或代表场景发现异常扩展趋势 |
| 完整四 AA 回归 | 首次承诺多 AA 支持，或共享深度、resolve、透明合成改变 |
| 多 GPU/驱动 | 新 GL 用法、驱动相关修复、新平台承诺；同平台普通参数修复可复用兼容证据 |
| IME native 长测 | native bridge、窗口消息/线程、输入生命周期或相关平台变化 |
| 全局性能矩阵 | 全局提交/状态缓存/资源策略/测量协议变化确实影响各域；或一个大版本首次建立基线 |

同一里程碑的扩展结果只在其输入改变或出现反证时失效。没有新增风险，不为“再保险”在每次修复后重跑。涉及原问题的关键失败回归始终保留。

## 5. 最小场景矩阵：覆盖风险，不枚举全部组合

### 5.1 每个功能的常规 L2

- 一个主场景：最能暴露本次问题/功能的固定场景。
- 一个关键边界：例如深度断层、overflow、透明前后层、相机切换、雾体进出。
- 一个直接邻接组合：例如 GTAO+TAA、阴影+MASK、体积+透明。改动触及多个不同合同则分别覆盖，不能用一个组合代替所有。
- 资源或历史变化增加 resize 和注入失败后的恢复；纯数学调整不机械重复资源长测。

确定性数值和 shader 单测可用 64～256 尺寸；集成 smoke 优先使用现有小型隐藏窗口；最终视觉使用目标构图与固定分辨率。低分辨率结果只证明该配置，不能替代 4K 质量/性能承诺。

### 5.2 分辨率和 AA

开发期以 1080p 或更小的正确性场景为主。新增屏幕空间效果、尺寸计算、dispatch 边界或显存策略，才追加 4K 与非整尺寸（至少一种奇数宽高）。分辨率无关的纯 CPU parser/codec 不跑 4K。

局部算法优先 NONE（隔离算法）与实际默认 AA；新 AA 语义、共享 resolve 或透明覆盖改变时，NONE/FXAA/TAA/MSAA 都必须有功能证据，但不要求每个 AA 再乘全部灯数、相机路径和质量档。

组合覆盖使用风险表：行写“合同/曾经失败的交互”，列写“用例”，每个必需合同至少有一个对应证明。已知高风险三元组合不能用一般两两组合覆盖替代。无风险依据不增加笛卡尔积。

### 5.3 稳定性短测与长测

常规资源/历史修复先使用一次短序列覆盖进入、退出、尺寸往返、失败和恢复，各路径至少实际触发一次；不要把连续绘制 3,600 帧但未触发目标事件当作替代。

只有第 4.2 节触发时再做长 soak。历史已有的 3,600 帧/100 次切换可以作为扩展强度保留，不能为赶时间截成几帧仍沿用旧验收名称。

## 6. 性能：先有效、再比较，按需增加实验

### 6.1 两种执行强度

| 强度 | 默认规模 | 用途 |
| --- | --- | --- |
| PERF-S 探查 | 1 轮，约 60 warmup + 120 measured，目标配置一个 | 判断热点/方向；明确 informal，不签收性能 |
| PERF-F 正式 | 3 轮，每配置至少 120 warmup + 300 measured；正常队列 | 只验证本次必须证明的性能配置 |

上述帧数是新执行器的起点，不保证 JIT/频率已经稳定；同时检查预热后趋势。未稳定时延长相关场景预热并记录，不重复所有场景。现有 TAA/GTAO 的 30/60 任务不能因名字含 benchmark 自动升级为 PERF-F；旧正式证据保留其原规范身份。

只改变文案、注释、等成本颜色值且未改变 shader 分支/场景覆盖时，不新增 benchmark。修改算法、采样数、pass、上传、灯范围、几何量、显存或热路径时，执行代表性能。

### 6.2 配置最小化

常规新增效果的正式性能只选：

1. 1080p 主场景，效果 on/off。
2. 4K 或该功能实际容量边界，效果 on/off；仅在有相应承诺/风险时需要。
3. 算法专项另有必需 oracle 时增加该参考，例如 Clustered 的同灯数 full-scan。

不要每次跑完 0/8/128/256/512/1024 灯 × 所有分辨率 × 所有 AA。Clustered 初次基线或算法修改仍需零灯/少灯/典型灯数/full-scan/overflow 各自的合同证据；后续未改变算法与容量的画面修复可复用这些结果。

CPU-only 打包/队列优化优先一个代表分辨率和不同对象/灯数量；像素 shader 优化优先典型与高分辨率。压力场景用于定义极限，不自动变成所有配置必须达到 60 FPS 的承诺。

### 6.3 同一套采集合同

- 使用现有 `BenchmarkSampleCollector` 的提交帧身份、逐轮归档、去重、同帧完整 pass 配对和有界尾部回收；先迁移 GTAO 的旧 last-profile 采样。
- 正式 A/B 按轮交错且轮次交替先后顺序；性能任务串行，不与其他 GL 窗口、录屏/抓图、压力任务争用同一 GPU。
- 统计CPU准备、录制、提交、正常 wall 和 GPU；`glFinish` 隔离仅作归因，不作为正式正常运行替代。
- CPU/GPU p50、p95、逐轮结果与原始样本保留。说明计算的是“分位数之差”还是“对应样本差的分位数”，禁止混称。
- 完整 GPU 链先按同一提交帧相加，再求分位数；不能相加 pass p95。
- 必需 pass/每轮和完整组合覆盖率至少 95%；同时要求无重复/身份冲突、无未解释的缺样及收尾超时。覆盖率数字本身不证明缺失样本无偏。
- drain/窗口启动/等待单独报告墙钟；它们不是免费吞吐。诊断 readback 不放进正常测量窗口。

### 6.4 三种门槛分离

| 类型 | 基线 | 如何使用 |
| --- | --- | --- |
| 代码回退 | 上一个接受版本，在当前同机、同配置、相邻时间运行 | 以相对变化、绝对差值和重复性联合判断 |
| 功能开销 | 同候选 on/off；或同灯数算法参考 | 检查新增功能自身的 CPU/GPU/资源预算 |
| 产品预算 | 指定硬件档、分辨率、场景和质量设置 | 判断承诺的运行成本是否达到 |

旧 `v0.23.1` 的 GTAO 2% 和 `v0.17.2` 的静态场景 5% 结果保留为趋势，不能无条件跨版本、跨环境阻断新候选。新预算配置要绑定 workload、口径和参考环境，不能只写一个全局百分比。

回退阈值在正式运行前冻结。先用同版本 A/A 复测估计该机器的自然波动，确定绝对差值下限和相对阈值；不在本规范中拍脑袋把 2% 改成另一个通用值。新基线可以版本化建立，必须说明旧基线为何不再可比，并保留长期趋势以识别累积回退。

硬件身份相同只是可比的必要条件。报告记录供电/功耗策略、主要系统负载、内存压力、JVM/驱动与实际渲染参数。环境异常或结果漂移记 INVALID，修复环境后只复测相关性能；不清空已通过的数学/功能结果。

已批准的历史偏差仅在其版本/指标/硬件范围内有效。例如 0.24.1 的环境偏差不能自动豁免 0.24.3 GTAO 的同候选开关增量。纯 4K 字符串匹配不能作为永久 GPU 豁免。

### 6.5 限制无收益的反复跑分

一次探查确定瓶颈后再修改；候选冻结后正式跑一次。若结果临界且存在环境漂移，只安排一次针对该配置的确认实验，保留两次全部结果，不挑最好一次。两次仍不稳定就标 INVALID 并处理测量/环境，不不断重跑直到偶然通过。

真实且可重复的超预算保持 FAIL，进行优化或明确调整产品范围/质量档；调整后产生新的配置身份和证据，不能继续沿用旧配置名称。

## 7. 质量与正确性底线

以下受影响项不能用省时、缓存或人工看起来正常来替代：

- 算法修改：至少一个独立参考，覆盖本次改变的数学条件；期望值不由生产同一 helper 计算。
- 坐标/采样修改：旋转、边界、非整尺寸、无效数据的目标用例。
- 时域修改：移动/显露/参数变化中的实际事件序列，不能只用硬切镜清 history。
- 资源/所有权修改：失败回滚、resize、关闭及宿主状态，按实际路径验证。
- GL_INVALID、未获接受的严重 GL 消息、NaN/Inf、越界、泄漏、死锁：保持阻断。

图像验收分为“重复运行确定性”“冻结图回归”“独立正确性参考”，报告分列。320×180 平均图可快速发现整体变化；细边、薄物体、局部光尾用预先固定的全分辨率 ROI，不必每轮导出所有附件。

普通美术调整先看主镜头和一个关效果对照，不运行全部诊断输出。只有发现差异或修改内部算法时，才导出相应深度、法线、历史/散射等附件。参考图更新必须先说明预期视觉变化，不自动接受当前输出来覆盖旧金图。

## 8. 证据复用：减少重跑的主要机制

### 8.1 两层身份

- **交付身份**：完整候选/最终包哈希、版本、Git 状态；用于回答发布了什么。
- **用例输入身份**：该用例实际依赖的源码、shader/includes、生成器、资源、配置、参考、测试实现、构建选项和必要环境；用于回答旧结果是否仍可用。

不再要求 README 或无关 UI 文案变化使全部渲染性能证据失效。也不允许仅因文件名仍相同就复用结果。用例依赖必须包含共享类、动态加载资源和影响行为的构建代码；不能只靠直接 import 推导。

输入投影由版本化映射表维护，第一阶段允许人工明确列出。缺少映射或存在未解释差异时，不宣称自动可复用；补足分析，或重跑受影响用例。共享 backend/资源合同变化会使相关消费者失效。

### 8.2 允许复用的条件

| 证据 | 必要条件 |
| --- | --- |
| JVM/数学 | 用例与运行逻辑输入相同、JDK/相关依赖兼容；原结果实际执行且通过 |
| GL/图像 | 上述条件 + GPU/驱动/渲染设置及全部资源/reference 一致，且无新反证 |
| 性能 | 上述条件 + 同口径/负载/质量档；引用原运行时间；封版时用短控制实验确认当前环境仍在基准波动带内 |
| 扩展 soak/兼容矩阵 | 对应长期状态和平台合同未变；原事件覆盖完整，未出现新相关失败 |

控制实验异常只使性能可比性待查，不推翻算法正确性；短控制实验也不能替代一个发生过热路径变化的新功能正式 benchmark。

复用报告保留原 runId、输入 hash 和时间，记录当前候选的差异排除依据，标记 REUSED_PASS。不要复制旧 JSON 后把 candidateHash/generatedAt 改成新值。结果文件缺失、声明输入不完整、smoke 或旧失败结果都不能当作可复用通过。

Gradle UP-TO-DATE/FROM-CACHE 只是执行器信息，需要相符的证据文件和输入身份；`onlyIf`、禁用测试、NO-SOURCE、空 include、未启用 GL/readback 等原因不能归入同一种 SKIPPED 通过。

### 8.3 修复后的重新验证

假设 12 个必需用例中 10 个通过、2 个失败：修复后计算影响范围，只重跑那 2 个及受修复影响的其他用例。若修复共享 helper，可能需要重跑更多；必须由依赖解释。无需重跑不受影响的 10 个来得到同一天的时间戳。

发布元数据调整后做包身份/版本合同检查。只有元数据实际进入 shader、缓存键或运行逻辑时才使相应行为测试失效；编译器、代码生成选项和依赖修改不能作为“仅元数据”排除。

## 9. 结果状态与偏差

每个要求都有 applicability、execution、verdict 三个维度，避免把“未运行”混成“通过”。用户摘要至少支持：

| 状态 | 含义 | 是否满足当前要求 |
| --- | --- | --- |
| PASS | 本次有效执行并满足门槛 | 是 |
| REUSED_PASS | 有完整、仍有效的既有证据 | 是，明确引用 |
| NOT_APPLICABLE | 影响分析确认不属于此次范围 | 不进入此次必需集合 |
| NOT_RUN | 此次必需但尚未执行、证据也不能复用 | 否 |
| INVALID | 采样、环境、配置或输入身份不允许作结论 | 否；定向修复后复测 |
| FAIL | 有效测量/验证未满足要求 | 否 |
| ACCEPTED_DEVIATION | 对具体 FAIL/INVALID 的既有明确接受决定 | 仅在限定范围内；总体仍标“带偏差” |

偏差必须写明指标、场景、版本/候选适用范围、硬件、原结果、原因、直接来自项目所有者的接受依据及何时复审。已有授权在原范围内继续有效，不重复询问；没有授权不能由测试执行者自行扩大。新的规范也不等于对未知未来失败的预先豁免。

功能错误、样本伪造/误归档和未解决资源安全问题不归入普通“硬件性能偏差”。受影响功能可明确从该版本承诺中移除，但必须同步能力声明、默认配置和相应拒绝行为。

总体状态：必需项全部 PASS/REUSED_PASS 为“范围内通过”；含有效接受决定为“范围内带偏差通过”；其余为“不通过/证据不足”。报告列出范围外项，不能把有限验收表述成所有配置都通过。

## 10. L3 发布收口清单

1. 当前候选执行或复用完整无桌面 JVM/架构/API/资产/依赖 guard；最终包版本与资产正确。
2. 本次所有改动域都有 L2 证据，接口/数据/生命周期跨域变更有直接消费者证明。
3. 一个代表性综合场景短验证作为整包启动检查；渲染版本包含默认 AA、正确输出目标与 UI 共存，resize/宿主按受影响合同选择。
4. 需要新增的正式性能只跑当前受影响配置；其他指标继承有效证据并注明时间/范围。
5. 第 4 节触发的扩展验证已完成或有明确接受决定；未触发的项写 NOT_APPLICABLE 及依据。
6. 必需用例不为空；预期测试数量/关键 case ID 存在；无意外跳过、smoke、只开/只关模式冒充正式证据。
7. 无未解释输入变化，版本报告与结构化证据一致。发布证据收口不要求把所有报告重生成同一天。

用例失败也要写出最终 manifest/summary，保存已完成结果并标明依赖阻塞。整体 exit code 仍失败，不能吞掉异常以继续发版。独立无 GPU 的检查可继续；依赖错误状态的昂贵 GL/性能任务应停止。

## 11. 当前仓库立即可用的执行方式

本节命令是已有入口示例，不是一份必须依次执行的清单。默认使用 Gradle 增量构建；只有需要真实复现失败或旧任务缓存合同不完整时，才对选定入口使用 `--rerun-tasks`。它也可能重跑前置任务，不能常规加在巨大聚合入口上。

| 本次目标 | 可选择的现有入口 | 注意 |
| --- | --- | --- |
| 普通编译/无桌面基线 | `quickVerification`；L3 可用 `check demoClasses` | 同一候选已有有效结果可复用 |
| GTAO 数学/设置 | `test --tests "*GtaoAnalyticReferenceTest" --tests "*GtaoPassesTest"` | 按实际改变补对应测试 |
| GTAO 实际像素/resize | `glSmoke --tests "*GtaoShaderGlTest" --tests "*GtaoReconstructionGlTest" --tests "*GtaoHistoryResizeGlTest"` | 选择后检查报告有实际执行的 GL 用例 |
| TAA/共享表面 | `runRender3dTemporalIntegration`，需要画质时加 `runRender3dTemporalQuality` | 原质量场景对普通运动证明有限，新增问题加定向用例 |
| Clustered | `runRender3dClusteredIntegration` | 另选资源/fence/失败回归，不能假设固定 include 覆盖所有新测试 |
| 视觉 profile | `test --tests "*VisualProfileCodecTest"`、`runRender3dVisualProfileIntegration` | 仅选受影响场景的 baseline 叶子任务，避免默认整套质量聚合 |
| 阴影 | `test --tests "*ShadowCacheStateTest"`、`runRender3dDynamicShadowIntegration` | 不改性能路径可复用容量数据 |
| embedded | `embeddedJvmVerification`、`embeddedGlVerification` | 仅在宿主/共享 GL 状态/目标相关改动或兼容收口使用 |

例如修复 GTAO 历史尺寸问题，可先执行：

```powershell
.\gradlew.bat test --tests "*GtaoPassesTest"
.\gradlew.bat glSmoke --tests "*GtaoHistoryResizeGlTest"
```

之后根据是否触及 Generation/共享历史，再增加对应 transaction 用例和一个 GTAO+TAA 场景；不因任务完成就机械接上完整 `localGlVerification`。

特别注意：当前 `glSmoke` 无 filter 会执行完整 test suite；`localOutdoorVerification`、`runRender3dVisualBaselineQuality`、`localRender3dV0243Verification` 也不是短 smoke。`glDebugPolicyGuard`/资源汇总可能通过依赖拉起其他任务，不能仅根据名字判断成本。必要时先用 Gradle `--dry-run` 查看选定命令的依赖范围。

当前完整 Clustered benchmark 尚不能凭本文自动缩成代表配置；需要第 12 节加入配置选择器。GTAO 的旧采样/正式性问题修复前，其旧任务成功不自动成为 v2 PERF-F 证据。过渡期报告分别列出“旧规范已有证明”和“v2 尚缺证明”，不通过改配置跳过检查来制造通过。

## 12. 执行器改造要求

本节为待实现工程要求；这次规范更新不修改 Gradle 或 benchmark 行为。

### 12.1 最小改造顺序

1. 增加版本化用例清单，记录 case ID、所属域、合同、输入、叶子入口、预期用例、成本等级和升级条件。暂不建设通用测试平台。
2. 增加只生成计划的入口：读取完整差异，列出必测/复用/范围外及原因、预估耗时；它本身不执行 GPU 工作。
3. 抽出定向 JVM/GL 叶子任务，避免 glSmoke 再跑全量 JVM；为场景、配置和质量任务添加可靠选择器。不同任务下相同测试按 case ID 去重。
4. GTAO/TAA/Clustered 共用必要的采样基础与正式 manifest 合同；保留各自负载、预算和 oracle。
5. 新汇总无论成败都写结果，校验正式性、输入、required case 集合与偏差范围；不从 Markdown “通过”二字推断机器结果。
6. 将发布入口依赖改为冻结的选测计划；原全量聚合作为显式扩展入口保留。等新路径自身验证通过后再切换默认，禁止先删旧门禁再补证明。

建议新增入口名为 `acceptancePlan`、`focusedAcceptance`、`focusedReleaseReadiness`；**这些名称目前只是提案，不是可运行命令**。新入口的执行模式和批准清单不可由任意 benchmark 参数静默改变。

### 12.2 计划/报告的最小字段

```yaml
policy: focused-acceptance-v2
level: L2
candidate: <完整候选身份>
base: <上一接受候选身份>
changedDomains: [gtao-history]
affectedContracts: [history-resize, successful-frame-commit]
requiredCases: [gtao-history-resize, temporal-transaction, gtao-taa-smoke]
reuse: []
excluded: [{domain: text-ime, reason: 无输入或共享合同变化}]
performance: {required: false, reason: 未改变每帧执行、资源规模或提交路径}
estimatedWallTime: <依据最近真实运行记录估计，不填写虚构耗时>
```

这是格式示意，不是当前改动的真实判定。实际报告还需每个 case 的 execution/verdict、输入/环境/阈值 hash、原 runId、原始结果路径、失败原因、复用依据和实际墙钟。性能用例明确 formal、normal/isolated、实际配置与采样状态。

### 12.3 验证新执行器本身

用小型合同测试证明：纯 Markdown 不选 GL；shader include 会找到消费者；共享深度会触发多个效果；失败后只失效相关证据；错误环境/缺样/smoke/空测试/onlyIf skip 不能变 PASS；缓存结果必须有对应文件和 hash；失败仍生成报告。

只需一次真实 GL 采样集成确认合成样本测试与实际 query 一致。无需为了证明选测器能缩减测试，再先执行一遍所有旧性能矩阵。

## 14. 如何衡量规范是否真的节省时间

每次记录总墙钟、构建/启动/测试/等待分项、实际执行 case 数、复用数、重复执行数和发现的缺陷。先收集三次代表性修复，比较完成同一验收目的的时间；不预先宣称节省了某个百分比。

若耗时主要来自 JVM/GL context 启动，在不污染测试隔离的前提下合并同域短用例；若来自无关聚合依赖，拆叶子入口；若来自等待结果，修复 query 生命周期；若来自重复恢复场景，用有效证据复用。性能测量与正确性 readback 分开执行。

首轮落地的成功标准：一次局部渲染修复能够在 L2 范围内签收；一次文档更新不启动 GL；一次共同底层修复能明确扩大兼容范围；一个失败候选仍有完整报告；没有新增漏检或把未测项标为通过。
