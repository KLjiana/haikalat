# v0.20 渲染核心与资源生命周期

状态：M5-M6 已完成，并通过 M8 纯 JVM与真实 GL 生命周期验收。

## 现有职责边界

```text
CommandBuffer
├─ CommandStream          SoA opcode/int/object/matrix/fence arena
├─ PendingPipelineState   pending state 合并与 flush
└─ CommandExecutor        记录顺序执行与 StateCache

RenderGraph
├─ RenderGraphCompiler    topology/依赖编译
├─ RenderTargetManager    window/relative framebuffer generation owner
├─ RenderTargetManager    fixed-size framebuffer lifetime owner
├─ PassResources          pass 内逻辑资源视图
└─ FrameProfile           CPU/GPU 诊断快照
```

这几个内部组件已经存在，因此没有为了“拆文件”再增加等价 wrapper。v0.20 本轮把重点
放在 generation/lifecycle 的可证明行为：

- `RenderGraph.resize` 先为全部 window/relative-size pass 创建 candidate
  `RenderTargetManager`；fixed-size pass 由独立 owner 持有且不会因窗口尺寸变化重建；
  任一 framebuffer 创建失败时关闭 candidate 并保持 active graph/尺寸不变；
- candidate 完整成功后才替换 manager、更新窗口尺寸、刷新 attachment lookup，再关闭旧
  generation；
- `RenderTargetManager.create` 先创建 replacement，再退休同名旧 target；
- `RenderTargetManager.resize` 批量候选成功后原子替换，关闭异常会聚合为 suppressed；
- `RenderGraph.close` 即使一个 target/timer 关闭失败也继续清理其余 owner，最后把 graph
  标记为 closed，重复 close 幂等；
- `TaaHistory.resize` 先创建新 framebuffer，失败时保留旧 history，成功后清除 temporal
  valid 状态并关闭旧 framebuffer。

M8 真实 GL 回归同时断言窗口 resize 后 fixed shadow texture id 不变、window-sized color
texture id 变化；完整 `glSmoke`、`glResourceLifecycleVerification`、
`sceneAssetGlVerification` 和 `sceneSubmissionGlVerification` 均通过。

## 线程和失败规则

- graph topology、target generation 和 pipeline resources 只在 render owner thread 操作；
- CPU 异步场景只能提交 generation-tagged plan，GL candidate 在 owner thread 激活；
- candidate 失败不关闭 active generation，也不把半成品写入逻辑 attachment lookup；
- close 采用逆序/尽力清理，主异常保留 suppressed 细节。

M5/M6 后续若要引入正式 `RenderGraphGeneration` 类型，必须先证明现有 candidate manager
无法满足跨帧 lease/fence，再扩大 API；当前 facade 和 allowlist 不变。
