### 2.4 限时报告修复

`verify.ps1` 超时后会在 `finally` 再次 `taskkill`。若进程树已退出，`taskkill` 报错会
覆盖 `TIMEOUT` 报告。修复为统一的 `Stop-VerificationProcess`：

- 先检查 `HasExited`；
- 清理异常不再中断报告写入；
- 超时后等待进程退出再进入 finally。

验证：`verify.ps1 -Mode Jvm -TimeoutSeconds 1` → `status=TIMEOUT`、`exitCode=124`、
`elapsed≈1.43–1.51s`；正常 300 秒运行 → `PASS`；非法 `JAVA_TOOL_OPTIONS` 导致 JVM 启动失败时记为 `INVALID`／exit 2，而不是测试 `FAIL`，且不重试全量套件。

### 2.5 测试不稳定审计：场景关闭竞态

全量 `check` 首次复跑发现 `SceneAssetServiceTest.reloadWhileHandleIsClosingCompletesCleanly`
间歇失败：`SceneAssetService.closeManaged` 在 `CompletableFuture.cancel(true)` 上收到
`CancellationException`，关闭路径把竞态异常抛给调用方。单测／类级运行通过，失败只在全量
套件时序下出现，说明这是时序相关而不是固定断言错误。

修复：关闭路径捕获正在取消的完成阶段可能抛出的 `CancellationException`／`CompletionException`，
继续执行上传和 ready 资源清理；handle 已从 `managedScenes` 移除，不能发布新计划。类级和
全量 `check` 随后通过。该修复属于测试暴露的产品关闭健壮性问题，测试本身未删除或放宽断言。

### 2.11 Windows `@TempDir` 清理故障隔离

本轮的 `focusedRender3dJvmTest` 连续两次因不同用例失败，原因相同：
`java.io.IOException: Failed to delete temp directory ...\<root>`。涉及
`VisualProfileCodecTest` 与 `FrameDiagnosticsTest`；两个用例都只用 `Files.*` 便捷方法，
没有未关闭的流。这是 Windows 上外部句柄（索引/杀毒）短暂占用系统临时目录导致的清理失败，
不是产品缺陷，也不是断言失败。JUnit 5.10 不提供关闭清理或自定义清理策略的配置
（`CleanupMode` 需要 5.11+），因此不升级依赖、不吞异常。

处理：共享 Test 管道把 fork 出的测试 JVM 的 `java.io.tmpdir` 指向
`build/tmp/junit`，把这类环境噪声限制在 `build/` 内，断言与失败语义不变。
验证：`focusedRender3dJvmTest` PASS；`verify.ps1`（Focused）PASS 59.5s；
`verify.ps1 -Mode Jvm` PASS 23.5s；`check --rerun-tasks` 1150 tests、0 失败。

### 2.14 复审 P1：全跳过/空运行不能算通过

### 2.15 复审 P2：报告绑定候选内容与归档证据

提交号＋修改文件数无法区分同一文件的不同修改。`verify.ps1` 现在：

- 记录 `workingTreeSha256`：对 `git ls-files --cached --others --exclude-standard` 的路径
  （去重排序）逐个写入「相对路径 + 0x00 + 文件内容 SHA-256 + 0x00」后取总哈希；
  另记 `workingTreeFileCount`。
- 把本次运行的 JUnit XML 复制到 `<reportDir>/junit/`，并在 `result.json.evidence` 记录
  `archive`、`files`、`tests`、`executed`、`skipped`、`failures` 和归档内容 `sha256`。

实测：同一提交、同样 323 个未提交条目与 2159 个文件，仅修改一个文档字节后指纹由
`76c481d8…` 变为 `6e091832…`；恢复内容后回到原指纹。GL 正常运行的证据归档哈希为
`ed3951dc…`，路径记录在 `evidence.archive`。报告另记 `evidenceFreshness`
（`FRESH`／`REUSED_TASK_OUTPUT`／`MISSING`）。

GL 属于 GPU 证据，不能复用 UP-TO-DATE 的旧 XML：`-Mode Gl` 固定追加 `--rerun-tasks`
（本机实测 114.6s，仍在 300s 限时内）；若证据时间早于本次运行开始，判 `status=FAIL`，
原因写入 `error`。负例实测：关闭 `--rerun-tasks` 后第二次运行任务 up-to-date，包装脚本
返回 `status=FAIL`、`reused=True`、`error=GL evidence is stale (task was up-to-date)`。

### 2.16 复审补充：验收期间修改候选必须判失败

只计算开始指纹仍不够：验收运行中途修改文件时，报告仍可能 PASS。`verify.ps1` 现在在运行结束
（写报告前）重新计算同一指纹：

- 新增 `workingTreeSha256After`、`workingTreeFileCountAfter`、`candidateStable`；
- 前后指纹不一致时，即使 Gradle 退出 0 也判 `status=FAIL`、`exitCode=1`，并把
  `Candidate content changed during verification (before=…, after=…)` 写入 `error`；
- 指纹不可用时 `candidateStable=null`，不伪造结论。

负例实测（后台运行 `-Mode Gl`，5 秒后向 `docs/guides/test-contracts.md` 追加一行并保持到运行结束）：

```
status=FAIL  exit=1  candidateStable=False  elapsed=104.1s
before=41e07ba3499b…  after=7b6cb61e50a2…
error=Candidate content changed during verification (before=41e07ba3499b, after=7b6cb61e50a2)
```

恢复文件后正常 `-Mode Jvm` 与 `-Mode Gl` 均 `candidateStable=True`、`status=PASS`
（GL `executed=314`、`skipped=0`、`reused=False`，约 99–105s）。

边界：这是运行开始／结束两次快照的比较，能发现“运行中被改且结束时仍不同”的候选；若改动在
结束快照前被还原，内容指纹回到原值，不会报错。不要用“改了又改回”的方式操作候选。
