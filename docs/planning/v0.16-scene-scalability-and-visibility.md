# v0.16 场景扩展、可见性裁剪与 Render Queue 实施计划

> 状态：已验收，工程版本定为 `0.16.0`；release commit/tag 由仓库发布流程生成
> 目标版本：`0.16.0`
> 基线版本：`0.15.0`
> 版本主题：为中型静态场景建立 bounds、每帧场景快照、相机/阴影视锥裁剪和可测量的 Render Queue
> 核心原则：先用 CPU 可见性闭环证明数据合同与瓶颈，再决定是否引入 GPU culling、MDI 或空间索引

## 1. 执行摘要

v0.15 已把帧时间、RenderGraph pass、资源、GL message 和 subsystem 摘要统一进可冻结、可导出的诊断链路。项目现在可以回答“慢在哪里”，但普通场景渲染路径仍有以下结构性限制：

- `Scene` 只保存 `MeshRenderer` 列表，并缓存 forward/shadow 静态排序；
- 每个普通 renderer 无局部 bounds 或世界 bounds；
- geometry pass 会遍历并提交全部 renderer，即使对象完全位于相机外；
- shadow pass 会再次遍历全部 caster，即使对象位于方向光 shadow volume 外；
- 同一 `ModelUpdater` 在 shadow 与 geometry pass 中分别执行，动态 updater 可能在同一帧得到不一致矩阵；
- pass 内临时创建 `Matrix4f` 并逐 renderer 重新计算 model matrix，没有正式的每帧 scene snapshot；
- 当前排序只减少部分 shader/material/mesh 切换，没有独立 Render Queue 合同或构建耗时统计；
- diagnostics 能看到最终 draw 数，但看不到候选、可见、被裁剪对象以及 queue build 成本；
- StressDemo 的百万实例是单 mesh/少 draw 吞吐证明，不能代表多 mesh/material 的 scene traversal 压力。

v0.16 不直接实现 GPU-driven renderer。它先建立一条最小、完整、可验证的 CPU 场景可见性链路：

```text
MeshData / Mesh local bounds
           |
           v
Scene renderer membership + stable sort metadata
           |
           v
SceneFrameBuilder (每 renderer 每帧只求一次 model matrix)
           |
           +-- world bounds
           +-- camera frustum classification
           +-- shadow frustum classification
           |
           v
SceneFrame / RenderQueue
           +-- forward opaque/additive/alpha entries
           +-- shadow caster entries
           |
           v
现有 RenderPipeline / CommandBuffer / RenderGraph
           |
           v
v0.15 diagnostics + deterministic scalability benchmark
```

版本完成定义：

> 框架能够为普通静态或动态 `MeshRenderer` 计算可靠的局部/世界 bounds，在每帧开始时只执行一次 transform updater，以非抖动相机视锥和方向光 shadow volume 独立构建 forward/shadow Render Queue；完全不可见对象不录制 draw，透明与 mirrored transform 语义不回退；diagnostics 能显示候选、可见、裁剪、状态切换和 queue 构建成本；100、1,000、10,000 对象确定性场景具备正确性、分配和性能基线。

## 2. 版本目标与非目标

### 2.1 必须完成

1. 为可裁剪 Mesh 建立有限、合法、不可变的局部 AABB。
2. 支持任意 affine model matrix 下的世界 AABB，包括平移、旋转、非均匀缩放和负缩放。
3. 从稳定、非 TAA jitter 的 view-projection matrix 提取六平面 frustum。
4. 每个普通 renderer 每帧只计算一次 model matrix，并供 forward/shadow pass 共同消费。
5. 相机 forward visibility 与方向光 shadow visibility 独立判定。
6. 构建稳定 Render Queue，保持 opaque/additive batching 和 alpha 用户顺序合同。
7. 对缺少可靠 bounds 的 Mesh 采用显式 `UNCULLABLE`，永远保守保留，不错误消失。
8. 将 visibility/queue 指标接入 v0.15 diagnostics 和 JSON export。
9. 新增确定性可见性 Demo/任务和 100、1,000、10,000 对象基准。
10. 覆盖 resize、TAA jitter、mirrored transform、边界相交、相机移动和失败恢复。
11. 保持现有 PBR、glTF、阴影、HDR、Bloom、曝光、AA、UI 与实例路径不回退。
12. 以实测结果决定 v0.17 是否值得进入 GPU culling + MDI，不预先承诺答案。

### 2.2 明确非目标

- 不实现 compute shader frustum culling；
- 不实现 Hi-Z、software occlusion、hardware occlusion query 或 portal culling；
- 不实现 `glMultiDraw*Indirect`、indirect-count 或 GPU command compaction；
- 不实现 bindless texture、texture array、descriptor table 或材质 atlas；
- 不实现 BVH、八叉树、KD-tree、loose octree 或动态空间数据库；
- 不引入 ECS、entity handle、component storage 或 scene graph runtime；
- 不实现 LOD、mesh simplification、impostor 或 streaming；
- 不实现 glTF animation、skin、morph target；
- 不对 `InstancedRenderer` 的十万/百万实例做逐实例 CPU 裁剪；
- 不改变 RenderGraph topology，不把每个对象变成 graph pass；
- 不在 v0.16 改为 deferred、clustered 或 tiled lighting；
- 不修改透明混合公式，不把 alpha 对象自动合并或实例化；
- 不以 `glGet*`、GPU readback 或每对象 timer query 实现统计；
- 不把 diagnostics、Demo benchmark 或具体相机类型依赖进 core mesh 数据层。

## 3. 当前架构事实

### 3.1 已有可复用能力

- `MeshData` 是可在纯 JVM 阶段解析和验证的几何数据；
- `VertexLayout` 已有 `VertexSemantic.POSITION`，无需假设 position 永远位于 attribute 0；
- `Mesh.from(MeshData)` 是 CPU geometry 到 GPU mesh 的正式上传边界；
- `SceneObject.ModelUpdater` 和 `MeshRenderer.modelMatrix()` 已能表达每帧动态 transform；
- `SceneDrawOrder` 已区分 opaque、additive、alpha，并保护 alpha 用户顺序；
- `DirectionalShadowMap.lightSpaceMatrix()` 已定义方向光 shadow volume；
- `CameraUniforms` 已生成 projection/view，但 TAA 会修改投影 jitter；
- `RenderPipeline` 已把 shadow 与 geometry 作为独立 RenderGraph pass；
- `CommandBuffer` 和 state cache 已能统计 draw/state skip；
- v0.15 diagnostics 已支持 immutable frame snapshot、扩展 section 和 JSON export；
- glTF CPU 解析已验证 POSITION accessor bounds 包围实际顶点，但尚未把 bounds 保留到 runtime。

### 3.2 当前风险

- 直接给 `MeshData` record 增加 component 会破坏现有构造签名；
- 直接把 mutable JOML `Vector3f/Matrix4f` 暴露为 public bounds API 会破坏不可变合同；
- 使用 TAA jitter 后的投影做裁剪会造成边缘物体逐帧闪现；
- 用八个角逐对象逐帧分配变换会在 10,000 对象场景制造明显 GC；
- 用 bounding sphere 处理极端非均匀缩放虽安全但过度保守；
- shadow pass 复用相机 visibility 会错误丢掉屏幕外、但会投影进屏幕的 caster；
- alpha 对象按 shader/material 排序会破坏现有用户定义透明顺序；
- updater 在多个 pass 中重复执行可能带副作用或时间漂移；
- 将 live mutable queue 暴露给应用会让 pass 间结果可被修改；
- 为 10,000 对象直接每帧创建 record/list/matrix 会让“裁剪收益”被分配成本抵消。

## 4. 分层与所有权

### 4.1 依赖方向

```text
core.mesh
  Bounds3f、从 POSITION 数据计算 local bounds

subsystems.render3d
  Frustum、world-bounds transform、SceneFrameBuilder、RenderQueue

subsystems.render3d.RenderPipeline
  每帧构建一次 SceneFrame；各 pass 只消费 queue

runtime.diagnostics
  只接收值类型 visibility summary

demo/test
  scalability scene、参数、基准和人工验收
```

必须保持：

- core mesh 不依赖 Camera、Scene、RenderPipeline、diagnostics 或 Demo；
- Frustum 不调用 OpenGL；
- Render Queue 不拥有 Mesh、Material 或 GL 资源，只借用现有 renderer；
- RenderGraph 不负责对象裁剪或 scene traversal；
- diagnostics 不反向控制 visibility；
- Demo 不复制生产 queue/culling 算法；
- GPU 资源 owner 与 v0.15 保持不变。

### 4.2 生命周期

- local bounds 与 Mesh 同生命周期，是不可变值；
- `Scene` 拥有 renderer membership，不拥有 renderer 引用的 Mesh/Material 生命周期；
- `SceneFrameBuilder` 由 `RenderPipeline` 拥有并复用内部 arena；
- `SceneFrame` 只在当前 pipeline frame 有效，不能跨帧缓存或由应用关闭；
- forward/shadow queue 共享同一组 model/world-bounds snapshot；
- pipeline close 只释放 builder 的 Java arena，不额外关闭 renderer 资源；
- build 中途失败不能发布半成品 frame，下一帧从干净 arena 重新开始；
- resize 只更新相机 frustum 输入，不重建 Mesh bounds。

## 5. Bounds 数据合同

### 5.1 `Bounds3f`

建议在 `core.mesh` 或窄用途 `core.geometry` 中新增不可变值类型：

```java
public final class Bounds3f {
    public static Bounds3f of(float minX, float minY, float minZ,
                              float maxX, float maxY, float maxZ);
    public static Bounds3f unbounded();

    public boolean isFinite();
    public boolean isUnbounded();
    public float minX();
    public float minY();
    public float minZ();
    public float maxX();
    public float maxY();
    public float maxZ();
}
```

最终命名允许调整，但合同必须满足：

- 不公开 mutable JOML 对象或数组；
- finite bounds 的六个值必须全部有限；
- `min <= max`；
- 单点、平面和线 bounds 合法；
- empty geometry 不合法，因为当前 `MeshData` 本身禁止空顶点；
- `UNBOUNDED` 是显式状态，不用 `Float.MAX_VALUE`、NaN 或空 Optional 偷渡；
- equality/hashCode 稳定，可用于纯 JVM 测试；
- 不把 AABB 与 sphere 混合成带 mode 的大而全抽象。

`Bounds3f` 建议分类为 `advanced`。如果只由 Mesh/Scene 内部消费，也可先 package-private；不能为了测试单独扩大 public API。

### 5.2 从顶点数据计算

正式规则：

1. 从 `VertexLayout.attribute(VertexSemantic.POSITION)` 找 position；
2. v0.16 正式支持 position 为 `GL_FLOAT` 且至少 3 components；
3. 使用 stride 和 byte offset 遍历 interleaved vertex；
4. 所有 position xyz 必须有限；
5. index 只影响绘制拓扑，不改变 vertex-buffer local bounds；未引用顶点仍计入保守 bounds；
6. 计算时不创建逐顶点 Vector；
7. 计算只发生在 CPU asset/upload 边界，不在每帧重复；
8. 没有 POSITION semantic、非 interleaved builder 或不支持的 position 类型必须显式提供 bounds，否则为 `UNBOUNDED`。

不要默认读取前三个 float。CUSTOM layout、实例 matrix attribute 和非 position attribute 不能被误判为位置。

### 5.3 `MeshData` 与 `Mesh` 兼容策略

不建议改变 `MeshData` record component 列表。优先方案：

- 新增 `MeshData.localBounds()`，按 immutable vertex/layout 计算；
- `Mesh.from(MeshData)` 只计算一次并传给 Mesh builder；
- `Mesh` 保存 immutable local bounds，并提供只读 getter；
- `Mesh.Builder.bounds(Bounds3f)` 允许程序化/非交错 geometry 显式提供；
- builder 未提供且能从 interleaved POSITION 推导时自动计算；
- builder 未提供且无法推导时生成 `UNBOUNDED` Mesh；
- builtin、OBJ、glTF 主路径必须最终得到 finite bounds；
- fullscreen quad、特殊 procedural mesh 可以显式 unbounded，因为它们不进入 Scene visibility。

这保留现有 `MeshData(...)`、`MeshData.of/indexed` 和 `Mesh.Builder` 调用兼容性。若工程师选择把 bounds 存入 `MeshData`，必须保留全部旧构造器并更新 migration 文档。

### 5.4 glTF bounds

- glTF accessor `min/max` 继续作为输入合法性验证；
- canonicalization 后的 `MeshData.localBounds()` 是 runtime 事实来源；
- accessor bounds 与 canonical decoded bounds 不一致时保持 fail-fast；
- 不因 accessor 已有 bounds 而信任未验证数据；
- 同一 primitive 被多个 node 引用时共享 local bounds；
- node world transform 只在 scene frame 阶段生成 world bounds；
- mirrored node 不交换错误轴，world AABB 必须仍满足 min/max；
- root placement transform 与 glTF world matrix 合成后再计算 world bounds。

## 6. 世界 AABB 变换

### 6.1 算法

对 local AABB 使用 center/extents affine transform：

```text
localCenter  = (min + max) * 0.5
localExtents = (max - min) * 0.5

worldCenter  = M * vec4(localCenter, 1)
worldExtents = abs(mat3(M)) * localExtents

worldMin = worldCenter - worldExtents
worldMax = worldCenter + worldExtents
```

该算法必须：

- 支持旋转；
- 支持 non-uniform scale；
- 支持 negative/mirrored scale；
- 支持 shear，只要 matrix 是有限 affine matrix；
- 不逐帧创建八个角或临时 Vector；
- 对 finite input 产生 finite output；
- model matrix 含 NaN/Infinity 时 fail-fast，并包含 renderer/debug name；
- local unbounded 时 world 仍 unbounded；
- 不尝试用逆矩阵；
- 不把 perspective matrix 当作 model matrix。

### 6.2 精度与边界策略

- 内部使用 float，与现有 JOML/OpenGL transform 一致；
- plane/AABB 测试增加小的 scale-aware epsilon，边界相切视为可见；
- epsilon 不能按世界坐标固定放大到吞掉大场景；
- 极大坐标导致非有限结果时明确失败，不静默裁剪；
- 零 scale 产生退化 bounds，仍视为合法；
- 负零不影响分类；
- 测试覆盖坐标原点、正负象限、极小/中等/较大尺度。

## 7. Frustum 合同

### 7.1 平面提取

`Frustum` 是纯 JVM、不可变或内部可复用的六平面集合：left、right、bottom、top、near、far。

输入为 OpenGL clip-space 的 `projection * view` matrix。要求：

- 明确采用 JOML column-major 访问语义；
- 六平面归一化；
- 零长度或非有限 plane 直接失败；
- 提供 `OUTSIDE / INTERSECTING / INSIDE` 三态分类；
- hot path 可只使用 `outside(bounds)`，但测试保留三态；
- unbounded 永远返回 INTERSECTING/visible；
- 相切不判 outside；
- 不分配 plane 对象/Vector；
- 不调用 OpenGL。

### 7.2 相机 frustum

可见性必须使用非抖动投影：

```text
stableProjection = perspective(camera.zoom, aspect, near, far)
cameraFrustum = stableProjection * camera.view
```

- near/far/FOV/aspect 必须与 `CameraUniforms` 的正式渲染配置共享同一事实来源；
- 禁止复制两套写死的 `0.1/100.0`；
- TAA jitter 只影响 shader projection，不影响 visibility frustum；
- resize 后 aspect 在下一帧更新；
- 最小化恢复只在有效 framebuffer 尺寸上更新；
- camera 移动/旋转/FOV 变化每帧可更新；
- 可选 conservative guard band 只能由内部常量或 settings 定义，并有测试。

建议提取 package-private `CameraMatrices` 或 `CameraProjection`，由 CameraUniforms 与 visibility builder 共享 projection 参数和非抖动 matrix。不要让 culling 读取 UBO 内容。

### 7.3 shadow frustum

- 从当前方向光 `lightSpaceMatrix` 提取独立 frustum；
- caster 是否在 camera 外与 shadow 是否可见无直接关系；
- camera 外但处于 shadow volume 内的 caster 必须保留；
- camera 内但处于 shadow volume 外的 caster 可从 shadow queue 剔除；
- shadow settings/focus 改变时本帧立即使用新 matrix；
- 没有 shadow-casting directional light 时 shadow queue 为空，行为与当前 pipeline 一致；
- instanced shadow caster 暂时保持整体提交，不做逐实例 shadow culling；
- shadow volume 的 conservative epsilon 单独测试，避免边缘 caster 闪烁。

## 8. 每帧场景快照

### 8.1 为什么需要 `SceneFrame`

v0.16 不应只在两个 for-loop 前各加一个 `if (frustum)`。正式修复必须保证：

- updater 每 renderer 每帧只执行一次；
- shadow 与 forward pass 使用完全相同的 model matrix；
- world bounds 与 draw 使用同一 transform；
- visibility 统计来自实际 queue，而不是另一次估算遍历；
- 未来 GPU upload/MDI 可以消费同一 frame input；
- 动态 updater 失败时不会发布半帧 queue。

### 8.2 内部结构

建议 package-private 结构：

```text
SceneFrameBuilder
  reusable renderer entries arena
  reusable forward index arena
  reusable shadow index arena
  stable sort metadata cache

SceneFrame
  frameIndex
  sceneRevision
  entryCount
  model matrices
  world bounds
  forward queue indices
  shadow queue indices
  statistics
```

每个 entry 至少包含：

- borrowed `MeshRenderer`；
- renderer 原始 insertion index；
- 本帧 immutable model matrix snapshot；
- world bounds；
- forward visibility classification；
- shadow visibility classification；
- blend category；
- sort keys 或对 stable metadata 的引用；
- mirrored/front-face 标记。

内部允许使用 primitive arrays 和复用 `Matrix4f[]`，但发布后的 frame 在两个 pass 消费完成前不可被改写。当前 RenderPipeline/RenderGraph 同线程顺序执行，可以先用单 slot；若未来跨线程录制，必须升级 lease/ring，而不是默许数据竞争。

### 8.3 构建顺序

每帧正式顺序：

1. 获取当前 camera、window size 和 shadow light matrix；
2. 创建 stable camera frustum 与 shadow frustum；
3. 遍历 Scene renderer membership；
4. 对每个 renderer 执行一次 updater；
5. 验证 model matrix finite/affine；
6. 从 mesh local bounds 计算 world bounds；
7. 独立分类 camera/shadow visibility；
8. 将可见 entry index 写入对应 queue arena；
9. 对 forward/shadow index 做稳定排序；
10. 冻结当前 SceneFrame；
11. shadow pass、geometry pass 只消费 frame；
12. frame 成功后把真实统计发布给 diagnostics。

若任一步失败：

- 不发布新的 SceneFrame；
- RenderGraph/FrameDriver 走 v0.15 incomplete failure frame；
- builder 清空 active counts，不保留半排序数组；
- 下一帧可以复用 arena；
- 原异常包含 renderer index/name、阶段和 bounds/transform 上下文；
- 不关闭用户 Mesh/Material。

### 8.4 Scene revision

`Scene` 增加单调递增 membership revision：

- `add(renderer/object)` 增加 revision；
- 未来 remove/replace 若加入也必须增加；
- 动态 light 参数不改变 renderer revision；
- revision 只用于失效 stable sort metadata/membership cache，不跳过每帧 transform；
- overflow 使用 long 并 fail-fast 或允许自然长期不可达，不回退为相同 revision；
- `renderers()` 仍返回不可变 snapshot；
- v0.16 不新增并发 mutation 支持，Scene 修改仍由 render owner 线程负责。

## 9. Render Queue 与排序

### 9.1 Forward queue

分区顺序保持：

```text
OPAQUE -> ADDITIVE -> ALPHA
```

OPAQUE/ADDITIVE 排序键：

1. shader/program identity；
2. material identity；
3. mesh/VAO identity；
4. 原始 insertion index 作为最终稳定 tie-breaker。

ALPHA 在 v0.16 保持现有用户 insertion order，不自动按距离排序。原因：现有 API 没有定义透明对象中心、层级或用户 override，贸然改为中心点 back-to-front 会造成视觉兼容变化。透明排序改进应单独立项并配套材质/排序策略 API。

要求：

- 不使用不稳定 sort；
- 不以 mutable `hashCode()` 作为唯一顺序；
- 相同输入和 scene revision 产生相同 queue；
- culling 只删除 entry，不改变剩余 alpha 相对顺序；
- mirrored front-face 来自本帧 model snapshot；
- material mutation若不改变 material identity，不要求重建 membership；bind 时仍读取当前 material instance；
- close 的 Mesh/Material 在正式 draw 边界保持现有 use-after-close fail-fast。

### 9.2 Shadow queue

shadow queue 条件：

- `castShadows == true`；
- world bounds 与 shadow frustum 非 OUTSIDE；
- unbounded caster 保守保留。

排序键保持以 mesh/VAO 为主，必要时包含 mirrored front-face 或 shadow shader variant。当前 shadow pass显式关闭 face culling，因此 mirrored 不要求拆批；若未来开启 face culling，再把 front-face 纳入状态键。

### 9.3 不新增公共 Render Queue API

第一版 queue 是 `RenderPipeline` 内部实现。只有出现以下真实调用者后才考虑 advanced public API：

- 第二种 scene renderer；
- 应用自定义 pass 需要消费同一 visibility；
- GPU culling/MDI builder 需要稳定输入；
- 工具需要只读选择具体 visible object。

v0.16 diagnostics 只发布计数和时间，不暴露 `List<MeshRenderer>`、model matrix arena 或 native sort keys。

## 10. RenderPipeline 集成

### 10.1 构建与执行边界

- pipeline build 创建 `SceneFrameBuilder`，但不执行对象 updater；
- 每次 `RenderPipeline.execute` 在 graph pass record 前构建一次 SceneFrame；
- shadow executor 使用 `frame.shadowQueue`；
- geometry executor 使用 `frame.forwardQueue`；
- `lastShadowCasterDrawCount` 改为真实可见 caster draw 数；
- scene draw count 与 diagnostics 使用 queue 真实值；
- `hasPbrMaterials()` 和 vertex-layout validation 可继续在 build 时遍历全 scene，不受 runtime culling 影响；
- background、postprocess、UI 和 instanced renderer 保持原路径；
- culling 开关只影响普通 scene renderer，不改变 graph topology。

### 10.2 配置

建议在 `RenderSettings` 增加 advanced、默认开启的窄配置：

```text
sceneVisibility = ENABLED | DISABLED
```

或使用单一 boolean `frustumCulling`。不要在第一版暴露 plane epsilon、算法类型、空间结构、线程数等调参。

`DISABLED` 的作用：

- A/B 正确性和性能对照；
- 所有 renderer 进入 forward queue；
- 所有 `castShadows` renderer 进入 shadow queue；
- 仍使用 SceneFrame，仍保证 updater 每帧一次；
- diagnostics 标记 culling disabled；
- 不是旧路径旁路，不能维护两套 scene traversal 实现。

### 10.3 TAA 与 temporal correctness

- visibility 使用 stable non-jittered frustum；
- shader 继续使用 jittered projection；
- TAA history 不因 culling enabled 自动失效；
- 快速进入视锥的对象第一帧必须绘制并正确写入 motion/history 现有合同；
- v0.16 当前没有 per-object motion vectors，不在本版本新增；
- 边缘对象连续 32 帧 TAA jitter 不得交替 visible/culled；
- resize 后第一有效帧使用新 aspect visibility。

## 11. Diagnostics 扩展

### 11.1 Scene visibility section

在 v0.15 `DiagnosticsSnapshot.SceneSummary` 基础上扩展或增加嵌套 visibility summary：

```text
cullingEnabled
sceneRevision
candidateRenderers
finiteBoundsRenderers
unboundedRenderers
forwardVisible
forwardCulled
shadowCandidates
shadowVisible
shadowCulled
modelUpdateNanos
boundsTransformNanos
frustumTestNanos
queueSortNanos
totalQueueBuildNanos
opaqueDraws
additiveDraws
alphaDraws
shaderChanges
materialChanges
meshChanges
```

约束：

- 所有计数来自实际 SceneFrame/queue；
- `visible + culled == candidate`，考虑 unbounded 已包含在 visible；
- shadow candidate 只包含 castShadows；
- 时间使用 `System.nanoTime` 的阶段差值，不做每对象 timer；
- OFF 不记录；BASIC 记录核心计数和 total；DETAILED 记录完整阶段；
- export 使用 schema v1 的可扩展 section 或明确升级 schema；若改变必需字段则升级到 schema v2 并保留 reader/migration 文档；
- UI Overview 显示 visible/candidate 和 cull ratio；Passes/Graph 不混入对象统计；
- 新增 Scene/Visibility 页面只有真实信息量足够时才做，不为标签数量机械加 tab。

### 11.2 状态切换计数

不能仅用 `StateCache.applied/avoided` 推测 queue 质量。SceneFrame/RenderPipeline 在录制顺序中直接统计相邻 entry 的：

- shader identity change；
- material identity change；
- mesh identity change；
- blend category change；
- mirrored/front-face change。

这些是 CPU queue 统计，不执行 OpenGL 查询。计数应与实际 forward queue 相邻项一致，并有纯 JVM 测试。

### 11.3 Freeze/export

- frozen capture 保留该帧 visibility summary；
- resize integration 能比较 resize 前后 candidate 不变、visible 合理变化；
- failure frame若 SceneFrame build 失败，visibility section 标记 unavailable/incomplete，不复制上一成功帧假装当前结果；
- JSON 校验候选/可见/裁剪不变量；
- 不导出每个 renderer matrix/bounds，避免 capture 爆炸；
- debug panel 可显示 top-level计数，不做逐对象 inspector。

## 12. 基准场景

### 12.1 两类证据

必须同时使用：

1. **程序化共享资源网格场景**：精确生成 100、1,000、10,000 renderer，控制可见比例、mesh/material 组合和 transform；
2. **真实多 mesh/material glTF 场景**：验证 asset sharing、node transform、mirrored/non-uniform scale 与 PBR 路径。

程序化场景用于容量和 A/B，不宣称代表真实游戏内容；glTF 场景用于纵向合同，不强求达到 10,000 独立资产节点。

### 12.2 程序化布局

默认矩阵：

| case | 对象数 | 预期可见比例 | mesh/material | 用途 |
| --- | ---: | ---: | --- | --- |
| small | 100 | 约 70% | 2 mesh / 3 material | correctness、人工观察 |
| medium | 1,000 | 约 25% | 4 mesh / 8 material | queue/state 排序 |
| large | 10,000 | 约 10% | 4 mesh / 16 material | CPU traversal、allocation、draw reduction |

- frustum 六平面外对象；
- 与每个平面相交对象；
- near/far 边界对象；
- negative scale；
- non-uniform scale；
- 动态 updater；
- unbounded fallback probe；
- camera 外、shadow 内 caster；
- camera 内、shadow 外 caster；
- opaque/additive/alpha 混合。

## 13. 性能合同

### 13.1 测量方法

- Java 21、相同 JVM 参数；
- 同一机器、GPU driver、电源状态；
- 1920×1080 与 3840×2160；
- VSync off、hidden window、debug callback 条件一致；
- warmup 至少 100 帧，正式至少 1,000 帧；
- 每项五轮，报告 median 和 paired difference；
- 分离 CPU SceneFrame build、CPU command record、GPU pass、present；
- 记录 allocation bytes/frame；
- 记录 visible draw、state changes 和 query wait；
- enabled/disabled 使用同一 SceneFrame pipeline，只切换 classification。

### 13.2 目标

- 100 个全部可见对象：enabled 相对 disabled 的 CPU submit median 回退目标不超过 5%；
- 10,000 个全部可见对象：SceneFrame build 不得产生无界增长，记录 overhead而不伪称有收益；
- 10,000 个约 10% 可见对象：普通 forward draw 至少减少 85%；
- 10,000 个全部隐藏对象：除显式 unbounded probe 外不录制普通 draw；
- warmup 后 SceneFrame/queue 新增 allocation 目标不超过 64 KiB/frame；
- updater 每 renderer 每帧恰好一次，不随 pass 数增加；
- culling 不产生 GPU readback、query wait 或 `glFinish`；
- queue sort 不逐帧创建 renderer wrapper/Comparator/stream 中间集合；
- diagnostics OFF/BASIC 不因 10,000 对象导出逐对象数据；
- shadow draw reduction单独报告，不与 forward draw 合并。

以上是目标而不是允许调高的装饰数字。未达到时先用 v0.15 diagnostics、JFR 和外部 GPU profiler定位；若瓶颈来自 O(n log n) sort，应缓存 stable opaque keys或使用 primitive index sort，不直接跳到 GPU culling掩盖 CPU 数据问题。

## 17. 故障与恢复合同

### 17.1 Bounds失败

- 非有限 position在 asset/upload边界失败；
- 缺失 semantic不失败，降级 unbounded并可记录warning；
- 显式 invalid bounds立即失败；
- glTF accessor谎报bounds继续失败；
- 不因诊断关闭而忽略数据错误。

### 17.2 SceneFrame失败

- updater异常保留原cause；
- 错误包含 renderer index/debug identity；
- active arena counts回滚；
- 不发布半 queue或上一帧统计；
- FrameDriver发布当前sequence的incomplete frame；
- 下一帧可以重试；
- cleanup异常作为suppressed，不覆盖主异常。

### 17.3 Draw失败

- v0.15 active query/debug group恢复继续有效；
- queue只借用资源，不额外close；
- failed frame不交换任何未来visibility history（v0.16本身无跨帧visibility history）；
- 下一帧重新构建，不能复用失败帧entry count；
- resource use-after-close继续在正式draw边界失败。

## 20. v0.17 决策门

v0.16完成后，使用同一10,000对象场景和diagnostics数据决策：

### 进入 GPU culling + MDI 的条件

至少满足以下多数证据：

- SceneFrame CPU traversal/culling仍占CPU frame显著比例；
- 可见对象仍有数千，draw/command record成为主要成本；
- 多mesh/material能形成稳定indirect batch；
- state/binding已不是首要瓶颈或有明确bindless/array策略；
- GPU有足够余量承载compute culling；
- OpenGL 4.6目标硬件支持所需indirect-count能力；
- 能定义失败清理、barrier、buffer ring和deterministic验证。

### 不进入 GPU culling 的信号

- CPU culling后draw已足够少；
- 瓶颈转为fragment、shadow、PBR或postprocess；
- 场景主要是少量大mesh；
- 材质绑定而非draw count占主导；
- 真实需求更需要animation、KTX2或画质功能。

若不满足GPU-driven条件，v0.17候选默认顺序：

1. glTF animation与skin最小闭环；
2. CSM/SSAO等画质增强；
3. KTX2/BasisU纹理资产路径；
4. Render target texture inspector；
5. 只有真实大型动态场景证明必要时再引入空间索引。

v0.16的成功不是“使用了最复杂的裁剪算法”，而是让每个普通对象从资产bounds到最终draw拥有一致、可测量、可演进的可见性合同。
