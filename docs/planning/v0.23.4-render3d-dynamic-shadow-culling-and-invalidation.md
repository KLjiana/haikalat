# v0.23.4 Render3D 动态阴影精细裁剪与失效计划

> 状态：已完成并发布
>
> 目标版本：`0.23.4`
>
> 实施基线：`v0.23.3`，提交 `185c3a2`
>
> 版本主题：把方向光 cascade、点光 cube face 和聚光 tile 从“全场 caster、全局失效”收紧为保守的逐 view 裁剪、逐 view 缓存失效与可诊断增量更新

## 1. 版本定位

v0.23.1 已经建立多局部光阴影、固定 atlas、稳定 light slot、dirty tile 缓存和统一 `ShadowFramePlan`；v0.23.2～v0.23.3 完成 GTAO 及其发布修复。现在阴影系统的主要问题不再是“能不能画”，而是动态场景发生局部变化时，系统仍然按过大的范围重画。

在 balanced 配置下，一帧最多存在 20 个独立 shadow view：

- 4 个方向光 cascade；
- 2 盏点光 × 6 个 cube face；
- 4 个聚光 tile。

当前 `ShadowCacheState` 使用全场 caster revision 参与每一个缓存键。任意一个 caster 的 transform、material、skin 或 morph 变化，都可能让全部 20 个 view 同时失效。方向光 CSM 的各级 cascade 复用同一份 caster 全集；点光和聚光则在每个 face/tile 内重新扫描全部 renderer。静态帧的 tile 复用已经有效，但动态帧仍会迅速退化为全量 CPU 遍历和全量 shadow draw。

v0.23.4 只解决这条链路：先为每一个 shadow view 建立保守、稳定、可复用的 caster 集合，再让 GPU 缓存以该集合的真实变化为失效边界。它是 Render3D 内部加固版本，不增加新的阴影算法，不改变 Forward/PBR 主架构，也不提前引入通用空间索引或 GPU-driven 提交。

## 2. 当前基线与已确认缺口

### 2.1 已有可复用能力

- `ShadowFramePlan` 已统一方向光、点光和聚光的选择、槽位与 dirty 信息。
- `ShadowCacheState` 已有成功帧提交、失败帧放弃和 miss reason 诊断的基本结构。
- `SceneFrameBuilder` 已缓存 model matrix、world bounds、forward queue 和 shadow queue 所需的 primitive array。
- `WorldBounds` 与 `Frustum` 已支持 AABB 分类，可直接作为保守裁剪基础。
- light 拥有稳定进程内 ID；atlas 槽位跨帧稳定。
- 普通 mesh、`MASK`、skin、morph 和方向光 instancing 已进入 shadow caster 路径。
- 静态 balanced 场景在 warm-up 后可以达到 `0 rendered / 20 reused`。
- `Render3dDiagnostics.ShadowSummary` 已能报告 cache hit/miss、miss reason、tile 数量和 atlas 内存。

### 2.2 当前问题

| 问题 | 当前行为 | 影响 |
| --- | --- | --- |
| CSM caster 集合过粗 | 多 cascade 时关闭 shadow frustum culling，每级绘制同一全集 | 远级/近级重复提交大量不相交物体 |
| 点光逐 face 扫描全集 | 每个 dirty 点光槽位的六个 face 都扫描全部 renderer | CPU 测试和 draw 数按六倍放大 |
| 聚光逐 tile 扫描全集 | 每个 dirty spot tile 扫描全部 renderer | 小光锥也承担全场提交成本 |
| 全局 caster revision | 任意 caster 变化进入每个 shadow cache key | 局部变化可使 20 个 view 全部失效 |
| 点光以六面 block 为失效单位 | 一个 face 变化也重画整个 cube | face 间无局部复用能力 |
| 失败帧仍可能信任旧 key | depth tile 已被部分覆盖，但失败时仅丢弃 pending | 恢复后可能把不完整内容误判为 cache hit |
| local shadow 未覆盖实例批次 | point/spot pass 只提交普通 renderer | 视觉能力和缓存身份都不完整 |
| 诊断只有最终 tile 命中 | 无 caster-view 测试、引用、裁剪和计划复用数据 | 无法判断优化是否真正生效 |

## 3. 版本目标

v0.23.4 必须同时满足正确性、性能和可解释性，不能只减少 draw count。

1. 为每个 active shadow view 生成独立、保守且确定的 caster 列表。
2. 方向光按 cascade、点光按 cube face、聚光按 tile 进行绘制和缓存失效。
3. caster 变化只使其旧 view 与新 view 的并集失效；完全位于所有 shadow view 外的变化不得触发 shadow redraw。
4. 空集合 view 仍要执行局部清理并提交有效的“空内容”缓存状态，不能遗留 ghost shadow。
5. 阴影帧失败后，所有可能已写入的 dirty view 必须保持 invalid，下一帧强制重建；未触碰的 clean view 可以继续复用。
6. 实例批次以 batch 级保守 bounds 和 revision 加入方向、点光、聚光阴影；继续保持同一帧一次实例数据上传。
7. warm-up 后的静态场景不产生每帧 Java/native 分配；未变化的裁剪计划走 O(1) 复用快路径。
8. 新增聚合诊断，能够回答“测试了多少 caster-view、保留多少、裁掉多少、哪些 view 为什么重画”。

## 4. 非目标

- 不实现 Virtual Shadow Maps、ray-traced shadows、contact shadows、PCSS、VSM 或 EVSM。
- 不增加 shadow atlas 容量，不提高 1 directional / 2 point / 4 spot 的预算。
- 不实现 BVH、octree、loose grid 或面向全引擎的通用空间索引。
- 不实现 compute culling、multi-draw indirect、indirect count 或 GPU-generated draw list。
- 不做逐实例 compact/indirect shadow culling；实例批次在本版本只做 batch 级裁剪。
- 不引入第二套 scene visibility 开关；继续服从已有 `RenderSettings.sceneVisibility()`。
- 不修改阴影滤波、bias preset、cascade split 或 GTAO 算法。
- 不为了复用代码合并方向光正交投影、点光 cube 投影和聚光透视投影的数学差异。
- 不把内部 shadow caster 计划提升为公共场景/ECS 抽象。

## 5. 核心设计

### 5.1 固定的 shadow view 身份

内部使用最多 20 个稳定 view slot，避免每帧创建 view 对象或列表：

| view slot | 含义 | 最大数量 |
| --- | --- | ---: |
| `0..3` | directional cascade 0～3 | 4 |
| `4..15` | point slot 0～1，每槽六个 face | 12 |
| `16..19` | spot slot 0～3 | 4 |

每个 slot 记录以下 package-private 状态：

- view 类型、light slot、cascade/face 索引；
- 当前 view-projection 与保守裁剪参数；
- active、dirty、volatile 和 empty 标记；
- caster slice 的 offset/count；
- 精确 membership bitset；
- membership、transform/model、material、deformation 的逐 view epoch；
- 上一成功 GPU 内容对应的 cache key。

固定编号只用于一代 `PipelineGeneration` 内的数组寻址。light 被重新分配到某槽位时，已有 `lightId`/allocation key 仍负责触发 `NEW_ALLOCATION` 或 `LIGHT` 失效，不能只依赖 slot 相同。

### 5.2 新增内部 `ShadowCasterPlanner`

新增 package-private `ShadowCasterPlanner`，由 `RenderPipeline` 每帧在 `SceneFrame` 冻结、`ShadowFramePlan` 完成以后调用。它只负责 CPU caster 可见性和逐 view 内容 epoch，不创建 GL 资源，也不直接发 draw。

输入：

- 当前 `ShadowFramePlan`；
- 冻结后的普通 renderer model/world bounds/revision 数组；
- 当前实例批次的 aggregate bounds 与 revision snapshot；
- `RenderSettings.sceneVisibility()`；
- 当前 `PipelineGeneration`。

输出使用可复用 primitive storage：

- 一个按 view slot 排列的扁平 `int[] casterIndices`；
- 每个 view 的 `offset/count`；
- 实例 batch 的 view membership mask；
- 每个 view 的内容 epoch 与本帧失效原因；
- 聚合 culling statistics。

不得为每个 view 创建 `List<SceneRenderer>`、stream、lambda 或临时 `Frustum`。数组仅在容量不足时按倍数扩容，warm-up 后保持稳定。

### 5.3 确定性顺序

`SceneFrameBuilder` 先生成一次基础 shadow candidate 顺序，沿用现有 render queue 的确定性规则。各 view 只在该顺序中过滤，不再单独排序。

这样可以保证：

- 开关 fine culling 不改变同一 view 内仍可见 caster 的相对顺序；
- 同输入产生相同 flattened slices 和诊断；
- 不为 20 个 view 重复承担排序开销；
- 后续性能回归可以区分“裁剪成本”和“排序成本”。

### 5.4 不使用哈希碰撞决定正确性

cache 是否失效不能只由一个聚合 hash 决定。规划器维护每个 view 的精确 membership bitset，以及每个 caster 上一帧的稳定 ID、bounds、model、material、skin/morph revision。完整重建时使用 bitset 精确比较；增量更新时根据发生变化的 caster，更新其旧 membership 与新 membership 的并集。

每个 view 的分类 epoch 只在精确比较确认变化后单调递增：

- `membershipEpoch`：caster 加入或离开；
- `transformModelEpoch`：仍属于该 view 的 caster model/geometry 变化；
- `materialEpoch`：影响 shadow alpha/culling 的材质状态变化；
- `deformationEpoch`：skin/morph 输出变化；
- `instanceEpoch`：实例 batch 内容变化。

`ShadowCacheKey` 存储这些逐 view epoch。hash 可以作为快速拒绝手段，但不得作为避免重画的唯一依据。

## 6. 保守裁剪规则

### 6.1 方向光 cascade

- 从每级 cascade 的实际 light view-projection 构建独立 frustum。
- 用 caster world AABB 对该级 frustum 做 outside test。
- 在 cascade 边缘加入由 shadow texel 尺寸、filter radius 和 bias 推导的保守 padding。
- AABB 与两个 cascade 都相交时允许重复进入；不得为了降低 draw count 强制只归属一级。
- camera/light matrix 经 texel snapping 后完全相同时复用原 view plan；矩阵变化只重建受影响 cascade。

### 6.2 点光 cube face

点光先执行 light range 与 AABB 的球体/包围盒 broad phase，再对六个 face 分别执行 frustum test：

1. 不与 light range 相交的 caster 不属于任何 face。
2. 与 range 相交后，可同时属于一个或多个 cube face。
3. cube seam 附近按 guard band 保守扩张，允许相邻 face 重复，禁止出现接缝漏影。
4. 点光近裁面以内或 bounds 不可靠的 caster 保守加入所有潜在 face。

`ShadowCacheState` 的点光缓存从每 slot 一个 key 改为每 slot 六个 key；`PointShadowSlotPlan` 对外仍是内部类型，但必须提供逐 face dirty、miss reason 和 caster slice。一个 face 发生变化时不得默认重画其余五面。

### 6.3 聚光 tile

- 使用聚光实际 perspective view-projection 做 AABB/frustum test。
- 先用 light range 做 broad phase，降低锥体测试数量。
- 对 cone 边界加入与 filter kernel、tile guard band 对应的保守 padding。
- 聚光方向、角度、range 或矩阵变化时只失效该 light 的 tile。

### 6.4 无可靠 bounds 的 caster

以下情况一律保守处理：

- bounds 缺失、非有限、退化或用户自定义 renderer 不提供 revision；
- deformation 会改变 bounds，但当前无法给出可信更新；
- 自定义 shadow callback 的读写范围不可分析。

这类 caster 标记为 `volatile`，加入所有 active view，并使其所属 view 每帧 dirty。诊断必须报告 volatile caster/view 数量，避免静默吞掉性能。

### 6.5 关闭 scene visibility

当 `RenderSettings.sceneVisibility()` 为 `false` 时，所有基础 shadow candidate 都进入每个 active view；缓存仍按逐 view epoch 工作，但不进行空间剔除。这是明确的兼容与问题定位路径，不能删除。

## 7. 精细失效合同

### 7.1 caster 状态变化

| 变化 | 必须失效的 view | 不应失效的 view |
| --- | --- | --- |
| caster 在同一 view 内移动 | 该 caster 旧/新 membership 并集 | 从未包含它的 view |
| caster 进入一个 view | 新 membership 对应 view | 其他不相交 view |
| caster 离开一个 view | 旧 membership 对应 view；即使新集合为空也要清理 | 其他不相交 view |
| caster 在全部 light volume 外移动 | 无 | 全部 shadow view |
| shadow material/alpha 变化 | 当前与上一 membership 并集 | 不相交 view |
| skin/morph 变化 | 当前与上一 membership 并集；bounds 不可靠时保守扩大 | 可证明不相交 view |
| scene generation 替换 | 全部 active view | 无 |

移动 caster 时必须保留上一帧 membership，不能只按新位置失效；否则 caster 离开的旧 tile 会残留 ghost shadow。

### 7.2 light 与 camera 变化

- directional light 参数变化：失效它的 active cascades。
- camera 变化：只比较实际 cascade matrix；texel snapping 后 matrix 未变则继续复用。
- 一个 point light 移动或 range 改变：重新构建该 light 的六面 membership；只重画 membership、matrix 或内容 epoch 实际变化的 face。
- 一个 spot light 移动、旋转、cone/range 改变：只重建并失效其 tile。
- quality、resolution、bias/PCF、atlas layout 或 pipeline generation 变化：遵守已有 `SETTINGS`/`GENERATION` 全量失效合同。

### 7.3 空 view 清理

dirty view 的新 caster count 为零时，shadow pass 仍必须：

1. 用 viewport/scissor 限定目标 tile/face；
2. 将 depth 清为远平面；
3. 不发 caster draw；
4. 在整帧成功后提交新的空集合 key。

禁止用跳过 pass 的方式表达空集合，否则 atlas 会保留上一帧内容。

### 7.4 失败帧事务

GPU depth 内容无法回滚，因此缓存元数据不能假装具有数据库式回滚能力。采用“执行前失效、成功后提交”合同：

1. `prepare()` 确认某 view dirty 后，立即使其上一成功 key 不再可命中。
2. shadow pass 只允许在该 view 的 tile/scissor 内清理和写入。
3. `frameSucceeded()` 提交本次新 key。
4. `frameFailed()` 丢弃 pending key；dirty view 继续 invalid，下一帧强制重画。
5. 本帧未触碰的 clean view 保留上一成功 key，可继续复用。

新增 `FRAME_FAILURE` 或等价 miss reason，让恢复帧可以解释强制重画来源。

CPU membership plan 与 GPU depth cache 分开管理：GL 帧失败不必销毁仍然正确的 CPU 裁剪计划，但绝不能保留可能已覆盖 tile 的 GPU valid key。

## 8. 动态增量快路径

### 8.1 完整重建条件

以下情况允许重建全部 active view：

- 新 `PipelineGeneration` 或 scene generation；
- shadow view 数量/layout 改变；
- visibility 开关变化；
- planner 容量或内部合同重置；
- 无法可靠确定发生变化的 caster。

完整重建仍须复用数组，并记录 `fullRebuild=true` 诊断。

### 8.2 增量更新条件

`SceneFrameBuilder` 向 planner 暴露 package-private 的 changed-entry 信息。对每个发生变化的 caster：

1. 读取上一帧 membership mask；
2. 仅对 active/changed view 重新测试新 bounds；
3. 取 old/new membership 并集；
4. 精确更新相关 view 的 bitset、slice 和分类 epoch；
5. 未受影响 view 保持原 slice/key。

若 caster 和 view matrix 均未变化，整个 planner 返回 `planReused=true`，不扫描全场、不重建 flattened list。

### 8.3 slice 重建

基础实现可以只重建受影响 view 的 slice，再将结果写入可复用 back buffer；禁止在热路径频繁移动大量小数组。推荐使用双缓冲 flattened arena：

- front 保存当前已发布 slices；
- back 按固定 view 顺序重写需要发布的计划；
- 容量不足时倍增；
- frame freeze 后交换；
- renderer 执行期间计划只读。

如果 M0 基准证明 20 个 view 的 slice 拼接成本远低于预算，也可每次变化时重写全部 slice，但必须保留“只重新做受影响的空间测试”这一核心收益，并在性能报告记录选择依据。

## 9. 实例阴影合同

v0.23.4 不做逐实例 fine culling，但必须补齐 batch 级身份与 local-light shadow：

- `InstancedRenderer.beginFrame()` 在已有矩阵准备过程中计算全部实例的 aggregate world bounds。
- 用可复用 primitive snapshot 对矩阵 float bits 做精确比较；发生任何变化时递增 `instanceTransformEpoch`。
- aggregate bounds 与某 view 相交时，该 view 绘制整个 batch；不相交时跳过整个 batch。
- 实例 batch 加入 directional、point 和 spot shadow pass。
- 同一帧继续只准备/上传一次 instance matrix 数据，各 shadow view 与 forward pass 复用该上传。
- batch 从旧 view 移到新 view 时，旧/新 membership 并集均失效。
- 无法计算 aggregate bounds 时，将 batch 作为 volatile caster 保守加入所有 active view。

逐实例 compact、每 face 不同 instance list 与 indirect submission 明确留给未来 GPU-driven 项目，不能在本版本破坏当前单次上传合同。

## 10. 绘制路径调整

`RenderPipeline` 的三个 shadow executor 改为消费 planner slice：

- directional：每个 dirty cascade 只遍历自己的 caster slice；
- point：每个 dirty face 独立清理、绘制和提交 key；
- spot：每个 dirty tile 只遍历自己的 caster slice；
- clean view 不绑定 framebuffer、不清理、不扫描 caster；
- dirty empty view 只清理，不发 draw；
- instanced batch 根据 view membership mask 在相应 view 提交。

已有 `lastDirectionalShadowCasterDrawCount()`、`lastPointShadowCasterDrawCount()` 和 `lastSpotShadowCasterDrawCount()` 继续表示实际 draw 数。特别是 point draw count 不再具有“必然是六的倍数”的隐含假设；现有 Demo/test 如依赖该假设，必须改为检查逐 face 计划与最终像素正确性。

## 11. 诊断与公共兼容性

### 11.1 新增只读诊断

不修改 `Render3dDiagnostics.ShadowSummary` 现有 record components，避免破坏构造器和外部读取。建议为 `RenderPipeline` 增加一个附加只读快照：

```java
public ShadowCullingStatistics lastShadowCullingStatistics();

public record ShadowCullingStatistics(
        boolean available,
        boolean planReused,
        boolean fullRebuild,
        int activeViews,
        int dirtyViews,
        int reusedViews,
        int emptyViewsCleared,
        int candidateCasters,
        int volatileCasters,
        int casterViewTests,
        int casterViewReferences,
        int culledReferences,
        int directionalReferences,
        int pointReferences,
        int spotReferences,
        long buildNanos) {
}
```

快照必须：

- 只包含有界标量，不保留 per-object/per-view Java collection；
- 在 pipeline 未运行或关闭后返回 `available=false` 的安全值；
- 不产生每帧对象风暴；若现有 diagnostics freeze 必须生成不可变对象，只允许一个有界快照分配；
- 加入公共 API allowlist 和兼容测试。

缓存 miss reason 增加 `FRAME_FAILURE`；现有 reason 名称与语义保持兼容。

### 11.2 不变的公共定位

- 不修改 `RenderDevice`、`RenderGraph`、`Material`、`Mesh`、`SceneObject` 的公共定位。
- 不修改 `LocalShadowPipelineSettings` 的 record shape。
- 不增加新的用户配置；已有 `sceneVisibility` 同时控制 forward 与 ordinary shadow spatial culling。
- `ShadowCasterPlanner`、view slot、membership bitset 和 per-face plan 全部保持 package-private。
- 关闭 fine culling 的路径只用于已有 visibility 开关、测试对照和兼容，不形成第二套长期公共模式。

## 12. 实施里程碑

### M0：锁定基线与失败用例

目标：先证明当前粗粒度行为和失败风险，再修改生产代码。

- 将 Gradle 版本改为 `0.23.4-SNAPSHOT`。
- 记录 v0.23.3 balanced 静态、1/100 动态 caster、10k 稀疏 caster 的 CPU/GPU/draw 基线。
- 增加“移动一个 caster 导致无关 tile 失效”的现状测试。
- 增加“partial shadow write 后 frame failure 仍可能命中旧 key”的回归测试。
- 固定 20 个 view slot、face 顺序、边界 padding 和 empty clear 合同。
- 记录当前 local shadow instancing 缺口，建立预期像素测试。

完成条件：失败测试能够稳定复现问题，基线数据可供 M4 对照。

### M1：逐 view caster 计划与绘制

目标：先改变“画谁”，暂时允许缓存仍较保守。

- 实现 `ShadowCasterPlanner`、固定 view slot 和 flattened caster slices。
- CSM 改为 per-cascade AABB/frustum culling。
- point 改为 range broad phase + per-face frustum culling。
- spot 改为 range broad phase + cone frustum culling。
- shadow executors 消费各自 slice。
- 实现 dirty empty view 的局部 depth clear。
- `sceneVisibility=false` 保留全量 caster 对照路径。

完成条件：开启/关闭裁剪的最终像素一致，稀疏场景 caster-view references 明显下降。

### M2：逐 view 缓存失效与失败安全

目标：改变“何时重画”，建立完整正确性合同。

- 用逐 view 精确 membership/epoch 替换全局 `CasterRevisions` 对所有 key 的污染。
- point cache 从每 light block 一个 key 拆为每 face 一个 key。
- 实现 old/new membership 并集失效。
- 实现执行前 invalid、成功后 commit 的 GPU cache 事务。
- 新增 `FRAME_FAILURE` 诊断。
- light/camera/settings/generation 的既有 miss reason 保持正确。

完成条件：局部 caster 变化只重画相关 view；失败恢复帧无 stale/partial shadow 命中。

### M3：增量快路径与实例 batch 加固

目标：避免为了精细失效新增更高的 CPU 固定成本。

- 暴露 package-private changed-entry snapshot。
- 复用 view bitset、slice arena、frustum 和统计存储。
- 实现 unchanged-frame O(1) plan reuse。
- 实现只重测 changed caster/changed view 的增量路径。
- 为实例 batch 增加 aggregate bounds 与精确 matrix snapshot revision。
- 补齐 point/spot instanced shadow，并保持单帧一次 instance upload。
- 对 unknown/volatile caster 实施显式保守回退。

完成条件：warm-up 后静态帧零热路径分配；实例 batch 在三类 shadow 中视觉正确且上传次数不回退。

### M4：诊断、压力门禁与发布闭环

目标：让收益可测、回归可查、版本可发布。

- 增加 `ShadowCullingStatistics` 与 diagnostics 展示。
- 新增确定性动态阴影集成 Demo。
- 新增稀疏与密集场景 benchmark。
- 更新能力矩阵、Render3D 阴影指南、测试指南、changelog 和性能报告。
- 远端可用后确认 Windows/Linux 无桌面 CI 继续通过。
- 所有门禁通过后，将版本从 `0.23.4-SNAPSHOT` 调整为 `0.23.4`。

完成条件：功能、GL 日志、性能、文档和版本号同时闭环；不得只以单元测试通过作为发布依据。

## 14. 测试与验收矩阵

### 14.1 纯 JVM

- 一个 caster 只进入实际相交的 directional cascades。
- cascade 边界 caster 保守进入相邻级，不产生漏选。
- 点光 range 外 caster 不进入任何 face。
- 点光 cube seam caster 同时进入必要相邻 face。
- 聚光锥外 caster 被剔除，锥边 caster 保守保留。
- unbounded/invalid bounds caster 进入全部 active view 并标记 volatile。
- `sceneVisibility=false` 时所有 candidate 进入全部 active view。
- caster 在同 view 内移动只递增相关 transform/model epoch。
- caster 从 face A 移到 face B 时 A、B 都 dirty，其余 face 保持 clean。
- caster 离开最后一个 view 时旧 view dirty 且生成 empty clear。
- caster 在所有 view 外移动时 shadow dirty view 数为零。
- material、MASK alpha、skin 和 morph 只失效 membership 并集。
- camera 变化但 snapped cascade matrix 未变时 plan/key 可复用。
- light slot 复用给不同 stable light ID 时触发 new allocation。
- frame failure 后 dirty key 不可命中，未触碰 clean key 仍可命中。
- 完整重建的 bitset 比较不依赖 hash 唯一性。
- caster 顺序和 flattened slices 对同输入确定。
- arena 容量 warm-up 后保持复用。
- 实例矩阵任意一个 float bit 变化都会推进 batch revision。
- aggregate instance bounds 与三类 view membership 正确。

### 14.2 GL smoke

- culling on/off 在 OPAQUE、MASK、skin、morph 场景产生一致的最终阴影像素。
- CSM cascade 边缘移动相机，无漏影、闪断或明显 popping。
- point caster 跨 cube face 时旧面清除、新面出现，接缝连续。
- spot caster 进出锥体时 tile 正确更新。
- 最后一个 caster 离开 view 后无 ghost shadow。
- 在部分 shadow view 已绘制后注入异常，恢复帧强制重画且无 stale cache hit。
- 实例 batch 同时向 directional、point、spot 投影，且每帧 instance upload 次数保持一次。
- resize 不重建固定 shadow atlas，view plan 与 cache 仍正确。
- 全程无 `GL_INVALID_*`、无 `HIGH`，新增 `MEDIUM` 必须分类并有明确解释。

### 14.3 确定性 Integration

新增 `runRender3dDynamicShadowIntegration`，固定窗口、关闭 VSync、有限帧运行以下序列：

1. 静态 warm-up，确认 `0 rendered / 20 reused`。
2. 移动一个 caster，但仍处于同一小范围 view 集合。
3. 让 caster 跨越 point cube face，确认旧/新 face 更新。
4. 让 caster 离开 spot cone/light range，确认旧 tile 清理。
5. 在全部 shadow view 外继续移动，确认零 shadow redraw。
6. 分别推进 skin 与 morph revision，确认只更新相交 view。
7. 移动一盏 point/spot light，再轻移 camera，确认互不相关 view 复用。
8. 注入一次 shadow pass failure，下一帧恢复并重建受影响 view。
9. 触发 resize，确认固定 shadow atlas 尺寸和缓存合同不变。

每一步同时断言最终像素、dirty/reused view、miss reason、caster references、draw count、GL log 和正常退出。

## 15. 性能门禁

M0 先记录 v0.23.3 同机数据，M4 使用相同 GPU、分辨率、quality 和场景比较。首版目标如下：

| 场景 | 门槛 |
| --- | --- |
| 静态 balanced warm-up 后 | `0 rendered / 20 reused`，planner `planReused=true`，热路径零分配 |
| 默认小场景 | 相比 v0.23.3 CPU/GPU 中位数回退均不超过 2% |
| 10k 稀疏静态 caster | caster-view references 相对全量 20-view 基线减少至少 80% |
| 10k 中仅 1 个 caster 动态 | 只测试/重建相关 caster/view；shadow redraw 不得退化为 20 view |
| unchanged planner | 同机 release/JVM 预热后中位数目标 `≤ 0.05 ms` |
| 单 caster 增量 | 中位数目标 `≤ 0.25 ms` |
| 10k × 20 view 强制完整重建 | 中位数目标 `≤ 2.0 ms`，并单独记录 P95 |
| 实例 batch | 单帧 instance buffer prepare/upload 次数不高于 v0.23.3 |

若机器噪声使绝对时间无法稳定复现，以五轮中位数、P95、空间测试数、caster-view references 和实际 draw 数共同判断。不得通过缩小 bounds、取消边界 padding、漏掉 MASK/skin/morph/instances 或降低 shadow quality 达成指标。

## 18. 风险与控制

### 风险一：过度裁剪导致漏影

控制：全部测试采用保守 bounds、cascade/cube/cone guard band；边界可以多画，不能少画。culling on/off 必须做像素对照。

### 风险二：只按新位置失效导致 ghost shadow

控制：始终保存 old membership，失效集合取 old/new 并集；empty view 必须清理。

### 风险三：缓存 hash 碰撞造成 stale shadow

控制：bitset 与 revision 精确比较是正确性依据，hash 只允许作为快速拒绝。

### 风险四：精细计划 CPU 成本高于节省的 draw

控制：changed-entry、固定 20 view、primitive arena、unchanged O(1) reuse；密集场景同时保留完整重建基准。

### 风险五：point per-face 更新产生 seam

控制：face frustum padding、相邻 face 重复 membership、独立像素和跨 face 动画测试。

### 风险六：失败帧污染仍被复用

控制：dirty key 执行前失效，只有完整 frame success 才重新 valid；局部 scissor 保证 clean tile 未被触碰。

### 风险七：逐实例裁剪诱发范围膨胀

控制：v0.23.4 明确停在 batch aggregate bounds，不引入 compaction、indirect 或第二套实例上传。

## 19. 完成定义

只有同时满足以下条件，v0.23.4 才可以发布：

- 三类 shadow view 均使用独立 caster slice。
- point shadow cache 已细化到 face，方向光已细化到 cascade，spot 保持 tile 粒度。
- caster old/new membership 并集失效、empty clear 和失败帧 invalidation 均有自动化证明。
- 普通 mesh、MASK、skin、morph、实例 batch 的视觉结果正确。
- static warm-up、局部动态和全部 view 外动态行为满足合同。
- 默认 JVM 门禁、GL smoke、动态 integration 和 local verification 全绿。
- GL 日志无未解释 HIGH/MEDIUM，生命周期无泄漏、悬挂或重复释放。
- 性能门槛通过且有五轮数据，不以单次最好结果代替。
- 公共 API allowlist、能力矩阵、指南、changelog、性能报告和发布报告已更新。
- 版本号最终为 `0.23.4`，工作树干净，发布提交可复现。

## 20. v0.23.4 之后

本版本完成后，Render3D 的动态阴影 CPU 主路径将具备足够稳定的局部性。后续再根据 profiling 选择下一步：

1. caster 数量继续增长且 CPU 空间测试成为瓶颈时，再评估 scene-wide BVH/loose grid；
2. 大型实例批次成为瓶颈时，再评估 GPU culling + indirect shadow submission；
3. 阴影质量而非提交成本成为瓶颈时，再评估 contact shadow、PCSS 或其他软阴影方案。

这些方向都不能反向扩大 v0.23.4 的范围。
