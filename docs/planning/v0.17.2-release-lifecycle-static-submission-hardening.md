# v0.17.2 发布工程、GL 生命周期与静态提交加固实施计划

## 实施状态（2026-07-22）

代码、无桌面测试、完整本地 GL、JFR 与 GL 日志审计已完成。2026-07-22 的证据链复查修复了
GL 门禁执行顺序/输入声明、性能不可比较原因、候选 Git 身份和实际 benchmark 参数记录。
当前 `releaseReadiness` 会正确阻止不可比较或身份矛盾的证据；优化材质覆盖判定、矩阵 arena 写入与空
pending-state flush 后，最终静态 all-visible 五轮 CPU 中位数为 `2.835 ms`，已通过 `3.126 ms` 的 5%
回归门槛；完整本地 readiness 的 71 项任务也已通过。正式 tag 仍等待人工检查和远端 CI，不提前声明
外部发布完成。

## 1. 版本定位

v0.17.2 是 v0.17 系列的第二个补丁版本，主题是 **发布可信度、OpenGL 资源生命周期和静态场景提交成本的进一步收敛**。

本版本不增加新的渲染功能，不新增 subsystem，不扩展稳定公共 API，也不把项目推进到 GPU-driven rendering。实施顺序固定为：

1. 发布工程自动化；
2. OpenGL 状态与资源生命周期加固；
3. 静态场景内存与命令录制优化；
4. GL 日志策略贯穿所有里程碑；
5. 只建立最小可用的结构化性能基线。

版本目标为 `0.17.2`。开发阶段使用 `0.17.2-SNAPSHOT`，只有完整发布门禁、文档一致性和 Git 发布状态全部满足后，才能调整为正式版本号。

## 2. 开工前置条件

v0.17.2 不接收 v0.17.1 的未完成发布收尾。开工前必须先完成：

- `preview.vert` 和 `preview.frag` 已登记到 `docs/licenses/assets.tsv`，路径、许可、版本和 SHA-256 均通过 `assetManifestGuard`；
- v0.17.1 的性能报告和发布报告没有尾随空格，报告内容与真实命令结果一致；
- v0.17.1 的当前修复、新增测试和文档已经形成一致的 Git 快照，不存在漏掉的 untracked source/test/resource；
- `localGlVerification localReleaseVerification --rerun-tasks` 通过；
- GL 日志中没有真实 HIGH、`GL_INVALID_*` 或未解释的 MEDIUM；
- v0.17.1 已使用正式版本号完成 release commit/tag，或者发布人明确决定取消 v0.17.1、将修复整体并入 v0.17.2。两种状态必须二选一，不能让两个版本共享一组未归档工作树。

若任一项不满足，先完成 v0.17.1，不允许通过修改 v0.17.2 计划来掩盖旧版本门禁失败。

## 3. 总体目标

### 3.1 必须完成

1. 一个命令能够可靠回答“当前候选是否具备本地发布条件”，失败信息直接指出版本、资产、文档、Git、JVM、GL 或性能中的具体阻塞。
2. 所有发布资源必须具有八字段资产记录和正确哈希；新增资源遗漏时，在执行完整测试前快速失败，并生成可复制的候选记录。
3. 发布报告不能再手工声称不存在的验证结果；至少要有机器生成的验收摘要作为证据。
4. OpenGL owner 关闭、RenderGraph rebuild、失败回滚和 native id 被驱动复用后，设备状态缓存不能继续把旧对象当成当前绑定对象。
5. 资源生命周期加固不得在正常逐 draw 路径加入 GLFW 查询、全局锁或 OpenGL 同步点。
6. 静态场景保持当前 O(1) scene frame/queue 复用，同时降低每帧分配与命令录制中的重复工作。
7. GL HIGH、MEDIUM 和 `GL_INVALID_*` 必须在 JUnit GL smoke 与 JavaExec integration 中使用同一套审计策略。
8. 建立 schema 固定、可比较、带环境指纹的最小性能结果，不把跨硬件绝对时间误当成回归。

### 3.2 应当完成

- 发布门禁输出人类可读 Markdown 和机器可读 JSON；
- release report 的验证表由机器结果生成或校验；
- GL 消息白名单包含明确的 vendor、id、入口、理由和失效日期；
- 静态 all-hidden 场景进一步降低 allocation，mostly-hidden 场景降低 command record 时间；
- 发布失败时保留本次任务参数、版本、Git 指纹、GL 环境、消息摘要和失败阶段；
- 发布工程代码集中在独立 Gradle 脚本或小型 buildSrc-free helper 中，避免继续膨胀根 `build.gradle`。

### 3.3 非目标

v0.17.2 明确不做：

- Vulkan、第二图形后端或 Gradle 多模块拆分；
- ECS、GPU culling、Hi-Z、MDI、bindless 或 persistent scene command list；
- 新的 PBR、后处理、UI widget、场景编辑器或资源编辑器功能；
- shader hot reload、完整 pipeline cache 或驱动二进制 shader cache；
- RenderGraph 拓扑编辑和 draw-call replay；
- 为消除厂商性能提示而进行未经测量的大规模 shader 变体系统；
- 通过提高现有静态性能门槛来让测试变绿；
- 自动执行 commit、tag、push 或发布到远端。

## 4. 架构约束

### 4.1 公共 API

- 默认不新增稳定公共类型或方法。
- 发布工程只属于 Gradle/build tooling，不进入 runtime API。
- GL 消息策略属于验证配置，不成为应用层公共接口。
- 生命周期 epoch、删除通知和状态缓存同步必须保持在 backend 内部或 package-private 边界。
- 静态 draw plan、统计累加器和缓存键保持在 `subsystems.render3d` 内部。
- 若实现确实需要公共 API 变化，必须先更新 allowlist/migration 文档并单独评审，不得顺手暴露。

### 4.2 性能路径

- 正常资源未删除时，epoch 检查只能是 O(1) primitive comparison。
- 不允许在每条命令前调用 `glGet*`、`glfwGetCurrentContext` 或获取进程级锁。
- 静态场景快路径必须保留 membership、camera、viewport、shadow matrix、visibility setting 和 resource lifetime 的完整失效条件。
- dynamic/TransformSource/animated updater 继续走现有更新路径，不能被误判为 immutable。
- diagnostics OFF 时不能因为基线或日志采集增加生产 draw、blit、readback 或对象快照。

### 4.3 失败语义

- 发布门禁中的任一未知状态按失败处理，不按通过处理。
- 资源关闭失败不能阻止后续资源尽力关闭；首个异常为主异常，其余作为 suppressed failure。
- 状态缓存失效失败不能保留“仍然有效”的假状态。
- 性能结果缺少环境指纹、warmup、samples 或场景参数时标记为不可比较，不生成绿色结论。
- 日志策略无法识别的 HIGH/MEDIUM 默认失败；只有精确匹配的审计项可以通过。

## 5. 里程碑一：发布工程自动化

### 5.1 拆分发布构建逻辑

新增 `gradle/release-verification.gradle`，将下列逻辑从根 `build.gradle` 中集中管理：

- 资产 manifest 校验；
- 版本与文档一致性校验；
- Git candidate 状态校验；
- 验证证据收集；
- `releaseReadiness` 聚合任务；
- 本地发布摘要生成。

根 `build.gradle` 只负责 `apply from:` 和现有任务依赖，不再继续堆叠大段发布脚本。该拆分属于 build logic 整理，不改变构建产物。

### 5.2 资产 manifest 工作流

保留 `docs/licenses/assets.tsv` 为唯一提交清单，继续使用八字段合同：

1. path；
2. purpose；
3. owner/source URL；
4. license；
5. version/date；
6. sha256；
7. transformation；
8. redistributable。

新增两个任务：

#### `assetManifestGuard`

继续作为只读严格门禁，并补强：

- manifest path 必须使用 `/`，不得包含 `..`、绝对路径或大小写不一致的重复记录；
- 每条记录正好八个非空字段；
- path 集合与 `src/main/resources`、`src/demo/resources` 完全一致；
- SHA-256 必须是 64 位小写十六进制；
- `redistributable` 只能是 `yes`；
- 项目自有资源允许 `project license`，第三方资源必须给出来源与明确许可证；
- hash 不一致时同时输出 expected、actual 和资源路径；
- 缺失记录时在同一次失败中列出全部缺失资源。

#### `suggestAssetManifestEntries`

该任务只生成 `build/reports/release/missing-assets.tsv`，不得自动修改提交清单。对每个缺失资源填充：

- path；
- 根据扩展名推断的 purpose 候选；
- `TODO` owner/license/version/transformation；
- 实际 SHA-256；
- `TODO` redistributable。

因为许可与可再分发性需要人工判断，生成任务不能默认写 `yes`，也不能绕过 guard。

### 5.3 版本与文档一致性

新增 `releaseMetadataGuard`，接受 `-PreleaseVersion=<semver>`，发布 0.17.2 时执行：

```powershell
.\gradlew.bat releaseMetadataGuard "-PreleaseVersion=0.17.2"
```

必须验证：

- Gradle `project.version` 精确等于 `0.17.2`，正式发布不允许 `SNAPSHOT`、`rc` 或其他前缀后缀；
- `docs/releases/v0.17.2-release-report.md` 存在；
- release report 标题、状态和版本与 Gradle 一致；
- capability matrix 的“正式稳定版本/当前开发版本”没有矛盾；
- changelog 中存在 v0.17.2 条目，且不再标记为开发中；
- release report 引用的性能结果文件存在；
- 所有被报告为“通过”的命令在本次机器验收摘要中有对应成功记录；
- 文档日期不能早于所引用验证结果的时间；
- `git diff --check` 与 `git diff --cached --check` 均无空白错误。

开发阶段不强迫 `check` 使用正式版本；只有 `releaseReadiness` 强制要求 `-PreleaseVersion` 和正式版本状态。

### 5.4 Git candidate 状态

新增 `releaseGitGuard`，用于 release commit 前的 staged candidate：

- 允许存在 staged changes；
- 不允许存在 unstaged changes；
- 不允许 `src`、`docs`、`gradle`、根构建文件下存在 untracked 文件；
- 不允许 staged deletion 漏掉对应迁移/清单更新；
- 输出 HEAD、branch、staged diff SHA-256 和 candidate tree 指纹；
- detached HEAD 只警告，不直接失败；
- 不执行 add、commit、tag、push 或 reset。

另提供 `releaseCleanTreeGuard` 给 release commit 之后使用，要求工作区和 index 完全干净。

### 5.5 验证证据与聚合入口

新增 `releaseReadiness`：

```powershell
.\gradlew.bat releaseReadiness "-PreleaseVersion=0.17.2" --rerun-tasks
```

执行顺序固定为：

1. `releaseGitGuard`；
2. `releaseMetadataGuard`；
3. `assetManifestGuard`；
4. dependency/public API/architecture guards；
5. JVM `check`；
6. `localGlVerification`；
7. `localReleaseVerification` 中未被前者覆盖的 native/IME/集成任务；
8. 静态提交硬门槛；
9. GL 日志审计；
10. 生成摘要。

由于 Gradle task graph 可能去重，不以“tasks 数量”作为覆盖证明；摘要必须记录实际入口、结果和关键场景。

生成：

- `build/reports/release/readiness.json`；
- `build/reports/release/readiness.md`；
- `build/reports/release/gl-messages.json`；
- `build/reports/release/performance.json`。

摘要至少包含版本、HEAD、candidate diff hash、dirty 状态、Java/LWJGL/OS/GPU/driver、任务结果、性能门槛、GL 消息计数和失败阶段。

### 5.6 里程碑一验收

- 新增资源但未登记时，`assetManifestGuard` 在运行 GL 测试前失败，并生成完整候选行；
- hash、license、字段数、重复 path 和不可再分发分别有 JVM/build logic 测试；
- snapshot 冒充正式版本、报告版本不一致、报告引用不存在结果分别失败；
- staged candidate 可以验证，存在 unstaged/untracked source 时失败；
- release report 不能声明本次摘要中不存在的成功任务；
- 所有任务只读 source tree，除 `build/reports` 外不写入其他路径。

## 6. 里程碑二：OpenGL 状态与资源生命周期加固

### 6.1 问题模型

OpenGL native id 只在当前 context 生命周期内代表对象。删除 VAO、program、texture、sampler、buffer 或 framebuffer 后，驱动可以把同一个整数 id 分配给新对象。若 `GlRenderDevice` 仍缓存旧 id，新对象第一次绑定可能被错误跳过，产生：

- `GL_INVALID_OPERATION`；
- draw 使用错误 VAO/program/texture；
- framebuffer 或 sampler 状态串扰；
- 测试单独运行通过、连续创建/关闭 pipeline 后失败；
- Java owner 已关闭但状态缓存仍声称对象已绑定。

v0.17.2 要修复这一类问题，而不只在某个 pipeline close 点手工补一个 invalidate。

### 6.2 backend context epoch

在 backend 内新增 package-private 的 context-scoped invalidation registry，建议命名为 `GlContextStateEpoch`。合同如下：

- 每个当前 `GLCapabilities` 身份对应一个单调 epoch；
- 删除任何可能被 device 缓存的 GL 对象后递增 epoch；
- `GlRenderDevice` 在一次 command submission 开始时比较当前 epoch 与已观察 epoch；
- epoch 不同时清空 Java 状态缓存，再执行本次命令；
- 没有当前 capabilities 时返回无上下文状态，不调用 GLFW；
- context A 的删除不能使 context B 的 cache 失效；
- registry 不保存强引用导致 context 永久泄漏；
- epoch 溢出必须安全失败，不允许回绕后误判相等。

第一版采用粗粒度全状态失效。资源删除频率远低于 draw 频率，先保证正确性；没有证据前不做 per-resource bitset 或复杂依赖图。

### 6.3 删除通知接入范围

逐一审计并接入：

- VertexArray；
- ShaderProgram；
- Texture2D/TextureCube；
- Sampler；
- Uniform/vertex/index/instance buffer；
- Framebuffer 与 renderbuffer；
- query/timer 对象（仅当进入 device cache）；
- preview conversion 拥有的临时目标；
- RenderGraph rebuild/resize 创建和关闭的 attachment。

每个 owner 的 `close()` 必须遵循：

1. 验证 owner/context/thread 合同；
2. 删除 native object；
3. 只有删除调用成功后发布 epoch 变化；
4. 清空自身 id/closed 状态；
5. 重复 close 保持幂等；
6. 失败时不伪造“删除成功”。

若现有 wrapper 在删除前先标记 closed，应调整为异常安全的两阶段关闭，不扩大到公共 API。

### 6.4 submission 边界

epoch 同步只发生在受控边界：

- `GlRenderDevice` 开始执行一个 CommandBuffer；
- RenderGraph 开始执行一个 compiled frame；
- 必须兼容测试直接执行单个 command buffer 的入口。

不允许：

- 每条 command 查询 epoch；
- 每次 bind 调用 GLFW/OpenGL 查询当前 native state；
- 为验证缓存而调用 `glGetIntegerv`；
- 在生产路径使用 `glFinish`、`glFlush` 或同步 readback。

### 6.5 pipeline 与 graph 生命周期

保留 `RenderPipeline` 对使用过的 device 做最终 invalidate 的防御性逻辑，但把它定位为 owner-boundary safety net，而不是唯一正确性来源。必须覆盖：

- build 成功后 close；
- build 中途失败并回滚；
- resize 导致 attachment 重建；
- graph rebuild 后 native id 被复用；
- 同一个 device 顺序执行多个 pipeline；
- pipeline A 关闭后 pipeline B 复用相同数字 id；
- close 过程中一个资源失败，其余资源继续释放；
- device 重复 invalidate 和 pipeline 重复 close。

### 6.6 生命周期测试

新增或扩展真实 GL 测试：

1. 连续创建/关闭至少 128 个 pipeline，复用同一个 device；
2. 主动制造 VAO、program、texture、FBO id 重用，验证首次 bind 不被跳过；
3. resize/rebuild 循环 100 次，无 HIGH、`GL_INVALID_*` 或错误像素；
4. build failure 的部分资源全部关闭，下一次 build 可以成功；
5. 两个 context 的 epoch 互不污染；
6. 无当前 context 时诊断和清理前置检查不触发 `GLFW_NOT_INITIALIZED`；
7. callback/command failure 后 cleanup 仍执行，后续帧不 use-after-close；
8. `invalidateState()` 重复执行安全。

新增 `glResourceLifecycleVerification` 并接入 `localGlVerification` 与 `releaseReadiness`，不接入无桌面默认 `check`。

### 6.7 里程碑二验收

- 删除可缓存对象后，下一次 submission 必定重新建立状态；
- 无新增逐 draw GL 查询、锁或同步点；
- pipeline matrix、resize、failure cleanup 和 id reuse 测试通过；
- JFR/基准中未观察到 epoch 机制造成可测量的普通帧回归；
- 所有资源 owner 的 close/rollback 合同更新到 `docs/architecture/resource-ownership.md`。

## 7. 里程碑三：静态场景内存与命令录制优化

### 7.1 当前基线

v0.17.1 加固后的本机基线：

- `10k static/all-hidden`；
- 100 warmup + 1,000 measured frames；
- `SceneFrame + queue` 约 `0.003–0.004 ms`；
- 当前硬上限保持 `0.15 ms`；
- 整帧 allocation 约 `4.0–4.3 KiB/frame`；
- all-hidden 仍保留一个 unbounded probe；
- queue reuse、camera/resize/light/membership 失效语义已有测试。

v0.17.2 不再优化已经足够低的 frustum/sort，而是先定位统计发布、命令录制和 frame diagnostics 的剩余分配。

### 7.2 先测量再修改

新增 `runSceneSubmissionStaticJfr` 或复用现有 JFR 入口，固定：

- 10,000 static/all-hidden；
- 10,000 static/mostly-hidden；
- 10,000 static/all-visible；
- 1,000 warmup + 10,000 measured frames；
- VSync off、debug callback on、固定窗口和相机；
- 分别记录 scene build、command record、execute、diagnostics 和 allocation stack。

报告必须列出前十个逐帧 allocation site。没有 allocation stack 证据前，不得提前设计公共 command cache。

### 7.3 统计对象收敛

优先检查并消除：

- `SceneFrame.Statistics` 每帧新建；
- `VisibilityStatistics.from()` 后又由 `withCommandEncoding()` 二次复制；
- diagnostics summary 对同一帧重复转换；
- queue reused 时重复复制完全相同的分类统计；
- Java record/list 临时包装。

建议做法：

- `SceneFrameBuilder` 内部使用可复用 primitive accumulator；
- command encoding 完成后只构造一次对外不可变 `VisibilityStatistics`；
- diagnostics 在帧发布边界复制一次值，不持有 builder 可变引用；
- 失败帧继续发布 UNAVAILABLE/FAILED，不复用上一成功帧统计；
- 公共不可变快照语义保持不变。

### 7.4 静态 queue binding plan

当且仅当 forward queue 已复用且全部 renderer/model 满足 immutable 合同时，缓存 package-private `QueueBindingPlan`，预计算：

- shader 切换位置；
- material template 切换位置；
- mesh 切换位置；
- blend/front-face/mirrored 切换位置；
- shadow mesh 切换位置；
- 不依赖每帧 uniform 的稳定 draw metadata。

失效条件与 scene queue 保持一致，并额外包含：

- graph/pipeline generation；
- shader/program lifetime generation；
- mesh/VAO lifetime generation；
- material template identity；
- shadow enabled 和 pass kind。

MaterialInstance override 仍在 render-record 边界按实例处理，不能因为共享 Material template 而跳过不同 override。动态模型和 alpha insertion order 不得进入错误快路径。

### 7.5 CommandBuffer 边界

v0.17.2 不引入公开 secondary command buffer。允许的优化只有：

- 复用 command arena 容量，避免稳定场景反复扩容；
- 将已经拥有快照语义的内部矩阵/对象 payload 通过 package-private owned path 写入 primitive arena；
- 避免同一帧对同一静态矩阵做两次对象复制；
- 复用稳定 binding plan，仍逐帧录制需要的命令；
- 保持 public `setUniformMat4`、material override 和失败回滚语义不变。

禁止：

- 缓存包含已关闭 native handle 的完整 CommandBuffer；
- 跨 graph generation 重放旧命令；
- 绕过矩阵快照，把调用方可变 Matrix4f 引用留到执行阶段；
- 为降低数字而关闭 diagnostics 或删掉正确性命令；
- 使用 `custom()` 建立未经守卫的提交后门。

### 7.6 数值目标

硬门槛：

- `10k static/all-hidden SceneFrame + queue <= 0.15 ms`，保持不变；
- 所有静态门槛连续运行五轮通过；
- 无 HIGH、`GL_INVALID_*`、线程悬挂或错误像素；
- dynamic/mixed 场景统计与最终像素不回退。

工程目标：

- all-hidden allocation 从约 `4.0–4.3 KiB/frame` 降至 `<= 2.5 KiB/frame`；
- mostly-hidden command-record median 相对 v0.17.1 同机基线改善至少 15%，或在报告中用 allocation stack 证明剩余成本来自不可省略的公共快照；
- all-visible 不得出现超过 5% 的 CPU median 回退；
- epoch/lifecycle 加固在无资源删除的稳定帧中不得造成超过 2% 的 CPU median 回退。

工程目标未达成时不能直接改大数字。必须记录原因、JFR 证据和是否推迟到下一个 minor 版本；硬门槛不得豁免。

### 7.7 里程碑三验收

- static all-hidden、mostly-hidden、all-visible 各五轮结果归档；
- camera movement、resize、light direction、membership 和 transform mutation 都能正确退出快路径；
- MaterialInstance 隔离、mirrored front face、alpha 顺序和 shadow caster 数量保持正确；
- command/matrix/object payload 计数与实际 draw 一致；
- allocation 改善由 JFR stack 和 benchmark 同时证明，而不是只看 FPS。

## 8. 贯穿项：OpenGL 日志审计

### 8.1 单一策略文件

新增 `config/gl-debug-policy.tsv`，每行至少包含：

- vendor pattern；
- renderer/driver pattern；
- severity；
- source；
- type；
- message id；
- 允许的测试或 Gradle task；
- message pattern；
- rationale；
- owner；
- added date；
- expiry/review date。

策略采用精确匹配优先。不得仅按 `MEDIUM`、vendor 或宽泛文本整体忽略。

### 8.2 当前消息处理

- `GL_INVALID_*`：任何入口均立即失败；
- 真实 HIGH：任何入口均立即失败；
- DiagnosticsContracts 主动注入的 application HIGH `id=99999`：只允许在该精确测试中出现一次，文本必须匹配；
- NVIDIA `id=131218` shader specialization：只允许已登记的 program/state matrix 测试和 preview 预热入口；
- NVIDIA `id=131154` pixel transfer synchronization：只允许明确执行验收 readback 的测试阶段；
- 新 id、新测试入口、新文本或超出次数全部失败。

### 8.3 JUnit 与 JavaExec 统一

- `GlDebug.assertNoError()` 保持对 GL error 和 HIGH 的即时失败；
- GL smoke XML 日志继续在 task 结束后扫描；
- 所有 JavaExec integration 将 stdout/stderr 保存到 `build/reports/gl/<task>.log`；
- integration 结束后使用同一 policy parser 审计；
- 进程正常退出但日志含未授权消息时，Gradle task 仍失败；
- 进程失败且日志也有 GL 错误时，保留进程异常为主原因，并附带 GL 摘要。

### 8.4 131218 专项处理

建立最小 shader/state matrix，记录：

- program id/逻辑 shader 名；
- VAO layout；
- blend/depth/cull/front-face；
- framebuffer format/sample count；
- 首次与重复 draw 是否触发消息。

若可通过测量期前的一次受控预热消除消息，则实施预热；若属于驱动按合法状态专门化且无法消除，保留窄白名单。不得为了消除提示生成无限 shader permutation。

### 8.5 131154 专项处理

- 把 `glReadPixels` 验收放在明确的测试收尾阶段；
- 性能测量窗口内禁止 readback；
- 日志摘要标记该消息来自 correctness probe；
- 生产 Demo 和普通 integration 不得出现未声明的同步 readback。

## 14. 风险与回退

### 14.1 context epoch 误用

风险：context identity 错误可能造成跨 context 污染或漏失效。

回退：先保留 pipeline owner-boundary invalidate，并让 epoch 只负责额外全失效；多 context 测试稳定后再依赖它作为主要保障。

### 14.2 过度缓存命令

风险：旧 native handle、MaterialInstance override 或动态矩阵被跨帧重放。

回退：只保留 primitive statistics 和 binding decision cache，继续逐帧录制 draw/uniform 命令。

### 14.3 日志白名单过宽

风险：真实驱动错误被既有 id 掩盖。

回退：策略必须绑定 vendor、id、入口、文本和次数；无法精确描述就不加入白名单。

### 14.4 发布任务依赖 Git

风险：source archive 或无 Git 环境无法执行。

回退：默认 `check` 不依赖 Git；只有显式 `releaseReadiness` 要求仓库环境，并输出清晰错误。

### 14.5 性能噪声

风险：调度抖动导致误判。

回退：使用五轮 median、环境指纹和不可比较状态；不自动覆盖基线，不用单轮 FPS 放行。
