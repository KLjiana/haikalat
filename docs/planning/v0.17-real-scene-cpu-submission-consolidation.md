# v0.17 真实场景压力与 CPU 提交收敛实施计划

> 状态：`0.17.0` 正式版；本地发布门禁与人工验收完成，远端 CI/tag 由发布流程继续归档
> 目标版本：`0.17.0`
> 基线版本：`0.16.0`
> 版本主题：用真实多 mesh/material 场景验证 v0.16 可见性架构，并收敛静态场景重复计算与逐 draw 分配
> 核心原则：先消除已经测量到的 CPU 浪费，再以量化结果决定是否建设 GPU culling、Hi-Z 与 MDI

## 1. 执行摘要

v0.16 已为普通 `MeshRenderer` 建立 local/world bounds、稳定相机与阴影视锥、单次 updater
`SceneFrame`、primitive Render Queue 和 diagnostics 闭环。程序化 10,000 renderer / 10% 可见场景
将普通 forward draw 从 10,000 降到 1,000，CPU median 从约 `4.8 ms` 降至约 `0.9 ms`。

这证明 CPU frustum culling 有效，但还不能直接证明项目需要 GPU-driven renderer：

- 现有主要压力场景由程序化 mesh/material 组合构成，不代表真实 glTF 的 node、primitive、材质和纹理分布；
- `SceneFrameBuilder` 仍会在每帧执行所有普通 renderer 的 model updater 和 world-bounds 变换；
- camera、shadow matrix、scene membership 和静态 transform 全部不变时，forward/shadow queue 仍会重新分类和排序；
- `CommandBuffer.setUniformMat4()` 为快照语义逐命令创建 `Matrix4f`，可见 draw 增加时产生线性分配；
- `RenderPipeline` 会为相邻且相同的 shader/material 重复录制 frame/material bindings，虽然
  `StateCache` 能避免部分 GL 调用，但不能消除 JVM 录制成本；
- 10,000 全可见场景约为 `2.5 MiB/frame`，10% 可见场景约为 `252 KiB/frame`，分配与可见 draw
  近似线性增长；
- 当前数据尚未说明 CPU queue、command encoding、driver draw submission、材质碎片或 GPU 像素成本中
  哪一项会在真实场景首先成为瓶颈。

因此 v0.17 不实现 GPU culling 或 MDI。它完成四条纵向闭环：

1. 建立可重复的真实多 mesh/material glTF 场景压力矩阵；
2. 为明确静态的 transform/world bounds 建立 revision 驱动缓存；
3. 对稳定 camera/shadow 输入复用独立 queue，并保持所有 v0.16 可见性语义；
4. 将 matrix command snapshot 编码进可复用 primitive arena，并按实测结果减少重复 binding 录制。

版本完成定义：

> 框架能在不引入 ECS、场景树、GPU culling 或新后端协议的前提下，让明确静态的普通 renderer
> 不再每帧重复生成 model/world bounds，让未变化的 camera/shadow queue 可独立复用，让矩阵命令快照
> 不再逐 draw 分配对象；真实 glTF 压力场景具备可复现的 CPU、GPU、allocation、draw、材质碎片和
> cache-hit 证据，并能据此给出 v0.18 是否进入 GPU-driven 的明确结论。

## 2. 版本目标与非目标

### 2.1 必须完成

1. v0.16 先形成干净、可复现的 `0.16.0` 发布基线。
2. 增加真实、多 node、多 primitive、多 material 的 glTF scalability 场景。
3. 保留资源共享：压力对象不得通过复制 GPU mesh/texture 伪造规模。
4. 区分明确静态 transform source 与任意动态 `ModelUpdater`。
5. 静态 transform 未改变时复用 model matrix 和 world bounds。
6. 动态 updater 继续每 renderer 每帧恰好执行一次，不改变 v0.16 合同。
7. camera 与 shadow queue 使用独立 cache key、独立失效和独立统计。
8. TAA jitter 不得参与 camera queue cache key；稳定 view-projection 才是 visibility 事实来源。
9. `CommandBuffer` 的 mat4 快照迁移到可复用 primitive storage，不再创建逐命令 `Matrix4f`。
10. 保持命令录制后的稳定快照语义，调用方修改源矩阵不得影响已录制命令。
11. 根据 allocation profile 减少相邻相同 shader/material 的重复 frame/material binding 录制。
12. diagnostics 增加 static/dynamic、transform/bounds cache hit、queue reuse 和 command encoding 指标。
13. 建立程序化与真实 glTF 两套 100、1,000、10,000 renderer A/B 基准。
14. 覆盖相机移动、灯光移动、resize、scene mutation、静态 transform mutation、动态 updater 和失败恢复。
15. 完成后以量化门槛决定 v0.18，不用“现代渲染器应该有 MDI”代替证据。

### 2.2 明确非目标

- 不实现 GPU frustum culling、compute culling、Hi-Z occlusion 或 software occlusion；
- 不实现 `glMultiDraw*Indirect`、`glMultiDraw*IndirectCount` 或 draw-command SSBO；
- 不引入 ECS、BVH、octree、scene graph、spatial partition 或层级 bounds；
- 不把 glTF 主路径扩大为骨骼、动画、morph、BLEND、transmission 或高级扩展；
- 不把静态对象自动合并为实例，不改变现有 `InstancedRenderer` 定位；
- 不引入 bindless texture、texture array 或全局材质表；
- 不修改 alpha insertion-order 合同，不顺带实现透明距离排序；
- 不新增第二后端，不拆 Gradle 多模块；
- 不公开 `SceneFrame`、queue arena、cache key 或 live diagnostics 内部数组；
- 不为了减少行数拆分 `CommandBuffer` 或 `RenderPipeline`；
- 不把 JFR、Nsight 或驱动特定扩展变成运行时依赖。

## 3. 基线与问题陈述

### 3.1 v0.16 已确认的基线

以 `docs/performance/v0.16-scene-visibility-2026-07-19.md` 为基线：

| 场景 | visibility | draw | CPU median | queue | allocation |
| --- | --- | ---: | ---: | ---: | ---: |
| 100 all-visible | enabled | 100 | 约 `0.09 ms` | 约 `0.008 ms` | `27 KiB/frame` |
| 10,000 large | disabled | 10,000 | 约 `4.8 ms` | 约 `0.8 ms` | `2,502 KiB/frame` |
| 10,000 large | enabled | 1,000 | 约 `0.9 ms` | 约 `0.5 ms` | `252 KiB/frame` |
| 10,000 all-visible | enabled | 10,000 | 约 `5.2 ms` | 约 `1.0 ms` | `2,502 KiB/frame` |
| 10,000 all-hidden | enabled | 1 | 约 `0.4 ms` | 约 `0.4 ms` | `2.2 KiB/frame` |

由此可以确认：

- SceneFrame/queue arena 自身已经接近 allocation-free；
- 剩余分配主要跟随可见 draw 数，而不是候选 renderer 数；
- all-hidden 仍有约 `0.4 ms` 的 10,000 对象 traversal/model/bounds/classification 成本；
- all-visible 中 CPU submit 与 allocation 明显高于 queue build，逐 draw 录制仍是主要问题；
- GPU culling 最多能解决候选分类与 draw generation 的一部分，不能自动解决材质碎片和每 draw uniform 协议。

### 3.2 当前代码事实

- `MeshRenderer.of(..., Transform)` 内部仍通过 updater 每帧生成矩阵；
- 任意 `SceneObject.ModelUpdater` 是带潜在副作用的回调，框架不能猜测它是否静态；
- `Transform` 只通过受控 setter 修改，具备增加单调 revision 的条件；
- glTF runtime 在 instantiate 时已经得到固定 node world matrix，但当前把它包装为普通 updater；
- `SceneFrameBuilder` 已缓存 membership 相关 mesh/material/blend 元数据；
- forward 与 shadow visibility 的数学输入已经分离；
- `CommandStream` 已使用可复用 primitive/object SoA arena；
- mat4 命令仍通过 `new Matrix4f(value)` 保存快照；
- vec/int/float uniform 已使用 primitive bits 编码，可作为 mat4 改造参考；
- `StateCache` 优化的是执行期 GL state，不等价于减少录制期命令数量和对象分配。

### 3.3 主要风险

- 把任意 updater 当成静态会吞掉副作用或动画；
- 只使用 hash 判断 matrix/cache equality 会有碰撞导致错误复用；
- 把 TAA jitter 纳入 visibility key 会造成每帧 queue miss 和边缘闪烁；
- camera queue 与 shadow queue 共用 key 会错误丢失独立 caster；
- 缓存 material bind 时忽略 `MaterialInstance` mutation 会产生陈旧 uniform/texture；
- 把矩阵对象引用直接塞进 command stream 会破坏命令快照语义；
- 基准复制完整 GPU 资产会把 upload/显存问题混入 scene traversal；
- 只测 all-hidden 会高估 culling/cache 收益；
- 为追求低 allocation 绕过正式 `CommandBuffer` 会失去真实代表性。

## 4. 分层与所有权

### 4.1 依赖方向

```text
core/assets/gltf
  负责真实 glTF CPU 数据和验证
          |
          v
subsystems/render3d/gltf
  负责共享 GPU 资源与固定 node transform 实例化
          |
          v
subsystems/render3d
  Scene / MeshRenderer / SceneFrameBuilder
  静态 revision、bounds cache、forward/shadow queue cache
          |
          v
core/command
  primitive mat4 snapshot 与可复用 command arena
          |
          v
backend
  按既有命令执行 OpenGL，不感知 Scene 或 glTF

runtime/diagnostics
  只接收冻结后的计数与耗时，不持有 renderer/queue

demo/test
  构造真实压力场景、A/B 参数、自动门禁与人工验收
```

禁止新增：

- `core/command -> subsystems/render3d`；
- `core/assets -> runtime/diagnostics`；
- `backend -> glTF/SceneFrame`；
- diagnostics 对 mutable queue 或 model matrix arena 的引用；
- benchmark-only 类型进入 main public API。

### 4.2 生命周期

- glTF GPU mesh/material/texture 继续由 `GltfSceneAsset` 所有并逆序释放；
- 多个 scene instance 只借用共享 GPU 资源，不取得 close 权；
- static transform revision 与 renderer 一起存在，不拥有 GPU 资源；
- SceneFrame/queue cache 由 `RenderPipeline` 内部 builder 所有，build/close 时清空；
- CommandStream primitive arena 由 `CommandBuffer` 所有，`reset()` 只清计数、保留容量；
- diagnostics snapshot 是值类型冻结结果，不能延长 scene 或 GPU resource 生命周期。

## 5. 真实 glTF 压力场景

### 5.1 资产要求

增加或复用一个项目自有、许可明确、体积受控的 glTF/GLB 场景，至少包含：

- 4 个以上 mesh primitive；
- 8 个以上 material identity；
- base-color、normal、metallic-roughness、occlusion/emissive 中至少三类纹理角色；
- shared mesh 被多个 node 引用；
- shared material 被多个 primitive 引用；
- non-uniform scale 与至少一个 mirrored transform；
- OPAQUE 与 MASK；BLEND 继续按当前正式拒绝或限定合同处理；
- finite accessor bounds，并由 loader 复核实际 POSITION 数据；
- `.gltf` external resource 与 `.glb` 至少保留现有自动化覆盖，不要求压力资产各做一份。

不得下载版权不明的第三方 showcase 资产。若现有自有资产不足，优先扩展程序生成的自有 glTF fixture，
并在文档中记录生成脚本、SHA-256 和资源用途。

### 5.2 扩容方法

压力规模通过重复实例化同一个已上传 `GltfSceneAsset` 获得：

- GPU mesh、texture、sampler、material 共享；
- 每个实例只拥有 root transform 和对应普通 renderer membership；
- 不为每个实例重新 decode/upload；
- 实例布局使用确定性公式，不使用未记录随机 seed；
- renderer 总数而非 root instance 数作为 100/1k/10k 容量口径；
- 输出 unique mesh/material/texture、renderer、visible draw 和 estimated VRAM；
- 同一场景支持 all-visible、mixed、mostly-hidden 和 camera-motion 四种布局。

### 5.3 Demo 参数

新增独立 `GltfSceneScalabilityDemo`，或为现有 scalability suite 增加明确的 asset case。建议参数：

```text
--scene=<classpath gltf/glb>
--renderers=100|1000|10000
--layout=all-visible|mixed|mostly-hidden|camera-motion
--visibility=enabled|disabled
--static-cache=enabled|disabled
--queue-cache=enabled|disabled
--command-matrix-arena=enabled|disabled
--frames=<positive>
--warmup=<non-negative>
--rounds=<positive>
--size=<width>x<height>
--resize=<frame>:<width>x<height>
--deterministic
--verify
--diagnostics-export=build/diagnostics/<file>.json
```

生产 API 不暴露这些开关。A/B 开关只存在于 demo/benchmark 或 package-private 测试 seam，避免形成长期兼容债务。

## 6. 静态 Transform 与 Bounds 缓存合同

### 6.1 保守分类

renderer 只分为两类：

1. **明确 revisioned**：由 `MeshRenderer.of(..., Transform)` 或新增固定矩阵工厂创建；
2. **动态/未知**：任意现有 `ModelUpdater`，继续每帧执行一次。

禁止通过以下方式猜测静态：

- updater class 名称；
- 连续两帧矩阵相等；
- lambda identity；
- scene 长时间没有 membership mutation；
- renderer 来自 glTF 就默认静态；
- 用户没有主动调用某个非既有 API。

动态/未知是默认回退路径，行为必须与 v0.16 完全一致。

### 6.2 `Transform` revision

`Transform` 增加 package-private 单调 revision：

- 每个 position/rotation/scale setter 在成功修改后递增；
- setter 输入必须继续复制，不暴露内部 mutable vector；
- revision 溢出使用 fail-fast，不静默回绕；
- 是否对“设置为相同值”递增不影响正确性，第一版允许保守失效；
- `matrix(out)` 不修改 revision；
- 不新增 public `markDirty()`，避免调用者忘记维护合同。

`MeshRenderer.of(..., Transform)` 使用内部 revisioned model source，不再依赖无法识别的 lambda。
不得改变 `MeshRenderer` record component 或现有 canonical constructor，以免扩大兼容破坏。

### 6.3 固定矩阵场景对象

为 glTF 固定 node transform 提供最小工厂，例如：

```java
SceneObject.fixed(mesh, material, matrix, castShadows)
```

要求：

- 工厂复制输入矩阵，调用方后续修改不影响实例；
- 拒绝 non-finite、perspective 或不满足既有 transform 合同的矩阵；
- 固定对象 revision 在生命周期内不变；
- 不给现有 `SceneObject` record 增加 component；
- 不公开内部 marker/cache key；
- 现有构造器与任意 updater 继续保持动态语义。

若工程实现能在不新增公共工厂的情况下让 glTF runtime 表达同一合同，可以使用更小的 package seam，
但不得通过反射或类型名判断。

### 6.4 SceneFrame 缓存

每个 renderer arena slot 至少保存：

- 上次成功 model revision；
- 稳定 model matrix；
- 稳定 mirrored 标记；
- 稳定 world bounds；
- model cache hit/miss；
- bounds cache hit/miss。

构建规则：

1. membership revision 变化时同步 slot，并让新增/替换项 cache miss；
2. 动态 renderer 每帧执行 updater，成功后更新 model/bounds；
3. revisioned renderer 仅在首次或 revision 变化时重建 model；
4. model 未变化且 mesh local bounds identity/值未变化时复用 world bounds；
5. model 更新失败时不提交新 revision；
6. world-bounds 更新失败时不发布半更新 cache；
7. 下一帧允许从最后一次完整成功状态重试；
8. remove 后清除 renderer 强引用，避免 arena 保留用户资源；
9. culling disabled 仍消费同一 model/bounds cache，不恢复旧双 updater 路径。

## 7. Forward/Shadow Queue 独立复用

### 7.1 Forward cache key

forward queue 只有在以下输入全部不变时才可复用：

- scene membership revision；
- 所有影响 world bounds 的 renderer revision aggregate；
- stable、non-jittered camera view-projection 的逐分量值；
- framebuffer width/height 或等价 aspect；
- scene visibility enabled/disabled；
- 影响 sort key 的 mesh/material/blend identity metadata revision。

不得只保存 32/64-bit hash 后相信无碰撞。允许 hash 快速拒绝，但 cache hit 前必须比较保存的完整关键值，
或使用不会遗漏 mutation 的单调 revision 组合。

### 7.2 Shadow cache key

shadow queue 独立保存：

- scene membership/bounds revision；
- directional light-space matrix 完整值；
- shadow enabled/disabled；
- caster membership/castShadows metadata revision；
- shadow sort metadata。

camera 移动可能改变方向光 shadow volume，因此如果 `DirectionalShadowMap.lightSpaceMatrix()` 以 camera
position 为输入，shadow key 必须包含最终 light-space matrix，不能只看 light identity。

### 7.3 失效与复用

- TAA phase/jitter 不使 forward queue 失效；
- resize/aspect 变化使 forward queue 失效；
- camera view/projection 参数变化只使 forward queue 失效；
- shadow light-space 变化只使 shadow queue 失效；
- bounds revision 变化使受影响的 forward/shadow cache 失效；
- material uniform value变化不影响 visibility，但可能影响 material binding cache；
- alpha 顺序仍由剩余可见对象的 insertion order决定；
- queue build 失败不替换上次成功 key，但当前帧必须失败，不能绘制旧 queue；
- diagnostics 必须区分 `reused` 与 `rebuilt`，不能把复用耗时伪装为完整 build。

第一版可以整条 queue 失效，不要求增量插入/删除或 dirty-object partial culling。

## 8. CommandBuffer Matrix Primitive Arena

### 8.1 当前问题

`setUniformMat4()` 当前通过 `new Matrix4f(value)` 建立稳定快照。语义正确，但 10,000 可见 draw 会制造
至少 10,000 个矩阵对象；shadow/geometry 同时录制时数量进一步增加。

### 8.2 正式方案

在 `CommandStream` 增加可复用 primitive matrix storage：

- 可以使用 `float[]`，也可以使用现有 `int[]` 保存 `Float.floatToRawIntBits`；
- 每个 mat4 命令顺序写入 16 个分量；
- command payload 保存 arena offset，不保存 mutable `Matrix4f`；
- executor 从 primitive arena 读取并调用现有 DSA uniform 路径；
- `reset()` 清计数但保留高水位容量；
- 扩容采用有界倍增并使用 `Math.multiplyExact`/明确容量检查；
- 录制时完成快照，源矩阵随后变化不影响执行；
- execute failure 后 reset/reuse 不读取旧 offset；
- 不能为 executor 每条命令重建 `Matrix4f`；
- 不改变 public `setUniformMat4()` / `trySetUniformMat4()` 签名。

### 8.3 不顺带扩大

- 不引入公共 raw uniform-location API；
- 不让应用直接借用 CommandStream arena；
- 不增加 `Runnable custom()` 路径；
- 不在本版本把所有 uniform 改为 UBO/SSBO；
- 不实现跨帧 secondary command buffer；
- 不缓存引用用户矩阵；
- 不用 native allocation 替代可复用 heap primitive arena，除非 profile 证明 heap copy 是瓶颈。

## 9. 重复 Binding 录制治理

### 9.1 先测量再改造

使用 JFR allocation profile、diagnostics command counts 和局部计时确认：

- 每 draw `uModel` snapshot；
- 每 draw `MaterialInstance.bind()`；
- 每 draw frame-global uniform/texture binding；
- shader uniform-location lookup；
- texture/sampler bind command；
- pending pipeline state flush；
- mesh bind与 draw opcode；
- diagnostics 或 collection iteration。

报告必须列出前十个 allocation site 和 bytes/frame。不能只凭代码观感做全局缓存。

### 9.2 允许的最小优化

若 profile 证明重复录制占比显著，RenderPipeline 可增加 pass-local binding cursor：

- shader identity 变化时录制一次 frame-global binding；
- `MaterialInstance` identity 变化时录制 material/override binding；
- mesh identity 变化时录制 mesh binding；
- front-face/mirrored 变化时仍录制对应 state；
- 每个 pass 开始、command buffer reset、失败恢复后 cursor 均为 invalid；
- shadow 与 geometry 不共享 live cursor；
- PBR binder、environment 和 shadow texture 的 shader相关 binding 必须纳入 shader cursor；
- mutable material 在帧开始前修改后，首次 bind 必须读取最新值；
- 不跨帧复用 material command payload，避免陈旧 texture/uniform；
- use-after-close 继续在正式资源边界 fail-fast。

若 identity 去重无法保证 mutable override 正确性，则优先只去重 frame-global shader binding，不强行缓存 material。

### 9.3 Material revision 可选门

只有 profile 证明 material override 重复录制仍是主要热点时，才允许为 `MaterialInstance` 增加内部 revision：

- 每次 uniform/texture override mutation 递增；
- clear 递增；
- cursor key 使用 identity + revision；
- 不改变 public setter 返回类型；
- 不公开 mutable map 或 live revision；
- 必须覆盖同一帧录制前 mutation 和相邻 renderer 共享 instance。

这不是里程碑 1 的前置条件，也不能为了“结构完整”提前加入。

## 11. 性能测量合同

### 11.1 测量矩阵

程序化与真实 glTF 两类场景都执行：

| 规模 | 布局 | visibility | static cache | queue cache | command arena |
| ---: | --- | --- | --- | --- | --- |
| 100 | all-visible | on/off | on/off | on/off | on/off |
| 1,000 | mixed | on/off | on/off | on/off | on/off |
| 10,000 | 10% visible | on/off | on/off | on/off | on/off |
| 10,000 | all-visible | on/off | on/off | on/off | on/off |
| 10,000 | all-hidden | on/off | on/off | on/off | on/off |
| 10,000 | camera-motion | on | on | expected miss | on |

不要求穷举所有 32 组合。正式报告至少保留：

1. v0.16 compatibility baseline；
2. 只开 static cache；
3. static + queue cache；
4. static + queue + primitive matrix arena；
5. 最终完整实现；
6. camera-motion 强制 queue rebuild 对照。

### 11.2 测量规则

- hidden window、VSync off、debug callback和分辨率一致；
- 1080p 与 4K；
- warmup 至少 100 帧，正式至少 1,000 帧；
- 每项至少五轮；
- A/B 顺序交替，报告 paired median difference；
- CPU 分离 SceneFrame、queue、command record、execute/present；
- GPU 分离 shadow、geometry、postprocess；
- 记录 current-thread allocation bytes/frame；
- 保存 JFR allocation profile 与环境信息；
- 记录 draw、shader/material/mesh changes、cache hit 和 visible ratio；
- 不调用 `glFinish`；
- GPU query 继续使用既有延迟读取协议；
- 性能结论以 CPU/GPU frame time 为主，不以短时 present FPS 单独下结论。

### 11.3 v0.17 发布目标

硬门槛：

- 现有动态 updater 每 renderer 每帧仍恰好一次；
- 明确静态 renderer 首帧 miss，后续无 mutation 帧 model/bounds cache hit 率为 100%；
- camera/light/resize/mutation 后对应 cache 在第一帧正确 miss并产生正确像素；
- 10,000 all-visible command matrix snapshot 不创建逐 draw `Matrix4f`；
- 10,000 all-visible 整帧 allocation 相对 v0.16 的约 `2.5 MiB/frame` 至少下降 75%，目标不高于
  `512 KiB/frame`；
- 10,000 / 10% visible 整帧 allocation 相对约 `252 KiB/frame` 至少下降 50%，目标不高于
  `128 KiB/frame`；
- 10,000 static/all-hidden、camera不变时 SceneFrame + queue median 目标不高于 `0.15 ms`；
- 100 all-visible compatibility path CPU median 回退不超过 5%；
- camera-motion 强制 rebuild 不得比 v0.16 同口径回退超过 5%；
- draw 数、最终像素、alpha顺序、shadow caster和 mirrored front-face 不回退；
- GL error、资源泄漏、线程悬挂和 use-after-close 为零。

分析目标，不作为可随意修改的硬门槛：

- 真实 glTF mixed 场景 command record 降低至少 20%；
- 静止相机 queue reuse 后 queue build 降至测量噪声附近；
- material/frame binding 命令数量与 identity change 数接近，而不是与 draw 数完全线性；
- allocation 降低后无明显 CPU copy 或 object-payload 扫描回退。

若硬门槛未达到，必须在发布报告写明原因、profile 证据和后续选择，不能只改文档目标数字。

| 事件 | model cache | bounds cache | forward queue | shadow queue | material cursor |
| --- | --- | --- | --- | --- | --- |

## 14. 故障与恢复合同

### 14.1 Model/bounds 失败

- 异常包含 renderer index和失败阶段；
- 不提交新的model revision；
- 不提交新的world bounds；
- 不发布当前SceneFrame；
- 下一帧从最后完整状态重试，但不能绘制旧frame冒充成功；
- 不关闭用户Mesh/Material。

### 14.2 Queue cache 失败

- cache hit前完成所有key一致性验证；
- rebuild中途失败时active counts清零；
- 上次成功queue可以留作内存复用，但当前帧禁止消费；
- forward失败不能让geometry绘制旧queue；
- shadow失败走既有RenderGraph failure与cleanup；
- diagnostics标记incomplete，不发布旧命中率。

### 14.3 Command arena 失败

- 扩容失败不留下可执行的半条mat4命令；
- opcode只在容量与16分量写入条件满足后正式发布，或reset能可靠丢弃半状态；
- executor异常后仍走既有prepared batch/fence cleanup；
- `reset()` 后旧object/primitive payload不可达；
- close资源责任不因primitive arena改变。

## 19. v0.18 GPU-Driven 决策门

### 19.1 进入 GPU culling + MDI 的必要条件

以下条件应同时成立，而不是满足任意一条：

1. v0.17静态/queue/command优化均已达标；
2. 目标硬件真实glTF场景中，CPU scene+command submission仍持续超过约`2 ms`；
3. 可见普通draw仍稳定在3,000以上，且不是人为all-visible极端case；
4. 至少70%的候选draw可共享兼容shader、vertex/index和material binding协议；
5. GPU不是由fragment、shadow fill、透明或postprocess主导；
6. allocation已收敛，瓶颈不是JVM对象创建；
7. OpenGL目标环境具备所需indirect/count/SSBO能力，并有明确fallback；
8. CPU生成indirect commands的过渡方案也能带来收益；
9. 能定义资源所有权、barrier、counter reset、failure recovery和diagnostics合同；
10. 有真实Demo和自动化GL验证预算。

进入后也应拆为独立版本：先CPU-built MDI，再GPU frustum，再Hi-Z；不要一次提交三套协议。

### 19.2 不进入 GPU-driven 的信号

出现任一主要信号时优先选择其他方向：

- 10k mixed真实场景CPU提交已低于约`1.5 ms`；
- 10%可见时draw约1,000且整体帧时间已满足目标；
- 材质/纹理碎片导致无法形成有效MDI批次；
- alpha/MASK/双面差异主导draw分组；
- GPU主要受fragment、shadow、PBR或4K带宽限制；
- camera-motion queue rebuild仍不是主要成本；
- bindless/texture array会先要求扩大材质公共协议；
- GPU-driven会迫使项目引入ECS/场景树/复杂资源表才能勉强成立。

若不进入，v0.18候选优先级为：

1. RenderGraph texture preview与调试可视化；
2. 明确的透明排序策略API；
3. 基于实测的阴影或材质绑定优化；
4. UI allocation剩余收敛；
5. 真实需求驱动的局部场景层级，而不是通用ECS。

## 20. 最终原则

v0.17 的成功不是让 benchmark 数字看起来更现代，也不是提前铺设一套未被使用的 GPU-driven 抽象。
它应当让项目回答四个具体问题：真实资产下对象、材质和 draw 如何分布；静态对象每帧究竟还做了多少无用工作；
逐 draw command/uniform 快照制造了多少 JVM 成本；完成这些 CPU 收敛后，GPU culling + MDI 是否仍有足够收益。

只有这四个问题都有可复现证据，项目才应该继续扩大渲染协议。否则保持当前 OpenGL 单后端、普通 renderer
加显式 instancing 的结构，反而是更强壮、更容易维护的选择。
