## 4. 测试价值规则

### 4.1 按合同测试，不按类配对

- 不要求每个生产类都有一个同名测试类，也不以覆盖率百分比作为新增测试的充分理由。
- 测试应验证用户可见行为、跨模块合同、数学性质、资源所有权、失败恢复、兼容边界或已修复缺陷。
- 多个实现类共同满足一个合同，可以由一个领域测试覆盖；一个高风险合同也可以需要多个不同层级的测试。
- 构造器默认值、简单 getter/setter、无分支委托等无需独立测试，除非它们属于公开兼容合同或曾造成实际缺陷。
- 测试断言应验证结果或不变量，不以复制实现逻辑的断言冒充独立 oracle。

### 4.2 测试分层

| 层 | 适用内容 | 约束 |
|---|---|---|
| JVM 逻辑 | 数学、策略、状态机、解析、纯数据合同 | 不启动桌面或 GL；优先快速、确定、局部诊断 |
| GL/消费者 | shader 编译和像素行为、真实 framebuffer、资源生命周期、跨 Pass/模块集成 | 仅对需要真实 GL 的合同使用；GL context、readback 和严格日志明确启用 |
| 场景/视觉 | 端到端构图、时域事件、宿主集成和人工视觉 | 只覆盖需要场景上下文的风险；不以截图代替数值或资源合同 |
| 扩展压力 | soak、容量矩阵、多硬件、正式性能 | 按明确触发条件单独运行；不得挂在每轮局部开发默认入口上 |

相同断言不得无理由地同时复制在普通 `test`、`glSmoke`、多个 `local*Verification` 聚合任务和 release 任务中。聚合入口应复用唯一 case 清单或叶子任务，并报告真正执行的 case ID。

### 4.3 新增测试的最低说明

每个新测试或一组参数化用例至少能回答（放在变更说明或已有合同条目中即可，不要求每个方法单独写文档）：

1. 防止哪种具体回归，属于哪个稳定合同？
2. 为什么现有更高层或更便宜的测试不能充分证明它？
3. 失败时提供什么可诊断信息？

若答案只是“这个类新增了，所以给它配一个测试”，应先寻找现有领域合同测试的扩展点；只有形成独立行为边界时才新建测试类。

## 5. 测试精简流程

先盘点，再合并，最后删除。按领域合同或用例组标为 `KEEP`、`MERGE`、`RETIRE` 或 `REWRITE`，注明合同、执行入口、已有运行成本、可用历史结果和替代证据。无需为凑齐盘点数据预跑两遍全部测试。

- `MERGE`：把重复断言并入更强的领域合同测试，保留不同故障模式、消费者或 oracle。
- `RETIRE`：只用于合同已删除、被新生产路径取代或无独立断言价值的用例；记录被移除的 case 和替代证据。
- `REWRITE`：用于不确定、依赖隐式全局状态、环境假设不明、偶发超时或失败报告无法定位的用例。
- 不因测试失败、运行慢或暂时难修而静默删除；若用例确实不稳定，先分类根因和决定其正确状态。

0.27.5 的目标是整理一份领域合同清单和首批重复/过时用例审计，不预先承诺把 261 个文件压到某个数字。是否删除具体用例以合同覆盖不退化、替代验证实际执行为准。2026-11-09 首批已用 `MERGE` 把 6 个同域单 case 类并入 3 个领域测试（断言全保留，测试类 252→247，case 总数仍 1150），未做 `RETIRE`。

第一批审计有三个明确切入点：

- 无过滤的 `glSmoke` 当前会运行开启 GL 后的完整测试集，包含 JVM 用例；与 `test` 叠加时会重复执行。建立明确的 GL 叶子选择，保留旧入口兼容或显式列为扩展，避免静默改变历史命令含义。
- `check` 同时依赖完整 `test` 和筛选同一测试集合的 API、架构、scene 等任务。盘点实际重复 case，聚合执行去重，同时保留单独调用各 guard 的能力。
- 设置类的简单默认值断言可并入领域策略用例，但范围拒绝、NaN/Inf、防御性拷贝和独立数值公式仍有价值。例如 `VolumetricSettingsTest` 已同时覆盖多个配置类的快照和输入合同，不能因文件名像单类测试就删除；`GtaoPassesTest` 的相位序列也不能被 shader 成功编译替代。

对读取源码后匹配字符串、私有字段名或精确 helper 调用顺序的测试，审查它究竟在检查架构承诺还是偶然实现形状；只约束实现形状的部分优先改为行为、编译或类型边界检查。架构依赖和公开 API 合同检查继续保留。

## 6. 失败、超时与重试

- 默认自动重试为零。正确性失败保留 FAIL；环境不满足记 INVALID；必需测试没跑、过滤为空或被跳过记 INCOMPLETE/NOT_RUN；超时记 TIMEOUT。任何一种都不能变成 PASS。
- 测试失败后先保留候选身份、case ID、JUnit XML、stdout/stderr、GL 日志和耗时，再判断是产品缺陷、测试缺陷还是环境问题。
- 只有确认是可恢复的启动/环境问题时，才允许一次定向复跑；相同失败再次出现就停止重试并记录诊断，不循环扩大到全量套件。
- 给单个测试和整个入口设置有限超时。超时需杀掉本次启动的 Gradle/JVM 进程树，不杀其他 IDE/任务的共享进程；结束前仍需写出 TIMEOUT 报告。
- GL 测试默认单 fork/串行，避免共享窗口、context 和原生资源制造并发干扰；与 GL 无关的 JVM 测试不应继承该限制。
- 不使用任意 sleep 掩盖竞态；同步等待要有明确事件、期限和超时诊断。
- 保持正确性、环境有效性和性能预算三类结果分开：不可比的旧硬件性能阈值不能拖住普通功能开发；真实像素错误、资源泄漏、事务错误不能通过降低阈值、扩大日志白名单或替换参考图变绿。

## 7. 默认验证入口

保留现有分层意图，并在 0.27.5 中去重命令、确认入口和实际执行集合一致：

| 入口 | 默认范围 | 何时运行 |
|---|---|---|
| 快速检查 | 格式/编译/相关 JVM/必需架构与 API guard | 局部开发；不自动创建 GL context |
| 定向验收 | 受影响领域的 JVM + 必要 GL/消费者 + 一个必要场景 | 功能完成、渲染路径或资源合同变更 |
| 扩展验收 | 长测、正式性能、质量/容量矩阵、多硬件 | 明确触发或封版申请时运行 |

现有 `verify.ps1` 默认 300 秒、零自动重试；0.27.4 当前候选的直接 Gradle 聚焦验收加 `--rerun-tasks` 实测约 74 秒，这不是限时脚本自身的耗时证明。0.27.5 应保留限时约束并验证超时/失败报告，不在没有耗时数据的前提下再拍一个更紧预算。默认使用增量构建，只有明确需要时才重跑选定任务；正式命令以整理后的 `docs/guides/testing.md` 为准。

先让一个版本化合同清单驱动选择与结果核对，再考虑自动按 diff 选测。清单以领域合同为单位，只有必须精确覆盖的缺陷才登记到方法，避免维护一份重复全部 JUnit 方法的手工数据库。资源、shader include 或共享 surface 变化要覆盖直接消费者；无法判断时扩大到相关共享边界，不能静默视为无影响。自动证据缓存留到输入映射可信后再启用。

## 8. 未来实时渲染技术提案卡

在新增一项技术前，先补一张简短技术卡，避免实现和测试范围到中途才出现：

| 字段 | 内容 |
|---|---|
| 技术与承诺 | 解决的问题、适用范围、明确不支持的情况 |
| 输入/输出 | 数据格式、色彩空间、深度/法线/运动向量约定、分辨率和时间语义 |
| 集成边界 | 所属模块、消费者、Pass 顺序、共享 surface 及 API 可见性 |
| 生命周期 | GPU owner、创建/销毁、resize、发布前失败回滚、发布后退役异常保留已发布状态、历史失效与宿主借用 |
| 正确性 oracle | 独立解析/参考、数学不变量、最小真实消费者和必要像素事件 |
| 成本门槛 | 代表硬件/分辨率、GPU/CPU/显存预算；未申请正式预算时明确 NOT_EVALUATED |
| 验证计划 | 必需 case ID、分层入口、超时、何种变更触发扩展矩阵 |
| 回退 | 质量降级、功能关闭和资源回收的明确行为 |

验证顺序为独立 oracle 或纯逻辑合同、最小生产消费者、必要的真实 GL/场景、按承诺执行性能与质量矩阵。一个技术卡可以由少量高信息量测试覆盖，不按实现类数量推导测试数量。

在现有能力矩阵中维护技术间的输入依赖、互斥条件和成熟度（实验、已集成、已验收），沿用 0.27.4 的控制入口和模块 owner。组合验证按真实交互选择代表对：共享深度、时域、HDR、透明、宿主借用等高风险关系必测；其余可使用成对组合，不枚举 40 多个功能的全部开关排列。原型先进入最小 Demo，证据成立后再接正式管线；本版本不为未来全部技术预造通用调度框架。

以下为 0.27.5 的设计要求。首批已修改 `check` 依赖、新增 `glLeafVerification` 并修复限时报告；Gradle 脚本全面拆分、测试与 Demo 依赖拆分仍待实施。优先收敛当前已经出现的维护问题；不把每条文字规则都转成新增测试或新的审批步骤。

### 10.1 Gradle 职责与任务准入

当前根 `build.gradle` 326 行，`gradle/release-verification.gradle` 1,335 行，`gradle/demo-tasks.gradle` 1,258 行（含空行）。长度仅作定位线索：发布脚本混有任务装配、资源清单解析、GL 日志规则、性能统计、证据汇总和合同断言，比根文件本身更需要按职责收敛。

- 根 `build.gradle` 保留插件、工具链、依赖与 source set 装配、标准产物和各职责脚本入口。功能特定场景、性能矩阵、长段结果分析不再直接追加到根文件。2026-11-09 已把无桌面门禁迁到 `gradle/verification-tasks.gradle`（根文件 324→181 行），并把 GL 策略解析迁到 `gradle/gl-policy.gradle`（发布脚本 1335→1205 行）；其余结果解析与任务装配的分离仍待后续。
- 按稳定职责组织脚本。相同 Test/JavaExec 任务的公共配置只维护一份，场景差异用数据描述；不要每增加一项技术就复制一整套 build、test、soak、benchmark、release 任务。是否引入 convention plugin 以真实重复为依据，不为拆文件而新造构建框架。
- 新任务先说明与既有入口的区别、输入输出、运行成本、是否需要 GPU、是否允许进入默认构建。只有新的执行语义才创建新任务；新增场景/质量档优先作为受校验参数或场景登记。
- 编译、打包、普通 `check` 不隐式启动真实 GL、性能矩阵或长测；完整无桌面 `check` 可以比日常定向检查更广。现有显式 GL 选项保留明确语义，不以名称为“quick”就宣称它是最小测试集。
- Gradle 配置阶段保持无副作用：不启动 GPU、运行 benchmark、改源码、执行 Git 提交或下载场景资产。依赖解析由 Gradle 按正常任务需求完成；必要的 Git 身份采集放在显式执行任务中。
- 生成任务声明实际输入与输出，生成物进入 `build/generated`。增量依赖涵盖所读 helper、shader include、模板及生成参数；不要用全局 `clean`、关闭全部缓存或常规 `--rerun-tasks` 弥补漏声明。当前 focused 证据强制新运行有明确原因，输入复用合同完成前不直接删掉该保障。
- 任务顺序和任务依赖分别表达：`mustRunAfter` 不能充当 `dependsOn`。报告读取者不能为了找日志而自动触发所有历史生产任务；失败仍归档，必需项未执行仍不通过。
- 历史版本入口需要兼容时保留薄别名或明确弃用说明，不保留多份独立实现。旧入口替换前比对实际执行 case 与报告语义。

### 10.2 构建依赖与产物边界

`testImplementation sourceSets.demo.output` 使测试编译依赖 Demo 输出，Demo 又接入程序化 shader 生成。先盘点哪些测试确实需要 Demo：共用 fixture、独立算法 reference 与实际场景消费者可以有依赖，普通纯 JVM 合同不应无理由依赖整套 Demo。仅在盘点证明收益时拆分 test fixtures 或相关 source set，不把所有参考代码迁入生产包。2026-11-09 尝试把显式 import 的 clustered／stress fixture 拆到 `demoFixtures`，因 `src/test/java/.../demo` 同包测试仍直接使用其余 Demo 类型而编译失败，已完整回退；在测试目录重组或独立 fixture 消费者出现前不拆。

依赖使用固定版本，保持 wrapper、JDK、LWJGL/BOM 和 `gradle.lockfile` 一致；不使用动态版本，不把 test/demo 库放进生产运行依赖。升级依赖必须说明用途、包体/原生平台影响和许可证，并更新受影响的 lock/guard；已有 `dependencyLockGuard` 硬编码部分坐标，若集中版本来源，需要同步迁移这个检查，避免建立两份版本真相。

版本号保留一个构建事实来源，生成的 `haikalat-build.properties` 从它派生。产物校验应覆盖实际 JAR 的版本、资源和 runtime classpath，隔离 JAR 验证不能被 main classes 目录兜底。新技术默认不自动升级所有依赖或引入多模块构建。
