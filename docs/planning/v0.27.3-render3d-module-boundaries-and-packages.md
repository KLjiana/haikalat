# 0.27.3 Render3D 模块边界收敛与包结构重组

> 计划日期：2026-11-09。状态：待实施。
>
> 使 Render3D 内部各功能模块符合 Subsystems 的依赖、生命周期、资源所有权和渲染装配约束；在迁移职责的同时调整包结构，使代码目录、功能边界与实际所有权一致。
>
> 本版本是整体迁移，不再逐个效果建立独立试点版本。内部按批次实施和验证，最终联合签收。本文不代表实现、版本号升级或发布完成。

## 1. 目标与完成边界

0.27.0 的体积雾、0.27.1 的 GTAO 和 0.27.2 的共享表面已经验证了候选准备、帧边界发布、借用与转交、失败恢复和历史隔离。0.27.3 将这些已有规则应用到现有 Render3D 功能，并补齐包级依赖约束。

```text
0.27.3
├── 必须完成
│   ├── 全部现有 Render3D 生产类型的职责、所有权和包归属清单
│   ├── 后处理整体边界：Bloom／曝光／色调映射／TAA／FXAA／解析雾
│   ├── 光照边界：帧灯表／Clustered／上传与绑定／诊断
│   ├── 阴影边界：方向光／点光／聚光／调度与缓存／采样输入
│   ├── 场景快照、几何、环境、AO、体积雾及现有扩展的实现归位
│   ├── RenderPipeline／PipelineGeneration 的编排职责收敛
│   ├── render3d 与 postprocess 单向协作、Java 可见性与 API 兼容
│   └── 实际生产入口、组合画面、失败和资源生命周期联合验收
├── 继续复用
│   ├── Backend／Core／RenderGraph／命令提交与资源管理
│   ├── 0.27.0～0.27.2 的具体 owner、共享输入和退役机制
│   └── 既有算法、Shader 语义、材质行为和实验功能等级
└── 范围外
    ├── UI、文字、动画、资源加载子系统的内部重写
    ├── 通用插件发现、FeatureModule 平台或第二套生命周期调度器
    ├── 新渲染算法、全新编辑器、全面 UI 特效扩展
    ├── Minecraft 地形／光照统一视觉整合
    └── 正式性能达标、全硬件矩阵及正式发布
```

完成标准是实际变化隔离：修改模块内部策略通常只改所属实现与必要装配，不再同时维护中心类中的第二套配置、分配或 producer 判断。只搬文件、缩短中心类或新增转发接口均不足以签收。

## 2. 基线与当前问题

基线使用 [0.27.2 独立验收](../releases/v0.27.2-independent-review-2026-11-09.md) 对应的完整工作区：HEAD `4719d1848875a9ee6d63533d63aeb9f7abd07cb5`，源文件清单指纹 `fb5aa256b743bbac29d73b8bd706611556d3429fc6beea08179cc521c67b769e`，包含未提交修正。M0 开工时重新核对身份，不能仅恢复 HEAD 作为等价基线。

当前主要切口：

- `RenderPipeline` 仍连接资源构造、功能装配、参数更新和多类执行细节；`PipelineGeneration` 的复用策略仍受 `sameNonModuleStructure` 的大范围匹配限制。
- `PostProcessPassBuilder` 同时持有 TAA、Bloom、曝光、色调映射、解析雾及相应状态，难以对单个效果实施局部替换。
- `postprocess` 引用 `render3d.ScreenQuad` 和 `TaaResolveInputs`，而 Render3D 又依赖后处理，形成包级双向依赖。
- 共享表面、GTAO、体积雾已有具体合同；其余功能不能仅靠共享一个包获得同等生命周期保障。
- 当前稳定公开类型很多；Java 子包不继承父包的 package-private 可见性，目录调整必须与 API 兼容及跨包合同一起设计。

保留并行工作，不重置、不清理、不自动提交或发布。旧墙面条纹与性能欠账继续单列。算法修复若确实必要，应独立记录原因、差异与正确基线，不混入机械迁移掩盖变化。

适用约束：[抽象密度控制](../architecture/abstraction-density.md)、[公共 API 分类](../architecture/public-api/README.md)、[渲染边界](../architecture/render-boundaries.md)、[共享表面合同](../architecture/v0.27.2-shared-scene-surface-contract.md)、[有侧重验收规范](../guides/focused-acceptance-policy.md)。

## 3. Subsystems 模块约束

下列规则是本版本交付合同，不以是否实现统一接口作为合格依据。

| 编号 | 约束 | 可检查结果 |
|---|---|---|
| C01 | 保持既有纵向依赖；Core／Backend／Runtime 不因迁移反向依赖具体功能 | 原架构门禁继续通过；不把领域状态下沉 Core 逃避检查 |
| C02 | 功能模块不反向访问 Pipeline／Generation 内部状态 | 跨模块取得明确的输入值、帧合同或窄绑定能力；无全局 service locator |
| C03 | 每个 GPU 资源只有一个 owner；借用者不能销毁 | 所有权表覆盖创建、借用、转交、resize、退役和关闭 |
| C04 | Graph 拥有其创建的附件，模块拥有程序及私有持久资源 | 模块贡献 Pass 声明，不能重复创建或释放同一 Graph 附件 |
| C05 | 纯 CPU 准备与 GPU 操作线程明确 | GL 分配、提交、销毁在正确线程／Context；复用现有队列，不新增无必要常驻线程 |
| C06 | 候选私有、帧边界提交、失败可解释 | 发布前失败保留旧状态；部分 GPU 写入不冒充像素回滚；退役失败保留可重试 owner |
| C07 | 标量、内容失效、资源规格和 Pass 拓扑分别处理 | 标量不重建资源；拓扑变化只替换依赖闭包中的必要资源 |
| C08 | 存储复用与历史有效性分别判断 | 调色或光照变化可以失效 TAA 内容，但不据此销毁其兼容存储；失效有原因 |
| C09 | 关闭功能不执行专属 Pass，不无故保留专属资源 | 共用输入按实际消费者保留；缓存若保留须写 owner、上限与清理条件 |
| C10 | 跨包可见性最小化，稳定 API 有兼容策略 | 不公开字段、不返回可变 owner 集合、不使用反射穿透；所有新增 public 类型分类 |
| C11 | 诊断属于实际生产过程 | 区分当前、复用与过期数据；关闭／失败不伪报新 GPU 测量 |
| C12 | 组合行为有端到端证据 | 通过实际配置入口运行 Graph、GPU 写读及资源事务，不以 DTO／模型测试替代 |

模块对另一模块的依赖不必全部消失；依赖应指向其公开输入合同，而不是具体资源容器或任意内部字段。无可选意义的基础设施无需添加假开关；零灯光不等于禁用所有光照，也不等于必须销毁所有共用缓冲。

## 4. 目标包结构与依赖方向

保留 `render3d` 作为三维渲染领域名称。根包保留稳定入口／兼容类型；实现按职责进入子包。M0 对每个类型确定最终归属，以下职责必须覆盖，允许根据真实依赖合并相邻小包，不得建立空目录或空壳模块。

```text
subsystems
├── render3d
│   ├── 根包兼容入口   RenderPipeline、Scene、Camera、现有配置／诊断等
│   ├── pipeline       装配、候选代、发布、帧级协调
│   ├── scene          渲染帧快照、可见性、队列与 revision
│   ├── geometry       普通／实例绘制、变形与材质绑定协作
│   ├── surface        共享深度／法线／运动／reactive 合同与生产
│   ├── lighting       灯表、Clustered、光照输入与诊断
│   ├── shadow         调度、图集、缓存、caster 与采样合同
│   ├── environment    天空、IBL、室外环境装配
│   ├── ao             GTAO、专用深度兼容路径、私有历史
│   ├── volumetric     体积雾、资源、历史及只读输出合同
│   └── 现有扩展包     VFX GPU 适配、debug、实验功能等逐项归位
├── postprocess
│   ├── 输入／输出合同与颜色链装配
│   ├── bloom／exposure／tonemapping
│   ├── temporal／fxaa／fog
│   └── 局部实现与公共绘制辅助（具体拆分由调用关系决定）
└── scene              保持现有场景资产、加载与热重载职责
```

顶层 `scene` 与 `render3d.scene` 在文档明确分别表示资产装配和渲染帧组织。本版本不强制将顶层 `scene` 更名为 `sceneassets`，避免无必要扩大外部迁移面。

依赖安排：

- `pipeline` 组合各功能，消费者不得反向引用 pipeline 实现。
- `surface` 提供通道事实；AO、体积雾及后处理消费输入，surface 不依赖这些效果的实现类。
- 光照帧数据与阴影采样合同分别有确定归属；Forward 和体积雾借用。调度器若需要光源数据，应接收快照，避免 lighting/shadow 实现互相持有。
- `postprocess` 最终不导入 `render3d` 类型。Render3D 装配方把表面／颜色输入适配为 postprocess 所有的合同；适配保留实际 producer、帧有效期和失败验证，不能退回到任意裸纹理 ID。
- `ScreenQuad` 等辅助类型先确定真实调用者：可由后处理提供分类明确的共享能力；只有确属通用 Core 职责且有多个真实消费者时才下沉。禁止新建无边界的 `common` 包收容循环依赖。
- 叶子实现可以依赖根包中保留的稳定值类型，但不得依赖 `RenderPipeline` 等兼容入口。门禁按类型职责区分，不能把整个根包放进无条件白名单。

### Java 可见性与兼容

优先保持稳定 FQCN、构造器和方法签名。稳定入口可以委托新实现，配置值类型可保留原位置，不为目录整齐强迫全部改名。兼容层只桥接调用，不保留另一份状态和算法。

现有 `TaaResolveInputs` 等公开类型迁移前核对 API 分类；必要时保留旧签名并转换到新合同，逐项写明源码／二进制兼容结果。`advanced` 变动更新迁移记录，`internal` 按实际用途重归类。不得把既有 stable 简单降级为 internal 绕过兼容要求。

跨子包必须 public 的实现入口应窄化、标为 internal，并限制允许的生产调用者。现有门禁不足以表达新边界时扩展检查，覆盖 import、静态导入与全限定类型使用；不是扩大旧白名单。更新清单和测试包后，测试仍要调用真实装配入口。

## 5. 职责迁移清单

以下类型位于现有 Render3D 根包，完整清单由 M0 补齐，包含子包与实验功能，不能把未列出的类默认为已完成。

| 领域 | 当前主要入口 | 必须迁移／保留的职责 |
|---|---|---|
| 管线与代次 | `RenderPipeline`、`PipelineGeneration`、`PipelineTopology`、`PipelineFeaturePolicy` | 保留公共配置、全帧顺序、组合验证和原子发布；构造、参数分类及私有实现移至所属模块；按资源兼容性替代大范围全有或全无复用 |
| 后处理 | `PostProcessPassBuilder`、`TaaHistory`、`TemporalFrameState`、`TaaResolveInputs`；postprocess 下各 Pass | 分离颜色链编排与效果 owner；TAA 特有历史进入 temporal，场景运动记录仍由场景／几何边界负责，不整体搬错 |
| 光照 | `FrameLightTable`、`ClusteredLightingBinder/Resources/PassBuilder`、`LightTablePacker`、`ClusterGrid/Math` | 模块管理帧数据准备、存储、assignment 与绑定；消费者不自行拼布局；保留缓存键、零灯光和诊断来源帧语义 |
| 阴影 | `ShadowFramePlan/Binder`、`ShadowLightScheduler`、`ShadowCasterPlanner`、`ShadowCacheState`、各 Atlas／Map | 模块归集调度、caster、程序与采样规则；Graph 仍持有附件；保持图集槽位、更新预算、缓存失效和实例批次复用 |
| 场景／几何 | `SceneFrameBuilder`、`SceneFrame`、队列／bounds、`InstancedRenderer`、`SceneDeformationDefaults`、draw binding | 每帧一致快照与共享实例准备；保留 OPAQUE/MASK/ALPHA/ADDITIVE、镜像／双面、skin/morph 与 previous 数据规则 |
| 表面／AO／雾 | `SceneSurface*`、`SceneReactivePass`、`Gtao*`、`Volumetric*` | 按已验收 owner 和输入边界搬迁；保持 raw/resolved、reactive 晚期生产、跨帧失效及候选私有回调 |
| 环境与材质连接 | `StylizedSkyRenderer`、室外配置、现有 IBL／PBR 相关实现 | 环境资源和更新归环境；材质消费光照／阴影／AO 合同；全局组合仍在装配层 |
| 扩展与诊断 | 现有 VFX GPU 适配、debug／预览及实验入口 | 与所属领域一起整理，保留扩展点、证据等级与兼容性；不把实验功能升级为 stable 承诺 |

### 中心对象允许保留什么

`RenderPipeline` 可以知道有哪些模块、哪些组合合法、整帧何时提交。`PipelineGeneration` 可以持有各 owner 及转交记录。它们不应直接掌握 Bloom 层级创建、Clustered 存储布局、阴影逐灯更新细节或各效果 shader 参数打包。

不以行数削减百分比验收。最终提交一份“移出职责／保留职责／实际调用链”对照，并用后处理、光照、阴影各一个真实配置变化证明修改影响范围收敛。

## 6. 生命周期与变化分类

| 变化 | 预期行为 |
|---|---|
| Bloom 强度、手动曝光等连续标量 | 参数更新；不重建图或 GPU owner；内容历史是否失效按具体语义判断 |
| Bloom 开关／层数、自动曝光模式、AA／HDR 规格 | 模块声明必要 Pass／存储变化；事务发布，保留兼容的无关资源 |
| 光源颜色／位置／数量等 | 遵守现有 Scene 配置能力；失效必要灯表／cluster／shadow 内容，不因打包变化无条件重建整管线 |
| 阴影开关、容量、分辨率、级联规格 | 按受影响图集、程序和缓存准备候选；无关效果 owner 保留；非法组合在发布前失败 |
| resize／切世界／热重载 | 复用原入口及代次合同，按依赖失效历史，旧帧输入不能复活 |
| 停用／关闭 | 专属 Pass 移出，借用关系撤销；释放或按显式策略缓存；共享资源最后消费者退出后才回收 |

M0 为这些变化列出“现有公开入口、现有能力限制、最小必要 API 调整”。主要入口包括 `applyVisualSettings`、`applyGtao`、`applyVolumetricFog`、`applyOutdoorEnvironment`、`Scene.setLight`、场景替换与 resize。不得绕过现有 `Scene.setLight` 的类型／阴影拓扑限制；需要新增安全的配置入口时，沿用同一候选事务，不能让调用方直接改内部 owner。

旧代、活动代和候选的峰值一起计数，共享附件只计一次。预算校验先于分配；估算不能冒充驱动显存实测。迁移不引入全局 `glFinish` 或任意线程 GL 操作。

## 7. 实施批次

所有批次属于同一个 0.27.3。完成一批后继续下一批，不要求逐模块重新立版本或重复请求确认；出现真实新合同或阻断失败时再做局部调查。

| 批次 | 工作 | 退出条件 |
|---|---|---|
| M0 冻结与映射 | 保存完整候选、类型归属／调用者／owner／API 表；冻结代表场景与依赖图；列选测清单 | 每个现有类型有目标或兼容保留理由；新边界无未解释循环；稳定入口迁移可审查 |
| M1 后处理整体迁移 | 效果 owner 与颜色链分离；raw/single/reactive 适配；解除 postprocess 反向依赖；同步拆包 | Bloom、曝光、TAA、FXAA、色调映射、解析雾均归位；单效果变化不重建无关 owner |
| M2 光照与阴影迁移 | 先固定帧灯表／采样合同，再迁移 light/cluster 与 shadow 调度、资源和绑定 | Forward、体积雾两个真实消费者通过；缓存、图集与失败提交行为保持 |
| M3 其余实现归位与中心收口 | 场景、几何、表面、AO、雾、环境、扩展迁移；清除临时桥接与重复决策 | 全类型清单闭合；根包只保留合理入口／兼容值；中心不再控制模块内部布局 |
| M4 联合验证与文档 | 更新 API 清单、门禁、依赖图、合同与迁移指南；验证打包及真实消费者 | 下列验收矩阵有证据；新鲜与复用明确；失败与未测项如实记录 |

每批使用可审查的小步变更，职责迁移与对应包移动一起完成；不先把全仓库改到无法编译再恢复。只在有明确重复和真实消费者时提炼公共机制，不为了统一命名新增薄包装层。

## 9. 执行预算与证据复用

- 按[有侧重验收规范](../guides/focused-acceptance-policy.md)执行，各批只跑受影响叶子任务与直接邻接用例，不反复跑全域门禁和性能矩阵。
- 普通功能签收默认总执行预算 5 分钟，包含启动与依赖等待。最终签收消费仍有效的各批证据，再补必要联合用例；不能通过连续拆成多个“5 分钟”调用规避本轮上限。超时记录已完成／未完成项，不能以预算不足跳过必需合同后宣称通过。
- 复用记录原候选、输入／Shader／环境身份和适用原因。包移动若影响资源定位、反射、构建或加载路径，对应旧证据失效；不能只凭算法文本未变复用。
- 新鲜 embedded GL 为必需。宿主协议未变时可复用旧 Minecraft 协议证据；借用／复制或宿主入口改变时补对应真实客户端操作。没有实际世界输入，不宣称 Minecraft 统一视觉已完成。
- 本版本不承诺 FPS 或驱动显存改善。未测性能继续 `NOT_EVALUATED`；资源账目只用于生命周期与按需分配结论。旧性能失败不自动关闭。
- 封版核对新增／迁移 API 的兼容调用、产物身份和相关 Shader 打包；源码测试与 JAR 隔离运行分别记录，不把旧 XML、跳过或 UP-TO-DATE 计为新鲜通过。
