# v0.14 项目收口、API 收缩与工程合同加固计划

> 状态：已完成并发布（`0.14.0`，2026-07-19）
> 目标版本：`0.14.0`
> 基线版本：`0.13.0`
> 版本主题：停止横向扩功能，通过删除、降级、内聚和自动化门禁，把现有 OpenGL 框架收紧为可长期维护的稳定基线

## 1. 执行摘要

v0.13 已完成静态 glTF、metallic-roughness PBR、GPU IBL、HDR 后处理、自动曝光、
retained-mode UI、异步上传、RenderGraph 和多条确定性 Demo 链路。项目当前缺少的不是另一项大型
渲染能力，而是对已经形成的公共合同、依赖范围、内部职责和发布流程做一次系统收口。

v0.14 不增加新的画面功能。它要解决以下问题：

- public 类型随着版本持续增长，但 stable、advanced、internal 的含义尚未全项目统一；
- glTF、场景配置、CommandBuffer 等热点类同时承担多个可独立验证的职责；
- Assimp 仍作为无 Demo、无端到端验证的实验入口存在，并带来额外 native 依赖；
- GPU owner 的失败清理、重复关闭、borrowed/owned 关系虽大多正确，但实现方式分散；
- Gradle 中存在多套局部验证入口，尚缺一个明确、可审计的正式发布门禁；
- 历史实施计划、当前事实、未来待办仍有交叉，工程师不容易判断哪份文档是事实来源；
- 当前仍是单模块 OpenGL 框架，继续增加抽象或拆 Gradle 多模块不会自动改善上述问题。

本版本以“可删除、可降级、可验证”为优先级：先缩小承诺面，再拆内部职责，最后统一发布证明。

## 2. 目标与非目标

### 2.1 必须达成的目标

1. 建立覆盖整个 main source set 的 public API 分类和变更守卫。
2. 删除没有纵向证明且会扩大 native/维护成本的实验能力。
3. 在不改变外部行为的前提下拆分高变更热点，降低单文件认知和测试成本。
4. 统一 GPU 资源 owner 的生命周期合同和失败清理方式。
5. 建立唯一的无桌面验证入口和唯一的本机完整发布验证入口。
6. 收敛文档事实来源，使能力状态、发布记录和未来规划不再互相覆盖。
7. 保持 v0.13 已承诺的 OBJ、glTF、PBR、UI、异步和 RenderGraph 行为不回退。

### 2.2 明确非目标

- 不增加 Vulkan、WebGPU 或第二渲染后端；
- 不拆 Gradle 多模块；
- 不增加 ECS、场景编辑器、shader graph 或资源数据库；
- 不增加 glTF animation、skin、morph、Draco、meshopt、KTX2 或高级材质扩展；
- 不实现 bindless texture、GPU culling、MDI 或 clustered lighting；
- 不为了减少行数机械拆分所有大类；
- 不把内部通用 helper 设计成新的公共框架；
- 不承诺二进制兼容尚未明确标为 stable 的类型；
- 不借本次收口改变画面、资产坐标、色彩空间或现有 Demo 视觉合同。

## 3. 当前架构判断

当前单后端架构足以继续承载中等复杂度 OpenGL 渲染功能：

```text
application / demo
        |
        v
subsystems (windowing, render3d, postprocess, ui)
        |
        v
core (command, graph, material, mesh, assets, runtime contracts)
        |
        v
backend (OpenGL resources, state cache, framebuffer, shader, texture)
```

本次不重新定义这张分层图。需要加固的是跨层允许集合和公共入口，而不是引入更多层级。

### 3.1 已接受的架构事实

- 项目是 OpenGL 4.6 专用框架，不假装已经后端无关；
- `backend ↔ core` 的少量 seam 由架构测试锁定，不以消灭所有双向引用为目标；
- `RenderGraph`、`CommandBuffer` 和 `RenderPipeline` 是核心纵向路径，不能通过新增旁路规避；
- Demo 是能力证明和集成测试入口，不是第二套生产框架；
- UI 是 subsystem，不进入 core；
- glTF CPU decode 位于 core assets，GPU upload/scene 实例化位于 render3d subsystem；
- main source set 不依赖 demo/test，demo 可以依赖 main，test 可以依赖两者输出。

### 3.2 v0.14 要收紧的边界

- `backend` 禁止依赖 `runtime`、`subsystems`、`demo`；
- `core` 禁止依赖 `subsystems`、`demo`；
- `runtime` 禁止依赖具体 Demo；
- `subsystems.ui` 禁止反向进入 core 的渲染协议；
- `core.assets.gltf` 禁止调用 OpenGL 或依赖 render3d runtime；
- `subsystems.render3d.gltf` 只通过公开 CPU asset contract 消费 glTF 数据；
- production code 中不得新增未经 allowlist 允许的 `custom()` 或裸 OpenGL escape hatch；
- stable public API 不得暴露 LWJGL、Jackson、JNA、Assimp 的具体类型。

## 4. 公共 API 收缩

### 4.1 分类定义

所有 public 顶层类型必须归入以下一类：

| 分类 | 含义 | 兼容要求 | 允许使用者 |
| --- | --- | --- | --- |
| `stable` | 推荐应用代码直接依赖的正式入口 | 删除或破坏性修改必须经过版本决策和迁移说明 | application、demo、其他 stable API |
| `advanced` | 面向诊断、扩展和高级控制的低层入口 | 可在次版本调整，但必须更新 changelog 和 allowlist | application、demo、测试 |
| `internal` | 因 Java 包结构或测试需求暂时 public，不构成兼容承诺 | 可随实现重构；生产调用范围必须受架构测试限制 | 指定包或测试 |

不能分类的 public 类型默认视为错误，不允许通过“暂时先 public”绕过。

### 4.2 全项目 allowlist

建立统一目录：

```text
docs/architecture/public-api/
  core.allowlist
  runtime.allowlist
  render3d.allowlist
  postprocess.allowlist
  ui.allowlist
  windowing.allowlist
```

每行格式固定为：

```text
<stable|advanced|internal> <fully-qualified-class-name>
```

架构测试需要做到：

- 扫描 main source set 的所有 public 顶层类型；
- public 类型必须恰好出现在一个 allowlist 中；
- allowlist 中不存在已删除或改名的类型；
- stable 类型的 public/protected 签名不得出现禁止依赖；
- internal 类型的生产调用者必须位于允许包集合；
- 新增 public 类型时，测试错误必须直接给出类型名和应更新的 allowlist；
- 删除 stable 类型时，测试错误必须提醒提供迁移记录。

### 4.3 glTF API 重新分类建议

v0.13 将 glTF 顶层 public 类型整体列为 stable，范围偏大。v0.14 建议调整为：

| 类型 | 建议分类 | 原因 |
| --- | --- | --- |
| `GltfAssetLoader` | stable | CPU 加载正式入口 |
| `LoadedGltfScene` | stable | CPU/GPU 两阶段边界的必要值对象 |
| `GltfRuntimeLibrary` | stable | glTF GPU 共享资源 owner |
| `GltfSceneAsset` | stable | GPU asset 与 scene 实例化入口 |
| `GltfLoadOptions` | advanced | scene selection、strict policy、limits 仍可能调整 |
| `SceneSelection` | advanced | 选择策略可能扩展，不应过早冻结所有变体 |
| `GltfAssetLimits` | advanced | 安全策略需要可演进 |
| `GltfSceneStatistics` | advanced | 诊断字段可能增加或重命名 |
| `GltfAssetException` | advanced | phase/location 结构保留，但不冻结所有构造形式 |
| `GltfAlphaMode` | internal 或 advanced | 应优先作为 asset 描述字段，不鼓励应用层控制 |

`LoadedGltfScene` 内部 DTO 如果必须对 GPU uploader 可见，应优先使用只读嵌套 record；不新增一组
独立 public DTO。所有集合继续返回不可变视图，矩阵和向量继续防御性复制。

### 4.4 API 收缩规则

- 能改为 package-private 的类型直接改，不为测试保留 public；
- 仅 Demo 需要的 convenience API 放入 demo source set；
- 多个只差默认参数的 overload，保留一个完整入口和一个最常用 convenience 入口；
- 不新增 `Manager`、`Registry`、`Context`、`Service` 等模糊公共抽象；
- builder 只有在参数数量和可选组合确实需要时保留；
- getter 不应暴露 mutable internal collection、JOML mutable object或 native handle；
- `id()` 等 native handle 入口若确实需要，分类为 advanced，并限制调用包；
- public 异常应包含可操作上下文，但不暴露第三方异常作为主要合同。

## 5. 删除 Assimp 实验入口

### 5.1 决策

v0.14 默认删除：

- `AssimpModelLoader`；
- `lwjgl-assimp` compile/runtime 依赖；
- 与 Assimp 相关的文档能力条目和未使用配置；
- 仅为该入口存在的测试或 fixture。

### 5.2 删除理由

- 没有正式 Demo；
- 没有端到端自动化验证；
- 只支持真实文件系统路径，与 classpath 主资源合同不一致；
- 与已完成的 OBJ/glTF 主路径重叠；
- 增加 native artifact、平台矩阵和发布包体积；
- public loader 会让使用者误以为 FBX 等格式已被正式支持；
- 继续修补它会把 v0.14 从收口版本重新变成资产功能版本。

### 5.3 兼容与迁移

- changelog 明确记录 `AssimpModelLoader` 是删除的实验 API；
- README 和能力矩阵将支持格式明确为 OBJ 与静态 glTF 2.0；
- 使用 Assimp 的本地项目应先离线转换为 glTF；
- 若未来存在无法离线转换的真实需求，以独立计划重新引入；
- 重新引入时必须同时具备 classpath/文件路径策略、Demo、测试、许可证和平台验证。

### 5.4 验收

- `rg "assimp|Assimp" build.gradle src/main src/test docs` 只允许出现在历史 changelog；
- Gradle dependency report 不再包含 `lwjgl-assimp` 及 natives；
- OBJ 与 glTF 集成测试继续通过；
- 打包 runtime classpath 不再包含 Assimp jar/native。

## 6. 高变更热点拆分

拆分原则不是“超过 500 行就拆”，而是一个类同时存在多个输入合同、失败阶段、缓存或测试边界时才拆。

### 6.1 `GltfAssetLoader`

外部入口保持：

```java
public final class GltfAssetLoader {
    public LoadedGltfScene load(AssetRef ref);
    public LoadedGltfScene load(AssetRef ref, GltfLoadOptions options);
}
```

内部建议拆为 package-private 组件：

```text
GltfAssetLoader                 facade、phase 转换、最终组装
GltfDocumentReader             .gltf JSON、.glb chunk、duplicate key
GltfUriResolver                external/data URI、mime、容量限制
GltfBufferTable                buffer、bufferView 的范围和只读访问
GltfAccessorDecoder            scalar/vector、stride、normalized、sparse
GltfMaterialDecoder            PBR factor、texture role、sampler、alpha policy
GltfNodeDecoder                scene selection、hierarchy、TRS/matrix、world transform
GltfMeshCanonicalizer          primitive、normal/tangent fallback、canonical layout
```

约束：

- 所有组件 package-private；
- `GltfAssetLoader` 是唯一 public 构造入口；
- 不复制 root JSON map；
- accessor decoder 不依赖 node/material decoder；
- URI resolver 不知道 MeshData 或 Material；
- CPU 阶段不引用 OpenGL 方法；
- 每个失败都转换为带 phase、location、dependent URI 的 `GltfAssetException`；
- v0.13 已修复的 sparse 零存储复用、范围验证和 selected-scene MASK 语义必须保留。

拆分完成后增加针对内部组件的 package test，但不能为了测试把组件改为 public。

### 6.2 `SceneAssetConfig`

建议拆为：

```text
SceneAssetConfig               immutable result + public load/parse facade
ScenePropertiesParser          .properties 语法
SceneTextManifestParser        行式 manifest 语法
SceneReferenceValidator        model/material/shader/texture 引用闭包
SceneValueParser               vector、boolean、enum、数字和错误上下文
```

约束：

- 两种语法必须生成同一组 immutable definition；
- 引用验证只执行一次；
- 错误包含配置键或行号；
- 不把 parser helper 暴露为 public；
- 不新增第三种场景格式；
- 不在本版本设计 ECS 或通用 AssetRegistry。

### 6.3 `CommandBuffer`

保留完整 fluent 录制 API，但将内部职责分离：

```text
CommandBuffer                  参数验证、录制顺序、public API
CommandArena                   primitive/object arena 与容量增长
CommandEncoder                 typed opcode 编码
CommandExecutor               opcode 解码和提交
PendingPipelineState          延迟状态合并
```

实施前先通过变更热点和测试确定真实边界。禁止：

- 改变命令顺序语义；
- 改变 snapshot ownership；
- 重新引入每命令对象；
- 破坏 pending state 的 draw/clear/pass/custom flush 边界；
- 绕开 `StateCache`；
- 为拆分类增加 public opcode API。

如果拆分不能在不增加分配和公共类型的前提下完成，本版本允许只提取 package-private arena/executor，
不追求文件长度目标。

### 6.4 `RenderGraph`

只在职责可验证时拆分：

```text
RenderGraph                    public graph lifecycle
RenderGraphCompiler            dependency、拓扑排序、读写验证
CompiledRenderGraph            immutable execution plan
RenderGraphExecutor            pass execution、profiling、cleanup
```

编译结果不得持有窗口或临时 framebuffer；resize 相关资源仍由明确 owner 管理。原有 target lifetime、
fixed-size shadow target 和 pass profiling 行为必须保持。

### 6.5 UI 暂缓全面拆分

`FontFace`、`UiDisplayList`、`UiGlyphAtlasGpu`、`UiSystem` 等体积较大，但 v0.14 不因行数全面改造。
先执行 allocation/profile，再只处理满足以下任一条件的热点：

- 10,000 quad 路径每帧分配显著；
- native owner 与布局/绘制职责混合导致失败清理困难；
- 同一逻辑在三个以上类重复；
- public API 被内部实现细节迫使扩大。

## 7. GPU 生命周期合同统一

### 7.1 标准 owner 合同

所有拥有 GPU/native 资源的类型必须满足：

1. 创建和关闭发生在拥有有效 context 的线程；
2. constructor/factory 中途失败会逆序关闭已创建资源；
3. `close()` 幂等；
4. 关闭后使用立即抛出明确异常；
5. cleanup 失败不会覆盖主失败，而是加入 suppressed；
6. borrowed 资源不由借用者关闭；
7. owner 关闭前若存在 active lease，必须 fail-fast 或有明确等待策略；
8. close 顺序与引用方向相反；
9. 统计值只计算实际创建的资源；
10. 测试覆盖重复 close、初始化失败和关闭后访问。

### 7.2 package-private `CloseStack`

允许提取一个小型内部 helper，用于 factory 初始化阶段：

```java
final class CloseStack implements AutoCloseable {
    <T extends AutoCloseable> T own(T resource);
    void releaseOwnership();
    void close();
}
```

限制：

- 不进入 public API；
- 不吞异常；
- 逆序关闭；
- 主异常由调用方保留，cleanup 以 suppressed 附加；
- 不承担线程调度、引用计数或资源查找；
- 不替代具有 active lease 的专用 owner。

优先应用于 glTF upload、PBR environment、Demo resource bundle 和 UI GPU 初始化。稳定的简单资源类不必
为了统一形式强制迁移。

### 7.3 owned/borrowed 命名

- 字段名或构造文档必须明确 ownership；
- `Material` 借用 shader/texture 时不得在 close 中释放它们；
- `GltfSceneAsset` 拥有 mesh/material/texture/sampler，但借用 runtime library 共享资源；
- `SceneObject` 借用 mesh/material，不成为 GPU owner；
- pipeline 借用 Scene，拥有自己的 graph/target/pass 资源；
- 测试 probe 不得依赖最终器或 GC 触发释放。

## 8. 依赖与构建收紧

### 8.1 依赖分类

每个 implementation 依赖必须在文档中对应一个正式能力：

| 依赖 | 正式用途 |
| --- | --- |
| LWJGL core/OpenGL/GLFW/STB | OpenGL、窗口、图像/HDR 解码 |
| FreeType/HarfBuzz/Yoga | UI 字体、整形和布局 |
| JOML | 数学类型 |
| Jackson Core | 严格 glTF JSON streaming parse |
| JNA/JNA Platform | Windows IME/native adapter |

删除 Assimp 后，不保留“可能以后使用”的依赖。新增依赖必须同时说明：

- 为什么 JDK/现有依赖不能满足；
- 进入哪个 source set；
- 是否带 native；
- Windows/Linux/macOS classifier；
- 许可证；
- 最小 Demo 或测试证明；
- 移除成本。

### 8.2 dependency locking

- 启用 Gradle dependency locking；
- 提交 lockfile；
- BOM 和直接版本保持单一来源；
- release verification 检查 lockfile 无漂移；
- 升级 LWJGL/JNA/Jackson/JUnit 必须作为独立提交并重新跑对应 native/GL 验证；
- 不在功能重构提交中顺带升级依赖。

### 8.3 source set 边界

- `main`：可复用框架代码和正式资源；
- `demo`：应用入口、benchmark、人工 inspector、演示资产；
- `test`：fixture、fault injection、测试 helper；
- `shaderGenerator`：只包含生成器及其直接资源。

新增架构测试：

- main 禁止引用 `.demo.` 包；
- main 禁止从 test resources 读取文件；
- demo helper 不得被 main public API 返回；
- benchmark 不得进入 main；
- test-only fault injection 保持 package-private。

## 9. 验证入口统一

### 9.1 默认无桌面门禁

定义 `check` 为所有环境都必须通过的门禁：

```text
check
  compileJava
  demoClasses
  test
  publicApiGuard
  architectureGuard
  assetManifestGuard
  dependencyLockGuard
```

要求：

- 不创建窗口；
- 不要求显示设备或 OpenGL context；
- Windows/Linux CI 都执行；
- 任一 public API、依赖、资产 hash 或架构边界漂移直接失败；
- 不依赖 task 执行顺序隐藏状态。

### 9.2 本机完整发布门禁

新增聚合任务：

```text
localReleaseVerification
  check
  glSmoke
  runDemoIntegration
  runDemoResizeIntegration
  runAsyncIntegration
  runPbrIntegration
  runPbrResizeIntegration
  runGltfIntegration
  runGltfResizeIntegration
  runUiIntegration
  runUiResizeIntegration
  runUiTextIntegration
  runUiSyntheticImeSoak
  runUiNativeSoak        # Windows only
```

`localReleaseVerification` 不挂到默认 `check`，避免无桌面 CI 失败。各任务必须有明确顺序，避免并行争抢
GLFW、显示设备或 native hook。

### 9.3 快速开发入口

保留较短入口：

```text
quickVerification = compileJava + demoClasses + test
localGlVerification = glSmoke + 核心确定性 Demo
localUiVerification = UI GL/integration/soak
localPbrVerification = PBR GL/integration/failure
localGltfVerification = glTF GL/integration/resize
```

局部入口服务日常开发，`localReleaseVerification` 才代表正式本机发布证明。文档不得把局部入口描述成完整
发布验收。

## 10. 架构守卫

### 10.1 包依赖守卫

必须覆盖：

- `backend !-> runtime/subsystems/demo`；
- `core !-> subsystems/demo`；
- `runtime !-> demo`；
- `core.assets.gltf !-> OpenGL/render3d`；
- `subsystems.ui !-> demo`；
- `subsystems.render3d.gltf !-> demo`；
- `shaderGenerator !-> demo/test`。

现有明确允许的 `backend → core` 类型集合继续使用 allowlist 锁定，不因本次重构扩大。

### 10.2 OpenGL 调用守卫

- 裸 `gl*` 调用只允许在 backend 和明确允许的 GL subsystem implementation；
- CPU asset loader、scene config、runtime DTO 和 UI layout/text model 禁止调用 OpenGL；
- `CommandBuffer.custom()` 生产调用保持零或明确 allowlist；
- 新 GPU 操作优先使用 typed command；
- 未出现第二个真实调用者前，不新增抽象命令。

### 10.3 资源 owner 守卫

通过测试和静态约定检查：

- public owner 实现 `AutoCloseable`；
- `close()` 有幂等测试；
- factory 有 failure injection 测试；
- active lease owner 有提前关闭测试；
- 关闭后调用有 fail-fast 测试；
- cleanup suppressed 行为有测试。

## 13. 代码质量规则

### 13.1 删除优先于抽象

每个候选 abstraction 先回答：

1. 是否已有至少两个真实调用者？
2. 是否消除了重复生命周期或失败语义？
3. 是否可以保持 package-private？
4. 是否能够通过独立测试证明？
5. 删除它是否比维护它更简单？

任何一项无法回答时，不在 v0.14 引入。

### 13.2 不以行数作为验收指标

大类允许存在，但必须满足：

- 单一公共职责；
- 内部阶段清晰；
- 失败边界可定位；
- 测试能够覆盖；
- 不迫使公共 API 扩大。

拆分后的总行数可能增加；验收关注依赖方向、变更隔离、测试边界和热路径分配。

### 13.3 热路径约束

- frame loop 不新增每对象临时集合；
- command recording 不恢复每命令对象分配；
- scene rendering 不在每帧解析 JSON、manifest 或 node DTO；
- glTF world transform 在实例化阶段冻结；
- retained UI 快照分配必须通过 profile 证明；
- GPU resource upload 可以分配，但必须有容量上限和失败清理；
- benchmark 与功能测试分开，不用单帧 FPS 冒充正式性能结论。

## 17. 风险与回滚策略

### 17.1 API 收缩破坏本地使用者

风险：0.x 阶段仍可能有应用直接依赖此前标为 stable 的诊断类型。

策略：先生成调用清单；能降为 advanced 就不立刻隐藏；必须隐藏时提供一版迁移说明，不保留无期限 deprecated
壳。若仓库外已有明确使用者，再单独评估兼容窗口。

### 17.2 拆分 loader 引入行为偏差

风险：错误 phase/location、selected scene、sparse、颜色空间或 tangent fallback 改变。

策略：拆分前冻结 characterization tests；每次只移动一个阶段；禁止同时改格式能力；CPU 和 GL 测试逐提交运行。

### 17.3 生命周期 helper 变成新框架

风险：`CloseStack` 扩张为线程调度、引用计数和资源注册中心。

策略：固定为 package-private、少量方法、只做逆序 close；复杂 owner 继续保留专用逻辑。

### 17.4 删除 Assimp 后出现格式需求

风险：使用者希望直接加载 FBX/DAE。

策略：推荐离线转 glTF；只有真实生产样例无法满足时才重新立项，并要求完整纵向证明，不回滚为无测试入口。

### 17.5 验证任务时间过长

风险：开发者跳过 `localReleaseVerification`。

策略：保留 quick/local subsystem 入口；正式聚合任务输出每阶段耗时和失败任务；仅 release candidate 强制完整运行。

使用场景为前提，不能在 v0.14 收口完成前并行启动。
