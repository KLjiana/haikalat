# v0.20 代码整理与逻辑优化计划

> 状态：M8 snapshot 验收完成
> 目标版本：`0.20.0-SNAPSHOT` → `0.20.0`
> 前置版本：`0.19.4`
> 主题：稳定现有能力、收敛职责、减少热路径分配、强化资源生命周期
> 基线：正式 `0.19.4` 提交 `51d830b`；完整 readiness 的静态 all-visible 性能回退已记录，
> v0.20 将以该结果作为优化目标，不覆盖或伪造原始证据。

## 1. 版本定位

v0.20 不再以增加新渲染能力为主要目标，而是作为一次“内部结构收敛版本”：

1. 保留 v0.19 已完成的 UI、SDF、Compositor、VFX、动画、场景资产和热重载能力。
2. 不改变 `RenderDevice`、`RenderGraph`、`Material`、`Mesh`、UI 对外入口的定位。
3. 将已经膨胀的编排类拆成可理解、可测试的 package-private 组件。
4. 将重复的线程检查、dirty 传播、矩阵变换、资源关闭和错误处理逻辑收敛到单一实现。
5. 让静态 UI、静态场景和无特效路径在稳定状态下不产生额外的每帧对象。
6. 让 resize、场景切换、热重载和 GL 资源重建都采用“候选生成成功后再切换”的事务式流程。

本版本的完成标准不是“类的行数变少”，而是：

- 每个运行时职责有唯一归属；
- 生命周期边界可以从代码和日志中解释；
- 热路径的分配、锁和临时容器有明确预算；
- 失败时旧状态仍可继续工作；
- 公共 API 和已有 Demo 行为不发生无意变化。

## 2. 当前代码评估

### 2.1 规模与风险

当前主代码约 459 个 Java 文件、5.2 万行，测试约 163 个文件、1.8 万行，Demo 约 49 个文件、近 1 万行。规模本身不是问题，真正的风险是多个系统把“编排、状态、资源、诊断和执行”集中在同一个类中。

优先关注的热点：

| 区域 | 代表类 | 主要问题 | v0.20 处理 |
|---|---|---|---|
| UI 树与帧录制 | `UiSystem`、`UiNode`、`UiDisplayList` | 树管理、脏标记、事件、变换、绘制命令和快照边界交叉 | 拆分编排、树状态、快照与绘制存储 |
| UI 执行 | `UiRenderer`、`UiCompositor` | 普通四边形、SDF、文字、分层、后处理资源与 RenderGraph 接入混在一起 | 保留 facade，拆分内部 renderer/plan/resource owner |
| UI 动画 | `UiAnimationSystem`、`UiTimeline` | 旧式 transition、track、sequence、signal、取消和 owner-thread 检查重复 | 统一时间源和调度内核，旧 API 作为适配层 |
| 动画运行时 | `AnimationController`、`AnimationGraph` | 状态迁移、曲线采样、pose 输出、中断、信号队列耦合 | 拆成 transition runtime、采样器、输出与事件队列 |
| 命令录制 | `CommandBuffer` | 公共 facade 承担 arena、快照、排序、执行前校验和生命周期 | 保持公共类型，内部拆成 arena/encoder/packet |
| 图与管线 | `RenderGraph`、`RenderPipeline`、`PostProcessPassBuilder` | 拓扑、资源代际、执行和重建逻辑边界不够清晰 | 引入 immutable plan 与 candidate generation |
| 资源资产 | `SceneAssetService`、`GltfSceneAsset`、`Texture2D` | 解码、上传、缓存、失败清理和激活状态交叉 | 拆分 load operation/cache/generation/activation |
| 字体与诊断 | `FontFace`、`UiTextEngine`、`DiagnosticsJsonExporter` | 稳定能力与资源/序列化细节集中 | 本版本只做边界和缓存清理，不改算法 |

### 2.2 已确认的重复逻辑

v0.20 应优先处理以下重复，而不是继续堆叠新的抽象：

- UI 和动画系统各自维护 owner-thread 检查；
- `UiNode`、`UiDocument`、`UiVisualTransform` 各自处理部分变换、逆矩阵和命中测试；
- layout dirty、paint dirty、transform dirty、resource dirty 的传播规则分散；
- 普通 UI、SDF、文字和 VFX 各自维护批次键和快照数据；
- RenderGraph、Compositor 和 Pipeline 都有“注册—编译—激活—关闭”的相似阶段；
- GL 资源持有者对初始化失败、部分创建成功和重复 close 的处理不完全一致；
- 动画 active list、timeline run list、signal queue 有相近的遍历和删除模式；
- 热路径存在临时 `Vector4f`、ID wrapper、集合和矩阵快照创建，需要以 profile 结果为准收敛。

## 3. 实施原则

### 3.1 先冻结行为，再整理实现

在 `0.19.4` 验收完成并记录候选提交哈希后，先建立行为基线，再开始 v0.20 重构。v0.20 的第一批提交不得混入 0.19.4 的功能修改。

每个重构提交必须回答：

- 公共入口是否保持不变；
- 执行顺序、排序稳定性和资源关闭顺序是否保持不变；
- 失败时旧对象是否仍然可用；
- 日志、诊断和 GL 错误上下文是否保持可追踪；
- 热路径是否减少或至少不增加分配。

### 3.2 Facade 稳定，内部 package-private

优先采用：

```text
现有公共类型
    └── package-private coordinator / plan / arena / owner
```

不为了拆文件而增加新的公共 runtime 抽象，不提前设计通用 ECS、统一 AssetRegistry 或第二渲染后端。

### 3.3 数据不可变，状态显式可变

- 配置、绘制快照、RenderGraph plan、Compositor layer plan 使用不可变对象；
- 帧内可变状态集中在 coordinator/runtime 中；
- active、candidate、retired、closed 等生命周期状态必须显式表达；
- 不再通过 `null` 或空集合隐式表达“尚未构建”和“已关闭”。

### 3.4 先解决正确性，再做微优化

不以类行数或单个局部 benchmark 作为拆分依据。所有热路径优化都要绑定可观察指标：

- 每帧分配字节数与对象数；
- UI draw/batch 数；
- RenderGraph pass 和资源重建次数；
- CPU frame p50/p95/p99；
- GL debug 中 HIGH/MEDIUM 消息；
- 关闭、重载和 resize 的耗时及失败率。

## 4. 总体架构目标

```text
用户 / Demo API
        │
        ▼
稳定 Facade（UiSystem / RenderPipeline / CommandBuffer / SceneAssetService）
        │
        ├── Coordinator：线程、生命周期、阶段编排
        ├── Plan：不可变拓扑、绘制计划、资源描述
        ├── Runtime：帧内状态、动画游标、active 列表
        ├── Arena：可复用的命令、矩阵、顶点、快照存储
        └── Owner：GL 资源、代际、关闭和失败回滚
```

边界要求：

- UI 只依赖允许的 core graph/backend 能力，不依赖 `render3d` 或 `postprocess` 的具体实现；
- core/runtime/backend 不反向依赖 UI；
- 生产代码继续禁止通过 `CommandBuffer.custom()` 绕过状态和排序；
- graph/pipeline 的 candidate generation 不得提前关闭 active generation；
- 场景和 UI 的异步加载不得直接在非 owner thread 创建或销毁 GL 资源。

## 5. 分阶段实施

### M0：候选版本冻结与工作区分流

**目标**：确保 0.19.4 的验收结果不会被 v0.20 重构污染。

工作项：

1. 等待另一条工作流完成 `0.19.4-SNAPSHOT` 验收。
2. 记录候选版本的提交哈希、构建参数、驱动信息和 GL 日志摘要。
3. 将 v0.20 工作分支从已确认的 0.19.4 基线切出。
4. 建立“公共 API、Demo 输出、GL 日志、资源关闭”四类基线清单。
5. 将本版本变更分为：
   - `refactor(ui)`
   - `refactor(animation)`
   - `refactor(render-core)`
   - `fix(lifecycle)`
   - `perf(allocations)`
   - `test(contracts)`
   - `docs(v0.20)`

验收：

- v0.20 分支没有携带未解释的 0.19.4 功能差异；
- 每个重构提交可以单独回退；
- 未运行或修改 0.19.4-SNAPSHOT 的验收流程。

### M1：公共 API 与包边界清点

**目标**：明确哪些是稳定 API，哪些只是 v0.19 期间意外暴露的实现细节。

工作项：

1. 为 `core`、`backend`、`runtime`、`subsystems.ui`、`subsystems.render3d`、`subsystems.postprocess` 建立公开类型清单。
2. 检查新增 UI/SDF/Compositor/VFX/动画类型是否真的需要 public。
3. 能降为 package-private 的类型先降级；无法降级的类型补充兼容性说明。
4. 对旧入口增加 `@Deprecated(forRemoval = false)` 适配层，不在 v0.20 删除。
5. 更新架构 allowlist，明确：
   - backend 允许依赖 core；
   - backend 不依赖 runtime/subsystems；
   - core/runtime 不依赖 subsystems；
   - UI 不依赖 render3d/postprocess；
   - 生产路径不调用 `custom()`。

验收：

- 架构测试覆盖新包边界；
- API diff 没有未记录的删除或行为变化；
- 文档中的类型名称与代码一致。

M1 交付记录：

- 以各域 allowlist 和 `stable-baseline.allowlist` 固化 401 个 public 顶层类型的分类快照；
- 补充包依赖、GL-free、`custom()` 和异步资源代次规则，见
  `docs/architecture/v0.20-api-boundary-inventory.md`；
- 保持现有 facade 和 stable 入口不变，M2 起的内部拆分优先使用 package-private 组件；
- `PublicApiCatalog`、`ArchitectureBoundaryTest` 及 UI/PBR/glTF 专项测试作为 M1 合同入口。

### M2：UI 树、快照与绘制存储收敛

**目标**：降低 UI 核心类的职责密度，建立清晰的 update → snapshot → render 链路。

#### 5.2.1 `UiSystem` 保留为编排 facade

将内部职责拆为：

- `UiUpdateCoordinator`：owner-thread 更新、输入派发、layout/paint 阶段调度；
- `UiSnapshotPublisher`：冻结当前帧快照并发布给渲染线程；
- `UiAttachmentController`：向 RenderGraph attach/detach UI pass；
- `UiDiagnostics`：帧计数、dirty 统计、fallback 和错误上下文。

`UiSystem` 只保留：

```text
update(input, time)
snapshot()
attachTo(graph, options)
close()
```

#### 5.2.2 `UiNode` 拆分树结构与节点状态

保持 `UiNode` 作为用户可见入口，内部拆分：

- `UiTreeLinks`：parent、children、插入顺序、cycle 检查；
- `UiNodeState`：style、layout box、visibility、opacity、transform；
- `UiEventRegistry`：监听器、capture/bubble 顺序和移除；
- `UiDirtyState`：layout、paint、transform、hit-test、resource 五类脏状态。

要求：

- child 顺序使用稳定的插入序号，不依赖 HashMap 遍历顺序；
- 删除节点时一次性解除 listener、timeline、effect 和资源引用；
- dirty 向上/向下传播规则集中在一个实现中；
- layout 没有变化时不得触发整棵树 paint。

#### 5.2.3 `UiDisplayList` 拆分录制器与 arena

保留 `UiDisplayList` 的快照/冻结语义，内部引入：

- `UiFrameRecorder`：transform、clip、layer 栈和命令录制；
- `UiSnapshotArena`：矩阵、颜色、圆角、图片 ID、文字和 effect 参数的帧内存储；
- `UiPrimitiveCommandStore`：普通 quad、glyph、SDF、layer/effect 命令；
- `UiDisplayListValidator`：栈平衡、索引范围、finite 值和冻结状态检查。

建议的数据流：

```text
UiNode tree
    → UiFrameRecorder
    → UiSnapshotArena（只在 dirty 时更新）
    → immutable UiRenderSnapshot
    → UiRenderer / UiCompositor
```

禁止：

- 在 render thread 重新访问可变 `UiNode`；
- 每个命令创建独立的 Matrix/Vector/ID wrapper；
- SDF 或 effect 未启用时分配对应 arena。

M2 交付记录：

- `UiSystem` 保持公共 facade，输入、快照发布、RenderGraph 挂接和诊断分别收敛到
  `UiUpdateCoordinator`、`UiSnapshotPublisher`、`UiAttachmentController` 和
  `UiDiagnostics`；
- `UiNode` 将树链接、dirty flag 和 listener 存储收敛到 `UiTreeLinks`、
  `UiDirtyState` 和 `UiEventRegistry`，并补充关闭子树后的 snapshot 合同；
- `UiDisplayListValidator` 统一 freeze、stack、resource 和 index 校验；结构化数组与
  `UiSnapshotExchange` slot arena 继续复用现有实现，避免只为移动代码增加热路径间接层；
- 所有新增组件均为 package-private，未修改 UI allowlist，职责与合同见
  `docs/architecture/v0.20-ui-consolidation.md`。

### M3：UI Renderer、SDF 与 Compositor 逻辑分层

**目标**：保留现有 UI 能力，但让普通 UI、SDF、文字和后处理不再共享一套过大的执行方法。

内部拆分建议：

- `UiPrimitiveRenderer`：图片、纯色 quad、glyph 基础批次；
- `UiSdfRenderer`：SDF shape 参数、圆角、边框和渐变；
- `UiLayerRenderer`：layer target、blur、shadow、blend；
- `UiRenderResourceOwner`：shader、texture、ring、atlas 和 FBO 的创建/关闭；
- `UiBatchKey`：预计算 shader/texture/blend/clip/layer key；
- `UiCompositorPlan`：不可变 layer 排序、父子关系和依赖；
- `UiCompositorResources`：与 GL context 绑定的实际 target 和中间纹理。

`UiRenderer` 和 `UiCompositor` 继续作为稳定 facade：

- renderer 接收 immutable snapshot；
- compositor 接收 immutable plan；
- resource owner 只在 GL owner thread 创建、替换和关闭；
- candidate resources 完整创建成功后才替换 active resources。

性能要求：

- 普通静态 UI 路径不创建 SDF、blur、shadow 或 effect target；
- SDF uniform 使用可复用 scratch/arena，避免每 draw 创建 `Vector4f`；
- batch key 在录制阶段生成，执行阶段不再拼装临时对象；
- layer 无变化时复用上一帧的排序和 target 描述。

M3 交付记录：

- `UiSdfRenderer` 将 SDF uniform 编码和颜色转换集中到 render-thread scratch，普通路径不再
  为每个 SDF batch 创建 `Vector4f`；
- `UiCompositorPlan` 在 RenderGraph mutation 前完成 layer 排序、树校验、预算和 pass 名称
  候选检查，`UiCompositor` 只负责注册已经验证的计划；
- `UiRenderResourceOwner` 统一 shader、sampler、VAO/EBO、vertex ring 和 glyph atlas 的
  owner-thread 初始化、候选失败回滚和逆序 close；
- renderer/compositor facade 与现有 `UiRenderer`、`UiCompositor` public API 保持不变。

### M4：动画运行时与 UI 动画统一

**目标**：减少 `AnimationController`、`UiAnimationSystem`、`UiTimeline` 之间重复的时间和 active-run 逻辑。

#### 5.4.1 共享时间与游标

新增 package-private：

- `AnimationClock`：帧时间、delta、暂停、缩放和单调性；
- `AnimationCursor`：clip、loop、ping-pong、segment 和结束状态；
- `AnimationRunList`：稳定遍历、延迟删除和容量复用；
- `AnimationSignalQueue`：按时间顺序发出信号，明确 once/repeat 语义。

#### 5.4.2 `AnimationController` 内部拆分

- `AnimationTransitionRuntime`：状态迁移、优先级、中断和 blend；
- `AnimationSampler`：clip/curve/morph 采样；
- `AnimationPoseOutput`：向骨骼、节点或材质输出；
- `AnimationEventSink`：信号、marker 和诊断事件；
- `AnimationController`：只编排这些组件并保持原有入口。

#### 5.4.3 UI 动画适配

`UiAnimationSystem` 和 `UiTimeline` 共享 `AnimationClock` 与 `AnimationRunList`，但不把 UI 属性强行抽象成通用 ECS component。

每条 `UiPropertyTrack` 声明影响范围：

```text
LAYOUT       → 重新 layout + paint
TRANSFORM    → 更新变换/命中测试 + paint
PAINT        → 仅重新 paint
COMPOSITOR   → 重新生成 layer/effect plan
```

要求：

- reduced-motion 策略在一个入口决定；
- cancel、finish、close 的顺序固定且幂等；
- 动画完成后不留下 listener、signal 或临时资源；
- 没有活动轨道时 `UiAnimationSystem` 不遍历整棵树。

M4 交付记录：

- `AnimationSignalQueue` 统一有界 signal 和优先级淘汰；
- `AnimationCursor` 复用状态机 source/target 的时间/loop 结果；
- `UiAnimationRunList` 让 UI active-run 更新使用容量复用的 index-based 删除；
- 具体语义和待收敛边界见 `docs/architecture/v0.20-animation-convergence.md`。

### M5-M6 交付记录

- `CommandStream`、`PendingPipelineState` 和 `CommandExecutor` 继续作为
  `CommandBuffer` 的内部职责边界，未新增 public escape hatch；
- `RenderGraph`/`RenderTargetManager`/`TaaHistory` 已采用 candidate-first、成功切换后
  retire 的 framebuffer 生命周期，close 异常会继续清理并保留 suppressed；
- RenderPipeline、SceneAssetService 既有 candidate scene/generation 协议与本轮 target
  generation 规则对齐，详见 `docs/architecture/v0.20-render-core-lifecycle.md`。

### M5：CommandBuffer、RenderGraph 与 Pipeline 内部整理

**目标**：在不改变公共定位的前提下，降低渲染核心的职责耦合。

#### 5.5.1 `CommandBuffer`

保留公共 `CommandBuffer` facade，内部按职责拆分：

- `CommandArena`：可复用 primitive/byte/object 存储；
- `CommandEncoder`：类型化命令写入和快照；
- `CommandPacket`：不可变提交包；
- `CommandValidator`：状态、资源生命周期和栈平衡检查；
- `CommandExecutor`：按既有顺序执行并接入 StateCache；
- `MatrixSnapshotArena`：处理 copy-on-submit 与 owned snapshot 语义。

规则：

- 公共 API 继续提供稳定快照语义；
- package-private owned-snapshot 入口只供受控批量路径使用；
- `custom()` 保留 profiling escape hatch，生产调用继续由架构测试限制；
- arena 在 frame end 清理，异常路径必须进入 abort/finalize。

#### 5.5.2 `RenderGraph`

内部拆分：

- `RenderGraphDefinition`：pass/resource 声明；
- `RenderGraphCompiler`：拓扑、读写依赖、barrier 和 alias 计划；
- `RenderGraphGeneration`：一组实际 GL target/resource；
- `RenderGraphExecutor`：帧内执行；
- `RenderGraphDiagnostics`：preview、统计和错误信息。

重建必须遵循：

```text
definition → compile candidate → allocate candidate
           → validate candidate → atomically activate
           → retire old generation
```

任何 candidate 失败时，active generation 保持可用。

#### 5.5.3 `RenderPipeline` 与 `PostProcessPassBuilder`

- `PipelineTopology`：不可变 pass 顺序和 feature 开关；
- `PipelineGeneration`：绑定当前 graph generation；
- `PipelineFrameExecutor`：每帧执行；
- `PostProcessRecipe`：后处理 pass 描述；
- `PostProcessTargetPlan`：目标纹理和尺寸策略。

`build()`、resize、feature toggle 都改为事务式替换，不在构建中途关闭 active pipeline。

### M6：资源生命周期与异步状态统一

**目标**：让 UI、场景、纹理、字体、图和管线遵循同一套可解释的生命周期。

推荐状态：

```text
NEW → INITIALIZING → ACTIVE
                 ├→ FAILED
ACTIVE → RETIRING → CLOSED
FAILED → CLOSED
```

工作项：

1. 为 `UiRenderResourceOwner`、`UiGlyphAtlasGpu`、`UiEffectRenderer`、`SceneAssetService`、`Texture2D` 和 graph generation 审查状态转换。
2. 初始化失败时按逆序关闭已创建资源。
3. `close()` 幂等；重复 close 不访问 GL 资源。
4. 明确资源所属线程和 context；异步线程只产生 CPU 计划或 decode 结果。
5. retired generation 使用 lease/fence，确认 GPU 不再访问后再关闭。
6. 所有失败日志带资源身份、generation、owner thread 和阶段。
7. 禁止 use-after-close、跨 context 销毁和“旧 generation 被新请求覆盖”。

### M7：热路径性能收敛

**目标**：用可复现指标证明整理确实改善了代码，而不是只改变文件结构。

#### UI

- 静态帧连续运行时，普通 quad path 的新增对象数为零或保持在既定预算内；
- dirty subtree 才重新 layout/paint；
- display-list snapshot、batch key、SDF 参数和 layer plan 复用；
- glyph atlas、blur target、shadow target 按需创建；
- render thread 不分配临时集合。

#### 动画

- active run list 容量复用；
- track apply 使用预解析属性句柄；
- signal queue 不在每帧创建临时排序对象；
- inactive controller/timeline 不触发全树更新。

#### 渲染核心

- CommandBuffer arena 在帧间复用；
- RenderGraph execute 阶段不重新编译拓扑；
- StateCache 命中时跳过重复 GL state 设置；
- resize 只重建尺寸相关 target；
- static scene 不产生额外 pipeline generation。

#### 观测指标

每次优化至少记录：

| 指标 | 基线 | 目标 |
|---|---:|---:|
| UI static frame p95 CPU | 以 0.19.4 基线为准 | 不回退，优先下降 |
| UI frame allocations | 以 0.19.4 基线为准 | 普通路径为 0 增量 |
| UI draw/batch 数 | 以 0.19.4 基线为准 | 不增加 |
| Graph rebuild 次数 | 以 0.19.4 基线为准 | 仅在 topology/size 变化时发生 |
| GL HIGH/MEDIUM 消息 | 以 0.19.4 基线为准 | 不新增，已有项逐项解释 |
| close/retire 残留资源 | 0 | 0 |

M7 交付记录：

- 静态 UI 只在首帧、可见 paint dirty、glyph upload 完成和 effect 生命周期变化时
  重录；五轮容量基准的十个测量窗口 snapshot publication 均为 `0`；

  基线基本持平，不再复现 v0.19.4 独立重跑的 `3.567 ms` 回退；

  结果见 `docs/performance/v0.20-m7-2026-07-28.md`。

## 6. 推荐提交顺序

```text
M0  freeze/branch
 └─ M1  API 与包边界清点
     ├─ M2  UI tree/display-list snapshot
     ├─ M3  UI renderer/compositor
     └─ M4  animation runtime convergence
         └─ M5  command/render graph/pipeline internals
             └─ M6  lifecycle/async cleanup
                 └─ M7  performance proof
                     └─ M8  contracts + release
```

每个提交只做一种类型的改变。不要在同一个提交里同时：

- 改 shader 行为和移动 Java 类；
- 改公共 API 和大规模格式化；
- 改资源生命周期和新增功能；
- 改基线数据和修复测试断言。

## 7. 可选执行路线

如果需要控制 v0.20 的风险，可以从以下路线选择：

| 路线 | 内容 | 周期/风险 | 适合情况 |
|---|---|---|---|
| A：UI 收敛 | M1～M4，重点整理 UI、SDF、Compositor、动画 | 最短/中 | 想先让 UI 代码可维护 |
| B：渲染核心 | M1、M5、M6，重点 CommandBuffer、Graph、Pipeline | 中/中高 | 近期要继续扩展渲染管线 |
| C：生命周期 | M1、M6、M8，重点异步、代际、关闭和错误回滚 | 中/低功能风险 | 当前最担心资源泄漏和热重载 |
| D：完整 v0.20 | M0～M8，按推荐顺序全部完成 | 最长/可控 | 希望把 0.19 的快速扩展收敛成长期底座 |

建议选择 D，但执行上先完成 A，再做 B/C；这样即使中途收尾，也能得到一个完整的 UI 内部整理版本。

## 8. v0.20 明确不做

以下内容不进入 v0.20：

- 新增 Vulkan、Metal 或第二个后端；
- 引入通用 ECS、公共 AssetRegistry 或全局服务定位器；
- 继续扩展新的 SDF 图元种类；
- 增加新的 VFX 类型或复杂粒子模拟；
- 大规模重写字体 shaping、Yoga 布局或 glTF 解码算法；
- GPU-driven scene、bindless 全面改造或复杂 PBR 新特性；
- 为了减少行数而进行无行为收益的机械拆文件。

这些内容应等 v0.20 完成并稳定后，基于新的边界重新评估。

## 10. 结论

v0.20 应被定义为“代码整理与运行时逻辑优化版本”，而不是新的功能版本。首要顺序是：

1. 等待并冻结 `0.19.4` 验收结果；
2. 整理 UI 树、DisplayList、Renderer 和 Compositor 的职责；
3. 统一动画时间、active run 和 dirty scope；
4. 拆分 CommandBuffer、RenderGraph、RenderPipeline 的内部阶段；
5. 统一 GL 资源代际、失败回滚和 close 语义；
6. 用分配、帧时、GL 日志和资源残留证明收益；
7. 通过契约与集成门禁后再发布 `0.20.0`。

在 0.19.4 尚未完成验收前，v0.20 只进行设计、职责清点和可独立回退的准备，不抢跑实现。
