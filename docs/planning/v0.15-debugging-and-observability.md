# v0.15 调试与可观察性实施计划

> 状态：已完成并发布为 `0.15.0`（2026-07-19）
> 目标版本：`0.15.0`  
> 基线版本：`0.14.0`  
> 版本主题：把已有 profiling、GL debug、资源标签和 UI 能力收拢成可验证的帧诊断闭环  
> 核心原则：诊断系统只能观察正式渲染路径，不能建立第二套渲染、资源或生命周期协议

## 1. 执行摘要

项目已经具备以下基础能力：

- `FrameDriver` 与 `RenderStatistics` 记录 CPU submit、present FPS 和最近一帧 profile；
- `RenderGraph` 为每个 pass 记录 CPU record 时间和非阻塞 GPU timer query；
- `FrameProfile`、`PassProfile`、`DebugOverlaySnapshot` 已能向 Demo 提供基础遥测；
- `GlDebug` 已安装 OpenGL debug callback、输出错误并为部分 GL object 设置 label；
- `StateCache`、实例缓冲、UI、glyph atlas 和 glTF asset 已分别暴露局部统计；
- v0.11 UI 已具备 `Panel`、`Label`、`Button`、`ListView`、`ScrollView`、`Toggle` 等构建工具面板所需的控件；
- 确定性 Demo、真实 GL smoke、性能基准和本地发布验证入口已经稳定。

当前问题不是“完全看不到性能数据”，而是信息分散且语义不够完整：

- GPU query 返回的是较早完成的样本，但 `PassProfile` 没有标记样本来源帧、年龄或不可用状态；
- `gpuNanos == 0` 同时可能表示真实零开销、尚无结果或 query ring 饱和，诊断结论会有歧义；
- 用户只能看到一行 HUD，不能查看帧历史、单 pass 明细、RenderGraph 拓扑、target 描述和状态缓存收益；
- GL debug callback 只写日志，没有有界结构化历史、严重度计数、去重和 UI 查询入口；
- GL 资源有 label，但缺少统一的存活清单、创建位置、估算字节数和失败清理证明；
- 出现偶发尖峰或错误时，没有“冻结当前诊断状态并导出”的标准工作流；
- 各 Demo 若自行拼装诊断 UI，会很快形成多套不一致的工具代码。

v0.15 的目标是建立一条完整但克制的诊断链路：

```text
正式渲染/资源路径
       |
       +-- RenderGraph timing/topology
       +-- FrameDriver/present/state statistics
       +-- GL debug message ring
       +-- tracked GL resource metadata
       +-- optional subsystem statistics
       |
       v
immutable DiagnosticsSnapshot + bounded history
       |
       +-- retained-mode DiagnosticsPanel
       +-- freeze / inspect
       +-- deterministic JSON capture
```

版本完成定义：

> 在不改变场景画面和正式渲染顺序的前提下，用户可以在主 Demo 中打开统一诊断面板，查看最近帧历史、每个 RenderGraph pass 的 CPU/GPU 样本及年龄、graph target、状态缓存、主要子系统统计、当前存活 GL 资源和结构化 GL 消息；可以冻结一份一致快照并导出 JSON；关闭诊断 UI 后不会留下资源、线程或明显热路径分配，所有关键行为均有纯 JVM、真实 GL 和确定性集成证明。

## 2. 目标与非目标

### 2.1 必须完成

1. 修正 GPU timing 的“结果属于哪一帧”语义，不再用 `0` 表示未知。
2. 建立单 owner、有界、不可变的帧诊断历史。
3. 提供正式 RenderGraph 拓扑与 target 元数据快照，不向 UI 暴露可变 graph 内部对象。
4. 将 GL debug callback 转换为有界、可查询、可过滤的结构化事件流。
5. 跟踪框架拥有的主要 GL 资源，能够发现确定性泄漏和失败路径遗漏。
6. 基于现有 UI subsystem 构建一个可复用诊断面板，接入主 Demo。
7. 支持暂停采样、冻结一致快照、清空统计和导出稳定 JSON。
8. 为关闭、无 context、query 饱和、异常帧、资源失败清理和重复 close 建立测试。
9. 建立诊断关闭与开启两种性能基线，避免工具本身污染被测对象。
10. 更新能力矩阵、测试指南、公共 API allowlist、changelog 和发布报告。

### 2.2 明确非目标

- 不建设完整场景编辑器、属性编辑器、ECS inspector 或 shader graph；
- 不允许诊断面板修改 RenderGraph topology、材质、资源所有权或原始 GL state；
- 不增加远程 telemetry server、WebSocket、HTTP endpoint、JMX bridge 或网络协议；
- 不接入 OpenTelemetry、Prometheus、Micrometer 等通用监控框架；
- 不自动启动或控制 RenderDoc、Nsight、PIX；只提供适合外部工具识别的 label/group；
- 不实现 RenderGraph texture 像素预览。深度、MSAA、HDR、cubemap 和 sRGB 预览需要单独的可视化策略，后续另立计划；
- 不实现 shader 热重载、运行时 shader 编辑或 shader permutation 浏览器；
- 不增加全局 service locator、静态 `Diagnostics.get()` 或任意线程可写的事件总线；
- 不把每条 draw command、每个 uniform 或每个场景对象复制进逐帧快照；
- 不要求 release build 完全移除所有计数器；应通过关闭采集使成本可预测且足够低；
- 不把 JVM allocation profiler、JFR parser 或 native GPU debugger 重新实现进框架；
- 不为诊断需求扩大 stable API。新增入口默认归类为 `advanced`，内部 DTO 优先 package-private 或嵌套只读类型。

## 3. 架构判断与约束

### 3.1 保持现有分层

```text
demo/application
  -> diagnostics UI composition
  -> subsystems (render3d, postprocess, ui)
  -> runtime diagnostics aggregation
  -> core graph/profile contracts
  -> backend GL message/resource/query facts
```

允许的依赖方向：

- backend 只生产 OpenGL 事实，不依赖 runtime、UI 或 Demo；
- core graph 可以消费 backend timer/query，但不依赖 UI；
- runtime 汇总 core/backend 的只读快照，不依赖具体 Demo；
- diagnostics panel 位于 UI subsystem 或 Demo 组合层，消费只读诊断接口；
- Demo 负责输入快捷键、面板附加和导出路径，不承担统计计算。

禁止的设计：

- `GlDebug` 直接创建 UI node；
- `RenderGraph` 持有 `UiSystem` 或文件 exporter；
- UI 通过 reflection、native id 或向下转型读取 backend 内部状态；
- resource tracker 强引用真实 `GlResource`，从而改变其生命周期；
- exporter 在 OpenGL callback 或 render pass 内执行磁盘 I/O；
- 为“方便调试”新增生产 `CommandBuffer.custom()` 或裸 `glGet*` 旁路；
- 诊断开关改变 pass 顺序、attachment 格式、shader variant 或最终像素。

### 3.2 Owner 与线程合同

- `FrameDriver` 是运行时诊断聚合器的 owner；关闭 driver 时停止采集并释放历史引用；
- `RenderGraph` 继续拥有 pass timer 和 target，只发布不可变描述；
- backend resource tracker 按当前 GL context 隔离，仅保存值类型元数据，不拥有资源；
- GL debug callback 只做有界事件入队和日志映射，不调用用户代码；
- 诊断快照在 render thread 的帧边界发布，读者只能读取不可变对象；
- exporter 消费已经冻结的快照，不读取活跃 graph/backend 对象；
- UI update 可以持有最近快照引用，但不能阻止有界历史淘汰旧帧；
- `close()` 幂等；部分初始化失败时按逆序关闭 UI/export worker 等已创建 owner。

### 3.3 采样层级

诊断配置固定为三个层级，避免几十个互相矛盾的 boolean：

| 层级 | 内容 | 默认用途 |
| --- | --- | --- |
| `OFF` | 保留现有必要错误检查，不写帧历史，不跟踪诊断资源元数据 | 性能对照、正式运行 |
| `BASIC` | 帧时间、pass timing、present、draw/instance、state cache、严重 GL 消息 | Demo 默认 |
| `DETAILED` | BASIC + RenderGraph target、资源清单、主要 subsystem 统计、完整允许严重度消息 | 人工诊断 |

层级在创建 `FrameDriver` 或 diagnostics session 时确定。v0.15 不承诺运行中改变采样层级；面板隐藏只停止 UI 更新，不隐式改变底层数据合同。需要运行时切换时后续再设计明确的 reset/epoch 语义。

## 4. 数据合同

### 4.1 GPU timing 样本必须有身份

当前 `GpuTimer` 的 8-slot query ring 保持非阻塞，但内部结果至少要记录：

```text
submissionSequence   该 query 被提交的单调递增序号
resultSequence       最近完成结果对应的提交序号
elapsedNanos         最近完成的值
available            是否至少得到过一个结果
skippedSubmissions   ring 被 GPU 占满时跳过的样本数
```

`RenderGraph` 为每次 execute 分配单调递增 `frameSequence`，并将 query 结果映射为 pass timing sample。公开快照必须明确区分：

- `PENDING`：已提交但尚无任何可用结果；
- `AVAILABLE`：具有已完成结果；
- `SKIPPED`：本次因 query ring 满而没有提交；
- `UNSUPPORTED`：平台或配置不支持该计数；
- `FAILED`：本帧在形成有效结果前失败，仅用于诊断，不伪装为零。

当状态为 `AVAILABLE` 时同时返回：

- `gpuNanos`；
- `sampleFrameSequence`；
- `sampleAgeFrames = currentFrameSequence - sampleFrameSequence`。

要求：

- 不等待 query 完成；禁止 `GL_QUERY_RESULT` 的阻塞读取；
- ring 满时丢弃采样而不是阻塞渲染；
- `sampleAgeFrames` 不得为负；
- 旧结果可以继续显示，但必须显示年龄；
- UI 用 `pending`、`skipped` 或 `N/A`，不得把未知显示为 `0.000 ms`；
- `FrameProfile.totalGpuNanos()` 只累加 `AVAILABLE` 样本；同时提供完整性标记，避免把不完整总和误认为整帧 GPU 时间。

兼容策略：

- 保留现有 `PassProfile(String, long, long)` 构造方式供迁移期使用；
- 新字段通过附加构造器、嵌套 timing value 或新 diagnostics DTO 表达，不能无提示改变旧 getter 含义；
- `FrameProfile` 和 `PassProfile` 仍为 advanced API；若签名调整，必须更新 allowlist baseline 和 migration note；
- backend query 细节不提升为 stable API。

### 4.2 统一帧快照

建议新增 `runtime.diagnostics` 包，公共面保持小而完整：

```java
public enum DiagnosticsLevel { OFF, BASIC, DETAILED }

public final class FrameDiagnostics implements AutoCloseable {
    public DiagnosticsSnapshot latest();
    public DiagnosticsHistorySnapshot history();
    public FrozenDiagnostics freeze();
    public void clear();
}
```

以上名称是实施约束而非必须逐字照搬；如果现有类可以自然演进，应减少顶层 public 类型。核心合同是：

- `latest()` 永远返回非 null 的不可变快照；
- 未完成第一帧时返回显式 empty snapshot；
- `history()` 返回一致的只读副本或不可变 view，不暴露可变 ring；
- `freeze()` 捕获同一 epoch 下的历史、graph、resource 和 message 数据；
- `clear()` 开启新 epoch，frame sequence 不回退，累计计数按文档定义清零；
- closed 后读最后冻结值或明确失败，行为必须固定并测试；
- 不返回 JOML mutable object、LWJGL 类型、native buffer 或 live collection。

每帧快照至少包含：

| 分组 | 字段 |
| --- | --- |
| identity | epoch、frame sequence、presented frame sequence、采样层级、是否完整 |
| frame | CPU submit、present interval/FPS、可用 GPU pass 合计、GPU 合计完整性 |
| scene | draw calls、instance count、普通/实例 renderer 数量（可取得时） |
| graph | topology revision、pass 数量、每 pass timing/status/age |
| state | applied changes、avoided changes、skip ratio、custom invalidation 次数（若已有计数） |
| upload | 当帧/累计 upload bytes、queue depth、拒绝或失败数量（可取得时） |
| ui | `UiFrameStats` 摘要（UI 已附加时） |
| resource | live count、estimated bytes、created/closed delta、high-water mark |
| messages | 各严重度新消息数、累计数、dropped count |

并非每个 Demo 都能提供所有 subsystem 字段。缺失必须使用 `Optional`、状态枚举或空 section 表达，不能用负数或虚构零值。

### 4.3 有界历史

- 默认保存最近 240 个已发布帧，约覆盖 60 FPS 下 4 秒；
- 容量可以通过 diagnostics config 在创建时设置，合法范围 `16..4096`；
- 使用预分配 ring slot 或有界不可变快照数组，不使用无界 `List`；
- 历史按 frame sequence 严格递增；
- 同一 frame 只发布一次，失败帧以 failure/incomplete 状态发布或完全不发布，二者必须选定并测试；
- 推荐发布 incomplete failure frame，便于把消息、资源 delta 和最后成功帧关联起来；
- freeze 后 live ring 继续运行，但 frozen capture 不再变化；
- clear 只清 live history 和累计统计，不修改已经返回的 frozen capture；
- DETAILED 模式每帧不得复制完整资源表和全部消息。帧历史只存摘要，详细清单在 freeze 时单独截取一次。

### 4.4 RenderGraph 描述快照

在不暴露 `Pass`、`Framebuffer` 或 texture native id 的前提下，提供只读描述：

```text
GraphSnapshot
  width / height / topologyRevision / sealed
  executionOrder[]
  passes[]
    name
    directDependencies[]
    targetKind = BACKBUFFER | MANAGED | EXTERNAL
    width / height / samples
    colorAttachments[]: logicalName + RenderFormat + storageKind
    depthAttachment: logicalName/format/storageKind
    clearColor / clearDepth
```

要求：

- 快照来自 compiled plan 和 framebuffer descriptor，不重新推导另一套拓扑；
- pass 顺序与实际执行顺序完全一致；
- resize 后 width/height 和 relative target 尺寸在下一帧更新；
- fixed shadow target 继续保持固定尺寸；
- external target 不伪造 owner 或 attachment；
- imported texture 只显示逻辑名、类型和已知尺寸，不转移所有权；
- topology 未变化时复用描述快照，不能每帧重建依赖字符串集合；
- graph inspector 是只读工具，不增加 enable/disable/reorder pass 功能。

### 4.5 资源跟踪

新增 backend 内部的 context-scoped resource registry。它跟踪框架 wrapper 创建和关闭的资源事件，不接管生命周期。

资源条目至少包含：

```text
resourceSequence       与可复用 native id 无关的框架唯一序号
kind                   BUFFER/TEXTURE/FRAMEBUFFER/RENDERBUFFER/PROGRAM/VAO/QUERY/SAMPLER/OTHER
label                  截断后的稳定 debug label
nativeId               advanced/debug-only；导出可选择脱敏
createdFrameSequence
closedFrameSequence    live entry 中为空
estimatedBytes         可估算时存在，否则 unknown
ownerHint              RenderGraph pass、asset、UI atlas 等非强引用字符串
contextIdentity        进程内不透明序号，不暴露 LWJGL capabilities
```

实施要求：

- registry 只保存值，不保存 `GlResource` 强引用；
- native id 删除后条目按 resource sequence 关闭，不能因 OpenGL 复用 id 误关联；
- 重复 close 不重复减少 live count；
- 构造中途失败必须关闭已登记条目；
- 多 context 数据隔离；context 销毁时输出仍存活条目的诊断摘要；
- label 最大长度固定，拒绝无界 asset 路径或 shader source；
- estimated bytes 使用明确规则并标记“估算”，不得宣称等同驱动真实显存；
- `OFF` 模式只保留错误诊断所需最小计数，不保存逐条资源历史；
- registry 本身不调用 `glGet*` 扫描驱动对象；
- raw GL escape hatch 创建的资源不在完整性承诺内，文档必须说明。

第一版正式覆盖：

- `GlBuffer`；
- `Texture2D`、`TextureCube`；
- `Framebuffer` 及其 owned attachment；
- `ShaderProgram`；
- mesh/quad/UI renderer 持有的 VAO；
- `GpuTimer` 与 pipeline statistics query。

sampler 等尚无统一 wrapper 的对象可以记录为 known gap，但不得因此新增只为计数存在的公共 owner。

### 4.6 GL debug 消息

将 callback 消息规范化为不可变 `GlDebugMessage` 值：

- monotonically increasing sequence；
- source、type、severity、driver id；
- sanitized message；
- first/last frame sequence；
- repeat count；
- context identity；
- render phase/pass name（能从 thread-local debug group 得到时）。

消息 ring 默认 256 条，配置范围 `32..4096`。策略：

- HIGH/MEDIUM 永不因通知刷屏而优先淘汰；
- LOW/NOTIFICATION 可按 `(source,type,id,message)` 连续去重；
- 保留 repeat count 和 dropped count；
- callback 内不抛异常、不执行 exporter、不更新 UI；
- callback 的 logger 行为保持，但允许按 severity 配置 notification 是否写日志；
- 文本去除 NUL，限制长度，保证 JSON 可安全导出；
- `glDebugMessageInsert` 注入的测试消息与驱动消息走同一路径；
- 没有 debug context 或扩展不可用时返回明确 `UNAVAILABLE`，不导致 Demo 失败。

### 4.7 Debug groups 与对象 label

- 每个 RenderGraph pass 执行边界使用正式 command opcode push/pop debug group；
- push/pop 必须平衡，pass callback 抛异常时在 `finally` 中恢复；
- command stream 不使用 `custom()` 实现 group；
- label 命名统一为 `<owner-kind>:<logical-name>`，例如 `RenderGraph:Geometry.color0`；
- shader、texture、buffer、FBO、query、VAO 均使用稳定且有限长度的 label；
- debug group/label 不改变 state cache，不产生 draw/dispatch；
- 无 debug 支持时 opcode 是明确 no-op；
- 架构 guard 继续禁止新增生产 `custom()` 调用。

## 5. 诊断面板

### 5.1 组件定位

提供可复用的 diagnostics panel composition，但不新建第二个 UI 系统。面板附加到已有 `UiSystem`，并继续位于最终后处理之后。

推荐结构：

```text
DiagnosticsPanel
  Toolbar
    Live/Paused  Freeze  Clear  Export  Close
  Overview
    FPS / CPU / GPU / draw / instances / messages / live resources
    recent frame bars
  Passes
    pass name / CPU record / GPU / status / age / target
  Graph
    execution order / dependencies / attachments / dimensions
  Resources
    kind filter / live only / label / age / estimated bytes
  Messages
    severity filter / source / repeat / frame / message
```

v0.15 不要求新增通用 `Table`、`TabView` 或图表 public widget。优先使用已有 `Panel`、`Button`、`ListView`、`ScrollView`、`Label` 和 `Toggle` 组合：

- tab 是按钮组加内容 panel；
- frame history 用固定数量、复用的 panel bar 表示；
- 表格使用固定 header 和虚拟/有界行列表；
- 详情使用只读 label；
- 若现有 `ListView` 无法满足大清单，先为其补通用虚拟化能力，并单独测试，不在 diagnostics 包复制滚动实现。

### 5.2 输入与交互

- `F1` 保持主 Demo 现有 CAMERA/UI 输入切换；
- `F2` 显示或隐藏 diagnostics panel；
- 面板显示时自动进入 UI 交互模式，关闭后恢复此前输入模式；
- 快捷键不在 `TextField` 编辑或 IME composition 中抢占输入；
- `Live/Paused` 仅控制面板是否跟随最新帧，不停止底层采集；
- `Freeze` 创建不可变 capture，并使所有 tab 查看同一时间点；
- `Clear` 需要显式按钮操作，不绑定容易误触的单键；
- `Export` 只导出当前 frozen capture；若尚未冻结，先原子 freeze 再导出；
- hidden/deterministic Demo 可以通过命令行直接触发，不依赖人工按键。

### 5.3 性能与自观察

诊断面板本身也会产生 UI pass、draw 和 CPU/GPU 时间。必须避免递归误导：

- frame profile 正常包含 `UiOverlay` pass；
- Overview 同时显示“scene/total”或明确标注 total 含 diagnostics UI；
- 当前面板渲染产生的 `UiFrameStats` 最早只能在下一帧显示；
- 面板不得尝试在本帧更新后重新布局第二次以显示自身结果；
- 文本只在显示值变化或固定刷新间隔到达时更新；
- 资源和消息列表只重建可见行，不每帧格式化全部条目；
- history bar node 数量固定并复用；
- 面板关闭时不进行行排序、格式化或 UI mutation；
- freeze 状态不继续产生 live list diff。

### 5.4 主 Demo 接入

`LearnOpenGlDemo` 是正式纵向证明入口：

- 保留现有场景、PBR/legacy、阴影、instancing、HDR、Bloom、曝光和 AA；
- 原 `LearnOpenGlOverlay` 的轻量 HUD 与动态灯控制保留；
- diagnostics panel 作为同一 `UiSystem` 下的可选 overlay，而不是创建第二个 `UiSystem` 或第二个 UI pass；
- 诊断附加不得改变 Bloom、auto-exposure、TAA history 或 final pass 拓扑；
- deterministic 模式提供参数控制显示、冻结和导出。

建议新增参数：

```text
--diagnostics=off|basic|detailed
--diagnostics-open
--diagnostics-freeze=<positive frame>
--diagnostics-export=<workspace-relative json path>
```

安全规则：

- export 路径默认限制在 `build/diagnostics/`；
- integration task 不接受任意绝对路径；
- frame 必须在有限运行帧范围内；
- `--diagnostics-export` 隐含在退出前完成 freeze/export，但不隐含 DETAILED，调用方必须明确层级；
- 参数错误在创建 window/GL context 前失败并给出具体键和值。

## 6. 冻结与导出

### 6.1 Frozen capture

一次 capture 必须来自一致边界，至少包含：

- schema version；
- engine version/build metadata；
- diagnostics level 和 epoch；
- OpenGL vendor/renderer/version 的安全字符串；
- window/framebuffer 尺寸与 AA/HDR/Bloom/exposure 配置；
- 有界 frame history；
- 当前 RenderGraph 描述；
- frozen 时的资源清单和汇总；
- frozen 时的 GL message 清单和 dropped counters；
- 各 section 的 availability 和 incomplete 原因。

freeze 不执行 `glFinish`、不等待 query、不读取 framebuffer。尚未完成的 GPU 样本保持 pending；不得为了“导出完整”破坏非阻塞合同。

### 6.2 JSON schema

- 文件顶层固定 `schemaVersion: 1`；
- 字段使用 lower camel case；
- 时间内部以整数 nanos 导出，UI 才转换为 ms；
- byte 使用整数，unknown 使用 `null`，不用 `-1`；
- enum 使用稳定大写字符串；
- map 输出顺序稳定，pass/frame/resource/message 按 sequence 排序；
- 浮点必须有限；NaN/Infinity 使 capture validation 失败；
- 使用 UTF-8 和 LF；
- 通过 Jackson streaming API 或小型内部 writer 输出，不暴露 Jackson 类型；
- 导出先写同目录临时文件，再原子 move；失败不留下伪装成成功的半文件；
- 同名文件默认覆盖仅限 `build/diagnostics`，应用自定义 exporter 的覆盖策略另行处理；
- exporter 错误返回具体路径、阶段和 cause，同时不终止 render loop；
- 默认不写绝对资源路径、用户目录、shader source 或完整 native pointer；
- `nativeId` 默认省略，可在明确 debug 配置下启用。

建议目录：

```text
build/diagnostics/
  learnopengl-frame-000120.json
```

### 6.3 确定性要求

自动化导出必须支持稳定比较：

- 允许测试注入固定 build metadata 和 clock；
- context identity 在单 capture 内稳定，但 golden comparison 可正规化；
- 不依赖 hash-map 迭代顺序；
- 不导出对象 `toString()`；
- 同一 synthetic snapshot 两次序列化字节完全一致；
- parser round-trip 测试验证必需字段、类型和顺序，不以整份大型 golden 文本锁死所有可扩展字段。

## 7. 公共 API 与兼容性

### 7.1 建议公共面

优先只增加下列 advanced 能力：

- diagnostics level/config；
- latest/history/freeze/clear 入口；
- 不可变 frozen capture 顶层入口；
- diagnostics panel 的 attach/update/close 入口（若需要让应用复用）。

其余类型优先采用：

- 顶层 capture 的嵌套 record；
- sealed/internal section；
- package-private collector、ring、formatter、export worker；
- demo source set 的命令行解析和组合代码。

### 7.2 现有类型演进

- `RenderStatistics` 保持现有统计含义，不把它膨胀成所有 subsystem 的 registry；
- `DebugOverlaySnapshot` 作为轻量 HUD DTO 保留，不强制旧调用方依赖完整 diagnostics；
- `FrameProfile`/`PassProfile` 补足 GPU availability/age 语义，但提供迁移兼容入口；
- `RenderGraph` 新增只读 description/snapshot，不暴露 `Framebuffer` 或 `Texture2D` owner；
- `FrameDriver` 提供 diagnostics 访问入口并负责帧边界发布；
- `GlDebug.enableDebugCallback()` 旧入口保留；结构化 sink/registry 为 backend 内部或 advanced；
- `GlResource.id()` 继续是 advanced native seam，不作为 diagnostics 的主身份；
- `UiSystem` 不感知 runtime diagnostics，只负责普通 retained UI。

### 7.3 API guard

- 新增 public 顶层类必须进入对应 allowlist；
- 默认分类为 `advanced`，除非有充分理由提升 stable；
- stable/advanced 签名不得暴露 LWJGL、Jackson、JNA、Yoga native 或 mutable JOML；
- diagnostics UI 不得成为 core/runtime 的依赖；
- backend 不得依赖 diagnostics panel；
- exporter 不得反向依赖 Demo；
- 生产 `custom()` allowlist 不扩大；
- 新增 native id 读取入口必须记录到 public API migration/分类说明。

## 10. 故障与恢复合同

### 10.1 帧失败

- pass callback 抛异常时必须关闭 active GPU query/debug group；
- 本帧发布 incomplete snapshot，记录失败阶段和分类，但不吞掉原异常；
- 已完成的旧 GPU query 结果仍可保留，不归属到失败帧；
- 下一帧继续执行时 ring、state cache 和 diagnostics epoch 保持可用；
- diagnostics collector 自身异常不得掩盖主渲染异常，应作为 suppressed failure 或日志记录。

### 10.2 资源失败

- 资源 native handle 创建成功后立即登记；
- 后续初始化失败由 owner 关闭并产生 close event；
- registry 发现 context 销毁时仍 live 的条目，输出 leak summary；
- leak summary 是诊断证据，不擅自删除未知资源；
- tracker 关闭失败不应导致重复 native delete。

### 10.3 callback 与消息溢出

- callback 内任何格式化/入队失败都被捕获；
- 溢出增加 dropped counter；
- HIGH/MEDIUM 优先保留，但 ring 始终有界；
- 重复 driver notification 不得无限增加条目；
- callback 在 context close 后不得写入已释放对象；现有 callback 生命周期持有策略需要补 context cleanup 或明确进程级 owner。

### 10.4 exporter 失败

- exporter 只读取 frozen capture；
- validation、open、write、flush、move 分阶段报告；
- 临时文件在失败后删除；
- exporter worker 若存在，close 时有有界等待和超时错误；
- Demo 有限帧退出必须等待明确接受的 export 完成；
- export 失败使 diagnostics integration 失败，但不伪装成渲染失败。

## 14. v0.15 之后的自然方向

完成本版本后，不立即根据主观感受选择下一项大型功能。先使用 diagnostics 面板和一个真实多 mesh/material glTF 场景采集证据：

- 若 CPU scene traversal、draw/binding 成为主瓶颈：进入场景扩展版本，评估 batching、GPU frustum culling 和 MDI；
- 若 asset 使用体验成为瓶颈：进入 animated glTF、材质/纹理检查或 KTX2 计划；
- 若画面质量成为主需求：评估 CSM、SSAO、SSR 或更完整透明材质；
- 若 UI 工具使用证明接口稳定：逐步增加 scene/resource inspector，但仍不一次性建设单体编辑器；
- 若 RenderGraph target 调试成为主要阻力：单独规划正确处理 HDR/depth/MSAA/cubemap 的 texture preview；
- 若外部 GPU 工具工作流频繁：补 RenderDoc/Nsight capture guide 和 marker 约定，不把第三方 debugger 生命周期纳入框架。

v0.15 的价值不只是多一个面板，而是让 v0.16 之后的功能排序第一次能够由同一套可重复证据驱动。
