|---|---|

| IO 与空间 | 粒子位置是世界空间；键计算：`viewDepth = -(uView * vec4(world,1)).z`，`eyeDistance = length((uView * vec4(world,1)).xyz)`（相机在 view 空间原点，透视/正交一致）。主键为 float 的保序 uint 映射；`BACK_TO_FRONT` 用按位取反实现降序，不改变比较方向。相同键的稳定策略把“粒子在活跃列表中的位置”作为次键。std430 布局：Particle 2×vec4（32 B）、counter/indirect 4×uint（16 B）、key `uvec2`（8 B）、index uint（4 B）。 |

| 生命周期 | 构造：校验 `sorting.enabled ⇒ 1 ≤ maximumSortedParticles ≤ capacity`（并 ≤ 硬上限 1,048,576），一次性分配所需 buffer/program/VAO，任一失败逆序关闭已创建资源后抛出。`resized(newCapacity)` 沿用当前 sorting；`resized(newCapacity, newSorting)` 用于替换排序代；候选人发布后由调用方关闭旧 owner。`reset()` 语义与 #27 相同（丢弃未提交发射、游标/seed 帧归零、下一帧逐槽清零），排序 scratch 不单独 reset：每个 enabled record 先写满整个 padded scratch 再读。`close()` 幂等，关闭后 `record/emit/settings/statistics/sortingSettings/reset/resized` 抛 `GlException`。 |
| 失败 | 非法 settings/sorting/时间/aspect/容量组合在进入命令流前抛 `IllegalArgumentException`/`NullPointerException`；`sorting.enabled` 的 owner 调 4 参数 `record` 明确拒绝（需要 view 矩阵）。排序 shader 对 `activeCount` 做 `min(count, capacity)` 防御；准备 pass 对越界 active index 写哨兵而不是采样粒子存储。失败帧不做像素回滚；统计只记录已录制请求量，不含 GPU 活跃数。 |
| 独立 oracle | 测试树 `GpuParticleSortingReference`：① `stableSort` 用 Java 稳定排序独立重算 `(metric, active position)` 顺序；② `composite` 独立重算 billboard 投影、`exp(-3.5r²)·smoothstep` falloff、预乘 alpha-over 与 8-bit 量化，按给定绘制顺序合成像素。`GpuParticleSortingReferenceTest` 先用手算值验证 oracle 本身（1 个 billboard 中心 = round(color·intensity·255)，far red→near blue 与反序的精确字节）。GL 用例把 GPU 读回的 sorted index/像素与这两个参考比较，并用独立断言核对键单调性与相同键稳定性。 |
| 质量档 | 不新增内部 Low/Medium/High 分支。成本旋钮是既有 `capacity`/每帧 `emit` 与新的 `maximumSortedParticles`（排序 scratch 与 dispatch 数上界，`sortCapacity = nextPow2(max)`；step 数 = `log2(sortCapacity)·(log2+1)/2`）。默认 `disabled()`，启用由调用方显式选择；建议配置见下表，未做 GPU 性能测量，`NOT_EVALUATED`。 |

## 排序合同

1. **范围**：排序只重排同一 owner 当前 active set 的 `[0, min(activeCount, maximumSortedParticles))`
   前缀。`activeCount`、间接命令与 `glDrawArraysIndirect` 的 count 完全不变；CPU 不读、不写、
   不映射计数。
2. **键**：`VIEW_DEPTH` 与 `DISTANCE` 都用调用方 view 矩阵；float 经“保序 uint”映射后比较，
   避免浮点比较与 NaN 分支。`FRONT_TO_BACK` 直接比较，`BACK_TO_FRONT` 对主键按位取反。
3. **相同键**：`STABLE` 以活跃列表位置为次键，相同主键严格保持 update 之后发布的相对顺序；
   `UNSTABLE` 次键恒 0，合同上不承诺相同键顺序（当前网络只在严格逆序时交换，实际也会保留相对
   顺序，但这是实现细节，不作承诺）。
4. **非 2 的幂**：scratch 容量向上取到 2 的幂，`[sorted, sortCapacity)` 槽写“排在所有有效键
   之后”的哨兵主键 `0xFFFFFFFF`（保序映射后的有限键最大为 `0xFF7FFFFF`，取反后仍在有限范围，
   两个方向的哨兵都排序最后），payload 写 `0xFFFFFFFF`；draw 只读 `[0, sorted)`，越界 index 在
   vertex 阶段被放到屏外。
5. **空集合/1 个元素**：排序 step 在 GPU 上读 counter 后提前返回，不读写 scratch；CPU 无法预知
   计数，因此 step dispatch 仍入队（不新增 indirect compute dispatch 命令）。空集合的 draw
   count=0，由 GL 语义保证不产生图元。
6. **部分排序**：`activeCount > maximumSortedParticles` 时只排序前 `maximumSortedParticles` 个
   活跃索引，其余按 update 发布的活跃顺序随后绘制；sorted draw 在 shader 内按同一
   `min(activeCount, maximumSortedParticles)` 选择索引来源。该边界在 owner 构造期校验。
7. **混合**：排序启用时 draw 从 #27 的加色 `GL_ONE/GL_ONE` 切换为预乘 `GL_ONE/GL_ONE_MINUS_SRC_ALPHA`，
   因为只有顺序相关混合才能观察到排序；深度测试仍开启、深度写仍关闭。disabled 时保留 #27 的
   加色路径与未修改的 `gpu-particle-indirect.vert`。
8. **barrier**：update→prep、prep→第一个 step、每个 step 之间、最后一个 step→draw 都有
   `GL_SHADER_STORAGE_BARRIER_BIT`；最终 barrier 同时含 `GL_COMMAND_BARRIER_BIT` 以发布间接命令。

## 与 #27 / #28 / 透明队列的接线点

- **#27**：本包是同一 owner 的增量；activeCount、counter SSBO 的间接命令别名、reset/update 语义
  未改变。排序 scratch 只在 `enabled` 时分配，disabled owner 的 `storageBytes` 与命令序列仍是 #27
  的值。
- **#28 OIT**：OIT 需要消费同一 active set 但替换 blend/附件；排序索引与 OIT 是同一透明集合的
  两条互斥路线。若 OIT 接管，应使用 disabled owner（不需要排序）或让 OIT 路径忽略
  `sortedIndices`；两者不叠加。
- **透明网格交错**：`VfxRenderer` 的 CPU 快照按远到近发布 primitive；GPU 粒子 owner 只排序自己
  的活跃集合。跨 owner/网格的前后顺序仍由调用方按深度排序后**按序提交 draw**，本包不提供跨
  owner 排序，也不读取其他透明队列。
- Integrator 需要接线：在 pipeline/feature 生成期构造 `GpuParticleSortingSettings`（建议默认
  `disabled()`），在 GPU owner 线程用 `new GpuParticleSystem(settings, sorting)` 构造；每帧在
  VFX/透明阶段调用 5 参数 `record`（必须传当前 view 矩阵）；容量或排序策略变化用
  `resized(newCapacity, newSorting)` 候选替换并在代次发布后关闭旧 owner；feature 关闭时关闭
  owner。`RenderPipeline.java`、`RenderFeaturesControl.java`、`RenderFeaturePolicy.java`、
  `PipelineFeaturePolicy.java`、`gradle/focused-verification.gradle`、`build.gradle`、
  `config/gl-debug-policy.tsv`、`docs/planning/haikalat-multi-agent-status.json`、
  `docs/architecture/public-api/README.md` 本包**未修改**，由 Integrator 同步。

## 明确限制与未验证项

1. **只排序同一 owner 的活跃集合**：不解决跨 owner、跨粒子系统或与透明网格的任意交错；调用方
   必须按自己的透明顺序提交 owner。该边界是公开合同，不是后续优化项。
2. **单 owner 共享一个颜色 uniform**（#27 的 ABI）：同一 owner 内所有粒子 RGB 相同，预乘 alpha-over
   的同色合成对顺序不敏感，因此**单 owner 的排序结果在像素上不可区分**。本包用排序索引读回 +
    CPU oracle 证明单 owner 顺序；像素级前后顺序证据来自多 emitter（不同颜色）合成用例。若后续
   需要单 owner 内可观察的前后覆盖，应先扩展每粒子颜色/材质（不属于 #26 范围）。
3. **无逐帧 CPU 同步**：不读活跃计数、不读排序结果、不按计数决定 draw；统计里的
   `sortDispatches` 是录制数，不是 GPU 执行确认。
4. **部分排序**：超过 `maximumSortedParticles` 的活跃索引不参与排序，按活跃顺序随后绘制；需要
   全量排序时把上界设为 capacity。
5. **dispatch 成本**：每个 bitonic step 一次 dispatch，step 数随 `log2(sortCapacity)²/2` 增长
   （1K → 55，4K → 78，16K → 105）。本版不合并 step、不使用 shared-memory tile 或 indirect
   compute dispatch；空/1 元素只跳过 GPU 访存，dispatch 仍入队（CPU 不读计数）。
6. **UNSTABLE 的实际行为**：合同不承诺相同键顺序；当前 compare-exchange 只在严格逆序时交换，
   因此实际也会保留相对顺序，但不得作为依赖。
7. **alpha-over 语义**：启用排序即切换为预乘 alpha-over（`GL_ONE/GL_ONE_MINUS_SRC_ALPHA`），不再
   是 #27 的加色；这是可观察的行为变化，调用方必须按“排序 = 需要前后顺序的 alpha 粒子”使用。
8. 未测：真实 VFX 场景/透明队列接线、与 OIT/折射/雾/TAA/MSAA 组合、多硬件、1920×1080 预算、
   显存峰值、性能收益；`NOT_EVALUATED` 保留。

## 首轮 GL 诊断与修复（2026-11-12）

Orchestrator 首轮真实 GL：`GpuParticleSortingGlTest` 7 case 中 **6 PASS、1 FAIL**。

失败 case：`sortKeyAndDirectionSelectTheDocumentedOrder`，
`array contents differ at index [1], expected: <0> but was: <1>`。

fixture（eye 在 (0,0,3)，view 矩阵由 `lookAt` 得到；VIEW_DEPTH = `-(view*pos).z` = 3 − z，
DISTANCE = `length((view*pos).xyz)`）：

| slot | world 位置 | VIEW_DEPTH | DISTANCE |
|---|---|---|---|
| 0 | (4, 0, 0) | 3 | 5 |
| 1 | (0, 0, 0) | 3 | 3 |
| 2 | (0, 0, 2) | 1 | 1 |

独立手算（以活跃顺序 [0,1,2] 为例；活跃顺序由 update 的原子追加决定，oracle 始终用 GPU 读回的
活跃顺序作为输入，因此其它顺序下期望与实际的对应关系不变）：

- VIEW_DEPTH FRONT_TO_BACK：`[2, 0, 1]`。slot 2 最近；slot 0/slot 1 深度同为 3，stable 次键保持
  活跃顺序。
- DISTANCE FRONT_TO_BACK：`[2, 1, 0]`。slot 1 距离 3 比 slot 0 距离 5 更近，尽管两者视图深度相同。
- VIEW_DEPTH BACK_TO_FRONT：`[0, 1, 2]`。深度 3 的一组按活跃顺序在前，再 slot 2。

根因：**测试 oracle 写错，生产排序正确**。GL 测试的 `oracleOrder` helper 把
`SortKey.VIEW_DEPTH` 硬编码在内部，distance owner 的期望因此被算成 `[2, 0, 1]`，而 GPU 按
配置的 DISTANCE 正确输出 `[2, 1, 0]`，于是 index 1 期望 0、实际 1。生产 shader/owner 的键、
方向取反、stable tie、哨兵与 barrier 均无错误；其余 6 个 case（多 emitter 合成、交换发射顺序、
空/单/非 2 的幂、stable 相同键、disabled 逐字节对照、生命周期）首轮全部 PASS。

修复（**仅测试**）：

- `oracleOrder(active, positions, key, direction)` 改为显式接收 key 与 direction，删除硬编码
  VIEW_DEPTH 的便利重载；三个调用点分别传 `(VIEW_DEPTH, FRONT_TO_BACK)`、
  `(DISTANCE, FRONT_TO_BACK)`、`(VIEW_DEPTH, BACK_TO_FRONT)`。
- 三个 owner 增加 `sortingSettings().key()/direction()` 断言，防止 oracle 与 owner 配置再次漂移。
- 在测试内写入上述手算表与说明。
- 未改生产代码与 shader，三个 shader 指纹不变。

修复后 GL 尚未重跑；必须在 GPU 串行阶段重跑同一命令并核对 7 case、0 skip、索引/像素读回与
`GL_NO_ERROR`，之前仍记为 `NOT_EVALUATED`。
