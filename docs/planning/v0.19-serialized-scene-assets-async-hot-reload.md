# v0.19 序列化场景、统一资产身份、异步加载与热重载实施计划

> 状态：规划中
>
> 目标版本：`0.19.0`
>
> 基线：`0.18.3` 与 2026-07-28 的 post-release glTF/Blockbench 接入
>
> 范围：序列化场景定义、统一资产身份、异步场景加载、开发期热重载

## 1. 版本目标

v0.19 不继续横向增加渲染效果，而是把已经存在的 glTF、PBR、动画、灯光、场景提交和资源
生命周期能力连接成一条可用于真实项目的场景生产链：

```text
AssetId
  -> ResourceSource
  -> 场景 JSON 读取与验证
  -> 依赖发现
  -> 后台 CPU 解码
  -> GL 线程分阶段上传
  -> 完整 SceneVersion
  -> 帧边界原子发布
  -> generation 失效与开发期热重载
```

完成后，应用应能够通过一个逻辑 `AssetId` 请求场景，在后台完成读取、解析和 glTF CPU
解码，只在 GL 线程执行有预算的 GPU 上传，并且始终只看到“完整旧版本”或“完整新版本”。
文件修改时，新版本加载失败不得破坏仍在运行的旧场景。

本版本的核心不是“把所有东西都做成通用 AssetRegistry”，而是证明以下四个合同可以组成
可靠闭环：

1. 场景文件是版本化、可验证、无 GL 对象的不可变数据；
2. `AssetId` 是场景、glTF 及其外部依赖的唯一应用级身份；
3. CPU 工作与 GPU 工作在线程和所有权上明确分离；
4. reload 使用 generation 和帧边界发布，不允许半成品或过期结果覆盖当前版本。

## 2. 当前基线与缺口

### 2.1 已有能力

当前代码已经提供：

- `subsystems.resources.AssetId`：规范化的 `namespace:path` 逻辑身份；
- `ResourceSource`：带字节上限的 directory/classpath 字节来源；
- `ResourceGenerationTracker`：逐资产单调 generation 和过期 ticket；
- `AsyncResourceDecoder`：在虚拟线程或调用方 executor 中读取并产生 CPU 值；
- `core.assets.ResourceLocator/AssetRef`：现有 OBJ、glTF 和 Demo 的路径读取接口；
- `GltfAssetLoader`：无 OpenGL 的 glTF/GLB CPU 解码；
- `GltfSceneAsset`：GL 线程上传、局部失败回滚和显式所有权；
- `GltfRuntimeLibrary`：可被多个 glTF asset 借用的共享 GPU library；
- `Scene`、`SceneObject`、`SceneLight`：实际渲染场景；
- `UploadSystem`：跨线程收集、GL 线程 flush 的上传设施；
- `GlRenderThread`：明确的 context affinity、初始化、失败与 cleanup 合同；
- `HotReloadableShader`：证明项目已经接受“成功后替换、失败保留旧值”的开发期行为。

这些能力可以复用，不需要再建立第二套 generation、第二套路径规范或第二套 GL owner。

### 2.2 尚未闭环的部分

目前仍存在以下断点：

- `SceneAssetConfig` 是 Demo manifest，不是稳定的生产场景格式；
- `SceneAssetConfig` 同时支持行文本和 properties，两种语法不适合作为长期版本化 schema；
- `AssetRef`、`ResourceLocator` 与 `AssetId`、`ResourceSource` 并存，但没有明确主次；
- `AsyncResourceDecoder` 尚未接入 glTF 与场景实例化主路径；
- `GltfSceneAsset.upload(...)` 是一次性同步上传，不能跨帧控制大资源上传预算；
- `Scene` 支持增加 renderer，但没有面向整体场景换代的 owner；
- 没有共享 GPU asset cache，同一 glTF 被多个场景引用时可能重复上传；
- 没有依赖图，外部 `.bin`、纹理或 glTF 修改后无法确定受影响场景；
- 没有统一的 reload 状态、失败诊断和帧边界发布协议；
- classpath 与 directory source 的可变性不同，目前没有明确热重载边界。

## 3. 明确范围

### 3.1 v0.19 必须完成

- 新增一个正式的 UTF-8 JSON 场景格式 `haikalat.scene` v1；
- 场景定义至少覆盖：
  - 唯一节点 ID；
  - 可选父节点；
  - translation/rotation/scale；
  - 一个活动相机；
  - 方向光、点光和聚光；
  - glTF/GLB 静态或动画实例；
  - cast-shadows 和初始动画选择；
- 所有场景及资源引用使用 `AssetId`；
- 支持 namespace 到 `ResourceSource` 的显式挂载；
- 支持场景相对资源引用；
- 场景读取、JSON 解析、引用验证、glTF 解码在后台执行；
- GPU 创建、替换和销毁只在拥有 context 的 GL 线程执行；
- 同一个 `(AssetId, generation, load variant)` 的 glTF 只上传一份 GPU asset；
- 多个场景实例通过 lease 共享 GPU asset；
- 场景只在全部依赖、GPU asset 和实例均成功后发布；
- 支持显式 reload；
- directory source 支持可选文件监控、去抖和变更合并；
- reload 失败时继续使用旧版本；
- 旧版本只在新版本成功发布且不再被当前帧使用后释放；
- 提供结构化状态、失败、generation、队列与耗时诊断；
- 提供纯 JVM、真实 GL 和 deterministic integration 验收。

### 3.2 v0.19 明确不做

- Prefab、场景继承和实例属性覆盖；
- ECS、脚本组件、行为树或物理世界；
- 可视化场景编辑器；
- 网络场景复制、存档或运行时状态序列化；
- 自动迁移任意旧场景 schema；
- 将所有纹理、shader、字体、VFX 都立即迁入一个泛型公共 AssetRegistry；
- shader 自动热编译；现有 `HotReloadableShader` 继续独立工作；
- classpath/JAR 内容的文件监控；
- HTTP、远程 CDN、ZIP/Pak 或按需下载；
- 运行时自动保存场景；
- reload 时自动迁移任意动画、脚本或游戏状态；
- GPU culling、MDI、Vulkan 或渲染架构重写。

如果实施中发现只有引入 Prefab 或 ECS 才能继续，应停止并缩小场景 v1，而不是把这些能力
偷偷并入 v0.19。

## 4. 总体架构

### 4.1 分层

建议新增 `subsystems.scene`，作为资源与 render3d 之间的应用级编排层：

```text
subsystems.scene
  ├─ 使用 subsystems.resources 的 AssetId、generation、source
  ├─ 使用 core.assets/gltf 的 CPU decoder
  ├─ 在 GL 线程调用 subsystems.render3d.gltf 的 upload/session
  └─ 最终构建 subsystems.render3d.Scene

subsystems.resources
  ├─ 不依赖 render3d、runtime 或 OpenGL
  └─ 只负责身份、来源、代次、后台读取和 CPU 结果发布

core.assets / core.assets.gltf
  ├─ 不依赖 subsystems.scene 或 subsystems.resources
  ├─ 继续保持格式解码职责
  └─ 通过 core 层的字节解析接口接收调用方提供的数据

runtime
  ├─ 不依赖 scene subsystem
  └─ 继续只提供 frame、render thread 和 diagnostics 基础能力
```

不把场景服务放入 `runtime`，因为当前架构测试明确禁止 runtime 依赖 subsystem
orchestration。Demo 或宿主应用负责在 GL 帧开始时调用场景服务的上传和发布入口。

### 4.2 关键数据流

```text
任意线程
  SceneAssetService.open(sceneId)
             |
             v
CPU executor / virtual thread
  read scene -> parse -> validate -> discover dependencies
             |
             +----> decode glTF A
             +----> decode glTF B
             |
             v
  immutable SceneBuildPlan
             |
             v
GL thread, frame start
  pumpUploads(budget)
    -> GltfGpuUploadSession.advance()
    -> instantiate complete scene
    -> generation recheck
             |
             v
  applyReadyScenes(activator)
    -> publish new SceneVersion
    -> retire old SceneVersion
```

任意阶段发现 ticket 过期时，该阶段停止向下游发布。已经创建的 GPU 资源必须在 GL 线程
逆序关闭，纯 CPU 结果直接丢弃并允许回收。

### 4.3 RenderPipeline 激活边界

当前 `RenderPipeline` 在构造时固定持有一个 `Scene`，并且 shadow pass、PBR binder 和
RenderGraph 拓扑会读取该场景。仅仅把 `SceneHandle.current` 换成新对象不会让已经构建的
pipeline 自动渲染新场景。因此 v0.19 必须把“资产候选已完成”和“渲染管线已接受候选”分成
两个步骤，不能在两者之间释放旧版本。

建议采用 prepare/activate/commit 协议：

```text
SceneVersion candidate READY
  -> service 在 GL 帧开始 prepare activation
  -> application/pipeline 接受 candidate Scene
  -> pipeline 激活成功
  -> service commit SceneHandle.current
  -> retire old SceneVersion
```

如果 pipeline 激活失败，service reject candidate、关闭 candidate instance/lease，并继续保留
旧 scene 与旧 pipeline。

`RenderPipeline` 增加受控的 `replaceScene(Scene)`：

- 只能在 GL 帧开始、任何 draw 之前调用；
- 用 `ScenePipelineSignature` 比较 directional/point/spot shadow pass、PBR binder 等拓扑；
- signature 相同时只替换 scene、camera/light binding 和 scene-frame cache；
- signature 不同时先在局部 `PipelineGeneration` 中完整构建新 graph/shader/binder；
- candidate pipeline generation 构建成功后才一次性交换 scene 与 generation；
- 构建失败关闭 candidate generation，原 pipeline 继续可用；
- 成功交换后逆序关闭旧 pipeline generation；
- 不在 `build()` 开头先破坏当前 graph。

`SceneAssetService.applyReadyScenes(SceneActivator)` 封装上述协议。`SceneActivator` 是受控的
场景激活回调，不是任意 GPU upload escape hatch。首个 `SerializedSceneDemo` 使用
RenderPipeline activator；纯 Scene 用户可以使用只交换 Scene 的默认 activator。

## 5. 名词与不可变合同

| 名词 | 含义 |
| --- | --- |
| `AssetId` | 稳定的应用级逻辑身份，例如 `demo:scenes/showcase.scene.json` |
| generation | 同一个 `AssetId` 的单调版本；不是文件时间戳 |
| ticket | 一次异步工作的 `(AssetId, generation)` 快照 |
| variant | 会改变解码或 GPU 结果的显式加载选项 |
| asset key | 内部 cache key：`AssetId + kind + variant` |
| CPU asset | 不包含 OpenGL/native handle 的不可变解码结果 |
| GPU asset | 必须在 GL 线程创建和关闭的共享资源 |
| lease | 钉住一个确切 GPU asset generation 的所有权凭证 |
| `SceneDefinition` | 场景 JSON 的不可变 CPU 表示 |
| `SceneBuildPlan` | 已解析依赖、等待 GPU 实例化的不可变计划 |
| `SceneVersion` | 一个完整、可渲染、拥有依赖 lease 的场景代次 |
| `SceneHandle` | 应用持有的稳定逻辑场景句柄，内部指向当前 `SceneVersion` |

必须遵守：

- identity 与 version 分离；generation 不写进 `AssetId`；
- path 与 load option 分离；scene selection、strict extension 等不能拼进路径字符串；
- CPU asset 不持有 GPU wrapper；
- GPU asset 不持有后台 executor；
- lease 关闭前 GPU asset 不得关闭；
- `SceneHandle` 不允许把半构建 `SceneVersion` 暴露给应用；
- reload 只推进 generation，不原地改写已发布 asset；
- 失败状态属于某一 generation，不得污染之后的 generation；
- 同一 key/generation 的并发请求必须合并，不能重复读取和上传。

## 6. 序列化场景定义

### 6.1 格式选择

正式格式固定为严格 UTF-8 JSON：

- `format` 必须为 `"haikalat.scene"`；
- `version` 第一版必须为整数 `1`；
- 使用 Jackson Core streaming API，不增加 databind 或反射模型；
- 开启 strict duplicate detection；
- 不接受 comments、trailing comma、`NaN`、`Infinity` 或重复字段；
- 未知字段默认失败；
- 字段错误必须包含逻辑 `AssetId` 和 JSON path；
- JSON 中不保存绝对磁盘路径。

旧 `SceneAssetConfig` 的 text/properties 格式继续服务已有 Demo，但冻结功能面。新功能不得同时
扩展三种场景语法。

### 6.2 v1 示例

```json
{
  "format": "haikalat.scene",
  "version": 1,
  "camera": {
    "node": "camera-main",
    "projection": {
      "type": "perspective",
      "fovYDegrees": 60.0,
      "near": 0.1,
      "far": 500.0
    }
  },
  "nodes": [
    {
      "id": "world",
      "transform": {
        "translation": [0.0, 0.0, 0.0],
        "rotation": [0.0, 0.0, 0.0, 1.0],
        "scale": [1.0, 1.0, 1.0]
      }
    },
    {
      "id": "camera-main",
      "parent": "world",
      "transform": {
        "translation": [0.0, 2.0, 6.0],
        "rotation": [0.0, 0.0, 0.0, 1.0],
        "scale": [1.0, 1.0, 1.0]
      }
    },
    {
      "id": "zombie",
      "parent": "world",
      "transform": {
        "translation": [0.0, 0.0, 0.0],
        "rotation": [0.0, 0.0, 0.0, 1.0],
        "scale": [1.0, 1.0, 1.0]
      },
      "renderable": {
        "type": "gltf",
        "asset": "demo:scenes/gltf/zombie.gltf",
        "scene": "default",
        "animated": true,
        "initialAnimation": "run",
        "loop": true,
        "castShadows": true
      }
    },
    {
      "id": "sun",
      "parent": "world",
      "transform": {
        "translation": [0.0, 4.0, 0.0],
        "rotation": [-0.2, 0.3, 0.0, 0.93],
        "scale": [1.0, 1.0, 1.0]
      },
      "light": {
        "type": "directional",
        "color": [1.0, 0.96, 0.9],
        "intensity": 3.0,
        "castShadows": true
      }
    }
  ]
}
```

### 6.3 引用语法

资源引用只允许两种形式：

```text
namespace:path/to/asset.glb
./relative/to/scene.glb
../shared/asset.glb
```

- 带 namespace 的值通过 `AssetId.parse(...)`；
- 以 `./` 或 `../` 开头的值通过拥有者场景 `AssetId.resolve(...)`；
- 为消除“相对于资源根还是场景目录”的歧义，v1 不接受无 namespace 且不以 `./` 或
  `../` 开头的资源引用；
- relative path 可以返回场景目录的父目录，但不得越过 namespace root；
- namespace 必须已在 `ResourceCatalog` 中挂载；
- 远程 URI、绝对路径、query、fragment 和 Windows drive path 继续拒绝。

### 6.4 节点与 Transform

- `nodes` 保持 JSON 顺序，作为相同条件下的确定性实例化顺序；
- `id` 在一个场景内唯一，区分大小写，建议使用小写 kebab-case；
- `parent` 可以引用后面定义的节点；
- parent graph 必须无环；
- 未声明 parent 的节点为 root；
- 一个节点最多包含一个 `renderable` 和一个 `light`；
- v1 不公开通用 component map；
- `translation` 和 `scale` 为三个有限浮点数；
- `rotation` 为 `[x,y,z,w]` 四元数，必须有限且长度非零，解析后规范化；
- scale 的每个分量必须有限且非零；允许负 scale，但沿用现有 glTF culling 限制并给出
  diagnostics warning；
- 缺失 transform 时使用 identity；
- 父子世界矩阵只在构建 `SceneVersion` 时计算，不在 v0.19 引入通用运行时 SceneGraph。

### 6.5 相机

- v1 必须且只能声明一个活动相机；
- `camera.node` 必须引用现有节点；
- 首版正式支持 perspective；
- `fovYDegrees` 范围为 `(1, 179)`；
- `near > 0`，`far > near`；
- orthographic 可以保留 schema 位置，但未实现前必须明确拒绝，不能静默按 perspective；
- reload 后相机回到新场景定义值；
- 应用需要保留自由相机状态时，通过 reload listener 在发布后重新应用，不做隐式状态迁移。

### 6.6 glTF renderable

- `type` v1 只正式接受 `"gltf"`；
- `asset` 必须解析为 `.gltf` 或 `.glb` 的 `AssetId`；
- `scene` 接受 `"default"`、`"index:<n>"` 或 `"name:<name>"`；
- `animated=false` 时只允许静态实例；
- `initialAnimation` 只有在 `animated=true` 时合法；
- 找不到指定动画时整次场景加载失败；
- `loop` 默认 `true`；
- `castShadows` 默认 `true`，但继续遵守当前 MASK shadow 限制；
- 同一 asset/variant 可被多个节点引用，GPU asset 共享、instance 状态独立；
- scene selection 和 strict extension policy 必须进入 variant key。

OBJ、自定义 shader/material 和 builtin mesh 保留在旧 `SceneAssetConfig`。只有实际出现正式使用者
且能够纳入统一所有权后，才扩展 scene v2 或兼容的 v1 renderable type。

### 6.7 灯光

- 支持 `directional`、`point`、`spot`；
- color、intensity、range、inner/outer cone 均必须有限；
- intensity 非负；
- point/spot 的 range 必须大于零；
- directional 使用节点旋转推导方向，不在 light 中重复保存 direction；
- point 使用节点 translation；
- spot 同时使用节点 translation 和 rotation；
- 灯光数量在 parse 后按当前 shader 正式上限验证：
  - directional 不超过 2；
  - point 不超过 8；
  - spot 不超过 4；
- 阴影选择仍由现有 RenderPipeline 规则完成；
- reload 改变灯光类型、数量或 cast-shadows 时构建新的完整场景/pipeline 绑定，不调用
  `Scene.setLight(...)` 绕过拓扑限制；拓扑发生变化时通过
  `RenderPipeline.replaceScene(...)` 的 candidate generation 事务重建。

### 6.8 解析限制

建议第一版固定：

| 项目 | 上限 |
| --- | ---: |
| scene JSON 字节 | 4 MiB |
| JSON nesting depth | 64 |
| 单字符串 | 4 KiB |
| nodes | 10,000 |
| root nodes | 10,000 |
| glTF renderables | 2,048 |
| lights | 使用正式 shader 上限 |
| parent depth | 256 |
| 单场景不同 asset key | 1,024 |

限制必须在分配大集合前检查。超限错误包含 scene `AssetId`、字段和实际/允许数量。

### 6.9 验证顺序

解析后按固定顺序验证：

1. format/version；
2. 根字段和数量限制；
3. node ID 唯一性；
4. parent 是否存在；
5. parent cycle 与深度；
6. transform 数值；
7. camera 引用与 projection；
8. renderable 字段组合；
9. asset 引用语法和 namespace；
10. light 字段和数量；
11. glTF 解码后验证 scene、animation 和 MASK/shadow 合同。

同一个输入必须产生稳定的首个错误。不得依赖 `HashMap` 迭代顺序决定错误信息。

## 7. 统一资产身份

### 7.1 唯一应用级身份

`subsystems.resources.AssetId` 保持唯一正式身份，不移动包、不创建 `SceneAssetId`、
`GltfAssetId` 或字符串别名。

```java
AssetId scene = AssetId.parse("demo:scenes/showcase.scene.json");
AssetId model = AssetId.parse("demo:scenes/gltf/zombie.gltf");
```

`core.assets.AssetRef` 继续存在，但定位收紧为：

- core 格式解析器内部的局部路径/诊断值；
- 旧 `ResourceLocator` 与 Demo API 的兼容类型；
- 不作为 scene service、cache、generation 或 reload 的 key。

不在 v0.19 移动或删除 `AssetRef`，避免破坏现有 glTF、OBJ 和 Demo API。

### 7.2 ResourceCatalog

新增应用级 `ResourceCatalog`：

```java
ResourceCatalog catalog = ResourceCatalog.builder()
        .mount("engine", ResourceSource.classpath("engine", EngineAssets.class))
        .mount("demo", ResourceSource.directory("demo", demoRoot))
        .build();
```

合同：

- 每个 namespace 只能挂载一次；
- catalog 构建后不可变；
- source 必须只服务声明的 namespace；
- 查找未知 namespace 立即失败；
- 不做隐式 fallback；
- 不把磁盘绝对路径暴露到 `AssetId`；
- diagnostics 可以报告 source kind，但不得用 host path 替代逻辑 ID；
- scene service 借用 catalog，不负责关闭调用方拥有的 source，除非未来引入显式
  closeable source contract。

### 7.3 core loader 适配

为避免 `core` 反向依赖 `subsystems.resources`，在 `core.assets` 提取最小字节解析接口，例如：

```java
public interface AssetByteResolver {
    byte[] readBytes(AssetRef ref, long maxBytes);
    boolean exists(AssetRef ref);
    AssetRef resolveRelative(AssetRef owner, String uri);
}
```

- `ResourceLocator` 实现该接口；
- `subsystems.scene` 提供绑定到某个 namespace 的 adapter；
- adapter 将 core 层 `AssetRef` 转换为 `AssetId(namespace, path)`；
- adapter 记录实际读取的依赖，用于 dependency graph；
- `GltfAssetLoader` 新增接收 `AssetByteResolver` 的重载；
- 原 `ResourceLocator` 重载保留并委托，不破坏现有调用方。

这样 core 仍不知道 `AssetId`，但应用级 cache、generation 和 reload 全部使用同一个
`AssetId`。

### 7.4 asset key 与 variant

内部 cache key 至少包含：

```text
AssetId
AssetKind = SCENE | GLTF
LoadVariant
```

glTF variant 至少包含：

- scene selection；
- strict/lenient required-extension policy；
- `GltfAssetLimits` 的稳定 fingerprint；
- 影响 GPU 资源内容的选项。

不得把 diagnostics、超时、优先级等不改变资产内容的参数写进 variant。

相同 `AssetId` 使用不同 variant 时允许产生不同 cache entry；reload 一个 `AssetId` 时必须
使该 ID 的全部 variant generation 失效。

### 7.5 lease 与共享

共享 GPU asset 使用内部 `AssetLease<T>`：

- lease 绑定确切 asset key 和 generation；
- acquire/release 由 scene service 管理；
- scene node 不直接关闭 `GltfSceneAsset`；
- 最后一个 lease 释放后，该 generation 进入 retirement；
- 新 generation 可以与旧 generation 暂时并存；
- 旧 generation 有活动 scene lease 时不得强行关闭；
- service shutdown 时先关闭 scene instance，再释放 asset lease，最后关闭
  `GltfRuntimeLibrary`。

首版不把通用 `AssetLease<T>` 提升为 stable 公共 API。只有 glTF 之外出现第二个正式 GPU
asset 使用者后再评估。

### 7.6 依赖图

每次成功 CPU 解码产出不可变依赖集合：

```text
showcase.scene.json
  -> zombie.gltf
      -> zombie.bin
      -> zombie.png
  -> arena.glb
```

内部 `AssetDependencyGraph` 同时保存：

- owner -> direct dependencies；
- dependency -> direct owners；
- 记录依赖关系的 owner generation。

发布新 owner generation 时原子替换其依赖边；失败或过期结果不得修改图。

依赖变化时：

1. invalidate 直接 asset；
2. 沿 reverse edges 标记依赖它的 glTF/scene；
3. 每个受影响 key 只推进一次 generation；
4. 已打开的 `SceneHandle` 自动请求最新 generation；
5. 未打开场景只更新失效状态，不主动加载。

## 8. 异步场景加载

### 8.1 状态机

每个 scene request 使用以下状态：

| 状态 | 线程 | 含义 |
| --- | --- | --- |
| `REQUESTED` | 任意 | 已捕获 scene ticket |
| `READING` | CPU | 读取 scene JSON |
| `PARSING` | CPU | 构建 `SceneDefinition` |
| `RESOLVING` | CPU | 解析和调度直接依赖 |
| `DECODING` | CPU | glTF/图片等 CPU 解码 |
| `WAITING_FOR_UPLOAD` | 任意 | CPU plan 完整，等待 GL |
| `UPLOADING` | GL | 分阶段创建 GPU asset |
| `INSTANTIATING` | GL | 创建独立 glTF instance 和 `Scene` |
| `READY_TO_PUBLISH` | GL | 完整版本等待帧边界 |
| `ACTIVE` | GL | 当前可见版本 |
| `STALE` | 任意/GL | ticket 过期，不得发布 |
| `FAILED` | 对应阶段 | 当前 generation 失败 |
| `CANCELLED` | 任意/GL | 调用方取消且不再发布 |
| `RETIRED` | GL | 已替换，等待释放 |
| `CLOSED` | GL | 资源已释放 |

状态转换必须单调；任何终态都不得重新进入活动状态。

### 8.2 SceneAssetService

建议应用级 owner：

```java
try (SceneAssetService scenes = SceneAssetService.create(catalog, options)) {
    SceneHandle handle = scenes.open(AssetId.parse(
            "demo:scenes/showcase.scene.json"));

    while (running) {
        scenes.pumpUploads(uploadBudget);   // GL thread, frame start
        scenes.applyReadyScenes(activator); // GL thread, frame start
        handle.scene().ifPresent(scene -> render(scene));
    }
}
```

公共行为：

- `open(AssetId)` 可从任意线程调用；
- 返回稳定的 `SceneHandle`；
- 首次加载成功前 `scene()` 为空；
- `ready()` future 在首个完整版本发布后完成；
- 多次打开同一场景创建独立 scene instance，但共享 GPU asset；
- `SceneHandle.close()` 可从任意线程调用，表示不再需要该实例；实际 retirement 排队到
  GL 帧开始执行；
- `SceneAssetService.close()` 必须在 GL 线程执行；
- `pumpUploads/applyReadyScenes/close` 校验 thread/context；
- `scene()` 只能在 frame owner 线程读取，且调用方不得跨
  `applyReadyScenes(activator)` 缓存旧 `Scene`；
- service close 后所有 request/reload 入口 fail-fast。

### 8.3 CPU 阶段

CPU executor 只允许：

- `ResourceSource.read`；
- UTF-8 JSON parsing；
- schema/reference validation；
- glTF/GLB document 和 accessor 解码；
- 图片解码为 CPU pixel buffer；
- bounds、tangent、animation 和 Morph CPU 数据准备；
- `SceneBuildPlan` 构建。

CPU executor 禁止：

- GLFW/OpenGL 调用；
- `Texture2D`、`Mesh`、`Material` 或 `GltfSceneAsset` 创建；
- 直接修改已发布 `Scene`；
- 在 generation lock 中阻塞读取；
- 等待 GL future 时占用有界平台线程。

当前 glTF 图片以 encoded bytes 保留到 upload 阶段。v0.19 应将 STB 图片解码提前到 CPU，
产出带宽、高、通道、颜色空间和像素 buffer 的不可变/显式 closeable CPU 值，避免
`Texture2D.fromEncoded(...)` 在 GL 线程承担不可控解码时间。

### 8.4 并发与合并

- 默认使用 Java 21 virtual-thread-per-task executor；
- scene service 允许注入 caller-owned executor；
- 同一个 asset key/generation 只有一个 CPU future；
- 其他请求订阅同一 future；
- 不同 glTF 依赖可以并行解码；
- 单场景设置最大依赖并行度；
- 全局设置最大 queued decoded bytes，超过时施加 backpressure；
- 不允许无限缓存失败 future；
- failure 可在同 generation 被观察，但显式 retry 必须推进 generation 或清除失败 entry；
- service close 后取消未开始任务，并拒绝新任务。

建议默认值：

| 配置 | 默认值 |
| --- | ---: |
| CPU executor | virtual thread per task |
| 单场景并行依赖 | 8 |
| 等待上传的 CPU bytes | 512 MiB |
| 同时上传 session | 4 |
| 单帧上传步骤 | 8 |
| 单帧上传软预算 | 2 ms |

软时间预算只用于停止开始下一个步骤，不承诺中断已经开始的一个 GL 调用。

### 8.5 分阶段 GPU 上传

把现有 `GltfSceneAsset.upload(...)` 内部实现提取为 package-private
`GltfGpuUploadSession`：

```text
NEW
 -> SAMPLERS
 -> TEXTURES
 -> MATERIALS
 -> MESHES
 -> MORPH_BUFFERS
 -> COMPLETE
```

要求：

- 每个 `advance()` 最多执行一个或有限个明确步骤；
- 每一步只在 GL 线程执行；
- session 持有局部 rollback owner；
- 任一步失败时关闭之前创建的全部资源；
- cancel/stale 时在 GL 线程关闭局部资源；
- `finish()` 只有 COMPLETE 时返回 `GltfSceneAsset`；
- 现有同步 `GltfSceneAsset.upload(...)` 保留，内部循环 drain 同一个 session；
- 不复制两套上传实现；
- 每个步骤记录预计/实际字节和耗时；
- 超大单纹理/单 mesh 仍可能超过软预算，因此受现有 asset limits 和单资源尺寸上限约束；
- v0.19 不承诺任意大资产零卡顿，但必须消除场景 JSON、glTF 解析和图片解码造成的
  render-thread 阻塞。

不得使用公开的任意 GL callback 作为长期 API。上传 session 是 typed glTF 路径，
`UploadSystem` 继续负责已有 buffer update；两者由场景服务在 frame start 统一 pump。

### 8.6 SceneBuildPlan 与实例化

`SceneBuildPlan` 至少包含：

- scene ticket；
- immutable `SceneDefinition`；
- 稳定拓扑顺序；
- 每个 renderable 的 asset key、generation 和 transform；
- camera 配置；
- light 配置；
- 已验证 initial animation；
- 直接与传递依赖集合；
- CPU byte estimate；
- diagnostics source locations。

GL 阶段在全部 GPU lease 可获得后构建：

- 新 `Camera`；
- 新 `Scene`；
- glTF static `SceneObject` 或 animated `GltfSceneInstance`；
- `SceneLight`；
- 负责关闭 instances 和 leases 的 `SceneVersion`。

任一实例化失败时：

1. 不发布新 `Scene`；
2. 逆序关闭已创建的 scene instances；
3. 释放已 acquire 的 leases；
4. 共享 GPU asset 仅在引用归零后退休；
5. 保留旧活动场景；
6. 记录失败 phase、asset ID、node ID 和 generation。

### 8.7 取消与过期

取消是“不再发布”而不是强制线程中断：

- 未开始读取：从队列移除；
- 正在读取/解码：设置 cancelled；允许 task 尽快结束；
- 等待上传：移除 plan 并释放 CPU buffer；
- 正在上传：不在 GL 调用中途打断，步骤结束后关闭局部资源；
- READY_TO_PUBLISH：发布前再次检查 ticket，过期则退休；
- ACTIVE：关闭 `SceneHandle` 后在下一个 GL 帧边界退休。

generation 必须至少检查：

1. read 前；
2. parse/decode 完成后；
3. upload 入队前；
4. 每次 upload session advance 前；
5. SceneVersion 实例化后；
6. 原子发布前。

## 9. 开发期热重载

### 9.1 开关与来源

热重载默认关闭，仅在显式开发配置下开启：

```java
SceneAssetOptions options = SceneAssetOptions.builder()
        .hotReload(HotReloadMode.DIRECTORY_WATCH)
        .reloadDebounce(Duration.ofMillis(150))
        .build();
```

支持：

- `OFF`：生产默认；
- `MANUAL`：只响应 `reload(assetId)`；
- `DIRECTORY_WATCH`：监听可监控 directory source，并保留 manual 入口。

classpath source：

- 不启动 watcher；
- manual reload 可以推进 generation，但如果 JAR 内容未变化只会重读相同内容；
- 不伪装成可热重载来源。

### 9.2 文件监控

建议新增可选的 `WatchableResourceSource` 能力或独立 `DirectoryResourceWatcher`，不要把
`Path` 方法塞进基础 `ResourceSource`。

文件监控合同：

- watcher 只发布逻辑 `AssetId` 变更；
- WatchService event 视为提示，不视为完整真相；
- OVERFLOW 时对已跟踪文件执行一次有界 rescan；
- create/modify/delete 合并；
- 以 `AssetId` 去抖，默认 150 ms；
- 同一 burst 只推进一次 generation；
- 临时编辑器文件不进入 asset graph；
- rename-save 表现为旧文件 delete + 新文件 create，最终合并为目标 asset 变更；
- watcher thread 不读取完整 asset、不解析 JSON、不调用 GL；
- watcher close 可重复且不得遗留非 daemon 线程。

JVM 单元测试主要使用可注入 change source，不依赖真实文件系统时序。真实 WatchService
只做少量集成验证。

### 9.3 reload 传播

收到 `AssetId changed` 后：

1. 对该 ID 执行 invalidate；
2. 查询 reverse dependency graph；
3. 计算受影响的已打开 scene handles；
4. 合并重复 scene；
5. 为每个 scene 捕获最新 generation；
6. 后台构建新版本；
7. 旧版本继续渲染；
8. 新版本成功后进入 `READY_TO_PUBLISH`；
9. GL 帧开始时原子替换；
10. 关闭已不再被使用的旧实例和 lease。

如果 dependency graph 尚无该文件，例如首次创建缺失纹理，应允许失败 entry 记录
“missing dependency”反向边，使文件后来出现时能够重新触发场景加载。

### 9.4 原子发布

`applyReadyScenes(activator)` 只在 GL 帧开始、任何 scene draw 之前调用。

单个 `SceneHandle` 的发布步骤：

1. 检查 service open；
2. 检查 scene ticket 仍为 current；
3. 检查全部 asset leases 仍匹配计划 generation；
4. 调用 `SceneActivator` 准备并接受 candidate；
5. activator 成功后将 handle.current 从 old 指向 new；
6. 更新 dependency graph；
7. 更新 diagnostics/current generation；
8. 将 old 加入本帧 retirement；
9. 关闭 old instances 并释放 leases。

activator 抛出异常时不得执行第 5～9 步；candidate 按失败路径关闭，旧 handle 和 pipeline
保持不变。

因为旧场景的 draw 已在上一帧同步提交，OpenGL 对已排队使用的 object 负责延迟实际删除；
wrapper deletion epoch 会让下一次 command submission 的状态缓存失效。应用不得跨帧保留旧
`Scene`、`MeshRenderer`、`GltfSceneInstance` 或 GL wrapper。

如果未来出现跨帧缓存完整 `CommandBuffer`，必须先引入显式 fence/lease；v0.19 不支持该用法。

### 9.5 reload 失败

任何失败都遵循：

- 当前活动版本不变；
- current generation 与 failed candidate generation 分开报告；
- 不清空 SceneHandle；
- 不把部分新 renderer 加入旧 Scene；
- 不关闭旧 GPU asset；
- 关闭 candidate 已创建资源；
- 相同失败不每帧刷日志；
- 文件再次变化或 manual retry 后允许新 generation 重试；
- diagnostics 保留有限失败历史。

首个版本不自动回退到 placeholder mesh，也不静默跳过失败节点。场景完整性优先。

### 9.6 运行时状态

v0.19 不自动迁移：

- 当前动画 state/time；
- gameplay component；
- 脚本变量；
- 临时 transform；
- 粒子存活状态；
- UI 状态。

reload 后使用新定义的初始值。提供一个可选、应用侧的发布通知：

```java
onScenePublished(SceneHandle handle, long oldGeneration, long newGeneration)
```

应用可按稳定 node ID 重新应用自由相机或测试状态。场景服务本身不理解游戏语义。

## 11. 兼容与迁移策略

### 11.1 SceneAssetConfig

- 保留现有类和两种 parser；
- 文档标注为 Demo/legacy manifest；
- 不再加入动画、层级、热重载或 async 字段；
- `LearnOpenGlDemo` 可继续使用；
- 新增独立 `SerializedSceneDemo` 作为 v0.19 正式入口；
- v0.19 完成后再决定是否迁移 `PbrDemo` 或 showcase；
- 不提供自动 text/properties -> JSON runtime 转换器；
- 可以提供一个开发期一次性转换工具，但不进入主 runtime API。

### 11.2 ResourceLocator 与 AssetRef

- 保持 source compatibility；
- `ResourceLocator` 实现新的 core resolver 接口；
- 新场景服务不以它们作为 cache key；
- 现有 glTF/OBJ 测试继续通过；
- 文档明确它们是 core 格式读取兼容层，不是 generation/reload identity。

### 11.3 glTF runtime

- `GltfSceneAsset.upload(...)` 行为保持同步和 source compatible；
- 内部改为 drain `GltfGpuUploadSession`；
- `GltfRuntimeLibrary` 的 active asset lease 行为不变；
- instance 必须先于 asset 关闭；
- Morph、skin、PBR、MASK、animation graph 和 shadow 行为不得回退；
- 新异步入口不能绕开现有四阶段 upload fault cleanup 测试。

### 11.4 版本

- build metadata；

## 14. 性能与预算

### 14.1 首版性能目标

- scene JSON parse 不在 render thread；
- glTF/GLB 解析不在 render thread；
- 图片 decode 不在 render thread；
- 稳定帧没有 scene service 临时集合分配；
- 无变更时 watcher 不触发 asset read；
- 同一 asset key/generation 不重复解码或上传；
- `applyReadyScenes(activator)` 在没有 ready candidate 时为 O(1) 或 O(active handles)
  的低常数操作；
- scene reload 不触发 `glFinish` 或 GPU readback；
- diagnostics 使用有界历史。

建议报告：

| 指标 | 场景 |
| --- | --- |
| scene read/parse/validate ms | 10、1k、10k nodes |
| glTF CPU decode ms | 现有 radio/zombie/showcase |
| image CPU decode ms | 小纹理与上限附近纹理 |
| wait-for-upload ms | 冷加载 |
| GL upload step max/avg ms | 冷加载 |
| total publish latency | 冷加载与 reload |
| frame CPU p95/p99 | 加载前、中、后 |
| cache hit ratio | 重复场景 |
| decoded queued bytes | 压力场景 |
| live/retired generations | reload soak |

### 14.2 不作虚假承诺

v0.19 的“异步”表示 I/O、解析和 CPU 解码离开 GL 线程，并且 GPU 上传可分阶段调度。
它不表示单个任意大小的 `glTexStorage/glTextureSubImage` 或 mesh allocation 可以被 OpenGL
中途抢占。发布说明必须列出单资源上限和真实 p99 数据。

## 15. 诊断与错误模型

### 15.1 SceneLoadException

建议结构化 phase：

```text
READ_SCENE
PARSE_SCENE
VALIDATE_SCENE
RESOLVE_DEPENDENCY
READ_DEPENDENCY
DECODE_DEPENDENCY
QUEUE_UPLOAD
UPLOAD_GPU
INSTANTIATE_SCENE
PUBLISH_SCENE
RELOAD_WATCH
SHUTDOWN
```

异常至少携带：

- scene `AssetId`；
- 直接失败 asset `AssetId`；
- scene generation；
- asset generation；
- phase；
- JSON path 或 glTF path；
- 可选 node ID；
- 根 cause；
- suppressed cleanup failures。

不在异常中打印完整 asset bytes、绝对用户目录或纹理内容。

### 15.2 SceneAssetSnapshot

快照建议包含：

- active scene handle 数；
- 每个 handle 的 active/candidate generation；
- 当前状态与 phase；
- pending CPU requests；
- pending upload sessions/bytes；
- cache entry 数；
- live/retired GPU generations；
- asset lease 数；
- watcher mode、pending changes 和 last overflow；
- 最近一次成功/失败 reload；
- read/decode/upload/publish 耗时；
- 当前 scene renderer/light 数；
- 有界最近错误列表。

diagnostics snapshot 是不可变 CPU 值，不暴露 GL wrapper、Path、executor 或 mutable future。

## 17. 架构守卫

新增/扩展测试：

- `core` 不得 import `subsystems.scene` 或 `subsystems.resources`；
- `backend` 不得 import scene/resources；
- `runtime` 不得 import `subsystems.scene`；
- `subsystems.resources` 不得 import render3d、runtime、LWJGL 或 backend；
- `subsystems.scene` 不得直接调用 GLFW；
- OpenGL wrapper 构造只能位于 GL upload/instantiate 路径；
- watcher package 不得 import render3d/backend；
- `AssetRef` 不得成为 scene cache/generation key；
- `Path` 不得出现在 serialized scene public value；
- `SceneAssetConfig` 不得依赖新 scene service；
- 任意 GL callback 不得成为 scene service 公共上传接口；
- pipeline replacement 必须先完成 candidate generation，再关闭 active generation；
- 新 public API 必须进入分类 allowlist；
- 新 package-private cache/session 不得误进入 public catalog。

## 18. 风险与回退

### 18.1 泛型 AssetRegistry 过度设计

风险：为了“统一”提前抽象所有资源类型。

处理：

- 对外只统一 `AssetId`、source 和 generation；
- cache/lease 先服务 scene + glTF；
- 只有第二个正式 GPU asset 类型出现后才抽公共泛型接口。

### 18.2 Scene v1 变成 ECS

风险：节点 component map、脚本和任意扩展迅速扩大范围。

处理：

- v1 固定 camera/light/gltf；
- unknown field 严格失败；
- 新组件另开版本评审。

### 18.3 GPU 上传仍产生尖峰

风险：一个大 texture/mesh 步骤超过软预算。

处理：

- 图片 decode 前移；
- 分阶段 session；
- 设置单资源上限；
- 记录真实 p99；
- 若仍超门槛，再单独设计 texture tile/chunk upload，不在本版本伪装完成。

### 18.4 watcher 不可靠

风险：WatchService 丢事件、重复事件或编辑器 rename-save。

处理：

- event 只是失效提示；
- debounce/coalesce；
- overflow rescan；
- manual reload 永远可用；
- 发布门禁以 manual deterministic reload 为主，watcher 做补充。

### 18.5 generation 与 lease 竞态

风险：旧结果晚到、旧 asset 过早关闭、新场景引用错误 generation。

处理：

- 六个 generation recheck 点；
- exact-generation lease；
- 帧边界发布；
- failure injection 和并发测试；
- 不在工作线程关闭 GPU asset。

### 18.6 热重载破坏运行状态

风险：开发者误以为动画和游戏状态会自动迁移。

处理：

- 文档明确 v0.19 重置到 serialized defaults；
- 提供发布通知；
- 状态迁移另立版本，不做隐式 best effort。
