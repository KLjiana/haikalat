# v0.23 Render3D 框架加固与能力扩展计划

> 状态：M0–M7 已完成；M8 发布收口尚未开始
>
> 目标版本：`0.23.0-SNAPSHOT` → `0.23.0`
>
> 基线版本：`0.22.2`（commit `3380cc3`）；glTF AnimationSet 已独立提交并通过验收
>
> 版本主题：稳定 Render3D 内部合同，同时补齐透明材质、深度解析、阴影与可见性链路

## 1. 版本定位

v0.23 不是一次渲染器重写，也不以堆叠新抽象为目标。它把接下来最重要的两件事合并为一个版本：

1. **Render3D 框架加固**：明确场景变更、帧快照、缓存失效、管线代次、资源所有权和失败恢复合同，降低继续扩展时的隐式耦合。
2. **Render3D 能力扩展**：在已有 PBR、glTF、RenderGraph、阴影、MSAA、Fog 和后处理基础上，补齐真正影响现代 3D 场景表现与可用性的纵向链路。

本版本的核心判断是：当前项目不是缺少更多顶层名词，而是几个已有能力没有形成完整合同。例如通用材质已经支持 `OPAQUE / ALPHA / ADDITIVE`，但普通 3D 透明物体没有基于相机深度的稳定排序；glTF 已支持 `OPAQUE / MASK`，但仍拒绝 `BLEND`；Fog 和 MSAA 都存在，但因为缺少 depth resolve 不能同时启用；级联阴影已有规划对象，但尚未成为正式渲染链路。

因此，v0.23 应当先把这些断点接通，再讨论 deferred、GPU-driven 或更复杂的材质模型。

## 2. 当前能力与主要缺口

### 2.1 已有基础

- `RenderPipeline` 已统一管理普通场景、阴影、后处理、窗口目标和嵌入式目标。
- `SceneFrameBuilder` 已具备相机裁剪、普通/阴影队列构建以及部分 revision 缓存。
- `Scene` 已区分 membership 与 lighting revision，`Transform`、外部相机也具有 revision。
- 通用 `Material` 已有 blend mode、depth test、cull mode 和对应状态映射；depth write 当前由 blend mode 派生，不是独立材质属性。
- PBR/IBL、glTF 静态资产、动画、Fog、Bloom、TAA、MSAA、自动曝光等能力已经存在。
- 单方向光、单点光和单聚光灯阴影链路可用，并已有 `DirectionalCascadePlan`。
- RenderGraph 已具有资源生命周期、resize 和 profiling/preview 基础。
- CPU frustum culling 和稳定 render queue 已经证明能承担当前规模场景。

### 2.2 v0.23 必须解决的断点

| 领域 | 当前状态 | v0.23 目标 |
| --- | --- | --- |
| 场景变更 | revision 已存在但粒度不完整 | 明确 membership、transform、lighting、material/render-state、camera、topology 六类变更 |
| 管线生命周期 | `RenderPipeline` 同时承担策略、构建、缓存和执行 | 保留公共门面，拆出 package-private 的帧状态与代次对象 |
| 普通透明物体 | blend 状态存在，ALPHA 队列仍主要依赖提交顺序 | 建立透明队列合同并进行稳定的 back-to-front 排序 |
| glTF 透明材质 | `BLEND` 被拒绝 | 正式支持 `alphaMode: BLEND`，接通 PBR alpha |
| MASK 阴影 | MASK 材质目前不能投射阴影 | 增加 alpha-cutoff shadow depth 路径 |
| Fog + MSAA | 两者不能同时使用 | 增加显式 depth resolve，并让 Fog 读取单采样深度 |
| 方向光阴影 | 单图可用，cascade 只停留在计划层 | 接入可选的 2–4 cascade atlas 路径并稳定矩阵 |
| 可见性 | O(N) CPU 扫描可用，缺少结构化指标 | 先补指标与失效合同，满足门槛后才引入空间索引 |
| 诊断 | 能看到 pass 和资源，难以解释“为什么重建/重排” | 输出队列、缓存、代次、resolve 和阴影选择原因 |

## 3. 目标与非目标

### 3.1 版本目标

- 在不破坏现有公共 Render3D 使用方式的前提下，形成可验证的内部生命周期合同。
- 让相同输入得到确定的队列、排序、pass 计划和资源代次结果。
- 支持普通 3D 与 glTF PBR 的有序 alpha blending。
- 支持 glTF MASK 材质正确写入 shadow depth。
- 允许 Fog 与 MSAA 同时启用，且 resize、嵌入式渲染和失败恢复行为一致。
- 将方向光级联阴影从“数据计划”推进为可选、可测试、可诊断的正式能力。
- 建立足够的观测与性能数据，为 v0.24 是否引入更高级可见性或光照架构提供依据。

### 3.2 明确不做

- 不引入 Vulkan、第二渲染后端或 Gradle 多模块拆分。
- 不改为 deferred renderer，不新增 G-buffer 主路径。
- 不做 GPU-driven culling、indirect draw、mesh shader 或 bindless 总重构。
- 不引入 ECS，也不把 `Scene` 改造成通用游戏世界。
- 不在第一版实现 weighted blended OIT、per-pixel linked list 或 depth peeling。
- 不实现 PBR transmission、refraction、clearcoat 等新的大材质模型。
- 不把 VFX 粒子透明管线和普通 PBR 透明材质强行合并。
- 不为了缩短文件行数拆分 `CommandBuffer` 或公共 RenderGraph API。

## 4. 架构原则

### 4.1 公共门面稳定

以下公共类型继续作为主要接入面，不因 v0.23 改变定位：

- `RenderPipeline`
- `Scene`
- `Material`
- `Mesh`
- `RenderGraph`
- `RenderDevice`

内部可增加 package-private 协作者，但不得要求现有 Demo 或宿主直接组装内部组件。

### 4.2 帧输入快照化

每帧渲染只消费一次性冻结的 frame snapshot。场景、相机或材质在快照之后发生的变更只能影响下一帧，禁止队列构建过程中读取不一致的可变状态。

建议内部数据流：

```text
Scene / Camera / Settings
          │ revisions
          ▼
RenderFrameContext（冻结输入）
          │
          ├── VisibilityFrameState
          ├── LightingFrameState
          ├── RenderQueueSnapshot
          └── PipelineFeaturePolicy
                         │
                         ▼
                 PipelineGeneration
                         │
                         ▼
                   RenderGraph execute
```

### 4.3 代次替换必须事务化

RenderGraph 或 framebuffer 拓扑变化时，必须遵守 candidate-first：

1. 根据冻结设置创建 candidate generation。
2. 完整校验资源、pass、attachment 和兼容性。
3. candidate 成功后原子切换 active generation。
4. 最后释放旧 generation。
5. candidate 失败时释放 candidate，旧 generation 继续可用。

任何 resize、MSAA、Fog、cascade 数量或嵌入式目标变化都不得先销毁当前可用管线。

### 4.4 能力必须沿纵向链路完成

每项新能力都需要同时覆盖：

- 资产/配置解析；
- CPU runtime 表达；
- 队列分类和排序；
- shader 与 GPU 状态；
- RenderGraph 资源和 pass；
- resize/close/失败恢复；
- 诊断与自动化测试；
- 能力矩阵与限制说明。

只有完成整条链路才可在 capability matrix 中标为完整。

## 5. 场景 revision 与缓存失效合同

### 5.1 revision 域

内部至少区分以下 revision，不要求全部暴露为公共 API：

| Revision | 典型变化 | 必须失效的内容 | 不应失效的内容 |
| --- | --- | --- | --- |
| membership | 增删 renderer、启停对象 | 可见性集合、普通/阴影队列、场景 bounds | shader/target generation |
| transform/model | 位置、旋转、缩放、蒙皮或 morph bounds | 对象 bounds、裁剪结果、透明深度键、阴影 caster queue | 材质分类 |
| lighting | 光源增删、参数或 shadow flag 变化 | light selection、shadow view/projection、lighting upload | 普通对象材质分类 |
| material/render-state | blend、alpha cutoff、cull、shader 变体、castShadow policy | queue class、pipeline state key、shadow caster 分类 | transform bounds |
| camera | view/projection、viewport、near/far | frustum、透明排序键、cascade splits | membership |
| topology/settings | MSAA、Fog、TAA、HDR、目标尺寸、cascade 数量 | PipelineGeneration / RenderGraph | Scene membership |

### 5.2 失效规则

- revision 比较只负责判定“输入是否变化”，不能替代对象生命周期校验。
- cache key 必须由稳定 ID、revision 和显式配置组成，不使用 `identityHashCode` 作为跨帧语义。
- 同一 revision 域一次变化只触发一次 epoch 递增，避免批量导入对象时反复重建。
- hot reload 或异步场景替换必须生成新的 asset generation，不得复用旧对象 revision 冒充相同内容。
- revision 溢出按“不相等即失效”处理，不依赖大小比较。

### 5.3 建议内部对象

- `SceneRevisionSnapshot`：冻结六类 revision。
- `FrameInvalidation`：描述本帧失效位和原因。
- `RenderQueueSnapshot`：冻结分类后的 renderer 引用、排序键和稳定序号。
- `ShadowCasterSnapshot`：冻结可投影对象及其 alpha policy。

这些类型优先保持 package-private；只有出现独立消费者后再评估公共化。

## 6. RenderPipeline 内部收敛

### 6.1 拆分目标

`RenderPipeline` 继续是公共 facade，但不再直接保存所有临时状态和每类策略。建议拆出：

| 内部类型 | 职责 |
| --- | --- |
| `PipelineTopology` | 由设置、目标尺寸、sample count、cascade 配置生成稳定 topology key |
| `PipelineGeneration` | 独占某一代 RenderGraph、targets、framebuffers 和 pass resources |
| `RenderFrameContext` | 本帧不可变相机、scene revisions、viewport、时间和 settings |
| `LightingFrameState` | 本帧光源选择、shadow light、cascade 矩阵和 revision |
| `VisibilityFrameState` | frustum、可见集合、剔除统计和透明深度键 |
| `PipelineFeaturePolicy` | 统一决定 Fog/MSAA/TAA/HDR/透明/阴影组合是否合法 |
| `Render3dDiagnostics` | 汇总队列、缓存、重建和 pass 原因，不直接执行 GL |

### 6.2 边界要求

- 纯规划对象不得调用 OpenGL。
- GL 资源只能由 `PipelineGeneration` 或明确的 owned resource 持有。
- `RenderPipeline.close()` 幂等；candidate、active、retired generation 的所有权清晰。
- pass callback 不得长期捕获旧 generation 或旧 scene renderer。
- 旧 generation 只有在不再被本帧命令引用后才释放。
- embedded borrowed target 仍由宿主持有，管线只持有经过验证的借用描述。

### 6.3 拓扑重建与每帧更新分离

需要重建 generation 的变化：

- framebuffer 尺寸或 sample count；
- HDR attachment format；
- Fog depth resolve pass 的有无；
- TAA history target 结构；
- cascade atlas 尺寸或 cascade 数量；
- 嵌入式目标描述变化。

只需更新 frame data 的变化：

- 相机矩阵；
- 灯光参数；
- 透明排序结果；
- cascade split 距离与矩阵；
- 材质 uniform/texture 内容；
- scene renderer 的可见性。

## 7. 透明材质与 Render Queue 合同

### 7.1 复用已有 BlendMode

不新增与 `BlendMode` 重复的公共 alpha 模型。内部将材质归类为：

- `OPAQUE`：不混合，depth test 开启，depth write 开启。
- `MASKED`：alpha cutoff/discard，depth test 开启，depth write 开启。
- `TRANSPARENT_ALPHA`：straight alpha，depth test 开启，depth write 关闭。
- `TRANSPARENT_ADDITIVE`：加法混合，depth test 开启，depth write 默认关闭。

`MASKED` 是渲染队列分类，不要求扩展通用 `BlendMode`；它可由 PBR/glTF material 的 alpha mode 派生。

### 7.2 队列阶段

建议正式队列顺序：

1. Shadow casters；
2. Opaque；
3. Masked；
4. Sky/background；
5. Transparent alpha；
6. Transparent additive；
7. Postprocess；
8. UI/overlay。

如果现有 sky 或 VFX pass 布局不同，可以保留 pass 边界，但普通 3D 透明对象必须在不透明深度完成后绘制，并在后处理输入确定之前完成 HDR 合成。

### 7.3 排序合同

- OPAQUE/MASKED：优先稳定 pipeline/material/mesh key，允许前到后深度作为次级优化。
- TRANSPARENT_ALPHA：以 camera-space depth 或视线方向投影距离进行 back-to-front 排序。
- 相同深度键必须用稳定 insertion ID/renderer ID 打破平局，结果不得随 JVM 地址变化。
- ADDITIVE：默认保持稳定提交顺序；只有基准证明有效时才按状态批次重排。
- 动画、transform 或 camera revision 变化必须使透明深度键失效。
- bounds center 作为第一版排序点；大型交叉透明 mesh 的排序误差应记录为已知限制。

第一版不承诺物体内部三角形排序，因此复杂毛发、玻璃壳层和互相穿插透明面仍可能需要内容侧拆 mesh。

### 7.4 状态合同

- alpha blending 第一版统一采用 straight alpha：`SRC_ALPHA / ONE_MINUS_SRC_ALPHA`。
- depth test 开启、depth write 关闭，不能由提交顺序偶然决定。
- cull/double-sided 继续遵循材质配置；glTF `doubleSided` 不得被透明路径覆盖。
- 透明对象不能写入 velocity/history-validity，除非 TAA 路径明确支持其 motion policy。
- 状态切换必须经过现有 pipeline state cache，禁止 pass 内散落裸 GL 开关。
- 透明 pass 结束后状态必须可预测地恢复，不能污染 VFX/UI。

### 7.5 glTF `BLEND`

- `GltfAlphaMode` 增加 `BLEND`。
- decoder 不再拒绝合法的 `alphaMode: BLEND`。
- `baseColorFactor.a` 与 base color texture alpha 共同参与 PBR alpha。
- `BLEND` 映射至 `TRANSPARENT_ALPHA`，默认 depth write 关闭。
- 仍需保留 `OPAQUE` 忽略 alpha、`MASK` 按 cutoff discard 的 glTF 语义。
- 导入报告应记录 alpha mode、double-sided、shadow policy 和不支持的扩展。
- transmission/refraction 不因支持 BLEND 而被视为已实现。

### 7.6 阴影 policy

- OPAQUE：正常写入 shadow depth。
- MASKED：使用带 base-color alpha 与 cutoff 的 shadow shader，正式允许投射阴影。
- BLEND：v0.23 默认不投射阴影，不允许静默按 opaque 写深度。
- 若未来需要透明阴影，应增加独立 policy 和验收，不在本版本用平均 alpha 近似。

## 8. MSAA Depth Resolve 与 Fog 闭环

### 8.1 目标

当主场景使用 MSAA 时，将 multisampled depth 显式解析为单采样 depth texture，供 Fog 和其他只读深度后处理使用，从而移除 Fog + MSAA 的当前互斥限制。

### 8.2 设计要求

- RenderGraph 中显式表达 `depth-msaa → depth-resolved`，不得在 Fog pass 内隐式执行。
- resolve 资源必须校验 format、extent、sample count 和使用阶段。
- resolved depth 与窗口相关 target 同步 resize。
- fixed-size shadow target 不因窗口 resize 重建。
- 非 MSAA 路径直接复用单采样 scene depth，不创建无意义的 resolve pass。
- embedded target 若不能提供可解析 depth，必须在构建 generation 时给出明确错误。
- resolve 完成后由 graph barrier/依赖保证 Fog 读取有效数据。

### 8.3 第一版范围

- 优先支持框架当前使用的 depth format 和 sample count。
- 使用 framebuffer depth blit 或已验证的等价路径，不引入通用“采样任意 multisample depth texture”抽象。
- 若驱动对特定 depth format 的 blit 有限制，应在 topology validation 阶段失败，而不是运行到 Fog pass 才报 GL error。

### 8.4 与后处理的顺序

建议顺序：

```text
Shadow → Opaque/Masked MSAA → Transparent → Color Resolve
                              └────────────→ Depth Resolve
Resolved HDR + Resolved Depth → Fog → TAA/Bloom/Exposure/Tone Mapping → UI
```

实际 TAA 与 Fog 先后需沿用当前项目已经验证的颜色空间合同；无论最终顺序如何，depth resolve 必须是独立、可诊断、可测试的 graph 节点。

## 9. 阴影系统加固与级联方向光

### 9.1 现有阴影加固

- shadow light selection 必须只由 lighting revision、camera revision 和 shadow settings 驱动。
- caster queue 由 membership、transform、material shadow policy 和 animation bounds revision 驱动。
- 未参与投影的普通材质变化不得重建整个 shadow topology。
- 每帧诊断应说明方向光/点光/聚光灯的选择结果和未选择原因。
- shader variant 与 attachment 状态必须在 generation 创建时完整验证。

### 9.2 MASK shadow depth

增加专用或变体化的 masked shadow depth 路径：

- 只绑定计算 alpha 所需的 texture/factor/cutoff。
- fragment shader 在 cutoff 以下 discard。
- 与主 PBR pass 使用相同 UV、texture transform 和 alpha cutoff 语义。
- 不为 shadow pass上传无关 PBR 参数。
- 缺失 alpha texture 时仍正确使用 factor alpha。

### 9.3 Directional cascades

将已有 `DirectionalCascadePlan` 接入正式管线，第一版建议：

- 支持 2–4 cascades，默认仍可关闭或保持单 cascade。
- 使用一个固定尺寸 depth atlas，避免此版本额外引入 texture-array 公共抽象。
- 2 cascades 使用 2×1 布局；3–4 cascades 使用 2×2 布局。
- split 采用 configurable practical split（uniform/logarithmic 混合）。
- 每个 cascade 对 light-space bounds 做 world-texel snapping，降低相机移动时的闪烁。
- PBR shader 根据 view depth 选择 atlas region，并在 split 邻域提供小范围 blend。
- cascade atlas 为固定尺寸资源，不随窗口 resize 重建。
- diagnostics 输出 split、atlas viewport、caster count 和矩阵稳定性信息。

### 9.4 边界

- 本版本不承诺多方向光同时投射 CSM。
- 点光与聚光灯仍遵循现有单灯选择上限，除非基准和场景需求证明必须扩大。
- 不在同一版本引入 virtual shadow map、EVSM 或光线追踪阴影。

## 10. 可见性与规模扩展

### 10.1 v0.23 必做

- 将 frustum culling 输入、对象 bounds revision 和结果缓存合同化。
- 区分“对象不可见”“无有效 bounds”“被 layer/mask 排除”“透明排序后仍可见”。
- 记录扫描数量、可见数量、剔除率、bounds 更新数、排序耗时和队列构建耗时。
- 动画/morph/skinning 更新后的 bounds 必须能显式使可见性缓存失效。
- shadow frustum/cascade caster 统计与主相机可见性分开。

### 10.2 条件性实现：CPU 空间索引

只有同时满足以下条件才在 v0.23 后半段实现 BVH/AABB tree 或类似 CPU spatial index：

- 代表场景稳定对象不少于 10,000；
- 70% 以上对象跨帧不移动；
- O(N) culling + queue scan 在代表机器上持续超过 2 ms；
- 索引维护成本小于节省的扫描成本；
- 普通、透明和 shadow caster 结果保持确定性。

若门槛不成立，本版本只交付指标、接口边界与基准结论，不为了“看起来高级”引入索引。

### 10.3 暂缓 GPU-driven

GPU culling、Hi-Z occlusion、multi-draw indirect 与 bindless 是后续独立里程碑。v0.23 只需保证现有 snapshot/queue 合同不会阻塞这些方向，不提前提交公共 API。

## 11. Render3D 诊断与可观察性

`Render3dDiagnostics` 至少记录：

- frame snapshot 的六类 revision；
- 本帧 invalidation bit 与可读原因；
- active/candidate/retired pipeline generation ID；
- topology key 及本帧是否重建；
- OPAQUE、MASKED、ALPHA、ADDITIVE 队列数量；
- 可见/剔除/缺失 bounds 数量；
- 透明排序耗时和稳定 tie 数量；
- shadow light selection、cascade 数量、各 cascade caster 数量；
- depth resolve 是否执行、源/目标 sample count 与尺寸；
- queue cache、shadow cache、pipeline cache hit/miss；
- pass callback 或 candidate build 失败阶段。

诊断默认保持低开销；详细对象列表仅在显式 capture/preview 模式下生成。不得为每帧日志创建大量字符串或集合。

GL debug 仍是发布门禁的一部分：测试退出码为 0 但出现未经白名单确认的 HIGH/MEDIUM 消息，不算验收通过。

## 13. 公共接口与兼容性

### 13.1 预期公共变化

- glTF alpha mode 增加 `BLEND` 枚举值。
- 如现有设置对象无法表达 cascade，可在 Render3D settings 中增加：
  - cascade enable；
  - cascade count（2–4）；
  - atlas size；
  - split lambda；
  - split blend range。
- 如诊断已有统一 snapshot，则只向现有结构追加 Render3D 字段，避免再建平行诊断系统。

### 13.2 不应发生的兼容性破坏

- 不要求调用方手工创建 `PipelineGeneration` 或内部 frame state。
- 不改变普通 `Scene.add/remove` 的核心使用方式。
- 不删除现有 `BlendMode`。
- 不把现有 opaque material 默认行为改成透明。
- 不改变关闭资源的所有权规则。
- 不因支持 depth resolve 要求无 MSAA 场景增加额外资源。

## 14. 测试计划

### 14.1 纯 JVM 测试

- 六类 revision 的变更与失效矩阵。
- revision 不变时 queue/graph generation 可复用。
- ALPHA back-to-front 排序、稳定 tie-break 和 camera/transform 失效。
- OPAQUE/MASKED/ALPHA/ADDITIVE 分类及状态映射。
- glTF BLEND decode、默认值、double-sided 与异常输入。
- MASK shadow policy 和所需 shader inputs。
- PipelineTopology 对 sample、Fog、尺寸、cascade 的 key 计算。
- candidate build 失败不替换 active generation。
- depth resolve descriptor 的 format/sample/extent 验证。
- cascade split、atlas viewport、texel snapping 和边界 blend 数学。
- diagnostics 的 bounded history 与 clear epoch。

### 14.2 GL smoke 测试

- opaque、masked、alpha、additive 的最终像素与 depth 行为。
- 两个和三个交叠透明对象的顺序与稳定性。
- glTF BLEND 资产主路径。
- glTF MASK 在主 pass 与 shadow map 中使用同一 cutoff。
- BLEND 默认不污染 shadow depth。
- MSAA depth resolve 后 Fog 读取正确深度。
- 非 MSAA Fog 不创建 resolve 资源。
- resize 后 color/depth resolve target 重建，shadow atlas 不重建。
- 2/3/4 cascade atlas viewport 和最终阴影采样。
- candidate generation 初始化失败、pass callback 失败和 cleanup。
- standalone 与 embedded target 的完整 close 顺序。

### 14.3 Integration 测试

- 普通基准 Demo 限定帧退出。
- 开启 glTF BLEND + MASK shadow 的内容场景。
- 4× MSAA + Fog + Bloom/TAA 的兼容组合。
- 确定性 resize，包括最小化和恢复。
- embedded borrowed target resize/replacement。
- 异步加载或 hot reload 在帧边界替换 scene generation。
- 连续切换 cascade count、Fog 和 MSAA，验证 candidate rollback。
- 多轮启动/关闭无线程悬挂、use-after-close 或 native 泄漏。

### 14.4 性能基准

- 100 / 1,000 / 10,000 个静态对象的 culling 与 queue build。
- 100 / 1,000 个透明对象的排序成本。
- 1080p 与 4K 下 4× MSAA depth resolve 成本。
- 单方向阴影与 2/4 cascade 的 CPU/GPU 增量。
- 静态相机、移动相机、少量动态对象三种 revision 场景。
- 关闭详细诊断与开启 capture 模式的开销差异。

性能底线：

- opaque-only 基准不能因透明能力产生超过 5% 的稳定回退。
- revision 不变的静态场景不应每帧重新分配队列容器或重建 shadow caster 集合。
- disabled Fog/MSAA/cascade 不应创建对应 GPU target。
- 若任何新功能无法达到基线，应允许按 feature flag 关闭，而不是拖慢默认路径。

## 17. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 透明排序仍无法处理 mesh 内部相交 | 明确第一版为 object-level sort，提供内容拆分建议，不虚假承诺 OIT |
| pipeline 拆分引入生命周期回归 | candidate-first、owner 表、失败注入和重复 close 测试先行 |
| depth resolve 驱动兼容差异 | 限定 format/sample 组合，创建时验证，GL 日志纳入门禁 |
| CSM 范围膨胀 | 限定单方向光、2–4 cascade、固定 atlas，不同时做新 shadow 技术 |
| revision 过细导致维护复杂 | 只保留能改变缓存结果的六类域，通过失效矩阵约束 |
| 空间索引提前设计 | 用明确性能门槛决定是否实施 |
| 新能力拖慢默认场景 | disabled path 零资源、低分支；opaque-only 独立回归基准 |

## 18. v0.23 之后的候选方向

完成本版本并取得真实数据后，再从以下方向选择 v0.24，不提前塞入 v0.23：

1. **高级透明**：weighted blended OIT、透明阴影或 transmission/refraction。
2. **大场景可见性**：CPU BVH、Hi-Z occlusion、GPU culling、MDI。
3. **光照规模化**：clustered/forward+ lighting、多 shadowed light。
4. **阴影质量**：EVSM、contact shadow、更智能的 cascade cache。
5. **材质扩展**：clearcoat、sheen、transmission 等 glTF/PBR 扩展。
6. **离线内容管线**：材质/mesh 预处理、shader variant 预热和缓存。

选择依据必须来自 v0.23 的 diagnostics、性能报告和真实示例，而不是仅凭功能列表。

## 19. 最终完成定义

v0.23 的成功不是 `RenderPipeline` 被拆成更多文件，而是以下事实同时成立：

- 场景、相机、材质和设置变化会精确地使正确缓存失效；
- 管线重建失败不会摧毁当前可用画面或泄漏资源；
- 普通 3D 与 glTF 透明材质具有确定、可解释的排序和状态；
- MASK 材质能够正确投射带 cutoff 的阴影；
- Fog 与 MSAA 可以在正式路径共同工作；
- 方向光级联阴影成为可选、稳定、可诊断的能力；
- 静态和 opaque-only 场景没有为新能力付出不合理成本；
- 所有结论都有自动化测试、GL 日志和性能数据支撑。

达到以上条件后，Render3D 才算从“已有很多功能”进一步进入“可以稳定继续扩展”的阶段。
