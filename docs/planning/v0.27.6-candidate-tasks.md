## 2. 候选方向对比

规模和风险为相对判断，不是工期承诺。各方案都应完成自己的生产调用、关闭／失败行为及必要验证。

| 方案 | 可见交付 | 主要复用 | 相对规模／风险 | 建议 |
|---|---|---|---|---|
| A 统一视觉控制面板与完整预设 | 在已有场景中调模块、看生效原因、保存／恢复完整配置、A/B 对照 | 0.27.4 控制器、现有 UI、VisualProfile codec 经验 | 中／中，主要风险是配置权威与异步状态 | 首选主线 |
| B 空间视觉参数混合 | 相机进出区域时曝光／Bloom／同 LUT 强度连续变化，区域可组合 | 旧 0.25.1 公式、统一配置与成功帧合同 | 中／中，主要风险是基值反馈、视图隔离与历史 | 推荐与 A 联合交付 |
| C 薄叶与 MASK 材质完善 | 同一叶片在正面、背面、背光及阴影中表现一致 | 现有 PBR、MASK、surface、shadow、glTF | 中／中高，跨多个 shader 消费者 | 想优先增加画质时替代 B |
| D 局部反射探针 | 局部室内／室外环境反射可配置，接入现有 IBL 回退 | PBR 环境预处理、IBL owner、模块开关 | 大／高，需要先明确探针来源与更新策略 | 可独立成为技术版本，不与 A+B 全打包 |
| E GPU 可见性／LOD 深化 | 指定大场景中减少不必要绘制，保持可见结果正确 | 现有 scene 队列、实例批次、MDI／Compute 基础 | 大／高，需要可比较的代表负载 | 有实际规模瓶颈再选 |
| F 真实宿主端到端整合 | 在 Minecraft 宿主中实际操作模块并确认状态、像素与生命周期 | 嵌入合同、统一控制、宿主工程 | 取决于宿主接线，跨仓库风险高 | 以近期 Minecraft 落地为目标时单独选 |

SSR、GI、云／大气、水等仍可保留在技术候选库。本次未展开算法研究或选定实现路线，不给出未经验证的性能收益与工期数字。选择 D／E 或这些方向后，先补技术卡与真实输入盘点。

## 3. 推荐组合：A + B

建议正式标题：**《0.27.6 视觉创作控制、预设与空间参数混合》**。

```text
0.27.6 推荐交付
├── 统一调参入口
│   ├── 模块树、总暂停与已有子开关
│   ├── 常用连续参数与依赖／互斥提示
│   └── requested / effective / revision / failure 展示
├── 完整作者预设
│   ├── 明确可持久化字段、版本与资源逻辑引用
│   ├── 严格解析、校验、原子保存／加载
│   └── 旧 schema 2 显式迁移与可重复 A/B 对照
├── 空间视觉区域
│   ├── 球／轴对齐盒、优先级、权重和边界混合
│   ├── EV、Bloom 强度、同一 LUT 强度
│   └── 每视图独立解析，固定基值，无逐帧反馈累积
└── 一条完整作者流程
    └── 调整 → 预览 → 保存 → 重载 → 穿越区域 → 对照结果
```

这是一个完整使用流程的版本，内部按配置、解析、UI、联合验证分批推进，不再把每个开关／效果拆成独立试点版本。

### A：控制面板与完整预设

主要落点是现有 demo／作者工具层、`RenderFeaturesControl` 和配置值类型；不让 main 依赖 demo，不在 UI 内复制依赖校验或创建 GPU 资源。

交付要求：

1. 用现有 UI 组件连接实际控制器，展示总开关和已有功能分组；无输入资源的功能显示不可用原因，不伪装为成功启用。
2. 一次编辑提交完整快照。界面区分草稿、请求、生效；旧请求失败不会覆盖新草稿，普通渲染帧也不隐式重试失败请求。
3. 盘点 `RenderFeatureSettings`、`VisualSettings` 与既有 profile 字段，定义唯一作者配置来源及兼容转换，不维护互相覆盖的两份有效配置。
4. 预设只持久化可重建的配置和逻辑资源引用，不保存 GL ID、callback、外部 IBL 对象或 owner。缺少所需资源时保留旧生效状态并解释失败。
5. 复用现有严格 codec／原子保存经验；旧 schema 2 不静默按新默认值解释。是否提升 codec 到 main 由真实库调用者决定，不为 UI 演示预造通用配置框架。
6. 暂停时 UI 仍可操作，子配置保留；恢复和加载通过统一事务进入生产路径。A/B 对照锁定必要的相机、场景时间及随机输入，避免把场景运动误当参数差异。

验收出口：实际鼠标／键盘修改至少覆盖一个标量和一个拓扑变化；保存／重载能恢复明确支持的完整作者状态；非法组合、文件损坏、资源缺失、候选失败均保留旧画面；render owner 线程与暂停语义正确。不能只验 JSON round-trip。

### B：空间视觉参数混合

承接 0.25.1 的纯 CPU 解析模型，放入 Render3D 领域内有明确职责的实现包。新包／类型命名在正式计划中确定，不重启一套模块框架。

交付要求：

1. 球／轴对齐盒、stable ID、priority、weight、blend distance 与逐字段 override；确定排序和重叠规则，保留旧计划的独立算例。
2. 每帧从全局作者基值计算，不以上一帧 resolved 输出再次混合。两个视图各自解析同一份区域定义，不能共享相机相关的有效结果。
3. 与控制器的关系必须先冻结：持久配置保存全局基值与区域定义，解析结果属于视图运行态；不能把每帧区域结果反写 requested 基值。拓扑由配置事务管理，连续结果由所属模块受控更新。
4. 参数白名单为曝光补偿 EV、Bloom intensity、同一 LUT intensity。AA／HDR、质量档、资源 ID、阴影容量不进入连续混合。
5. 区域不改变世界介质语义，不用相机越界来全局开关室内烟雾。MANUAL／AUTO 曝光补偿分别定义；未支持的组合明确拒绝。
6. 连续移动不触发逐帧 Graph 重建／GPU 资源分配；是否失效历史按输入语义判断。区域配置重载失败不改变正在使用的定义。

验收出口：独立混合算例、边界／重叠／顺序、双视图隔离，配合固定相机穿越路径的真实像素与资源计数；UI 调整、预设重载和暂停恢复使用同一有效配置合同。

## 4. 其他方案的最小完整范围

### C：薄叶材质

- 首版明确叶片参数、双面受光／背光透射语义及关闭基线，不扩展为通用 SSS、皮肤或完整材质家族。
- 覆盖 Forward、MASK、共享 surface、阴影、skin/morph 消费的一致性，不能只改善单个颜色 shader。
- 材质属性属于材质定义，不为每种叶片添加管线级全局开关；需要全局能力门控时才接统一控制。
- 选一个已有场景入口承载正／背／侧光和投影对照；必要独立参考先于主观美术结论。旧墙面条纹若影响镜头应单独定位，不混改 AO 算法。

### D：局部反射探针

- 先选定离线／预计算探针，或受控更新探针中的一种，冻结资产来源、影响区域、选择／混合、缺失回退和 PBR 消费合同。
- 必须明确 cubemap 格式、颜色空间、mip/粗糙度语义、捕获与采样先后、owner、加载失败与释放；现有全局 IBL 不等于已有局部探针能力。
- 第一个完整版本不同时承诺 SSR、动态 GI 和全场景逐帧探针更新。技术卡明确哪些遮挡／反射信息不支持。

### E：GPU 可见性／LOD

- 开工先保存代表场景的 CPU 提交、GPU 时间和绘制数量，确定瓶颈；不能仅因为 API 支持 Compute／MDI 就宣称有收益。
- 一次版本只选定遮挡剔除或 LOD 主线；保留 CPU/原路径对照、保守可见性及可诊断回退。
- Hi-Z 若成为所选算法输入，要先声明深度约定、上一帧复用、相机突变、MSAA 和 resize 规则；不能把一个没有消费者的深度金字塔当作最终功能交付。
- 这条路线若承诺加速，就必须单独安排对应正式性能验证；普通功能 PASS 不证明加速。

### F：真实宿主整合

- 先确认 HaikalatHost／目标 Minecraft 工程的当前接线及源码可用性，再决定本库和宿主分别修改什么。
- 聚焦一条真实生命周期：进入世界、执行效果切换、resize、切世界、退出；核对线程、借用附件和宿主状态恢复。
- 区分“自绘场景嵌入成功”和“对 Minecraft 世界几何施加统一效果”。若后者缺少深度、材质、法线或运动输入，列明集成缺口，不用模拟 FBO 测试替代宿主视觉。

## 5. 小型治理收尾，不再占满一个版本

以下与新功能开发并行安排，按影响与证据决定，不把整个 0.27.5 未选范围变成前置条件：

- `verify.ps1` 当前指纹采集失败可能留下 `candidateStable=null`。需要候选身份的签收应改为明确拒绝身份不可验证，并用隔离探针验证正常／异常路径。
- `-Mode Gl` 当前仍全局 `--rerun-tasks`。可收敛到强制 GL 叶子新执行，同时保留编译增量；必须保持旧 XML 不可冒充新 GPU 证据。
- 当前 `future-plans.md`／能力矩阵仍有“0.27.5 治理待实施”的旧摘要，正式确定 0.27.6 后同步这些当前入口，不改写历史运行身份。
- 按 diff 自动选测、证据缓存、test-Demo 拆分及远端 CI 不默认纳入本版。前两者需要可靠输入映射，后两者需要独立收益或环境证据。

## 6. 推荐实施与选测方式

若选择 A+B：

1. 冻结作者配置、兼容迁移和区域解析合同，盘点可序列化字段与资源引用。
2. 完成预设与纯 CPU 解析，再接真实控制器及每视图运行态。
3. 将面板和 A/B 对照接入一个现有主场景，复用组件与消费者测试。
4. 联合验证完整作者流程、失败保留、总暂停、resize 与历史；按运行身份保存结果。

遵循 0.27.5 技术卡／合同测试规则：扩展已有领域测试和现有 Demo，不为每个功能复制任务。普通定向验收默认 300 秒，按修改选择 JVM、必要 GL 和 UI 消费者；不自动叠加完整 `check`、GL 全集、性能和长测。预算不够时明确未完成项，不以截断测试换取 PASS。

本候选文档只做事实、链接与差异检查，不启动编译或 GPU。正式选择方案后再形成实施清单、具体入口、候选身份和验收 case；新渲染技术补足 0.27.5 第 8 节技术卡，未测成本写 `NOT_EVALUATED`。

## 7. 取舍结论

**默认推荐 A+B：完成从“代码能控制效果”到“作者能配置、保存并组合场景风格”的一大步。**

如果近期目标明确是新增画质，选 C 或独立的 D；如果目标是大型场景吞吐，选 E；如果目标是 Minecraft 实际交付，优先 F。以上为可选路线，不将六条主线同时承诺给 0.27.6。
