# v0.17.1 RenderGraph 资源预览与帧调试可视化实施计划

## 1. 版本定位

v0.17.1 的主题是 **RenderGraph 资源预览与帧调试可视化**。本版本不继续扩大渲染功能面，而是在 v0.15 诊断系统、v0.16 场景可见性和 v0.17 真实场景提交路径稳定之后，补齐开发渲染效果时最缺少的一块观察能力：在程序内部安全地查看 RenderGraph 中间结果，并解释资源的格式、尺寸、生命周期和生产关系。

这不是 RenderDoc 的替代品，也不是可编辑 RenderGraph。它解决的是高频、低摩擦的日常问题：

- 阴影图是否真的写入；
- HDR、Bloom、自动曝光各阶段的数值是否合理；
- resize 后目标是否重建为正确尺寸；
- MSAA resolve、深度和 cubemap 某个 face/mip 是否异常；
- 某个逻辑 attachment 当前由谁生产、采用什么格式、是否仍然有效；
- 不离开 Demo、不执行 CPU readback，就能快速定位黑屏、过曝、错误 mip 和错误依赖。

版本目标为 `0.17.1`。v0.17.1 应当保持项目的单 OpenGL 后端定位，并继续遵守现有 diagnostics、资源所有权、RenderGraph 和异步渲染线程契约。

## 2. 实施前基线

开始本版本前必须满足以下条件：

- v0.17 的 MaterialInstance 隔离问题已经修复，每个 SceneObject 的 override 不会污染同材质的其他对象；
- v0.17 新增的诊断接口已经按项目 API 策略归类，非必要接口不继续暴露为稳定公共 API；
- `compileJava demoClasses test` 通过；
- `localGlVerification` 在有桌面的本机通过；
- v0.17 的压力场景数据保留为性能回归基线；
- 当前 diagnostics OFF、BASIC、DETAILED 的行为和开销边界有测试保护。

若上述基线尚未满足，先修复基线，不允许把历史缺陷混入预览功能实现。

## 3. 目标

### 3.1 必须完成

1. 在现有 F2 DiagnosticsPanel 中浏览 RenderGraph pass 和 attachment，并选择一个可预览资源。
2. 支持下列资源的正确可视化：
   - 普通 LDR 与 sRGB 2D color texture；
   - HDR、单通道和双通道浮点 texture；
   - 深度 texture；
   - multisample renderbuffer 的按需 resolve；
   - 已显式注册的 cubemap face 和 mip；
   - 不可预览目标的明确原因提示。
3. 所有预览均在 GPU 内完成，生产路径禁止 `glReadPixels`、`glGetTexImage` 或同步 CPU readback。
4. UI、冻结诊断、JSON 导出和异步线程之间只传递值对象与逻辑资源键，不传递 OpenGL id、Framebuffer、Texture2D 或 TextureCube owner。
5. resize、graph rebuild、资源替换、pass 失败、窗口最小化恢复和 pipeline close 后不会出现悬空选择、use-after-close 或重复释放。
6. Diagnostics 关闭时不增加 RenderGraph pass、不增加 draw/blit、不改变最终像素，也不保留预览专用 GPU 资源。
7. 预览打开时开销有明确预算，不能破坏普通 Demo 和 v0.17 压力基线。

### 3.2 应当完成

- HDR exposure、范围、通道选择和 false-color；
- 深度线性化、近远平面和 shadow-depth 模式；
- cubemap 的六个 face 与合法 mip 选择；
- attachment 的尺寸、格式、sample count、storage kind、估算显存、producer 和下游 graph dependency 展示；
- 预览区域的缩放适配、最近邻/线性采样选择和像素坐标提示；
- 明确区分“冻结元数据”和“实时 GPU 像素”。

### 3.3 非目标

v0.17.1 明确不做：

- RenderGraph 节点编辑、拖线或运行时修改 pass 顺序；
- shader hot reload；
- 单帧 draw-call 重放；
- GPU 命令历史、pipeline state 全量抓取或 API trace；
- 导出完整纹理、截图批处理或远程 telemetry；
- 通用资源编辑器、材质编辑器或场景编辑器；
- 暴露原生 GL texture/framebuffer handle 给应用 UI；
- GPU-driven culling、Hi-Z、MDI、ECS 或第二渲染后端；
- 为了本功能拆 Gradle 多模块或重写 RenderGraph。

## 4. 现有架构判断

当前架构足以实现本版本，不需要新增通用 AssetRegistry 或重构 RenderGraph：

- `RenderGraph.Description` 已提供 pass、target、attachment、format 和 storage kind 元数据；
- `PassResources` 已能在 pass 执行期按逻辑名称解析 attachment 与 framebuffer；
- MSAA attachment 当前主要是 renderbuffer，必须通过 source framebuffer 做显式 resolve，不能假装它是 sampler2D；
- UI 已有 `UiImageId`、`UiImageResolver`、`UiImageRegion` 和 Image widget，可显示预览系统自己的普通 2D 输出纹理；
- 现有 UI shader 不负责解释 HDR、depth 或 cubemap，因此不能把任意 RenderGraph texture id 直接交给 UI；
- diagnostics snapshot 是纯值快照，不应因预览功能获得 GPU 所有权。

因此采用以下固定数据流：

```text
DiagnosticsPanel 选择逻辑资源键与显示参数
        |
        v
RenderPipeline 在 UiOverlayPass 执行期解析当前资源
        |
        v
GraphPreviewRenderer 在 GPU 上转换/resolve
        |
        v
预览系统自有的普通 sRGB 2D 输出纹理
        |
        v
现有 UiImageResolver + Image widget 显示
```

UI 永远只看到预览输出纹理，不直接持有被检查资源。被检查资源始终由 RenderGraph、PBR environment 或其原 owner 管理。

## 5. 核心数据契约

### 5.1 PreviewSourceKey

选择使用不可变逻辑键，不使用 native id。建议字段为：

- `pipelineGeneration`：RenderPipeline 重建时递增；
- `passName`：RenderGraph producer pass；
- `attachmentName`：逻辑 attachment 名称；
- `aspect`：`COLOR`、`DEPTH`、`CUBE`；
- `registeredName`：仅用于显式注册的非 graph 资源；
- `ownerGeneration`：cubemap/PBR environment 替换时递增。

普通 resize 不改变 `pipelineGeneration`，选择可在下一帧重新解析到新 texture id。pipeline rebuild、环境贴图替换或 close 会导致 generation 不匹配，选择进入 stale 状态并自动清除或显示占位符。

`PreviewSourceKey` 不承诺成为稳定公共 API。第一版保持在 render3d/diagnostics 集成边界内部；若未来至少有第二个独立调用者，再评估提取公共 inspection API。

### 5.2 PreviewSourceDescription

每个资源以纯值描述：

- logical key；
- display name；
- producer pass；
- downstream pass dependencies；
- width、height、mip count、sample count；
- internal format；
- texture/renderbuffer/cubemap storage kind；
- color/depth aspect；
- 是否可直接采样；
- 是否需要 resolve；
- 是否支持 mip/face；
- 估算显存字节数；
- availability 与不可用原因。

RenderGraph 当前只能可靠描述 pass dependency，而不能证明某个 downstream pass 一定采样了特定 attachment。UI 文案必须写“下游图依赖”，不得伪装成精确 texture consumer。

### 5.3 PreviewOptions

预览选项为不可变值对象，至少包含：

- mode：AUTO、COLOR、HDR、DEPTH、CUBE；
- channel：RGBA、RGB、R、G、B、A、RG；
- exposure EV，范围 `[-16, +16]`；
- value range min/max；
- false-color 开关；
- depth interpretation；
- near/far；
- cube face；
- mip level；
- filtering：NEAREST/LINEAR；
- checkerboard/background；
- update interval：1、2、4、8 帧。

所有输入必须 clamp 和验证。NaN、Infinity、`min >= max`、非法 face/mip 或非法 near/far 不得进入 shader uniform。

### 5.4 PreviewSummary

diagnostics 只发布一个值类型摘要：

- selected logical key；
- options；
- source available/stale/unsupported 状态；
- output dimensions；
- last successful frame sequence；
- last error code/message；
- resolve/conversion 路径；
- 本帧 draw、blit 与估算显存。

`FrozenDiagnostics` 与 JSON 可以复制该摘要，但不得包含纹理像素、GL id、owner、lambda、resolver 或 native address。

## 6. GPU 预览管线

### 6.1 独立输出目标

新增内部 `GraphPreviewRenderer`，由 RenderPipeline 创建、使用和关闭。它拥有：

- 一个普通 2D sRGB preview output texture；
- 对应 framebuffer；
- 一套专用 preview shader/program；
- 按需创建的单采样 color/depth resolve target；
- 一个小型 immutable pipeline state 描述；
- 资源 generation 与错误状态。

输出尺寸根据 UI 预览矩形保持宽高比，默认最长边 512，允许设置到 1024，但禁止跟随 4K 窗口盲目创建全尺寸副本。目标重建只发生在尺寸等级变化或格式不兼容时。

预览输出采用 sRGB 2D texture：preview shader 输出线性诊断颜色，framebuffer sRGB 转换负责写入；UI 采样时按 sRGB 解码，再按现有 backbuffer/UI 合同输出，避免重复 gamma 或遗漏 gamma。

### 6.2 执行时机

预览更新放在现有 UiOverlayPass 内、UI 正式绘制之前：

1. 根据当前逻辑 key 解析 live source；
2. 必要时执行 MSAA color/depth resolve；
3. 将 source 转换到 preview output；
4. 恢复 framebuffer、viewport、scissor、blend、depth、cull 和 sRGB 状态；
5. UiRenderer 通过现有 image resolver 采样 preview output。

不得因打开预览而改变 RenderGraph topology revision。不得动态插入新的 graph pass。所有预览命令必须发生在被检查 producer 完成之后，并且不得读取当前正在写入的 attachment。

### 6.3 防止反馈环

以下规则必须编码为验证，而不是依赖调用者自觉：

- 不能直接采样 UiOverlayPass 当前写入目标；
- backbuffer 默认不可预览，只显示 metadata 与原因；
- source texture id 与 preview output id 相同时拒绝绘制；
- source/resolve framebuffer 与 destination framebuffer 冲突时拒绝 blit；
- 未完成的当前 pass attachment 不进入 catalog；
- graph execution 失败后本帧 preview output 标为无效，不显示上一帧内容冒充当前帧。

## 7. 各类资源的显示策略

### 7.1 LDR 与 sRGB color

- RGBA/RGB 默认完整显示；
- 单通道复制到灰度；
- alpha 单独查看时显示灰度，可选择棋盘背景；
- channel mask 在 shader 中实现，不创建新的纹理；
- sRGB texture 依靠纹理格式自动解码，禁止手工重复 `pow`；
- integer、compressed 或项目尚未支持的格式必须明确标记 unsupported，禁止错误绑定到 float sampler。

### 7.2 HDR、R16F 和 RG32F

AUTO 模式按 format 选择 HDR 路径。必须支持：

- exposure EV；
- 默认轻量 tone mapping；
- raw range remap；
- 超范围高亮；
- NaN/positive infinity/negative infinity 的固定诊断颜色；
- luminance/R/RG 等通道查看；
- false-color 梯度。

预览 tone mapping 仅用于观察，不得复用或修改正式 post-process 自动曝光状态，也不得写回被检查资源。

### 7.3 Depth

深度预览提供：

- raw `[0, 1]`；
- perspective linear depth；
- orthographic/shadow depth；
- near/far range remap；
- 反转显示；
- false-color。

near/far 优先来自 producer pass 的显式 metadata；无法可靠获得时使用 UI 输入并标记为手工值。禁止从 projection matrix 猜测后把猜测结果当成事实。

第一版以项目当前非 reversed-Z 契约为准。未来若引入 reversed-Z，必须扩展明确枚举和测试，不能自动假设。

### 7.4 MSAA renderbuffer

MSAA attachment 不可直接采样。预览系统按需：

- 从 producer framebuffer blit color 到单采样 color texture；
- 从兼容 depth/depth-stencil source blit depth 到单采样 depth texture；
- depth resolve 强制 NEAREST；
- 验证尺寸、sample count、format compatibility 和 aspect；
- resolve 失败时显示错误，不回退到 CPU readback。

若现有 typed command 只能 blit color，应增加范围受控的 typed depth-resolve 命令；不得用 `CommandBuffer.custom()` 绕过状态缓存和测试守卫。

### 7.5 Cubemap

RenderGraph 当前不把 cubemap 当普通 attachment，因此只允许 owner 显式注册可借用的只读 cubemap source，例如：

- environment map；
- irradiance map；
- prefiltered environment map。

注册只提供逻辑名称、metadata、owner generation 和 render-thread resolver。所有权仍属于 `PbrEnvironment` 或原 owner。预览支持 `+X/-X/+Y/-Y/+Z/-Z` face 与合法 mip，使用 samplerCube 和明确的 face-UV 到 direction 映射。

资源替换或 owner close 后 resolver 必须立即失效。预览系统不得延长 cubemap 生命周期，也不得缓存其 GL id 到下一帧。

### 7.6 不可预览资源

以下情况显示 metadata 和具体原因：

- default framebuffer/backbuffer；
- 当前正在写入的 attachment；
- 未知、integer 或不受支持的 format；
- incomplete framebuffer；
- source 已关闭或 generation 过期；
- depth-stencil resolve 在当前驱动/格式组合下不兼容；
- 外部资源未显式注册；
- graph 尚未成功执行 producer pass。

禁止静默显示全黑，因为全黑无法区分“资源本身为黑”和“预览失败”。

## 8. UI 交互

### 8.1 DiagnosticsPanel 集成

沿用现有 F2 面板，不增加第二套调试窗口。建议布局：

- GRAPH 页：pass 树及其 color/depth attachments；
- RESOURCES 页：可搜索的资源表；
- 右侧或下方 preview pane：图像、状态和 controls；
- OVERVIEW 页：仅显示当前选择的简要状态，不强制渲染预览。

attachment row 可以键盘选择和鼠标选择。选中资源不等于开启更新；用户可单独暂停预览。

### 8.2 控件

最低控件集合：

- mode；
- channel；
- exposure；
- range min/max；
- false-color；
- depth interpretation 与 near/far；
- cube face/mip；
- nearest/linear；
- update interval；
- reset。

控件显示必须依据 source capability：普通 LDR 不显示 depth 参数，2D texture 不显示 face，单 mip 资源禁用 mip 控件。

### 8.3 Frozen 行为

冻结只冻结 telemetry、metadata、选择和显示参数，不冻结 GPU 像素。为避免误导，v0.17.1 采用以下明确行为：

- 进入 frozen 后停止更新 preview output；
- 面板显示“像素未被捕获，当前仅为冻结元数据”；
- 保留最后一次输出只能作为灰化背景，不得标注为 frozen frame；
- 导出只包含 PreviewSummary，不包含像素；
- 恢复 live 后重新解析 source，不能沿用旧 native id。

未来如果需要真正的单帧 GPU 快照，应作为独立版本设计显式 copy、显存预算和生命周期，不塞入本版本。

## 9. 生命周期与异常恢复

`GraphPreviewRenderer` 必须是明确 owner，资源释放顺序建议为：

1. 取消 UI resolver 对 preview output 的映射；
2. 关闭 resolve framebuffer/texture；
3. 关闭 preview framebuffer/texture；
4. 关闭 shader/program；
5. 清空 catalog、selection 和 error state。

必须覆盖：

- shader 编译中途失败；
- preview output 创建失败；
- color resolve 创建一半失败；
- depth resolve 失败；
- source 在选择后、绘制前失效；
- RenderGraph resize 成功与失败；
- pipeline rebuild；
- pass callback 抛异常；
- AsyncDemo shutdown timeout；
- 多次 close；
- panel close 后再打开；
- context 已失效时的清理策略。

创建中途失败要逆序关闭所有已经创建的 GL 对象。preview 失败不得使主渲染帧失败；它应记录有界诊断消息、禁用当前预览并让正式 UI/scene 继续工作。只有检测到可能破坏 GL 状态或资源所有权的内部不变量时，才允许 fail fast。

面板关闭后在渲染线程立即释放预览专用目标；关闭状态下不得长期占用显存。重复开关必须可重建且无泄漏。

## 10. 状态缓存与命令录制

- 预览绘制必须使用 typed CommandBuffer 路径；
- 新增的 depth resolve 也必须是 typed command；
- `CommandBuffer.custom()` 仍只允许现有 profiling escape hatch；
- viewport/scissor/framebuffer/blend/depth/cull/sRGB/sampler 状态必须被正确录制和恢复；
- preview conversion 禁用 depth test/write 和 blending；
- UI compositing 继续遵循 UiRenderer 的 blending 契约；
- source sampler 不得修改原 texture 的持久 sampling parameters，使用独立 sampler object 或已有安全 resolver；
- framebuffer completeness 只在创建/重建时验证，不能每帧同步查询；
- 不允许每帧调用会迫使 GPU/CPU 同步的 `glGet*`。

## 11. 资源预算与性能门槛

### 11.1 强制门槛

- Diagnostics 关闭且从未开启预览：0 个预览 GL 资源、0 draw、0 blit；
- 关闭已开启的预览后：专用资源在渲染线程释放；
- 普通 2D 预览：每次更新最多 1 次 conversion draw；UI 自身 image draw 按现有 batching 统计；
- MSAA 预览：每次更新最多 1 次 resolve blit + 1 次 conversion draw；
- cubemap 预览：每次更新最多 1 次 conversion draw；
- 生产代码中 0 CPU pixel readback；
- output 与临时 resolve 目标合计显存预算默认不超过 8 MiB；
- 预览开关、选择和 mode 改变不得改变 RenderGraph topology revision；
- 预览关闭时最终像素必须与 v0.17 基线一致；
- 预览打开时 preview rect 之外的最终像素必须一致。

### 11.2 参考性能目标

在项目记录基准机器上，以最长边 512 的输出测试五轮并报告 median：

- direct color/HDR/depth preview 增量 CPU 中位数不高于 0.15 ms；
- direct preview 增量 GPU 中位数不高于 0.25 ms；
- MSAA resolve + preview 增量 GPU 中位数不高于 0.45 ms；
- cubemap preview 增量 GPU 中位数不高于 0.30 ms；
- warm-up 后 preview 子系统每帧增量分配不高于 8 KiB；
- update interval 为 2/4/8 时，conversion/resolve 次数严格按节流下降。

这些数字是 v0.17.1 的发布门槛候选。若硬件差异导致绝对值不可比，报告绝对值和相对开销，不得删除“无 readback、命令数上限、显存上限和关闭零开销”这些结构性硬门槛。

## 12. 测试计划

### 12.1 纯 JVM 测试

- PreviewSourceKey equality/hash 与 generation 行为；
- catalog 从 RenderGraph description 生成正确资源条目；
- resize 保持逻辑选择，pipeline rebuild 使旧选择 stale；
- format 到 preview mode/capability 的映射；
- mip/face/channel/exposure/range/near/far 参数校验与 clamp；
- 显存估算覆盖常见 color/depth/MSAA/cubemap 格式；
- backbuffer、renderbuffer、unsupported format 的原因明确；
- frozen snapshot 只复制值，不复制 owner/native id；
- bounded error 去重与容量上限；
- diagnostics OFF/BASIC 不创建 preview request；
- 架构测试禁止 UI/diagnostics snapshot 依赖 backend texture/framebuffer owner；
- 架构测试继续守卫 `CommandBuffer.custom()` 生产调用集合。

### 12.2 GL smoke 测试

使用小尺寸、确定性已知图案：

- RGBA8 color 四象限颜色预览正确；
- sRGB 输入没有双重 gamma；
- RGBA16F exposure 与 range 转换输出预期像素；
- R16F/RG32F 通道映射正确；
- NaN/Infinity 使用约定诊断色；
- perspective depth 线性化边界正确；
- orthographic shadow depth 正确；

## 13. 公共 API 与兼容性

默认决策：v0.17.1 不新增稳定公共 RenderGraph inspection API。

- DiagnosticsPanel 使用逻辑值对象；
- RenderPipeline 在 UiOverlayPass 的现有执行边界内通过 PassResources 解析资源；
- cubemap 由 PBR subsystem 内部显式注册；
- UI 继续使用现有 Image/UiImageResolver，只解析 preview output；
- backend texture/framebuffer id 不进入 UI display list、FrozenDiagnostics 或 JSON；
- RenderDevice、RenderGraph、Material、Mesh 的公共定位不改变。

若实现中发现现有边界确实无法完成，允许增加一个标为 advanced/internal 的最小只读 inspection seam，但必须同时满足：

1. 不转移 GPU 所有权；
2. 不返回可跨帧保存的 raw handle；
3. 只能在 render thread 和 graph execution 有效期使用；
4. 有架构测试锁定唯一生产调用者；
5. 在 public API inventory 中分类并记录弃用/演进策略。

不得为了省事直接添加 `getTextureId(name)`、`getFramebufferId(pass)` 之类稳定公共 getter。

## 15. 推荐代码落点

最终名称可按现有命名调整，但职责应保持：

- `subsystems/render3d/.../preview/PreviewSourceCatalog`：逻辑资源目录；

- `demo/.../DiagnosticsPanel`：展示和交互，不拥有 GPU 对象；
- shader resources：color/HDR/depth/cube preview shader；
- `CommandBuffer`：仅在需要时增加受控 typed depth resolve；
- Gradle：`runPreviewIntegration` 和 local GL task 接线。

不要把所有逻辑继续塞进 DiagnosticsPanel、RenderGraph 或 CommandBuffer。Preview renderer 负责 GPU 转换，panel 负责交互，diagnostics 负责值快照，RenderGraph 继续负责资源调度与所有权。

## 18. v0.17.1 完成后的方向判断

完成本版本后再依据实际数据选择 v0.18，不提前承诺。候选顺序建议：

1. 如果预览系统显著提升问题定位效率：做真正的 GPU 单帧 snapshot 与有限资源导出；
2. 如果透明物体已成为场景表达瓶颈：做透明 render queue、排序和后处理边界；
3. 如果 v0.17 真实场景达到 CPU 提交门槛且可见 draw 规模上升：重新评估 GPU culling、Hi-Z 和 MDI；
4. 如果 UI 工具化需求持续增加：做 diagnostics 控件虚拟化、dock/layout 和 allocation 收敛；
5. 如果上述需求都不强：继续收口 API、错误语义、资源所有权和发布自动化。

当前数据仍不支持为了“看起来先进”直接进入 GPU-driven。v0.17.1 的价值是把现有渲染系统变得更透明、更容易验证，为后续功能选择提供真实证据。

## 19. 最终原则

v0.17.1 的成功标准不是“能把 texture id 画到屏幕上”，而是建立一条可信的检查链路：资源身份稳定、格式解释正确、GPU 生命周期清晰、失败不会伪装成黑图、关闭时没有成本、打开时成本可测、冻结和导出不谎报像素状态。只有同时满足这些条件，RenderGraph 资源预览才属于框架能力，而不是 Demo 中危险的调试捷径。
