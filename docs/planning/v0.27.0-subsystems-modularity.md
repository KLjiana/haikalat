## 1. 版本目标与第一阶段交付

v0.27.0 的目标是降低 Subsystems 内部的横向耦合，让功能的输入、输出、依赖、资源所有权和失败边界可以独立说明、验证和维护。保留现有 Backend/Core 基础与渲染算法，优先收敛中心对象的职责。

纵向的 `subsystems/runtime → core → backend` 约束不能替代 Subsystems 内部的协作合同。包目录变整齐、类变短、接口变多，都不能单独证明重构成功。

```text
v0.27.0 目标
├── 第一阶段：本计划必须交付
│   ├── 真实依赖图、变更影响面、资源与性能基线
│   ├── 体积雾内部边界：参数、帧输入、私有资源、Pass 与历史
│   ├── 光照／阴影／深度借用合同及 Shader 绑定合同
│   ├── 帧边界启停与候选提交、失败清理、代次隔离
│   ├── 不相关资源复用与有理由的历史失效
│   └── 生产路径测试、视觉对照和真实宿主验收证据
├── 后续阶段：第一阶段结论出来后再排期
│   ├── 选择第二个真实模块检验共性
│   ├── 有证据后提炼公共能力／生命周期合同
│   └── 按实际作者工作流完善风格配置、预览与参数联动
└── 本阶段不做
    ├── 全部 Subsystems 重写、Backend/Core 推倒重来
    ├── 通用插件发现、独立版本解析和热插拔市场
    ├── 新增高级渲染算法、全面扩展 UI 特效
    └── 用一个新的万能管理器替换 RenderPipeline
```

第一阶段完成的含义：体积雾已经在真实 `RenderPipeline` 路径中按上述边界工作，功能与画面无未解释回归，启停和故障行为有证据。仅完成拆包或新增一个未被调用的模块类，不算交付。

## 3. 目标组织与边界

以下为职责划分，类型名和包名由 M1 根据可见性、调用点决定，不要求逐项新建接口或管理器。

```text
宿主／调用方
└── RenderPipeline：兼容入口、帧级协调与装配
    ├── 请求处理：序号、准备状态、帧边界提交、结果诊断
    ├── 光照／阴影／场景表面：保持各自资源所有权
    │   └── 向体积雾提供明确的只借用输入与绑定能力
    ├── 体积雾内部模块
    │   ├── 参数与资源规格分类
    │   ├── CPU 准备／GPU 候选与私有资源
    │   ├── Pass 贡献与合成输出
    │   └── 历史计划、成功提交与失败失效
    └── RenderGraph：Pass 依赖、执行与图自有附件
```

### 3.1 三类职责分别设计

| 职责 | 必须表达 | 禁止承担 |
|---|---|---|
| 能力边界 | 输入输出、必需／可选能力、用途、内部稳定身份 | 读取其他模块任意内部字段、循环依赖 |
| 生命周期 | 准备、激活、停用、释放、任务结果与代次 | 操纵各效果全部实现细节、在任意后台线程调用 GL |
| 渲染装配 | 本帧纳入哪些 Pass、生产者／消费者连接、借用资源 | 保存所有效果业务状态、成为第二个 RenderPipeline |

先使用具体内部实现、必要的值合同或包内接口。公共 `FeatureModule` 只有在第二个真实消费者证明共性，或存在明确后端／测试隔离需要时才评审引入。每个新增抽象必须说明真实调用点、隔离了什么变化、失败行为与测试。

同一构建内的模块暂不引入独立语义版本和依赖解析器；资源代次、请求序号与确有必要的合同版本分别表达。稳定身份不等于插件系统。

### 3.2 输入、输出和资源所有权

| 资源／数据 | 所有者 | 体积雾权限与约束 |
|---|---|---|
| 相机、场景快照、光源帧数据 | 原生产者 | 只读，明确帧号／代次；不得跨代持有失效引用 |
| 深度、场景表面、光照表、阴影数据 | 原 Graph 或光照／阴影所有者 | 借用；格式、尺寸、采样数、坐标约定和生产者顺序可验证；不得释放 |
| 体积雾专属存储、程序和历史 | 明确的体积雾资源所有者 | 按需创建、停用释放；候选与活动资源不得混用 |
| Graph 创建的附件 | Graph | 模块只持有句柄；删除模块不能重复释放图资源 |
| 输出散射／透射与 reactive 等现有贡献 | 按现有实际资源逐项登记 | 说明消费者、有效期、禁用时的无雾语义及绑定回退 |

M1 必须把上表细化为实际对象清单。共享对象保留单一所有者；新旧图并存时明确借用期限、所有权转交和退役条件。第一阶段不为此新建全局共享资源服务。

Shader 输入与 Java 输入是同一合同的两面。缺失必需输入、错误布局、未声明的生产者或失效代次应在可执行提交前报错；可选输入使用明确的降级语义。检查透明物体与 VFX 的无雾变体，不能只移除计算 Pass 而残留对已释放数据的采样。

### 3.3 生命周期与请求处理

稳定状态可按下列语义表达，但不要求先实现通用状态机框架：

```text
REGISTERED → INITIALIZED ⇄ ACTIVE
       任意尚未销毁的稳定状态 → DISPOSED
```

- `INITIALIZED` 表示 CPU 准备完成、未参与绘制；GPU 是否驻留由独立资源策略表达。
- `ACTIVE` 表示完整配置已在帧边界发布；`DISPOSED` 为终态。
- `PREPARING`、`STOPPING`、失败原因属于请求执行状态或必要的显式过渡，不堆成大量永久状态。
- 同步兼容入口继续遵守现有渲染线程约束；如新增跨线程请求入口，明确其“已接收”和“已生效”的区别，不改变旧 API 的成功语义。

请求流：校验输入和预算 → 纯 CPU 准备（必要时异步）→ 正确 GL Context 所在线程创建候选 → 校验并编译候选图 → 安全帧边界发布 → 退役旧资源。

优先复用宿主执行器与既有调度入口。若审计证明缺少投递能力，只增加有界的必要机制，不额外启动常驻线程。请求必须携带序号／代次，定义队列上限、拒绝结果、关闭后的处理，以及过期 CPU 结果的丢弃与清理。

连续参数可合并为最新值；开启后立即关闭、准备中切世界、准备中关闭必须有确定结果。不能静默合并必须返回独立结果的操作。等待后台任务或 GPU 时不得持有阻塞渲染推进的锁。

### 3.4 参数、事务与历史

- **仅数值变化**：如密度，更新参数；不增加 Graph 拓扑 revision，不重新创建无关 GPU 对象。
- **规格／拓扑变化**：如启停、网格规格、需要不同 Pass 的配置，建立完整候选；校验预算时计入活动、候选和待退役资源的峰值。
- **世界／尺寸／重载变化**：明确代次和受影响资源集合，保持已有 resize 事务的完整性。
- **资源复用与内容有效性分别判断**：保留 TAA 存储不代表原历史像素仍适用。雾变化引起颜色变化时，可按依赖触发历史失效或 reactive；记录原因，避免无条件重置所有缓存，也避免强行保留错误历史。

| 失败位置 | 规定行为 |
|---|---|
| CPU 准备、GPU 候选创建、Shader／Graph 编译 | 清理候选，不发布半成品；旧配置继续可绘制 |
| 命令尚未提交 | 丢弃未提交工作，不提交历史成功状态 |
| 已部分提交并产生 GPU 写入 | 不宣称像素可回滚；隔离受影响结果、使必要历史失效并在后续帧恢复 |
| 新配置已发布，旧资源清理失败 | 新配置继续有效，记录并处理清理失败；不能伪装成发布前回滚 |

停用默认释放不再需要的体积雾专属资源；若保留缓存，必须有用途、上限、过期／回收方式及诊断值，不能把常驻资源改名为缓存来通过验收。GL 删除遵守正确 Context 与在途使用约束，不采用每次切换都全局等待 GPU 的捷径。

## 4. 实施顺序与退出条件

依赖顺序为 `M0 → M1 → M2 → M3 → M4 → M5`。每步形成可独立审查的变更；阶段结束前更新证据与未完成项，不靠日历日期宣布完成。

| 阶段 | 工作与交付物 | 退出条件 |
|---|---|---|
| **M0 基线审计** | 固定开工提交、工作区变更、测试环境和构建身份；绘制 Java 调用、Shader 绑定、Pass、资源所有权图；采集启停／密度／resize／重载调用链、历史提交、分配释放和性能；确定真实 Minecraft 宿主入口 | 事实、推测、已知缺陷分开；每个主要资源有所有者；同一输入的画面和性能可复跑；冻结验收场景与容差 |
| **M1 合同与切口** | 形成输入输出、参数分类、状态迁移、失败矩阵和所有权文档；设计借用合同与图依赖连接；说明拟新增类型的必要性 | 不依赖通用插件框架；无循环依赖；所有释放与退役路径明确；原公共入口兼容方案可审查 |
| **M2 体积雾职责内聚** | 迁移准备、私有资源、帧状态、Pass 贡献和成功／失败回调；装配处连接光照、阴影、表面、透明与 VFX；迁移生产消费者 | 真实 RenderPipeline 使用新边界；不存在双套活动实现；主要视觉行为保持；公共入口不泄漏模块内部实现 |
| **M3 生命周期与局部替换** | 实现帧边界启停、候选提交、过期请求处理、关闭和故障清理；缩小体积雾变更的资源替换范围；增加必要诊断 | 开关不再无理由重建光照／阴影／后处理私有资源；仅数值更新不重建图；失败保留可用状态；无重复释放或跨代引用 |
| **M4 框架回归与性能** | 执行第 5 节自动化及视觉对照，输出对象身份、资源字节、时序和故障证据；回归相关旧测试与架构守卫 | 无未解释画面变化；生命周期与泄漏验收通过；性能结论可追溯；不能用 skipped 或旧缓存结果冒充通过 |
| **M5 宿主与阶段结论** | 在实际 Minecraft 接入中执行启停、调参、切世界、resize、重载和关闭；记录渲染线程、目标借用、画面和错误日志；评估下一模块 | 实际宿主合同有证据；按第 7 节给出分层状态；决定后续范围，不自动推广所有 Subsystems |

M2 可以暂时保留整代替换以控制迁移风险，但这只是中间状态，不能据此关闭 M3。若共享所有权无法安全分离，先缩小切口并补合同，不强行迁移全部后处理。

## 5. 验收矩阵

以下用例必须穿过真实生产入口，不能仅测试独立模型或新增接口。新增测试名在实施时确定；表中不是现成测试已通过的声明。

| ID | 操作 | 必须提供的证据 |
|---|---|---|
| A01 冷启动关闭 | 从关闭状态创建并绘制 | 无体积雾 Pass，无无理由专属 GPU 分配；透明与 VFX 无已释放／未初始化雾输入 |
| A02 开启与停用 | 关闭→开启→绘制→停用→绘制 | 输入校验正确；只在完整提交后生效；停用后无雾 Pass，资源回落到明确基线，借用目标仍可用 |
| A03 连续调参 | 固定规格连续更新密度 | 参数确实影响像素；图 revision、无关资源身份稳定；无每帧编译／分配 |
| A04 规格变化 | 改变网格／质量规格 | 候选预算与峰值可见；仅必要资源替换；新旧对象的退役与所有权准确 |
| A05 准备故障 | 注入 CPU、分配、Shader 或图编译失败 | 逐项覆盖；旧配置仍真实绘制，候选无泄漏，错误保留原始原因 |
| A06 执行故障 | 在未提交与部分执行阶段分别注入失败 | 历史不错误提交；受影响历史失效范围与恢复帧可见；不宣称撤销已执行 GPU 写入 |
| A07 请求竞态 | 开启后立即关闭、过期准备返回、关闭期间请求 | 最终状态由有效请求确定；过期结果不发布；队列有界；所有请求结果明确 |
| A08 世界与分辨率 | 准备中切世界、resize、连续尺寸变化 | 代次正确，旧世界数据不进入新帧；资源释放准确；历史按依赖失效 |
| A09 重载与清理失败 | 重载失败；发布成功后注入退役失败 | 两类结果可区分；前者旧画面可用，后者新配置仍有效且清理失败可诊断 |
| A10 线程与 Context | 正常 owner 路径及错误线程／Context 调用 | 创建、绘制、销毁均在合法环境；非法调用在执行 GL 操作前被拒绝；两线程覆盖资源已实际初始化的关闭场景 |
| A11 组合视觉 | 雾开关配合光照、阴影、TAA、透明、VFX、支持的采样配置 | 同场景同相机同随机种子前后图像与指标；单采样／多采样生产者排序正确；无未解释回归 |
| A12 长时循环 | 至少 200 次启停，穿插 resize／重载／失败，再关闭 | 资源对象创建释放可对账，无持续增长；采集稳定期与峰值，关闭后所有者余额符合合同 |
| A13 真实宿主 | Minecraft 内重复 A02、A03、A08 与关闭／重载 | 接入提交、环境、操作记录、画面、日志；不释放宿主借用目标，不破坏后续绘制 |
| A14 变更局部性 | 回顾本次迁移并追踪一次体积雾参数或策略调整 | 通常只触及体积雾边界与必要装配；跨模块修改有合同理由；中心类没有换名搬家 |

优先扩展已有 `VolumetricSettingsTest`、`VolumetricHistoryPlanTest`、`PipelineTopologyTest`、`RenderPipelineTest`，以及 `VolumetricResourcesGlTest`、`VolumetricGenerationGlTest`、`VolumetricTemporalGlTest`、`VolumetricLifecycleSoakGlTest`、`RenderPipelineGlTest`。视觉与性能使用现有体积雾 Demo、Quality、TemporalQuality、Benchmarks 入口，补齐缺失操作，不另建只有理想路径的新 Demo 代替回归。

执行命令根据 M0 确认的 Gradle task 和过滤条件写入证据文件。正式验收记录退出码、实际执行／跳过数、提交与工作区身份、JDK、GPU、驱动、尺寸、采样、场景配置和资源哈希；架构／公共 API 守卫强制新鲜执行，必要时使用 `--rerun-tasks`。

### 性能与画面判定

M0 在相同硬件、固定场景下进行预热与重复采样，冻结测量帧数、CPU／GPU 时长统计、像素误差指标及容差，再开始结构迁移。无法确定的阈值必须明确待定原因，不能在看到重构结果后放宽标准。

分别记录冷启动关闭、稳定开启、停用后稳定期、切换峰值；CPU 帧耗时与 GPU Pass 耗时分别报告。资源按尺寸和格式核算的字节数应标为分配估算，不能冒充驱动实测显存。没有可靠显存工具时，可证明专属对象已释放，但不宣称显存下降了某个百分比。

本阶段性能目标是无未经解释和接受的回归，并消除关闭状态的无效执行／无理由驻留；不预设凭模块化就会提高 FPS。无法测量的项目标记 `NOT_EVALUATED`，保留为验收未闭合项。

## 7. 完成标准、范围控制与下一步

第一阶段结论分开记录：

- **结构与功能**：M0–M4 及对应自动化、视觉合同通过，真实生产调用已迁移。
- **性能**：有同条件前后数据和结论；未评估时明确保留限制。
- **宿主集成**：M5 有实际 Minecraft 证据。宿主不在当前仓库或暂不可运行时，交付接入清单和未完成项，状态写“框架内通过，宿主待验收”。
- **阶段整体**：所有必需项闭合后才能标记完成；版本发布、打包与 release readiness 另按发布流程判定。

迁移过程中出现画面变化、共享资源双重所有权、无法说明的性能回退或大范围 API 破坏时，停止扩大迁移范围，先恢复受影响合同。用可审查的小步提交控制回退；保留并行工作，不通过重置工作区撤销他人修改，也不长期保留两套活动渲染路径。

第一阶段结束后，再从实际依赖与改动压力中选择第二个模块。只有第二个模块验证了共性，才决定哪些内部合同值得公开。作者侧的风格预设、参数联动和统一预览另设后续任务，以一个真实目标场景及制作流程验收；模块边界改善不直接等于创作能力完成。
