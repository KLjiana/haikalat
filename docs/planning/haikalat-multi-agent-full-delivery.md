## 1. 范围与完成定义

- 跟踪全部 46 个技术编号。#1/#2/#3/#7 已有 0.28 实现，先复核真实范围并收尾；其余 **42 项全部进入交付队列**，不再每波询问是否继续。
- 每项交付一个范围明确、可配置、进入生产调用链且经过独立验证的完整实现。不能用空接口、占位开关、shader 编译、Demo 原型或研究报告替代生产交付。
- 高成本项目也必须推进：先验证关键可行性，再实现生产路径。若有确实不可解除的硬件、算法、资产或外部依赖阻塞，保留为 BLOCKED，说明证据和解除条件，继续其他任务；不能标 DONE 或偷偷移出清单。
- 全部技术“可用”不等于全部效果“同时开启”。质量档、互斥条件、容量和不支持输入必须显式表达；最终验证真实交互组合，不遍历 46 个开关的全排列。
- #32 是 SSS 目标，#33 是屏幕空间实现：可共用同一生产实现与资源 owner，但分别证明材质语义和屏幕空间算法合同。不能为了数量复制系统。
- #26 排序与 #28 OIT 都要交付，作为适用透明集合的显式可选策略；#37 随机透明另行交付。不能把三者混称为精确透明解。
- #44 DDGI 与 #45 VCT 都要推进、分别验收，默认互斥选用。基础场景表示仅在两者确有真实共享需求时复用，不要求同时驻留两套昂贵资源。
- 不承诺所有技术在 RTX 3050 Laptop 上同时达到某个帧率。榜单评分只是序数估计，毫秒、显存和性能收益必须来自实测。

## 3. 团队、权限与持续调度

### 3.1 角色

| 角色 | 职责与权限 |
|---|---|
| Orchestrator / Integrator | 建立共同基线、任务 DAG、文件 owner 和验证队列；分配任务；串行集成；维护状态、版本和最终结论 |
| Worker | 一个独立 worktree、一个活动工作包；实现最小完整范围、针对性测试、技术卡和使用说明；提交准确的 commit 与证据 |
| Reviewer | 独立只读审查实际 diff、算法参考、生命周期、消费者和测试分支；不改代码；发现回交 Worker |
| 验证执行者 | 由 Orchestrator 自任或委派；持有唯一 GPU 验证时段；归档真实结果，不与编码者自评混同 |

默认同时运行两个 coding Worker；确认 CPU/内存、工具槽位、文件职责与任务依赖允许后，可增至四个 coding Worker。总 Agent 数以 DSH 实际限制为准，Reviewer 使用释放的槽位。不创建 42 个常驻 Agent，不递归扩张子团队。

角色可复用，不要求每个任务另开 Orchestrator。每包实现后安排独立 Reviewer，不能让唯一作者自签收。审核和 GPU 等待期间，从 READY 队列继续派发不冲突任务。

### 3.2 工作树与提交

1. 检查 `git status`、暂存/未暂存 diff 和未跟踪文件，保存候选身份。
2. 从已确认的集成基线创建 Worker worktree，使用 `codex/render-<task-id>` 等分支。每次编辑前验证实际路径和 HEAD；分支名本身不证明已隔离。
3. 如果开始执行时已有未提交实现，使用安全的隔离快照包含必要 tracked/untracked 文件；保留源工作目录及暂存状态。不得只从旧 HEAD 开工，也不得为清空目录擅自 stash/reset/clean。
4. Worker 只能提交本包文件。不要 `git add .` 混入其他工作、build 证据、密钥或个人资源。
5. Worker 产出不可变 commit；Reviewer 审查该 commit。后续修复形成新 commit，并按受影响范围复审。
6. Orchestrator 串行 cherry-pick/merge 到专用集成分支，再运行跨包验证；不直接改用户源分支，不自动推送、tag 或发布。
7. 提交未集成前不能删除其 worktree 或唯一证据。完成后按工具能力归档，保留恢复入口。

### 3.3 文件 owner 与共享合同

- 同一文件、shader include 或资源 owner 同时只能有一个写入者；独立 worktree 不豁免此规则。
- Integrator 默认独占 `RenderPipeline`、`RenderFeaturesControl`、共享 surface 协议、根构建版本、聚焦任务筛选、公共 API 清单和最终验收汇总；可以显式临时转交某文件，但禁止交叉写入。
- #8/#16/#17/#31/#32/#33 共用的 PBR shader 由材质负责人顺序编辑；#23/#24/#25 和其他合成改动由后处理负责人分批编辑。
- #9/#10/#19 的 lighting/shadow 合同、#4/#11/#13 的场景颜色输入、#15/#26/#27/#28 的粒子 owner 均先确认共享边界，再分配非冲突工作。
- Worker 需要跨边界时提交最小接口变更请求和真实调用点，由 Integrator 确定唯一实现者。不能为绕过排队复制一套 pipeline、灯表、深度、历史或 shader。
- 修改 shader 或共享 helper 后重新计算受影响消费者，不能沿用“仅修改本包”的测试范围。

### 3.4 GPU 与预算

- 所有真实 GL、Showcase、读回、截图、性能和资源压力运行进入同一 GPU 队列，任意时刻只执行一个。GPU 时间不能由各 Worker 自行争抢。
- 无桌面 JVM 检查可以在不同 worktree 并行，但应限制 Gradle/JVM 并发，避免内存压力造成误判。
- 使用用户当前配置的 DSH 模型和已有预算设置；不得从 starter pack 推导本轮 $100 授权。没有计费数据就记录 unknown，不虚构花费。
- 不新增付费服务、购买资产或更换后端。需要此类资源时说明具体缺口并继续独立任务。

每包开工前，在对应实施说明补简短技术卡：适用范围/不支持输入、真实生产消费者、输入输出格式与空间、Pass 顺序、GPU owner、准备/提交/退役/失败、独立 oracle、质量档和验证范围。以现有抽象为起点，不预造 46 个 manager、Demo 或 Gradle 任务。

以下阶段用于调度，不是版本号或必须等待整波完成的屏障。满足实际前置、文件 owner 可用且有完整技术卡即可开始。表中技术编号为硬前置时会明确说明；其他输入指既有或已验收的真实合同，不强制依赖无关效果。

关键输入按真实需求冻结，不能一次性建设通用框架：

- 场景颜色：#4 的首个消费者明确 HDR 阶段、透明顺序、深度拒绝与读写分离；#11/#13 按此合同复用或有依据扩展。#4 不硬依赖暗角/颗粒/色差。
- 几何：#5 必须协调可见性 bounds、深度、shadow、velocity；未支持的 skin/morph 组合应在提交前拒绝，不能默默只改变颜色 Pass。
- 灯光：临时灯、表面光照、静态 shadow cache 各自 revision 和 owner 清楚。云影不硬依赖体积云。
- 粒子：#27 的活跃集合、间接命令与生命周期是 #15/#26 的前置。#28 可支持独立透明网格，但粒子集成依赖 #27。
- 时域：#34 先绑定一个已实现的真实信号（如 #20 SSR），然后供 #39 按其信号语义复用；避免 SSR/降噪的循环阻塞。#35 是独立重建路径，不把已有 TAA 改名交付。
- 场景表示：#44/#45 先明确动态场景可见性来源，单 owner 串行变更公共输入；DDGI 不因 GPU 带 RTX 就假定 OpenGL 有光追 API。

## 6. 实施、审查、集成循环

每包使用相同短循环，持续取 READY 任务，不因完成一个 wave 就结束整个请求：

1. **调查**：定位实际输入/owner/消费者和已有测试，排除重复造轮子；说明当前代码是否已部分实现。
2. **冻结合同**：补技术卡、依赖、明确范围和必需 case。独立参考、阈值和测量配置先于采集确定。
3. **实现**：生产 API/数据、GPU 消费、控制门/诊断、必要资源事务、使用入口一起闭合。参数有限性和不支持组合尽早拒绝。
4. **定向验证**：先 JVM/解析，再进入 GPU 队列验证真实消费者；完成后记录结果。不能只保证视觉开启路径，也覆盖关闭、数值编辑、失败与生命周期。
5. **独立审查**：Reviewer 读取实际 commit/diff 与证据；必要时提出小型反例。重点检查测试是否进入宣称分支、是否自证、是否真实覆盖集成路径。
6. **修复**：由原 Worker 修正；只重跑受影响合同和直接消费者，禁止无依据重试到绿。
7. **串行集成**：Integrator 合并被批准提交；解决共享冲突；按真实依赖验证组合，确认最终提交与证据身份一致。
8. **登记与继续**：更新状态/能力矩阵/使用文档；保存下一任务及未完成队列；继续派发 READY 项。

研究风险较大的 #37/#39/#40/#43/#44/#45 先做限定目标的 spike，但 spike 仅是实现前步骤。技术不可行时输出具体反证、已尝试路径和可行替代；替代若改变用户承诺，等待用户决定，原项保持 BLOCKED，其余任务继续。不要反复追加 Agent 重做同样实验。

## 7. 验证与质量档

### 7.1 单项完成门槛

一项只有同时满足下列条件才能 `ACCEPTED`：

- 所承诺的真实生产输入、渲染消费者、配置与诊断存在，默认开关及依赖/互斥清楚。
- 必需解析/JVM/GL 合同实际执行通过，或有完整有效的 REUSED_PASS；空选择/意外 skip/超时不能通过。
- 新资源具有 owner、容量/缓存边界、resize/关闭、发布前失败保留旧状态；适用时覆盖发布后退役失败和借用目标。
- 可通过既有领域 Demo 或组合场景操作和比较，有固定相机、时间、种子、曝光及有效的独立参考；像素自动证据与人工视觉分列。
- public API、资产许可/指纹、实际用法和限制同步；Reviewer 无未解决的正确性或资源安全阻塞。
- 集成分支上的直接消费者通过，不能只引用已发生输入变化的 Worker 结果。

按高风险交互选代表组合，不建立所有开关笛卡尔积：

### 7.3 性能与资源结论

- 为新能力提供 Low/Medium/High 中实际有意义的有界配置；默认采用保守范围，不将全开配置作为默认。
- 记录 RTX 3050 Laptop 实际设备/驱动/显存、输出和内部尺寸、AA、场景规模/覆盖率、质量档、计时口径。以 1920×1080 为代表目标，不能在未测时保证预算。
- 常规实现记录可用的 CPU/GPU 时间、draw/材质切换、附件/缓存及候选峰值；这些是开发观察，不自动升格正式性能 PASS。
- #27/#35/#41/#42 的“优化/重建收益”属于核心宣称：必须预先冻结代表 workload、对照方法和质量条件，按验收规范选择必要性能验证；没有相应结果则功能与收益状态分开，不宣称更快。
- 正式性能只对本轮相关配置选择，必要时按仓库要求使用扩展开关；不运行全部历史 benchmark/soak 来凑证据。不自创毫秒门槛或放宽质量阈值。
- 资源无界、GL 严重错误、NaN/Inf、泄漏、错误回收、未解释残影等保持阻塞，不能用较低质量档掩盖正确性错误。

### 7.4 命令与证据原则

从实际 Gradle 定义确认命令/任务图。按范围使用定向 `test --tests`、`glSmoke --tests`、`verify.ps1` 等已有入口；固定 focused 列表不会自动包含新 case。只有真实新需求才增改任务。

默认增量构建，不惯例 `clean`/`--rerun-tasks`。零自动重试；确认可恢复的环境故障最多一次定向复跑。验证结束检查 XML、case ID、skip、读回和候选身份。失败也归档，不改历史 PASS/FAIL。

每个集成检查点选择必要的完整无桌面检查与代表组合；不能每个小改动都串行叠加全量 `check`、全部 GL、Showcase 长测和全部性能矩阵。

## 8. 状态、证据与恢复

不建设新的通用任务框架。执行者在现有文档与简单 JSON 中维护清单即可：

- 持久任务状态：`docs/planning/haikalat-multi-agent-status.json`（执行启动时创建，不由本计划伪造当前状态）。
- 领域技术卡/实现说明：放对应计划或本计划旁的真实工作包文档，避免按 42 项机械复制空文档。
- 临时日志、截图、fixture、命令和归档：`build/reports/render-roadmap/<runId>/<taskId>/`。
- 每批验收摘要：现有 releases 目录中的实际候选记录；保留原 runId/输入 hash/环境/时间。build 证据若被清理，不能仅靠 Markdown PASS 声称仍可复用。

每个任务最少记录：

```json
{
  "taskId": "R04",
  "featureIds": [4],
  "state": "TODO",
  "scope": "由技术卡确定",
  "dependencies": [],
  "owner": null,
  "writePaths": [],
```

每次汇报只列新完成、真实失败/阻塞、当前 GPU 作业与下一批；不反复输出整份路线图。上下文或会话中断前写下已用命令、原始输出、当前提交和 nextAction。恢复时先读取状态并核验 Git/证据，不从头重跑，也不把没有运行中的进程写成“正在后台继续”。
